What this repo actually is

A Next.js frontend, full stop. There is no backend code in this repository. Every screen you see here calls out to a separate REST API hosted elsewhere. When people on the team say "the backend," they mean that external service, not anything in this folder.

The product itself is a marketplace for web3 domains, ENS names and similar assets. Users browse listings, connect a wallet or log in with email or Google, buy and sell domains, list in bulk, keep a watchlist, and check their transaction history and analytics.

01

The stack, in practice

Not just what's in package.json, but what's actually being used versus what's dead weight sitting in the dependency list.

Framework

Next.js 15, Pages Router (not the app folder convention). React 18.3.1, pinned via package.json overrides.

Data fetching

Redux Toolkit + RTK Query does almost everything. React Query is installed and wired up but effectively unused for real data.

Web3

wagmi + viem + Reown AppKit for wallet connect UI, ethers v5 for signing and address utilities.

UI

Bootstrap 5 is the real design system. Tailwind is configured but fully commented out, it does nothing today.

Worth knowing Both tailwind.config.ts and postcss.config.mjs have their entire contents commented out. Any Tailwind-looking class name you spot anywhere in this codebase will not apply any styling. Don't reach for a Tailwind class expecting it to work.
Also worth knowing The dev server always runs on port 3002, in both local dev and production, set directly in the npm scripts (next dev -p 3002). Not the Next.js default of 3000.

pages/_app.tsx entry point

The provider stack, plus a background timer that checks every 60 seconds whether the login token has expired and force-reloads the page if so. 

  useEffect(() => {
    const interval = setInterval(() => {
      const expiry = getExpiryDateFromToken();
      if (expiry && Date.now() > parseInt(expiry) * 1000) {
        deleteCookieAttribute(Cookie_Key.ACCESS_TOKEN);
        deleteCookieAttribute(Cookie_Key.REFRESH_TOKEN);
        if (!sessionStorage.getItem("token_expired")) {
          sessionStorage.setItem("token_expired", "true");
          window.location.reload();
        }
      }
    }, 60000);
    return () => clearInterval(interval);
  }, []);

  return (
    <GoogleOAuthProvider clientId={clientId}>
      <AuthProvider>
        <WagmiProvider config={wagmiAdapter.wagmiConfig}>
          <QueryClientProvider client={queryClient}>
            <Provider store={store}>
              <AutoLogoutHandler />
              <InitProvider />
              <AppContent Component={Component} pageProps={pageProps} router={router} />
              <ToastContainer hideProgressBar={true} />
            </Provider>
          </QueryClientProvider>
        </WagmiProvider>
      </AuthProvider>
    </GoogleOAuthProvider>
  )
pages/initProvider.tsx wallet bridge

Mounted globally, this grabs whichever wallet is connected through Reown AppKit, wraps it in an ethers Web3Provider, and stashes it in a small singleton so any component anywhere can grab the live wallet connection without needing to be nested inside a specific context. 

const { walletProvider, walletProviderType } = useAppKitProvider("eip155");
useEffect(() => {
  const effectiveProvider = walletProvider ?? (
    walletProviderType === 'INJECTED' || walletProviderType === undefined
      ? window.ethereum : null
  );
  if (!effectiveProvider) return;
  const provider = new Web3Provider(effectiveProvider, "any");
  providerManager.setWeb3Provider(provider);
}, [walletProvider, walletProviderType]);

Read it back anywhere with providerManager.getWeb3Provider(), defined in src/lib/provider-manager.ts.

The src/ folder, piece by piece

Organized loosely by feature rather than strict atomic design. Here's what lives where, and where to look first for a given kind of change.

component/

Nearly all UI. modals/, toast-message/, web3/ (contract ABIs), header/, footer/, wallet-connect/, and one folder per feature.

config/wagmi.ts

The one file defining every blockchain network the wallet connector supports.

constants/

Base API URL and a big list of fully-built endpoint URLs. Also a hardcoded API key, see the callout below.

context/AuthContext.tsx

The single place the whole app checks "am I logged in."

core/

The real backbone: enum/ (API paths, cookie keys), model/ (shared types), services/ (HTTP calls), redux/ (RTK Query + slices).

data/supportedTlds.ts

Static reference list of every domain extension the platform recognizes.

helpers/

Small utilities: turning any thrown error into a readable message, email validation.

hooks/ & utils/

Custom hooks, split inconsistently between both folders. Check both when hunting for one.

lib/

AutoLogoutHandler and the wallet-provider singleton, both mounted globally in _app.tsx.

template/layout/

The shared page shell every page wraps in: header, footer, global scripts.

types/

Plain TypeScript interfaces describing API response and request shapes.

Security note src/constants/BaseUrl.ts has an API_KEY constant committed in plaintext. Worth fixing, don't add more secrets alongside it.

Redux and RTK Query

This is where almost all page-level data comes from. One store, two separate RTK Query API instances, and four plain slices for state that needs to live outside the query cache.

src/core/redux/store.ts store 
export const store = configureStore({
    reducer: {
        [myApi.reducerPath]: myApi.reducer,
        [authApi.reducerPath]: authApi.reducer,
        domainSummary: domainSummaryReducer,
        allDomainListing: allDomainListingSliceReducer,
        userProfile: profileSliceReducer,
        history: historySliceReducer
    },
    middleware: (getDefaultMiddleware) =>
        getDefaultMiddleware().concat(myApi.middleware, authApi.middleware),
});

RootState and AppDispatch are exported from here, used everywhere as useSelector((state: RootState) => …).

src/core/redux/api.ts RTK Query base

The primary myApi instance. Endpoints start empty here and get attached later via injectEndpoints in domain.ts, domainListing.ts, userProfile.ts, watchlist.ts and others, the standard RTK Query "code splitting" pattern.

export const myApi = createApi({
  reducerPath: 'myApi',
  baseQuery: fetchBaseQuery({
    baseUrl: baseUrl,
    credentials: "include",
    prepareHeaders: async (headers) => {
      const token = getCookieValue(Cookie_Key.ACCESS_TOKEN)
      if (!!token) headers.set('Authorization', `Bearer ${token}`);
      return headers;
    },
  }),
  tagTypes: ['faq', 'profile', 'domain', 'watchlist', 'domain_listing' /* …and more */],
  endpoints: (builder) => ({}),
});
src/core/redux/domain.ts example injected endpoints

One of the files that injects real endpoints into myApi. Every query here becomes an auto-generated hook, exported at the bottom of the file.

export const DomainApi = myApi.injectEndpoints({
  endpoints: (builder) => ({
    getDomainList: builder.query<DomainResponse, {...}>({
      query: ({ limit = 12, page = 1, sort = 'ASC', search = '', tlds = [] }) => ({
        url: `${DomainDetailsApi}?${finalQuery}`,
        method: 'GET',
      }),
    }),
    // …getTrendingApi, getPremiumDomain, getPromotedDomain, GetDomainListedAndUnListedDomain
  })
})

export const {
  useGetDomainListQuery,
  useGetTrendingApiQuery,
  useGetPremiumDomainQuery,
  useGetDomainListedAndUnListedDomainQuery,
  // …
} = DomainApi;

This is the pattern to copy for any new list of domains: define the query here, import the generated hook wherever you need it in a component.

Hybrid pattern to know about Several endpoints in domain.ts and domainListing.ts use onQueryStarted to manually copy fetched data into the plain slices (setDomainSummary, setAllDomainListing). That means some UI state bypasses RTK Query's own cache in favor of these plain Redux slices, worth knowing before you assume a query's cache is the only source of truth for that data.

Talking to the backend

There are genuinely two separate HTTP calling mechanisms in this codebase. Knowing which one handles which kind of call will save you time when tracing a network issue.

RTK Query
→
listings, profile, watchlist, analytics, history
api.service.ts
→
login, register, wallet auth, logout, one-off calls
src/core/services/api.service.ts the older layer

A global axios interceptor attaches the bearer token to every axios request app-wide, on top of the per-function header logic in getApi/postApi/putApi/deleteApi below it.

axios.interceptors.request.use(
  (config) => {
    const authToken = getCookieValue(Cookie_Key.ACCESS_TOKEN)
    if (config.headers) {
      if (authToken) config.headers.Authorization = `Bearer ${authToken}`
      config.headers['Content-Type'] = `application/json`
    }
    return config
  },
  (error) => Promise.reject(error)
)

export function getApi(url, local, cookie) {
  // builds headers, fetches, and on failure runs the response through ErrorHandler,
  // which on a 401 tries a silent token refresh and retries the call
}

Also defined here: postApiCall (typed axios helper), axiosInstance (a plain axios.create), logoutUserApi, and postRefreshToken, the pre-emptive refresh used by AutoLogoutHandler.

Two refresh mechanisms exist error.service.ts's reactive 401 handler and api.service.ts's postRefreshToken, used pre-emptively by AutoLogoutHandler, do overlapping jobs slightly differently. If you're debugging an auth-related network issue, check both.

How a URL actually gets built

Every request resolves to the same shape: {NEXT_PUBLIC_API_URL}{path}. The path segments live as an enum in src/core/enum/api-endpoint.enum.ts (about 90 raw strings like /auth/login), and src/constants/Api.ts pre-builds full URL constants by concatenating baseUrl + API_ENDPOINT.X for the ones used directly by the RTK Query slices.

07

Login and session state

Three ways in, email/password, Google, and wallet signature, all converging on the same result: cookies get set, and AuthContext is told the user is logged in.

src/context/AuthContext.tsx source of truth

Starts as null, meaning "haven't checked yet." Every consumer needs to handle that third state, not just true/false.

const [authenticated, setAuthenticated] = useState<boolean | null>(null);

useEffect(() => {
  const accessToken = getCookieValue(Cookie_Key.ACCESS_TOKEN);
  setAuthenticated(!!accessToken);
}, []);

const login = () => {
  setAuthenticated(true);
  if (!router.pathname.startsWith("/seller-portfolio")) router.push("/");
};

const logout = () => {
  setAuthenticated(false);
  deleteCookieAttribute(Cookie_Key.ACCESS_TOKEN);
  router.push("/login");
};
src/core/enum/cookie.enum.ts cookie keys

Notice the cookie names themselves are long hash-like strings, not readable names like "accessToken", presumably to obscure them from casual inspection in devtools.

export enum Cookie_Key {
  ACCESS_TOKEN = '86b3901eea37a04e8547cd912225f548d2e0a92078887682ce831a433072f9d1',
  REFRESH_TOKEN = '6c8a7d4aa21708a432174e4cb5c6cfaf0218f5f3e52f9a76a7d95d2aaade2c83',
}

Session expiry, handled proactively

src/lib/AutoLogoutHandler.tsx, mounted globally in _app.tsx, independently tracks four things at once: JWT expiry with a 5-minute-before warning that offers to refresh the token, a 30-minute inactivity timeout, tab-visibility-based away-time tracking, and cross-tab activity sync through localStorage and the storage event.

Note Middleware (middleware.js) plays no real role in auth today, its IP-restriction logic is entirely commented out. All access control you see is client-side React state, plus a couple of getServerSideProps guards on /login and /register.

Wallet connection, step by step

Connecting a wallet doesn't by itself log anyone in. It kicks off a proper nonce-sign-verify challenge to prove the user actually controls that address.

Open wallet modal
→
Fetch nonce
→
Sign nonce
→
POST signature
→
Backend authenticates
src/component/wallet-connect/index.tsx WalletConect (sic)

Once wagmi's useSignMessage returns a signature, it's forwarded to the backend along with the checksummed address and the chain name.

const getWalletNonce = async () => {
  let wallAddress = ethers.utils.getAddress(address);
  const nonce = await getNonce(API_ENDPOINT.WALLET_USER_API, wallAddress)
  signMessage({ message: nonce })
}

const handleWalletSignin = async (signature) => {
  const checksummed = ethers.utils.getAddress(address);
  const response = await connectWallet({
    postSignatureApi: API_ENDPOINT.WALLET_AUTH_API,
    address: checksummed,
    signature,
    network: networkName ?? EVM_NETWORK,
    source: 'marketplace',
  })
}
Worth flagging createAppKit({...}) is called directly inside this component's render body, rather than once at module scope like most AppKit integrations do. It appears to work because AppKit guards against duplicate init internally, but it's an easy trap to copy into a new component without realizing why it should live outside the render path.

Supported networks

src/config/wagmi.ts lists mainnet, arbitrum, polygon (and its Mumbai testnet), arbitrumGoerli, arbitrumSepolia, bsc, bscTestnet, goerli, sepolia, and base, together in one adapter. That's a mix of live mainnets and several deprecated or testnet chains configured side by side, worth confirming with the team which ones are actually meant to be live before you assume the network picker reflects intentional product scope.

Route protection

ProtectedRoute.tsx reads authenticated from context and decides, on every route change, whether to let the page render or redirect somewhere else.

src/component/ProtectedRoute.tsx guard logic 
useEffect(() => {
  if (authenticated === null) return; // still checking auth

  if (!authenticated && !isPublicRoute(router.pathname)) {
    router.replace("/login");
  }
  else if (
    authenticated &&
    isPublicRoute(router.pathname) &&
    router.pathname !== "/" &&
    !router.pathname.startsWith("/seller-portfolio") &&
    !router.pathname.startsWith("/ens-marketplace")
  ) {
    router.replace("/");
  } else {
    setLoading(false);
  }
}, [authenticated, router]);

The three states of authenticated (null, false, true) map to three different behaviors here, "not yet known," "logged out," and "logged in", so any new redirect rule needs to account for all three, not just true/false.

10

Styling approach

Bootstrap 5 and large global stylesheets do essentially all the visual work. SCSS Modules are used sparingly, and Tailwind, despite existing as a config file, does nothing.

  • bootstrap/dist/css/bootstrap.min.css is imported in _app.tsx, and a second, locally vendored copy is linked again inside the Layout's Head, so Bootstrap CSS loads twice.
  • Most components use plain string classNames keyed into public/assets/css/style.css, custom.css, and responsive.css.
  • Real CSS Modules exist only in two places: styles/Toast.module.scss and src/component/domain-item/skeleton.module.scss.
  • styles/Auth-Component.module.scss and similar files use the .module.scss naming convention but are written more like global BEM-style SCSS, worth checking scoping behavior before assuming a class name in one of these files is safely isolated.

Environment and deploy

Deploys through AWS CodeDeploy onto an EC2 host managed by PM2, not Vercel, despite what the boilerplate README still says.

Double check this before you assume the app is pointed correctly The committed .env defines NEXT_PUBLIC_API_ENDPOINT, but next.config.ts actually reads NEXT_PUBLIC_API_URL. As committed, this specific file would not populate the app's base URL. Confirm whether a separate untracked .env.local has the correct name before assuming requests are reaching the right backend.

ecosystem.config.js bakes a specific EC2 public IP directly into the env_production block. That'll need updating manually if the instance is ever replaced. There's no Dockerfile and no automated test step in this pipeline.

Rough edges worth knowing about

So they don't surprise you later, or cost you an hour of confused debugging.

  • A hardcoded API key sits in plaintext in src/constants/BaseUrl.ts.
  • Two parallel HTTP calling mechanisms exist side by side, RTK Query and the hand-rolled fetch/axios layer, each handling different calls.
  • src/core/redux/reducer.ts is an empty, unwired slice, safe to ignore or delete.
  • A couple of filenames have literal typos, including one with a trailing space (CreateFileFromUrl .tsx, ReturnSessionDto '.ts'), easy to trip over if typing an import path by hand instead of autocompleting.
  • The login page exists as two identical copies, pages/login/ and pages/(auth)/login/.
13

Where to actually start

A suggested order, if you want to get productive quickly rather than trying to absorb everything at once.

  • Run the app and click through it as a real user would. Browse, search, open a listing, try connecting a test wallet.
  • Read pages/_app.tsx slowly. The provider order explains almost everything else you'll encounter.
  • Read AuthContext.tsx and ProtectedRoute.tsx together. This is the mental model you'll refer back to constantly.
  • Trace one simple page end to end, About Us or Contact Us are good choices, from the page file, to the component, to the RTK Query hook, to the endpoint enum. Doing this once by hand teaches the whole data-fetching pattern faster than reading the Redux folder in isolation.
  • Then trace a wallet-touching page, the buy-now flow or a listing page, using wallet-connect and initProvider.tsx as anchors.

From there you'll have enough context to pick up real tickets, since you'll already know where routing, state, API calls, and auth gating each live.
