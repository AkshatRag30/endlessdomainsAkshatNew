src/core/services/my-domains/bulkOrders.service.ts

New · 29 lines

Our layering rules say only core/services talks to the backend, so the call lives here. One function, postBulkOrders(request): it sends POST /marketplacev2/orders/bulk and returns the backend's answer (a batch id and one result per name).

The one special case: when the backend refuses every name, it answers with an error (400 BATCH_ALL_REJECTED) that still contains every name's reason. This file treats that as a normal answer, so the drawer can show the reasons instead of a vague error. Any other error is passed on.

2

src/helpers/my-domains/bulkBatch.ts

New · the main work

Pure functions: the wallet, the backend call and the error sorting are handed in from outside, so the rules can be tested without a wallet or internet.

  1. runBulkBatch(items, days, deps)The whole flow: prepare (wallet, counter, block time), build each order, leave out names that expire too soon, put the orders in one tree, ask for the one signature, check every signature leads back to you, then send. Returns one of three outcomes: "not signed" (back to the form), "post failed" (can retry), or "posted" (results).
  2. postSignedBatch(batch, deps)Only the sending part. Used for the first send and for every "Try again", with exactly the same bytes, so you never sign twice.
  3. mapBulkAnswers(batch, answer)Matches the backend's answers to our names by name (not by position, not by capital letters). A "duplicate order" answer means an earlier try already got through, so it counts as listed. A name with no answer is flagged.
  4. BULK_REJECT_REASONS and bulkRejectReason(code)The approved plain reasons for each backend code, e.g. ALREADY_LISTED becomes "Already listed". Signature or fee codes all become "Couldn't be checked, try again" and are logged as our bug.
  5. isRetryableResult(result)Decides who goes into "Try these again". Names that would fail the same way (already listed, not owned, name mismatch, older cheaper listing) are left out.

Phase 2 · 19 Nov 2026 · bulk signature helpers (F2 part 1)

Four files, all new building blocks. Nothing on screen changed and no existing function was touched; phase 3 connects these to the drawer. Committed 20 Nov as ce32655 (not pushed).

1

src/types/my-domains/bulk.ts

Changed · 33 lines added at the end

This file only describes the shape of data; it doesn't do anything. Our layering rules (CLAUDE.md §8 rule 5) say shared shapes live in src/types, so the three new ones went here.

Eip712Types
The format the wallet needs to know what it's signing: type names, each with its fields ("OrderComponents has offerer (address), zone (address), offer (list)…").
BulkOrderTree
Everything about one batch once the tree is built: orders (your real listings), height (levels, 6 for 50 names), types (the message description), leaves (a fingerprint per listing plus filler, 64 for 50 names), layers (every level from the leaves up to the root), root (the one fingerprint at the top) and value (the message the wallet signs, the orders nested in pairs).
DecodedBulkSignature
One listing's signature split back into its parts: the wallet's signature, the listing's position (leafIndex) and the proof (the neighbour fingerprints on the way up).
2

src/helpers/my-domains/bulkOrderTree.ts

New · the main work

Pure functions: data in, data out. No wallet, no internet, no screen. The top comment says what the file does, that it is ported from Seaport.js 4.4.1 (MIT), and that it deliberately differs from Seaport.js's broken type hash helper.

Constants

  • BULK_ORDER_MAX_HEIGHT = 24: the biggest tree Seaport allows. Our cap of 50 names (height 6) never gets close.
  • The byte sizes, named so the code reads clearly: 3 for the position, 32 per proof word, 64 or 65 for the signature.

Functions, in the order they're used

  1. bulkTreeHeight(count)How many levels the tree needs: 1 or 2 names give 1, 3 or 4 give 2, 50 give 6. Refuses 0 names.
  2. bulkOrderTypes(height)Builds the message description for the wallet: one line BulkOrder { tree: OrderComponents[2][2]... }, one [2] per level, on top of the order description we already had (EIP712_TYPES). This is Mohit's "don't hand write the type strings": the code builds the text, so a typo is impossible.
  3. bulkOrderTypeHash(height)The "shape fingerprint", made from the full type text. This is where we deliberately differ from Seaport.js's getBulkOrderTypeHash, which gives a wrong value (explained in the progress log, phase 2).
  4. emptyValue and emptyOrderComponents()Make the filler order: every number zero, every address zero, no items. A tree needs a power of two leaves (2, 4, 8 … 64), so 50 listings get 14 fillers. Nobody can ever buy one. Built from the type description, as Seaport.js's DefaultGetter does, instead of writing the zeros out.
  5. hashPair and nestInPairsTwo small helpers. hashPair fingerprints two fingerprints together (keccak256(left ‖ right)). nestInPairs turns [a, b, c, d] into [[a, b], [c, d]], the shape the wallet signs.
  6. buildBulkOrderTree(orders)The main builder: works out the height, adds fillers, fingerprints every order (the leaves), pairs and fingerprints level by level until one root is left, and returns all of it plus the nested message for the wallet.
  7. bulkOrderProof(tree, index)For the listing at position index: its neighbour fingerprints on the way up, one per level (6 for 50 names). With them anyone can rebuild the root from that one listing.
  8. bulkOrderDigest(root, height, chainId, seaport)Mohit's formula from the PDF: keccak256(0x1901 ‖ domainSeparator ‖ keccak256(typeHash ‖ root)), the number the wallet really signs.
  9. toCompactSignature(signature)MetaMask returns 65 bytes; Seaport accepts a 64 byte form that means the same (EIP 2098). Seaport.js and F2 use the short one, so this shortens it.
  10. encodeBulkSignature(walletSignature, index, proof)One listing's own signature: 64 byte signature, then the position in 3 bytes, then the proof. 259 bytes each for 50 names.
  11. bulkOrderSignatures(tree, walletSignature)Does the step above for every listing. This is what phase 3 sends to the backend.
  12. decodeBulkSignature(signature)The reverse: splits a signature back into its parts, telling the 64 and 65 byte forms apart by length, the same rule as Seaport and the backend. A normal single listing signature returns "not a bulk signature".
  13. rootFromProof(leaf, index, proof)Starts from one listing's fingerprint and climbs the tree with the proof; at each level the position says left or right. The answer should be the root.
  14. recoverBulkSigner(order, signature, chainId, seaport)Who signed this listing: split the signature, rebuild the root, rebuild the digest, ask the maths which wallet made the signature. Returns nothing if anything is malformed.
  15. findBadBulkSignatures(orders, signatures, seller, …)The safety check before posting (F2 step 5): checks every listing's signer is the seller and returns the positions that fail. Empty list means all good. The bulk version of the verifyTypedData check in the single listing flow.
