What happened, step by step

  1. Edit price → Remove this listing → Delist. MetaMask sent the Seaport cancel transaction: the listing is really cancelled on the blockchain.
  2. Our code then called cancel-bulk with the transaction hash so the backend records it. That call failed with 500.
  3. Our code showed "Cancel sent on the blockchain. The marketplace may take a minute to update.", closed the drawer and refreshed the table.
  4. The backend still thinks the order is active, so the row kept showing Edit price and no "Cancelling" label (that label also comes from the backend).
  5. Delist pressed again: our code had no memory of the first cancel, so MetaMask asked for a second cancel transaction. Harmless on chain (Seaport cancels it again), but a second small fee.

Once the backend is fixed, its chain watcher (BL-08 sweep) should see the cancel on chain and update the row by itself.

Update, 24 Nov (later the same morning): recovered by itself. The backend's chain watcher saw the cancel on the blockchain and confirmed it: the cancel email arrived, and after a refresh westbengal.og shows List. So an unrecorded cancel heals on its own; the seller just can't tell meanwhile, which is why the guard in section 6 still matters.

5. Likely cause (to confirm with Guru)

A database migration timing gap on stage, from the multi chain work. No code fix was needed; it healed once the database caught up.

When (UTC)What
23 Nov 10:25MC-06 merged into the multi chain branch: new amount columns and a chain aware "one active listing per name" index on the orders table, with a backfill on start
24 Nov 06:08MC-07 merged: chainId and tokenContract on listing status and listing history, and a new unique key (userId, chainId, tokenContract, tokenId)
24 Nov morningBulk post 500 (every try)
24 Nov 06:37cancel-bulk 500, half an hour after MC-07
24 Nov laterCancel recorded by the chain watcher, email sent, row shows List: writes work again
  1. With MC-07, every listing and every cancel writes the listing status row with the new key (upsertListed / upsertUnlisted on userId, chainId, tokenContract, tokenId).
  2. If the new code ran on stage before its migration added those columns and that key, the database refuses the write, the server doesn't catch it, and the answer is a 500. Both the bulk post and cancel-bulk do this write.
  3. Reads don't touch these columns, so my-domains and my-listings kept working. The error comes straight from the database, which fits the fast failure (under 0.4 s).
  4. MC-07 even logs this case: "MARKETPLACEV2 SCHEMA NOT MIGRATED: the MC-07 migration has not run on this database".
  5. Once the migration ran (or the backfill finished), writes worked again and the chain watcher confirmed the westbengal cancel.

Not confirmed: which branch stage runs and when the migration ran. Earlier suspects (the 23 Nov S3 and Google login changes) don't explain a 500 on these writes.

Question for Guru: "This morning POST /orders/bulk and /orders/cancel-bulk gave 500 on stage, and it cleared by itself around noon. Was stage running the multichain branch (MC-06 / MC-07) before its migration ran? Just want to confirm so we note the cause correctly."

The row kept showing the listing, and pressing Delist again sent a second paid cancel. The backend healed itself a few minutes later from the chain. We built safeguards for this (remember a sent cancel in the browser, show "Cancelling" at once, block a second paid cancel, retry recording with the same transaction hash), but they are not in your requirements and the code review found holes in them, so we removed them and kept only a clearer message: "Your listing is cancelled on the blockchain. The marketplace hasn't caught up yet, so it may still show as listed for a while. You don't need to delist it again." Do you want the full safeguards in this release?

If he says yes, rebuild them this way (the review's fixes):

  • Save at the moment of sending: write the entry (recorded false) as soon as the transaction hash exists, then mark it recorded; add a timeout to the record call (review H2).
  • Never prune an unrecorded entry because its row is missing (a failed page load or a non listed order like "Cancel again" or "Cancel older listings"); prune only after a successful record or when the backend shows the order settled (H1, H3).
  • Tie entries to the seller wallet and filter by the connected wallet; stop retrying on 403 or 400 (M12).
  • Check the transaction receipt; drop dropped, reverted or replaced transactions and offer Cancel again after about 30 minutes (M6).
  • Poll only while something can still change, and stop when the wallet proof lapses (M13); count only the hashes actually sent in bulk delist (L18).
