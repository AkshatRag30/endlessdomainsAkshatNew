3. High severity (5)

H1

Cancel safeguard memory is wiped when My Domains fails to load. The page passes the live listings to usePendingCancels as soon as loading ends. On a load error, the summary is empty, so the "live listings" set is empty and settledSentCancels deletes every remembered cancel, including ones the backend never recorded.

pages/seller-hub/my-domains/index.tsx:94 (only isLoading becomes null), helpers/my-domains/onChainCancel.ts:208, hooks/my-domains/usePendingCancels.ts:16

Scenario: exactly the 24 Nov outage: cancel-bulk fails (unrecorded), the seller reloads while my-domains also 500s → memory erased → when the backend is back the row shows for sale, Delist is allowed, second paid cancel. Fix: pass null on isError too, and never prune an unrecorded entry because its row is missing; prune only on a successful record or backend state. Checked: confirmed.

H2

A sent cancel is remembered only after the backend call finishes. saveSentCancels runs after runOnChainCancel returns, i.e. after the whole cancel-bulk record loop. callBackend has no timeout.

hooks/my-domains/useOnChainCancel.ts:73, helpers/my-domains/onChainCancel.ts:73-100

Scenario: transaction sent, cancel-bulk hangs, the seller closes the tab or delists again from another place → no memory, no guard, no retry → second paid cancel. Fix: save the entries (recorded false) the moment the transaction hash exists (an onSent step), mark them recorded after the record; add a timeout to the record call. Checked: confirmed.

H3

The cleanup deletes cancels for orders that aren't listed rows. "Cancel again" (an unconfirmed cancel, row not for sale) and "Cancel older listings" (old hidden orders) cancel hashes that are never in the live listings set, so the next refresh prunes them at once.

onChainCancel.ts:208, usePendingCancels.ts:44-46

Scenario: Cancel again → cancel-bulk fails → entry pruned, never retried, guard gone → the button is still there → second paid cancel. Fix: same as H1: never prune unrecorded entries by "row absent"; expire recorded ones by time or by the my-listings state. Checked: confirmed.

H4

The single listing drawer's Cancel stays clickable after the signature is in. While the old listing is being hidden (Edit price) or the new one posted, Cancel still shows. Pressing it says "Cancelled. Nothing was listed." and drops the result, but the hide and post carry on. Found independently by two reviewers.

listing-flow/ListingFlowModal/ListingFlowModal.tsx:230-236, 277, 467, listingOrder.ts:79-92; the per name bulk fallback has the same gap (BulkListingFlowModal.tsx:243-257)

Scenario: Edit price, sign, press Cancel during the hide: the old listing is hidden, the new post fails, and the seller is told nothing changed (the "your old listing was taken down" toast is swallowed): no live listing and a wrong message. In the per name fallback, a name posted just after Cancel shows as "Stopped before signing". Fix: report a "publishing" phase once signing is done and hide Cancel from then on (the one signature bulk path already does this). Checked: confirmed.

H5

Layering (CLAUDE.md §8): backend calls and data hooks inside the design system. listingOrder.ts (new on this branch) builds, signs and POSTs orders from a composite folder; useBulkListingActions (a hook) imports useListingFlowActions and listingOrder from that composite folder; BulkListingFlowModal, BulkDelistModal and ListingFlowModal call data hooks (useBulkListingActions, useNftApprovals, useOnChainCancel). None of these is in §8's allowed exceptions or the known violations list.

listing-flow/listingOrder.ts:84, hooks/my-domains/useBulkListingActions.ts:12-13, BulkListingFlowModal.tsx:17-22, BulkDelistModal.tsx:9

Risk: no runtime bug; it breaks the agreed structure and makes the drawer hard to test. Fix: move the POST to core/services/my-domains, the flow logic and useListingFlowActions to hooks/my-domains, and either lift the hooks into a connected wrapper or record these as known violations in §8 and the layering plan. Larger refactor: worth your decision. Checked: confirmed.

8. Done well

  • Exact port of Seaport's bulk signature scheme, proven against Seaport.js and checked again with ethers' own EIP712 hash.
  • Every signature verified locally against the seller before anything is posted; padding leaves can't get a proof.
  • Money as 6 decimal integers from the typed text to the signature (never Number()); totals use the same split as the signed order.
  • A failed post is retried with the same signed bytes, no new signature; a late signature after Cancel is never posted in the one signature path.
  • On chain cancel recomputes each order's hash and checks the offerer before any gas is spent; the 409 resend loop is capped.
  • Pure, injected, testable cores (runBulkBatch, runOnChainCancel, the tree); approvals read on the right chain; one Multicall3 read for expiries; dark mode and §4 rules followed; all browser storage access guarded.
