1. The ideas behind v2, explained simply

What a listing is

Listing puts nothing on the blockchain. Your wallet signs a message (a Seaport "order") saying "anyone may buy this name for this price until this date", and we store it on our server. A buyer later sends it to the Seaport contract, which checks your signature and swaps the name for the money.

Why today's drawer is annoying

The current branch signs one order per name. Fifty names means fifty wallet popups.

What a bulk signature is

All orders go into a small tree: every pair joins into a parent until one top is left (the root). The wallet signs only the root, once. Each order carries a short "proof" showing how it links up to the root. Fifty names, one popup. With 50 names the tree has 6 levels (64 spots, the empty ones filled with blank orders).

Off chain versus on chain cancel

Today "Delist" only tells our server to hide the order. The signed order still exists and can still be bought until it expires. An on chain cancel is a real transaction telling Seaport "this order is dead". It costs a little POL but is final. v2 switches Delist to on chain.

Approval

Before Seaport can move your names, your wallet must allow it once ("setApprovalForAll"). This is per NFT contract per chain. Today every name is UD on Polygon, so it is one approval.

The verified wallet

Our backend only accepts orders after your wallet proved it belongs to your account (a separate small signature, done now and then). The backend treats that verified wallet as the seller (the "maker") of every order.

How the real B1 differs from the plan's first guess

  1. Each result also has a batchId. When a name is listed, code and message are null (present but empty), not missing.
  2. Whole batch errors are HTTP 400 with a code: CHAIN_NOT_SUPPORTED, BATCH_EMPTY, BATCH_TOO_LARGE, BATCH_MIXED_MAKER (orders from more than one wallet), BATCH_DUPLICATE_ITEM, and CHAIN_UNAVAILABLE (a 503: the blockchain node isn't answering).
  3. The tricky one, BATCH_ALL_REJECTED. If every name is rejected, the server answers with an error, but the body still holds batchId and the full results. If we treat every error as "something went wrong", the seller sees a vague error instead of each name's reason. The success screen must read results out of the error body.
  4. A speed limit: 10 bulk calls per minute per user. Hammering "Try again" gets a 429 (too many requests), which needs a friendly message.

How "Cancelling" is stored

The backend has no cancel_pending status. It stores the order as cancelled plus extra fields saying it was on chain and not confirmed yet. That's fine for us: the My Domains listings endpoint turns this into status: "cancel_pending", and adds a yes/no field cancelNotConfirmed. Those two decide which of the three states a row shows. The catch: no code sets "not confirmed" yet. Mohit's 30 minute timer (60 on Ethereum) and the check for a failed cancel transaction aren't built.

The real B5 shape

  • Bulk cancel. POST /marketplacev2/orders/cancel-bulk with { orderHashes (1 to 50, no repeats), cancelTxHash }. It answers { results: [{ orderHash, status: "cancel_pending" }] }.
  • All or nothing, unlike bulk listing. One bad order fails the whole request: 403 if an order isn't yours, 400 CANCEL_MIXED_CHAIN if the orders are on different chains, 409 ORDER_NOT_CANCELLABLE with the problem hashes.
  • Single cancel. The same old route, POST /orders/{hash}/cancel, now takes an optional { cancelTxHash }. With it, the cancel is on chain. Without it, it's still the old off chain cancel.
  • Good news. Orders already cancelled off chain can still be cancelled on chain (gap 6).
  • Speed limit. The same as listing: 10 calls a minute.

The shared signing code

The backend uses the shared package @endlessdomains/order-builder (now at c89fe52), which has a signBulkOrders function. The backend's tests sign with it. We can't import it (it uses ethers v6; our site uses ethers 5.7.2), but it is the perfect reference: if our signatures equal what it produces, the backend accepts them.

3. What the plan misses or gets wrong

1

Names held in more than one wallet important

What it means
One account can have several linked wallets. My Domains shows names from all of them, and rows don't say which wallet holds each name.
Why it matters
The backend makes the verified wallet the seller of every order and rejects mixed sellers (BATCH_MIXED_MAKER). Selecting names from two wallets fails the whole batch with no clear reason. Same for delist: only the wallet that signed an order can cancel it, otherwise the transaction fails and still costs gas.
What I suggest
Before signing, read ownerOf on chain for the selected names (one quick read) and mark names held by another wallet: "held by another wallet, switch wallets to list it". Or ask the backend to add the owner wallet to each row. Same check before a delist.
2

"Exactly one signature" versus the wallet proof

What it means
The PDF's acceptance test says 50 names need exactly one signature. But our flow also checks the wallet proof (ensureWalletVerified), and if it is old, the wallet asks for a second signature first.
Why it matters
A tester sees two popups and fails the test, though nothing is broken.
What I suggest
Check the wallet proof when the drawer opens, not on the List click. Then List only ever asks for the one bulk signature.
3

Where the expiry date comes from

What it means
Our 7 and 14 day rules (orders end 7 days before the name expires; under 14 days left can't be listed) use renewalTimestamp from our database. The PDF says the backend reads expiry from the chain (UD expiryOf, where 0 means never expires).
Why it matters
If the two dates disagree, the drawer says a name is fine and the backend rejects it, or the other way round.
What I suggest
Ask Guru whether they always match for UD. If unsure, read expiryOf on chain for the batch, like the owner check.
4

Delist is also used on the marketplace home page

What it means
useDelistListing is used by My Domains rows and cards and also by pages/index.tsx. Today a delist can work with no wallet connected, since it only talks to our server.
Why it matters
An on chain cancel needs a connected wallet, on Polygon, with POL for gas. New states: no wallet, wrong network, not enough POL, popup closed. Phase 8 only mentions My Domains.
What I suggest
Add pages/index.tsx and those wallet states to phase 8.
5

The cancel function isn't in our contract list

What it means
We talk to Seaport through a short function list (SEAPORT_MIN_ABI in seaport-order-builder-v5.ts). cancel isn't in it.
Why it matters
Adding it edits a file the multi chain developer also edits (C3).
What I suggest
Only add, never change what's there, and tell the other developer (in their message).
6

Old "delisted" orders are still alive on chain

What it means
Every delist so far was off chain, so each of those old orders can still be bought at its old price until it expires.
Why it matters
With B7, relisting such a name at a higher price is refused with CHEAPER_ORDER_STILL_VALID (your older, cheaper order is still out there). This is the most likely way sellers will see the "cancel the old one first" prompt. Cancelling those needs their full signed data (rawOrder), so the backend must still return it for orders it marked cancelled.
What I suggest
Ask Guru once he's free (section 5) and design the prompt with this case in mind.
7

"Price cuts are free" has nowhere to live

What it means
Decision 1: price increases need an on chain cancel, price cuts stay off chain and free. But sellers have no "Edit price" button; to change a price, they delist and list again. (Checked on the branch 19 Nov: ListingFlowModal has a dormant 'edit' mode titled "Edit listing", and the My Domains page passes onEditPrice down, but MyDomainRow and MyDomainCard never use it, so no button shows. If Mohit wants Edit price, this is the starting point.)
Why it matters
With Delist always on chain, a seller who only wants a lower price pays gas. That goes against decision 1, and the plan doesn't say what to do.
What I suggest
Phase 1: Delist always on chain (simplest and safest). Raise "Edit price" with Mohit as separate work (V7).
8

One chain per batch is in two tickets

What it means
The PDF lists it both as C8 (multi chain developer) and inside F9 (you).
Why it matters
Without agreement you could both build it.
What I suggest
You build the select mode part (chain filter required, Select All counts only that chain). They keep "switch the wallet to that chain" (C4). It's in the message.
9

Smart wallet detection

What it means
Decision 10 wants a clear message for smart contract wallets. The usual check is "does this address have code on chain".
Why it matters
Newer normal wallets using EIP 7702 also have code (starting 0xef0100) yet sign normally. A plain check would wrongly block them.
What I suggest
Treat code starting with 0xef0100 as a normal wallet.
