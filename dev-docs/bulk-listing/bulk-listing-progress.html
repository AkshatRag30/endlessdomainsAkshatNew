3. How Cancel stays safe (E2)

2. How it works

  1. Listed rows and cards show Edit price (as Figma draws it) instead of Delist.
  2. The listing drawer opens in its edit mode ("Edit listing"), price prefilled. A note: "Lowering the price is free. To raise it, delist first (small network fee), then list again."

  6. Delisting is in the drawer: a red Remove this listing box under the note ("Cancels it on the blockchain so nobody can buy it. Small network fee." + Delist), which runs the phase 8 on chain cancel and closes the drawer.

7. Decisions

  • No fallback on a cancel. A cancel is the seller's choice, not a wallet limit; offering more popups would be pushy.
  • Fallback on a failed local check too. If a wallet signs but the signature doesn't lead back to the seller, the wallet hashed the big message differently. Per name signing uses the plain message every wallet supports.
  • The network and smart wallet checks come before the wallet proof and the signature, so the fallback can never be offered for problems it can't fix.
  • A failed code read counts as "not a smart wallet" on open (so a slow RPC doesn't block normal users); the check at List time is the real guard.
  • The per name flow is the October one, unchanged. Its "remaining" count bug (F6 item 3) is fixed in phase 5 with the other drawer fixes.
  • Phantom, Rabby and Coinbase marked not tested (your decision, 20 Nov): their test needs the domain owning account imported into each extension, and that key is not a throwaway test key.

How it works, step by step (matches F2 steps 2 to 5)

  1. Height. max(1, ceil(log2 n)): 1 or 2 orders give height 1, 3 or 4 give 2, 50 gives 6 (64 leaves). Zero orders, or more than height 24 allows, throw.
  2. Padding. The batch is filled up to 2h with an empty order (every field zero, empty offer and consideration), built from the EIP712 types the same way Seaport.js's DefaultGetter does. An empty order can never be filled.
  3. Type. BulkOrder { OrderComponents[2]...[2] tree }, one [2] per level, built in code from our existing EIP712_TYPES. No type string is typed by hand.
  4. Tree. Each leaf is the order hash (hashStruct(OrderComponents), our existing computeOrderHash); each parent is keccak256(left ‖ right), unsorted, as Seaport.js builds it.
  5. Message to sign. The padded orders nested in pairs ([[a, b], [c, d]] and so on), which is what the wallet shows and signs once.
  6. Each order's signature. The wallet's 65 byte signature is shortened to 64 bytes (EIP 2098, as Seaport.js does), then the 3 byte leaf index, then one 32 byte proof hash per level. For 50 names that is 64 + 3 + 6 × 32 = 259 bytes per order.
  7. Local check. For each order: split the signature, rebuild the root from the order hash and the proof (the index bits say left or right at each level), compute keccak256(0x1901 ‖ domainSeparator ‖ keccak256(typeHash ‖ root)), recover the signer and compare it with the seller. findBadBulkSignatures returns the positions that fail, so an empty list means the whole batch is good. This mirrors the verifyTypedData check in listingOrder.ts.

Decisions

  • Ported, not installed. Seaport.js needs ethers 6 and merkletreejs; this app is on ethers 5.7.2. The tree, type and padding code is ported from Seaport.js 4.4.1 (MIT, src/utils/eip712) to ethers 5, with a plain loop instead of merkletreejs. No new dependency. The file header says where every piece comes from.
  • The full type hash, not Seaport.js's helper. Seaport.js's getBulkOrderTypeHash hashes only the field text OrderComponents[2]..., which does not match the signed message (Seaport.js never uses it when signing). Ours hashes the full EIP712 type string. For height 6 the real hash is 0x1c19f719…0b55; the tests prove the digest built with it equals the digest the wallet signs. Explained in full under "Found while building" below.
  • 64 byte signature by default, 65 also accepted. We send 64 bytes as F2 asks and Seaport.js does. The decoder and the local check also accept the 65 byte form (Seaport and the backend's check 2 accept both), told apart by length.
  • Imports. The helper imports EIP712_TYPES, computeOrderHash and seaportDomain from src/lib/seaport-order-builder-v5.ts, as bulkListing.ts already does; no hooks, services or components.
  • Fixtures (plan question V1). The plan's default was the shared package's signBulkOrders, but the backend's packages aren't installed and that repo is private, so the fixtures come from Seaport.js itself, the reference the PDF names. A one off script, run from an isolated scratch folder with install scripts turned off, signed with a test only key derived from a phrase (ethers id(...)), so no raw key sits in the repo and the key was never funded. The script is kept in dev-docs/bulk-listing/scripts/ with a README on how to rerun it (local only, like all of dev-docs).

Found while building: Seaport.js's type hash helper gives the wrong value

Background. What the wallet actually signs is one 32 byte number, the digest. Mohit's PDF (B2 step 3) writes the formula: keccak256(0x1901 ‖ domainSeparator ‖ keccak256(bulkOrderTypehash(h) ‖ root)). Three ingredients: the domain separator (which says "Seaport 1.6 on Polygon at this address"), the tree's root, and the type hash. The type hash is a fingerprint of the message's shape: under EIP712 it is keccak256 of the full type text, which for a bulk order of height 1 is BulkOrder(OrderComponents[2] tree)ConsiderationItem(uint8 itemType,address token,…)OfferItem(…)OrderComponents(address offerer,…), every struct spelled out. Wallets, Seaport's contract and the backend all compute it this way, so all of them arrive at the same digest.

What we found. Seaport.js has a helper, getBulkOrderTypeHash(height), that is supposed to give this value. It hashes only the short text OrderComponents[2] (just the field's type, for height 1), not the full type string. So its answer is a different number:

HeightSeaport.js helperCorrect (full EIP712 type)
1 (1 or 2 names)0xe6ff1186…0x3ca2711d…
2 (3 or 4 names)0xe69f7b73…0xbf8e29b8…
6 (33 to 64 names)0xf8ec28c8…0x1c19f719…

How we know which one is right.

  1. Using the correct value in Mohit's formula gives exactly the digest that ethers' own EIP712 code hashes, and exactly the message the test wallet signed, for all five fixture batches. Using the helper's value gives a digest nobody signed.
  2. Seaport.js contradicts itself: its own self check, Eip712MerkleTree.getBulkOrderHash(), uses the helper's method and then compares with the real EIP712 hash. Run on our fixtures it fails every time with "expected derived bulk order hash to match".
  3. Signing with Seaport.js still works because its signBulkOrder never calls either of these two functions. It lets the wallet library hash the full type itself. The broken helper simply goes unused, which is how the bug has gone unnoticed.

Why it matters to us. Phase 2 had to build the digest by hand (Mohit's formula) to do the local check before posting (F2 step 5). If we had copied the helper, the local check would have rejected every valid signature, or, written the other way round, the check would compare against a value no wallet ever signs. We hash the full EIP712 type string instead (bulkOrderTypeHash in bulkOrderTree.ts), the fixture records the correct value, and a test pins it for every case.

Who else could be affected. Anyone who ported Seaport.js's helper to check bulk signatures by hand. The backend's check 2 lives in the shared package @endlessdomains/order-builder, which we can't read. If it used the helper, it would reject every bulk listing; Guru's tests sign with the package's own signBulkOrders, so a matching mistake on both sides could pass his tests and still fail with real wallets. Worth asking him once he's free; it's in the review page's questions.

In plain words. The wallet signs a fingerprint built from three parts. One part, the "shape fingerprint", must be made from the full description of the message. Seaport.js has a shortcut function that fingerprints only a short piece of that description, so it gets a different answer. Seaport.js itself never uses that function when signing, which is why nobody noticed. We use the full description, and we proved ours is right because it reproduces exactly what the wallet signed.
