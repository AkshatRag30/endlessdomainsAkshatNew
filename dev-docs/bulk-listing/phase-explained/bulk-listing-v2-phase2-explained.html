1. The story in six sentences

  1. Every listing is a message you sign in MetaMask. Until now, 50 names meant 50 messages and 50 popups.
  2. Seaport (the marketplace contract) has a trick: put many listings into a "tree", and sign only the very top of the tree, once.
  3. Mohit sir's ticket F2 asks for exactly that, and gives the steps.
  4. Phase 2 built that trick as pure maths: build the tree, give each listing its own signature, and check a signature is genuine. No wallet, no internet, no screen.
  5. To be sure the maths is right, we compared it with the official Seaport.js library, byte for byte, for batches of 1, 2, 3, 4 and 50 listings. Everything matched.
  6. Along the way we found a wrong helper inside Seaport.js itself (the "type hash" helper) and made sure we don't copy that mistake.

2. Words to know first

WordIn simple words
Listing / order"I sell this domain for this price until this date", in Seaport's format (called OrderComponents).
Hash / fingerprintA short code (32 bytes) made from any data. Same data always gives the same code; change one letter and the code is totally different. We use keccak256, Ethereum's fingerprint.
SignatureYour wallet's stamp on a fingerprint. Anyone can check which wallet made it, nobody can fake it. Free, no gas.
Typed data (EIP712)The way MetaMask shows a message with readable fields (offerer, price…) instead of gibberish. It needs a description of the message's shape, called the types.
TreeListings paired up, each pair fingerprinted, those paired again, until one fingerprint is left at the top.
LeafA listing's fingerprint at the bottom of the tree.
RootThe one fingerprint at the very top. The wallet signs this.
HeightHow many levels the tree has. 2 listings: 1. 3 or 4: 2. 50: 6.
PaddingA tree needs 2, 4, 8, 16, 32 or 64 leaves. Missing spots are filled with an empty listing that can never be bought.
ProofFor one listing: the neighbour fingerprints on the way up to the root. With them anyone can rebuild the root from just that listing.
DigestThe final 32 byte number the wallet really signs: made from Seaport's address and chain, the tree's shape, and the root.
Type hashA fingerprint of the message's shape (not its content). One of the three ingredients of the digest.
FixtureA saved file of correct answers that tests compare against. Like an answer key.

3. The tree, drawn (3 listings)

Say you list A, B and C. Three isn't a power of two, so one empty listing E is added. Height is 2.

LevelWhat is there
Top (root)R = fingerprint of (AB, CE) · the wallet signs this, once
MiddleAB = fingerprint of (A, B) · CE = fingerprint of (C, E)
Bottom (leaves)A · B · C · E (empty, can never be bought)

C's own signature = the wallet's one signature + C's position (2) + C's proof (E, then AB). From C plus E you rebuild CE; from CE plus AB you rebuild R; and R is what the wallet signed. So C can be bought on its own, and Seaport can check it, without knowing anything about A or B. Change C's price after signing and its fingerprint changes, the rebuilt root no longer matches, and the check fails.

6. File 2 · the maths · src/helpers/my-domains/bulkOrderTree.ts

2

Build the tree, sign the listings, check them

New · 222 lines · the heart of phase 2
In one line
Every function needed for "sign once for all names", as pure maths.
Where from
Ported from Seaport.js 4.4.1 (free MIT licence), the library Mohit sir's PDF names. We couldn't install it: it needs ethers version 6 and our site uses version 5. So the same logic was rewritten for ethers 5, with a simple loop instead of the extra tree library Seaport.js uses. The header comment says exactly where each piece comes from.
One difference
We don't copy Seaport.js's type hash helper, because it's wrong (section 10).

Sizes, named so the code reads clearly (lines 31 to 36)

  • BULK_ORDER_MAX_HEIGHT = 24: Seaport's limit. Our cap of 50 names is height 6, far below.
  • 3 bytes for the position, 32 bytes per proof step, 64 or 65 bytes for a wallet signature.

Building the tree

  1. bulkTreeHeight(count) · line 39How many levels: the smallest number of doublings that fits the listings, at least 1. 1 or 2 listings: 1. 3 or 4: 2. 5 to 8: 3. 50: 6. Refuses 0 listings.
  2. bulkOrderTypes(height) · line 47Builds the description MetaMask needs: one line BulkOrder { tree: OrderComponents[2][2]... } (one [2] per level) on top of the listing description we already had. The code writes the long text, never a person, so a typo is impossible. Mohit sir's F2 step 3 asks for exactly this.
  3. bulkOrderTypeHash(height) · line 55The "shape fingerprint", made from the full description text. This is where we deliberately differ from Seaport.js (section 10).
  4. emptyValue (line 61) and emptyOrderComponents() (line 80)Make the padding listing: every number zero, every address zero, no items. Built automatically from the description, the way Seaport.js does it, instead of typing the zeros by hand. Nobody can ever buy it: it offers nothing.
  5. hashPair (line 84) and nestInPairs (line 89)Two little tools. hashPair fingerprints two fingerprints together. nestInPairs turns [A, B, C, E] into [[A, B], [C, E]], the shape MetaMask signs.
  6. buildBulkOrderTree(orders) · line 100 · the main builderWorks out the height, adds padding, fingerprints every listing (the leaves), pairs and fingerprints level by level until one root is left, and returns all of it plus the nested message for MetaMask.
  7. bulkOrderProof(tree, index) · line 129For the listing at a position: its neighbour fingerprints on the way up, one per level. In the drawing, C's proof is E then AB.
  8. bulkOrderDigest(root, height, chain, seaport) · line 141Mohit sir's formula (PDF B2 step 3): the final number the wallet signs, made from "Seaport on Polygon at this address", the shape fingerprint, and the root.

Giving each listing its own signature

  1. toCompactSignature(signature) · line 148MetaMask returns 65 bytes. Seaport also accepts a 64 byte short form that means exactly the same (a standard called EIP 2098). Mohit sir's F2 step 4 and Seaport.js use the short one, so this shortens it.
  2. encodeBulkSignature(walletSignature, index, proof) · line 156Glues one listing's signature together: 64 byte signature + 3 byte position + the proof. For 3 listings that's 64 + 3 + 2 × 32 = 131 bytes; for 50 listings 259 bytes.
  3. bulkOrderSignatures(tree, walletSignature) · line 162Does that for every real listing (not the padding). This list is what phase 3 sends to the backend.

Checking a signature (F2 step 5)

  1. decodeBulkSignature(signature) · line 171The reverse of glueing: splits a signature back into its three parts, telling the 64 and 65 byte forms apart by length (the same rule Seaport and the backend use). A normal single listing signature returns "not a bulk signature".
  2. rootFromProof(leaf, index, proof) · line 191Starts from one listing's fingerprint and climbs: at each level the position says "am I on the left or the right?", so it knows which order to pair them in. The answer should be the root.
  3. recoverBulkSigner(order, signature, chain, seaport) · line 200Who signed this listing? Split the signature, rebuild the root, rebuild the digest, and ask the maths which wallet made the signature. Returns nothing if anything is malformed.
  4. findBadBulkSignatures(orders, signatures, seller, …) · line 218The safety check before sending: checks every listing's signer is you, and returns the positions that fail. Empty list means all good. The bulk version of the verifyTypedData check single listing already does.

10. The type hash bug we found in Seaport.js

!

Seaport.js's type hash helper gives the wrong value

Found 19 Nov

Background. The digest (what the wallet signs) has three ingredients: Seaport's address and chain, the root, and the shape fingerprint (type hash). The shape fingerprint must be made from the full description of the message: BulkOrder(OrderComponents[2] tree)ConsiderationItem(…)OfferItem(…)OrderComponents(…), every part spelled out. Wallets, Seaport's contract and the backend all do it that way.

The bug. Seaport.js has a helper, getBulkOrderTypeHash, that is supposed to give this. It only fingerprints the short piece OrderComponents[2]. So its number is different:

HeightSeaport.js helper (wrong)Correct
1 (1 or 2 listings)0xe6ff1186…0x3ca2711d…
2 (3 or 4 listings)0xe69f7b73…0xbf8e29b8…
6 (33 to 64 listings)0xf8ec28c8…0x1c19f719…

How we know ours is right. Using the correct number in Mohit sir's formula gives exactly what the test wallet signed, every time. Seaport.js's own self check, which uses the helper, fails with "expected derived bulk order hash to match". Seaport.js signing still works only because its signing function never calls the helper: the broken helper is simply never used, which is why nobody noticed.

Why it mattered to us. Our safety check (F2 step 5) builds the digest by hand. With the helper's number, it would have rejected every genuine signature.

Confirmed 20 Nov: Guru's own ethers 5 port on his test page (src/bulk-listing-testing/bulkSigning.ts) also uses the full description, the same as ours. And the real MetaMask test in phase 3 was accepted by the backend.

12. How phase 3 uses phase 2

Phase 2 was the engine on a test bench; phase 3 put it in the car. In src/helpers/my-domains/bulkBatch.ts (runBulkBatch):

  • buildBulkOrderTree builds the tree from the listings the drawer prepared.
  • The hook asks MetaMask to sign tree.types and tree.value once.
  • bulkOrderSignatures gives each listing its signature.
  • findBadBulkSignatures runs before anything is sent.

Result on 20 Nov: 8 names, one MetaMask popup, and the backend accepted every genuine signature. Details: bulk-listing-v2-phase3-explained.html.

13. Questions you might have

  1. Why not just install Seaport.js?It needs ethers version 6; our site is on version 5. Upgrading ethers would touch every wallet feature on the site. Porting about 200 lines was much safer, and the tests prove the port gives identical answers.
  2. Why do we need the answer key at all?Without it, the tests would only check our maths against itself. With answers made by the official library, a mistake in our port shows up immediately.
  3. Can someone buy the padding listing?No. It offers nothing and asks for nothing, so Seaport has nothing to transfer.
  4. Can a buyer buy one name from a batch without the others?Yes. That's the point of the proof: each listing carries its own way back to the signed root.
  5. Do we delete the test later?No. It stays as a guard: if anyone ever changes the listing format or this file, the tests catch it before users do.
  6. Who asked for this?Mohit sir's PDF, ticket F2 steps 2 to 5 (page 5), and B2 step 4 asks for tests against Seaport.js for heights 1, 2 and 6. Our plan's phase 2 put it in its own file first so it could be tested alone.
