Bulk listing v2 · phase 3 explained

Phase 3 in simple words: the 10 files

One page to understand everything phase 3 changed: what each of the 10 files is, why it exists, what is inside it, and how they work together when you list names. No prior knowledge needed. Written 20 Nov 2026; line numbers are as of that day.

1. The story in six sentences

  1. Before phase 3, listing 8 names meant 8 MetaMask popups, one per name, and 8 separate messages to our backend.
  2. Phase 2 built the maths that lets one signature cover many listings (a "tree" of listings, where the wallet signs only the top).
  3. Phase 3 plugged that maths into the bulk listing drawer, and connected it to Guru's new backend address that accepts many listings in one message.
  4. Now: you click List, MetaMask opens once, and all names are sent together in one message.
  5. If sending fails (bad internet, busy server), you can press Try again without signing again, because we keep the signed listings in memory.
  6. The backend answers name by name, so you see exactly which names went live and why the others didn't.

2. Words to know first

WordIn simple words
Listing / order"I sell this domain for this price until this date", written in Seaport's format. Signed by you, so nobody can change it.
SignatureYour wallet's stamp on a message. Free, no gas. Proves you agreed to exactly that message.
TransactionSomething written on the blockchain. Costs gas. (Listing needs none; approval and on chain cancel do.)
Bulk treeAll your listings arranged so that one signature on "the top" covers every one of them. Each listing then carries a short "path" to the top, so it can still be bought on its own.
Wallet proofA free signed text message that proves to our backend that the connected wallet is yours. It stays valid for about an hour.
BackendGuru's server. It checks every listing and stores the good ones so buyers can see them.
EndpointAn address on the backend you send a message to, like POST /marketplacev2/orders/bulk ("here are many listings").
Service (src/core/services)Our code that talks to the backend. Our rule: only services may do that.
Helper (src/helpers)Pure logic: data in, data out. No wallet, no internet, no screen. Easy to test.
Hook (src/hooks)The glue between the screen and the real world (wallet, services).
Composite (src/design-system/composites)A piece of screen, like the drawer or one of its steps. It only draws things and reports clicks.
Types (src/types)Descriptions of the shape of data ("a result has a name, ok yes/no, an error text"). They don't do anything; they stop mistakes.

4. File 1 · the service · src/core/services/my-domains/bulkOrders.service.ts

1

Sends the batch to the backend

New · 28 lines
In one line
The one and only place that sends "here are my listings" to Guru's bulk endpoint.
Like
The post office counter. You hand over one envelope with all your listings; it hands back the reply.
Why needed
Our rule (CLAUDE.md §8) says only core/services may talk to the backend. The plan named this exact file.

What's inside

  1. postBulkOrders(request) · line 13Sends the listings to POST /marketplacev2/orders/bulk using the same login as everything else on the site. Returns the backend's reply: a batch id plus one answer per name ("listed", or "rejected" with a reason code).
  2. allRejectedAnswer(err) · line 24The tricky case. When the backend refuses every name, it replies with an error instead of a normal answer. But inside that error it still lists each name's reason. This function digs those reasons out, so the drawer can say "theforceis.unstoppable: An older, cheaper listing is still live" instead of a useless "Something went wrong".

Example

You send 3 names. All 3 are already listed. The backend replies "error 400, BATCH_ALL_REJECTED", and inside: name1 ALREADY_LISTED, name2 ALREADY_LISTED, name3 ALREADY_LISTED. This file turns that into a normal answer with those 3 reasons, and the drawer shows "Nothing was listed" with "Already listed" next to each name.

Who uses it

Only the hook (file 4), through its postWithProof.

5. File 2 · the rules · src/helpers/my-domains/bulkBatch.ts

2

The rules of one batch

New · 179 lines · the heart of phase 3
In one line
The step by step recipe: build every listing, sign once, check, send once, read the answers.
Like
A recipe card. It says what to do and in what order, but it doesn't own the oven or the shop. Whoever uses the recipe hands those in.
Why "pure"
It never touches the wallet or the internet itself. The hook hands in "here's how to sign" and "here's how to send". That's why the tests can run it with a test wallet and a pretend backend, in one second, without MetaMask.

What's inside, in the order it runs

  1. runBulkBatch(items, days, deps) · line 125 · the main recipe Step 1, prepare: ask for the wallet proof if it's old, read your Seaport counter and the blockchain's current time (once for all names).
    Step 2, build: for each name, work out how long it can stay listed (the days you chose, or less if the domain itself expires sooner; if it expires within a day it's left out with "Expires too soon to list"), then build its listing.
    Step 3, if every name was left out, stop here: nothing to sign.
    Step 4, sign: put all listings in the tree (phase 2), ask the wallet once, give each listing its own signature.
    Step 5, check: make sure every signature really comes back to your wallet. If even one doesn't, send nothing.
    Step 6, send: pack everything into one message and hand it to postSignedBatch.
  2. postSignedBatch(batch, deps) · line 112 · only the sendingShows "Publishing", sends, and returns either the results or "send failed" together with the signed batch. Because the batch is returned, Try again can send exactly the same thing again, with no new signature.
  3. mapBulkAnswers(batch, answer) · line 88 · reading the replyMatches each answer to your names by name (not by position, and ignoring capital letters), so a reply in a different order still lands on the right name. "listed" means live. "DUPLICATE_ORDER" also means live: it happens when a retry arrives after the first try already got through. A name the backend forgot to answer gets "No answer for this name, try again". The names left out in step 2 are added at the end.
  4. BULK_REJECT_REASONS and bulkRejectReason(code) · lines 57 to 82 · the reasons you readTurn the backend's codes into the wording you approved, for example ALREADY_LISTED becomes "Already listed", CHEAPER_ORDER_STILL_VALID becomes "An older, cheaper listing is still live". Codes that mean our listing or signature was wrong all become "Couldn't be checked, try again" and are written to the console as our bug.
  5. isRetryableResult(result) · line 83 · who gets a second chanceDecides who appears in "Try these again". Names that would fail the same way again are left out: Already listed, Not owned, Name doesn't match, An older cheaper listing is still live, Expires too soon.
  6. BulkBatchPhase · line 32 · the four working screensverify wallet, preparing, signing, publishing. The recipe announces each one so the drawer can show the right screen.

What it gives back: always one of three outcomes

OutcomeMeansThe drawer then
not-signedStopped before anything was signed (you cancelled, wallet problem, check failed)Goes back to the form with a message. Prices are kept.
post-failedSigned, but the send didn't arriveShows "Signed, but not published yet" with Try again
postedThe backend answered for every nameShows the result screen ("5 of 8 domains are live")

6. File 3 · the tests · src/helpers/my-domains/bulkBatch.test.ts

3

Proves the rules work

New · 229 lines · 11 tests
In one line
Automatic checks that run the recipe with a test wallet and a pretend backend.
Like
A driving test course: we drive the recipe through every tricky situation and check it does the right thing each time.
Run it
npm test (about a second, no MetaMask needed).

What's real and what's pretend

  • Real: the listings (built with the same builder the site uses), the tree, and the signature (a real wallet signs, but it's a throwaway test wallet made from a sentence, so no secret key is stored anywhere).
  • Pretend: the backend. Each test decides what the "backend" answers, so we can try situations that are hard to cause for real (everything refused, server too busy).

The 11 tests, in plain words

#The test checks that…
110 names give exactly one signature and one send, and every listing carries its own correct position and path
2A single name also works
3Refused names get the right reason; the "older cheaper listing" case keeps the old listings' ids (needed in phase 8); only names that could succeed go into "Try these again"
4A duplicate counts as listed, and a name with no answer is flagged
5Answers in a different order or with different capital letters still land on the right name
6Names expiring too soon are left out, and if all of them are, MetaMask is never even opened
7If you cancel the signature, nothing is sent
8If you cancel the wallet check, nothing is signed or sent
9If the signature comes from a different wallet, nothing is sent
10After "too many requests", Try again sends exactly the same bytes and asks for no new signature
11After a failed send, the names left out earlier are still shown in the final result

What was added

Then runs the recipe.
  2. retryBulkPost · line 157 · Try againSends the kept, already signed batch again. No MetaMask popup.
  3. postWithProof · line 91 · send, with one safety netSends the batch. If the backend says "your wallet proof is too old" (it lasts about an hour), it asks for a fresh proof once and sends the very same batch again. Single listing already does the same.
  4. classifyBulkBatchError · line 18 · what went wrong?Sorts a failure into: you cancelled in the wallet; this wallet isn't linked to your account; too many tries (429); Polygon unavailable (503); anything else. The drawer uses that to pick the right message.
  5. refreshAfter · line 102If anything got listed, refreshes the My Domains table so the names show as listed.
  6. isWalletProofFresh (line 164) and verifyWallet (line 175)For the form's notice: "is the proof still fresh for this exact wallet?" and the Verify wallet button.

What was kept on purpose

signAndSubmitBulk (line 52), the old "one popup per name" way. Not used by the drawer any more, but phase 4 brings it back as a backup button ("Sign each name separately") for wallets that can't sign the big message, like some hardware and phone wallets. Mohit sir's F3 asks for this.

15. Questions you might have

  1. Why did 3 of my 8 names say "An older, cheaper listing is still live"?They were listed before and then delisted with today's delist button. That only hides the listing on our site; the old signed listing can still be bought directly on the blockchain until it expires. Listing them again at a higher price would let a buyer pick the cheaper old one, so the backend refuses. Phase 8 adds a proper cancel on the blockchain. Until then, those names can only be listed at or below the old price.
  2. Why is the old "one popup per name" code still there?Some wallets can't sign the one big message. Phase 4 offers the old way as a backup button. Mohit sir asked for that (F3).
  3. If I close "Signed, but not published yet", is my signature out there somewhere?No. It only lived in your browser's memory and was never sent, so nobody can use it.
  4. Can Try again create the same listing twice?No. It sends the exact same listings. If the first try had actually arrived, the backend answers "duplicate", which we count as listed.
  5. Is this the same as Guru's test page?For everything that matters to whether a listing is valid, yes: same listing details, same tree maths, same signing, same check, same message, same retry. Differences on purpose: we send the 64 byte short signature (Mohit sir's PDF asks for it; he sends 65; the backend takes both), we shorten a listing when the domain expires sooner, and we keep signed listings in memory instead of the browser. One small gap: his page checks you're on Polygon right before signing; ours relies on the drawer's network warning.
  6. Does it follow Mohit sir's plan?Yes for F2 steps 1 to 6, F6 item 4 and the B1 message shape. Some acceptance tests are still to do by hand (50 names, Rabby, Coinbase, a real retry). Full table: bulk-listing-progress.html, v2 Phase 3, section 4.
