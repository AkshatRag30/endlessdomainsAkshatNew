1. Who's involved

You (seller)
Pick names on My Domains, set prices, confirm in your wallet.
Our site
The frontend (this repo). Builds the listings, asks the wallet to sign, checks the signatures, sends them to the backend, shows results.
Your wallet
MetaMask (or another). Signs messages (free) and sends transactions (cost gas). It never sees our backend.
Our backend
Guru's API (uat while testing). Checks each listing, stores it, shows it on the marketplace, sends emails.
Seaport
The marketplace contract on Polygon (version 1.6, at 0x0000…eB395). At sale time it checks your signature and swaps the domain for USDT. It also records approvals and cancels.
Buyer
Anyone who buys a listed name, directly or through Trails.

The one idea to hold on to: listing is a signature, not a transaction. Your signed listing waits in our backend; nothing touches the blockchain until someone buys (or you cancel on chain). That's why listing is free and buying costs gas.

3

Approval (only if missing)

v2 in phase 6

Our siteYour walletSeaport

What it is. Seaport must be allowed to move your domain when it sells. You grant that once per NFT contract per chain with a real transaction, setApprovalForAll, which costs a little gas. If it's already granted, this step is skipped.

Code. OneTimeApprovalStep (the screen) · useListingFlowActions reads isApprovedForAll and sends the approval.

Today
  • Borrows the single listing hook with the first name only (useListingFlowActions(domains[0])), so only one contract is checked.
  • The gas shown is a placeholder.
v2
  • Group the batch by (chain, contract), check each, list only the missing ones with a real gas estimate (F5).
  • New hook useNftApprovals, reusable by the multi chain work.
4

Prepare

Same in v2

Our siteYour walletOur backendSeaport

What happens. Three things, once for the whole batch:

  1. Wallet proof. Our backend only accepts listings from the wallet linked to your account, so the wallet signs a short login style message once (ensureWalletVerified).
  2. Counter. Seaport keeps a number per seller (getCounter); every order must include the current one.
  3. Block time. The latest Polygon block's time; every order starts 300 seconds before it (so clock differences never make an order "not started yet").

Code. The prepare part of useBulkListingActions (src/hooks/my-domains/useBulkListingActions.ts).

5

Build one order per name

7 day margin in phase 7

Our site

What happens. Each name becomes one Seaport order (OrderComponents): you as seller, the domain NFT offered, two USDT payments asked (yours, and the marketplace fee), start and end time, a random salt, the counter.

Code. buildOrderComponents in src/lib/seaport-order-builder-v5.ts · the end time comes from bulkDurationSeconds in bulkListing.ts, which cuts the listing short if the domain expires sooner and skips names that expire too soon.

Today
  • Listing must end 1 day before the domain expires.
v2
  • 7 days before expiry (F9).
  • Where the expiry date comes from (database or chain) is question V10.
6

Sign

Built (phases 2 and 3)

Our siteYour wallet

Today: one popup per name
  • runBulkSigning (helpers/my-domains/bulkSigning.ts) loops over the names.
  • For each, signAndPostListingOrder (listing-flow/listingOrder.ts) asks the wallet to sign that one order.
  • 50 names = 50 MetaMask popups. Reject one and you're asked "continue or stop".
v2: one popup for all
  • buildBulkOrderTree puts the orders in a tree, pads it with empty orders (50 → 64), and prepares one message.
  • The wallet signs it once.
  • bulkOrderSignatures gives each order its own signature: the one signature + its position + its proof (259 bytes for 50 names).
  • If the wallet can't sign the big message: "Sign each name separately" runs today's loop (F3). Built 20 Nov in phase 4; see section 10.
  • Built 20 Nov: signAndSubmitBulkOnce in useBulkListingActions, screen "Sign once for all N names". Tested with MetaMask: 8 names, one popup.
  • The wallet proof is now done on the form ("Verify your wallet first") before List, so List opens only this one popup.

In plain words. Every listing becomes a fingerprint; fingerprints are paired and fingerprinted again until one is left at the top. The wallet signs only that top one, and it covers them all. Each listing then carries a short "path" up to the top, so it can still be bought on its own. Full detail: bulk-listing-v2-file-changes.html, phase 2.

7

Check locally, before sending

Built (phase 2)

Our site

Why. If our order building has a bug, we want to find it here, with the order in hand, not as a vague "bad signature" from the backend or a failed sale later.

Today
  • verifyTypedData after each single signature, must give back your address.
v2
  • findBadBulkSignatures: for every order, rebuild the top fingerprint from its path, recover the signer, compare with you. Any failure stops the batch before anything is sent.
8

Send to our backend

Built (phase 3, real endpoint on uat)

Our siteOur backend

Today
  • POST /marketplacev2/orders once per name, right after each signature.
  • A failed send means signing again.
v2
  • One POST /marketplacev2/orders/bulk with all orders (B1).
  • The backend checks each order on its own (B2, B3); a bad one doesn't block the rest (B4).
  • Signed orders stay in memory; "Try again" resends without a new signature (F6.4). A resent order already stored counts as listed.
  • The endpoint is live on uat since 19 Nov (PR #1024), so phase 3 talks to it directly; no mock.
  • Guru's internal test page, /bulk-listing-testing (on uat since 19 Nov), makes the same call with one signature and shows the raw answer, so we can compare our batch with his.

Results

Built (phase 3)

YouOur site

What you see. The success step: which names listed, which didn't and why. "Done" leaves select mode; "List more" stays in it. The My Domains table refreshes (DomainApi.util.invalidateTags(['domain'])).

Code. BulkListingSuccessStep.

Today
  • Results built from our own loop.
v2

4. After listing

10

Someone buys a name

No change for buyers

BuyerOur backendSeaport

What happens. The buy drawer loads the stored order and its signature from our backend (rawOrder + signature) and sends them to Seaport, directly (useBuyFlowActions) or through Trails (fulfillAdvancedOrder). Seaport sees the signature is a bulk one by its length, rebuilds the top fingerprint from the path, checks it was you who signed, and swaps the domain for USDT.

Why nothing changes here. A bulk signature is just a longer signature. The buy code passes it through untouched; Seaport does the extra work. To be sure, one real bulk signed listing will be bought through Trails before launch (B8, our phase 10).

11

You delist

Built (phase 8); see section 11

YouYour walletOur backendSeaport

Today: off chain
  • useDelistListing calls POST /marketplacev2/orders/{hash}/cancel.
  • Our backend hides the listing, but Seaport still treats the signed order as valid until it ends. Someone with a copy could still buy at the old price.
v2: on chain (F7)
  • Pick one or many listings in select mode.
  • Fetch each order's rawOrder, send one Seaport cancel(...) transaction for all of them (costs gas).
  • Tell the backend with the transaction hash (POST /orders/cancel-bulk).
  • Rows show Cancelling, Cancelled, or Cancel not confirmed (with "Cancel again").
  • Raising a price while an older, cheaper order is still alive is refused (CHEAPER_ORDER_STILL_VALID, with the old orders' olderOrderHashes); we offer to cancel them first. Price cuts: question V7.
  • The backend confirms each cancel from Seaport's events, checks the transaction, and after 30 minutes on Polygon marks it "not confirmed" and emails you. All of this is live on uat since 19 Nov (PR #1024).
