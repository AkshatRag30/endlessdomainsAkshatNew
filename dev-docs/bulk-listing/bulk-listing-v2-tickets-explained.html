1. The basics you need first

What a listing actually is

When you list a domain for sale on our marketplace, nothing is sent to the blockchain. Instead your wallet signs a message that says, in effect, "I agree to sell this NFT for this price until this date". That signed message is called an order, and the format comes from Seaport, the open marketplace contract (made by OpenSea) that our marketplace uses. The order's details are a structure called OrderComponents: seller, NFT, price, fee split, start time, end time and a few counters.

Our backend stores the order and its signature. When a buyer clicks Buy, the buyer sends the order plus your signature to the Seaport contract. Seaport checks the signature really came from you, moves the NFT to the buyer and the money to you. Listing is free because signing costs no gas; only buying costs gas.

Why bulk listing needs a change

Today, bulk listing 50 names means 50 orders, and our code asks the wallet to sign each one: 50 popups, one after the other (runBulkSigning in src/helpers/my-domains/bulkSigning.ts). That works but is painful. Seaport has a built in feature for exactly this: sign one message that covers all 50 orders. That is the heart of v2.

Three other words you'll keep seeing

Approval
Before Seaport can move your NFT on a sale, you must give it permission once, by sending a real transaction called setApprovalForAll (it costs a little gas). The permission is per NFT contract and per chain, so one approval covers every name from that contract.
Off chain
Only our backend knows. Free, instant, but the blockchain doesn't know about it.
On chain
Written to the blockchain by a transaction. Costs gas and takes a few seconds, but it is final and everyone has to respect it.

F2. One signature for the whole batch

F2

Sign once instead of 50 times

Plan phases 2 and 3 · the biggest ticket

The idea. Seaport lets you put many orders into a tree and sign only the top of the tree. Think of a family tree turned upside down. At the bottom are the orders (the "leaves"). Every two leaves are combined into one fingerprint (a hash), every two of those are combined again, and so on, until one single fingerprint is left at the top, called the root. Change any order even slightly and the root changes. So signing the root is the same as signing every order under it.

LevelWhat is there (example with 4 orders)
TopRoot = hash(AB, CD) · this is what the wallet signs, once
MiddleAB = hash(A, B) · CD = hash(C, D)
Bottom (leaves)Order A · Order B · Order C · Order D

The six steps from the ticket, one by one.

  1. Build every order first.Make all 50 OrderComponents before asking the wallet anything. Two values every order needs (your Seaport "counter" and the current blockchain time) are read once for the whole batch. Our branch already does this.
  2. Pick the tree size and pad it.A tree like this needs a power of two leaves: 2, 4, 8, 16, 32, 64. The height h is how many levels it has, h = max(1, ceil(log2 n)). For 50 names, 2 to the power 6 is 64, so h = 6 and there are 64 leaves. The 14 spare spots are filled with empty orders that can never be used. Since we cap a batch at 50, h is at most 6.
  3. Sign it in the format Seaport expects.The wallet signs "typed data" (EIP712), which is why MetaMask shows readable fields instead of gibberish. For bulk orders the type is BulkOrder(OrderComponents[2][2][2][2][2][2] tree), one [2] per level. The ticket says: don't type these long type strings by hand; copy the proven helper from Seaport's own JavaScript library (Eip712MerkleTree in Seaport.js), because one wrong character makes every signature invalid.
  4. Give each order its own signature.After the one wallet signature, we build a separate signature for each order by gluing together: the shared 64 byte signature, then the order's position in the tree (3 bytes, the "leaf index"), then 6 hashes (32 bytes each) called the proof. The proof is the list of neighbours on the way up, which lets Seaport rebuild the root from just this one order. So each order can be bought on its own, and Seaport checks it on every buy, whether direct or through Trails.
  5. Check it ourselves before sending.For every order, rebuild the root from its proof and confirm the signature comes back to your wallet address. Our single listing flow already does this kind of check (verifyTypedData); this is the same safety net for bulk. If something is wrong, we find out before the backend or a buyer does.
  6. Send them all in one request.Post all 50 orders in one call to the new backend endpoint B1 (POST /marketplacev2/orders/bulk, built by Guru, live on uat since 19 Nov (PR #1024)), then show each name's result: listed, or rejected with a reason (for example ALREADY_LISTED). Some can succeed while others fail; that's normal.

How we split it. Phase 2 builds the tree, padding, proofs and the local check as pure functions in a new file (bulkOrderTree.ts), with no wallet and no screen. Phase 3 plugs them into the drawer: one popup, one post, results per name. Guru's endpoint is live on uat since 19 Nov (PR #1024), so phase 3 talks to it directly, no mock.

F3. Keep the old way as a backup

F3

"Sign each name separately"

Built in phase 4 (20 Nov); wallets beyond MetaMask not tested

In plain words. A 64 leaf typed data message is big. Some wallets can't show or sign it: hardware wallets like Ledger, some phone wallets connected through WalletConnect, and smart contract wallets. If the one big signature fails, we show a button "Sign each name separately" that runs today's one popup per name loop. So our current code isn't thrown away; it becomes the fallback.

The test list. The ticket asks us to test on MetaMask, Rabby, Coinbase Wallet, Trust, Ledger through MetaMask and one WalletConnect phone wallet, and attach the results to the pull request.

You only have MetaMask and Phantom. Rabby and Coinbase Wallet are free browser extensions, so installing them would close most of the gap; Ledger and Trust need a device or phone. We record honestly in the test matrix which ones were not tested.

F4. Remove the "percentage of estimate" pricing

F4

Two pricing modes instead of three

Built and tested in phase 5 (23 Nov)

In plain words. The drawer currently offers three ways to price: one price for every name, set each name's price yourself, or a percentage of an estimated value. We have no real estimate for domains (the value is hardcoded to 0), so the third option makes no sense. F4 removes it from BulkPricingOptions and removes the "estimate" column from BulkNamesList. Mohit's decision 5 confirms: keep only the first two.

F5. The approval step, done properly

F5

Ask only for the approvals you're missing

Built in phase 6 (23 Nov), wrong network fix tested

In plain words. Remember an approval is per contract and per chain. A batch of 50 names might come from two contracts, so it may need two approvals, or none if you approved before. F5 says: group the selected names by (chain, contract), ask the blockchain for each group "is Seaport already approved?" (isApprovedForAll), and show only the missing ones, each with a real gas cost estimate.

Today. The bulk drawer borrows the single listing's hook with just the first name (useListingFlowActions(domains[0])), so it only checks one contract, and the gas number shown is fake. We replace that with a new hook (useNftApprovals) that takes a contract and chain.

F6. Four bugs Mohit found in our branch

F6

Correctness fixes

Items 1 to 3 built in phase 5 (23 Nov); item 4 in phase 3
1

The fee says "2.5%" no matter what. It's typed into the text (BulkListingFormStep.tsx line 193). If the marketplace fee changes, the screen would lie. Fix: calculate it from the fee setting (in basis points, where 250 bps = 2.5%).

2

The end date shown isn't the one signed. The screen calculates the end date from your computer's clock (Date.now()), but the real orders use the blockchain's time minus 300 seconds. They can differ. Also, some names get a shorter end date because the domain expires sooner. Fix: show the real end time that was signed, and list the names whose listing was cut short.

3

A wrong count when you reject. If you reject a signature, a prompt says how many names are "remaining". That count wrongly includes names that would be skipped anyway because their domain expires too soon. Fix: count only names that will really be listed.

4

Retry asks you to sign again. If sending to the backend fails (network blip), today's retry starts over and asks the wallet again. With one bulk signature that's wasteful: the signature is still valid. Fix: keep the signed orders in memory and retry only the sending.

F7. Delist on chain, one name or many

F7

Make "delist" truly final

Built and tested in phase 8 (23 Nov); price cuts stay free via Edit price (option B)B5 and B7 live on uat; price cut rule waits on Mohit (V7)

The problem today. Our Delist button (useDelistListing.ts) only tells our backend "hide this order". It's off chain. But your signed order still exists, and Seaport still considers it valid until its end date. Anyone who kept a copy could still buy your domain at the old price directly through Seaport. So "delisted" isn't really delisted.

What F7 asks for.

  1. Cancel on the blockchain.Fetch each order's original details (rawOrder, the exact signed OrderComponents) and send one transaction to Seaport's cancel function with all of them. After that Seaport refuses those orders forever. It costs gas, but one transaction covers any number of orders.
  2. Bulk delist too.Use the same Select mode as bulk listing to pick several listed names and cancel them all in that one transaction. The single Delist button moves to the same on chain path.
  3. Tell the backend.After sending, call the backend's cancel endpoint (B5) with the transaction hash, so it can watch the blockchain and confirm.
  4. Show three states on My Domains.Cancelling (sent, waiting for the blockchain), Cancelled (confirmed), and Cancel not confirmed (the transaction never confirmed), which shows a warning that the listing can still be bought plus a "Cancel again" button.
  5. Handle "a cheaper order is still alive".Say you listed a name at $100, delisted it off chain, and now list it at $150. The $100 order is still valid on Seaport, so a buyer could grab it cheaper. The backend will refuse the new listing with CHEAPER_ORDER_STILL_VALID (B7). We then offer: "cancel the old orders on chain first".
  6. Price cuts may skip the cancel.If the new price is lower, the old higher order doesn't hurt you (nobody pays more when a cheaper one exists), so Mohit's decision 1 says the cancel may be skipped. Whether we skip it or always cancel is question V7, waiting on Mohit.

Extra work the review found. Our Seaport function list (SEAPORT_MIN_ABI) has no cancel yet, the marketplace home page also uses Delist, and the screens need states for "wallet not connected" and "not enough gas".

F9. Product rules from Mohit's decisions

F9

Four rules to apply

Built in phase 7 (24 Nov); smart wallet part in phase 4
1

Listings end 7 days before the domain expires, not 1 day. A buyer shouldn't buy a name that dies the next day. In code this is the safety margin in bulkListing.ts (lines 173 to 178).

2

Names with less than 14 days left can't be listed. They show as not eligible in Select mode (decision 8).

3

One chain per batch. Once you select a name on one chain, names on other chains can't be added. One signature can only cover one chain's Seaport (decision 2).

4

A clear message for smart contract wallets. These wallets (Safe, for example) sign differently and often can't do this kind of order, so we explain that instead of failing silently (decision 10). Careful: newer MetaMask accounts upgraded with EIP 7702 look like smart contracts on chain (their code starts with 0xef0100) but sign normally, so they must not get this message.
