Words to know first

The doc assumes you already know these. Read this once and the rest becomes much easier.

Seaport
The smart contract on Polygon that runs our marketplace sales. A seller signs an "order" saying "I'll give this domain for this price", and anyone who calls Seaport with that signed order and pays the price gets the domain.
Order / rawOrder
The seller's offer in Seaport format: who is selling (offerer), what they give (the domain NFT, in offer), what they want back (USDT amounts, in consideration), start and end time, and so on. rawOrder is that data as our API returns it.
Signature
The seller's wallet signature over the order. It proves the seller really agreed. Without it Seaport refuses the sale.
Order hash
A unique ID for one order, a long hex string. Our API looks orders up by it.
USDT on Polygon
The only currency our listings are priced in today. Buyers currently must hold USDT on Polygon to buy.
Trails
An outside payment service. The buyer pays with whatever token they have on whatever chain (for example USDC on Base), and Trails converts and delivers the exact USDT on Polygon, then runs the purchase for them.
Intent
One Trails payment. When the buyer signs in the Trails widget, Trails creates an intent with an intentId. You can ask Trails for its status any time.
Calls / calldata
A "call" is one instruction to a smart contract: which contract (to), which function with which arguments, encoded as hex bytes (data), and how much native coin to send (value). Trails needs us to hand it the exact calls to run on Polygon.
Destination
Where the money finally needs to arrive and be used: Polygon (chain id 137), USDT, the listing price. The "origin" is where the buyer pays from.
Recipient
Who receives the domain in a Seaport sale. This one word is the most important idea in the whole doc (see Destination calls).
uat
Our testing environment. Note: it already points at real Polygon mainnet, so tests spend real money.
Probe
Mohit's experiments that proved Trails works. "Probe P3" was a real 0.25 USDT purchase on mainnet; "probe E7" tested a refund.
Poller
A backend job that watches the chain and records every Seaport sale in our database. That's how receipts, history and My Domains update.
POL
Polygon's native coin, normally needed to pay gas. With Trails the buyer should need none.
Section 1

Summary

In one lineYou can build the whole "Pay with any token" checkout on the frontend today, and make real purchases on uat, without waiting for the backend.

Normally a new payment method needs new backend endpoints. Mohit's point is that two things our backend already does are enough to get started.

Reason 1: we can already get the signed order

GET /marketplacev2/orders/:orderHash returns rawOrder and signature. With those two things the browser can build the exact purchase instructions itself, so there's no need for the server to build them.

Reason 2: the rest of the site already notices the sale

The backend poller records every Seaport sale under whoever received the domain (OrderFulfilled.recipient). A Trails purchase uses fulfillAdvancedOrder with the recipient set to the buyer. So the poller sees "buyer X bought domain Y" exactly like a normal sale, and receipts, history, My Domains, and the buy and sell emails all keep working with zero changes.

What still needs the backend

Server side tracking, verification and refund emails. So the instruction is: put all Trails logic behind one small interface now. When the backend endpoints arrive later, they replace the browser version and the UI doesn't change at all.

It has already been proven on Polygon mainnet on 3 Nov 2026 (probe P3): a real 0.25 USDT order was sold, the domain went to the buyer, and the payout split was exact. Section 4

The seam

In one lineAll Trails logic sits behind one interface, so swapping the browser version for a backend version later is a one file change.

"Seam" just means a clean cut point in the code. Components never talk to Trails or to the chain directly; they only call three methods on a CheckoutSource. Today a browser implementation does the work. Later a backend implementation calls the server's endpoints. Because both return the same shapes (copied from the backend plan's API contract), the components never notice the switch.

// buying-flow/trails/checkoutSource.ts
export type Hex = `0x${string}`

export type PreparedCheckout = {
  checkoutId: string       // browser: crypto.randomUUID(); backend: server uuid
  orderHash: Hex
  buyer: Hex               // Seaport recipient
  expiresAt: string        // ISO, now + 15 min
  destination: { chainId: 137; token: Hex; amount: string }   // USDT minor units
  calls: { to: Hex; data: Hex; value: string }[]              // [approve, fulfillAdvancedOrder]
  route: { bridgeProvider: 'RELAY'; bridgeProviderFallback: false; slippageTolerance: number }
}

export type CheckoutStatus =
  | 'prepared' | 'attached' | 'executing' | 'succeeded'
  | 'refunded' | 'failed' | 'expired' | 'mismatch'

export type CheckoutState = {
  status: CheckoutStatus
  intentStatus?: string
  destinationTxHash?: Hex
  refundTxHash?: Hex
  sale: { fillTxHash: Hex } | null
  refund: { chainId: 137; token: Hex; amount: string; to: Hex } | null
}

export interface CheckoutSource {
  prepare(orderHash: Hex, buyer: Hex): Promise<PreparedCheckout>   // throws CheckoutError
  attachIntent(checkoutId: string, intentId: Hex): Promise<void>
  getStatus(checkoutId: string): Promise<CheckoutState>
}

Reading those types in plain words

PreparedCheckout is "everything Trails needs to start": an ID for this checkout attempt, which order, who the buyer is, when this prepared checkout goes stale (15 minutes), the destination (Polygon, USDT, the price in the smallest units, so 0.25 USDT is "250000"), the two calls to run, and the route settings (use the RELAY bridge, no fallback bridge, a slippage limit).

CheckoutStatus is the list of states a purchase can be in. CheckoutState is a status plus useful details: transaction hashes, the sale (once our backend sees it), and the refund (if Trails sent money back).

What each method does now vs later

MethodWhat it meansBrowser version (now)Backend version (later)
prepareCheck the order and build the callsExisting GET /orders/:orderHash, live checks on the Polygon read RPC, build the two callsPOST /marketplacev2/trails/checkouts
attachIntentRemember which Trails payment belongs to this checkoutSave {checkoutId, orderHash, intentId} to localStoragePOST /checkouts/:id/intent
getStatusWhere is this purchase now?Trails GetIntentReceipt plus our existing sale receipt endpointGET /checkouts/:id

Choosing which version to use

Decide in exactly one place: if GET /marketplacev2/trails/config answers, the backend exists, so use the backend version. Otherwise use the browser version, but only when NEXT_PUBLIC_TRAILS_ENABLED is on.

Section 6

Building the destination calls

In one lineBuild exactly two calls: approve USDT for Seaport, then fulfillAdvancedOrder with the buyer as recipient.

The Trails wallet on Polygon will run these two instructions in order, using data loadOrder() already fetches:

  1. approve(Seaport, price) on the USDT contract. Lets Seaport pull the price from the Trails wallet.
  2. fulfillAdvancedOrder(order, [], 0x0, buyer) on Seaport. Buys the order. The last argument is the recipient.
The rule you must never break
The person who pays here is the Trails wallet, not the buyer. Seaport's simpler functions, fulfillOrder and fulfillBasicOrder, always send the domain to whoever paid. That would put the domain in the Trails wallet, where it gets stuck (the probe confirmed this really happens). Only fulfillAdvancedOrder lets us name a different recipient, so the domain goes to the buyer.

The build code from the doc, explained

import { encodeFunctionData, erc20Abi, parseAbi, zeroHash } from 'viem'
import { toOrderParameters } from '@/lib/seaport-order-builder-v5'   // lines 162 to 165, drops counter

const seaportFulfillAbi = parseAbi([
  'struct OfferItem { uint8 itemType; address token; uint256 identifierOrCriteria; uint256 startAmount; uint256 endAmount; }',
  'struct ConsiderationItem { uint8 itemType; address token; uint256 identifierOrCriteria; uint256 startAmount; uint256 endAmount; address recipient; }',
  'struct OrderParameters { address offerer; address zone; OfferItem[] offer; ConsiderationItem[] consideration; uint8 orderType; uint256 startTime; uint256 endTime; bytes32 zoneHash; uint256 salt; bytes32 conduitKey; uint256 totalOriginalConsiderationItems; }',
  'struct AdvancedOrder { OrderParameters parameters; uint120 numerator; uint120 denominator; bytes signature; bytes extraData; }',
  'struct CriteriaResolver { uint256 orderIndex; uint8 side; uint256 index; uint256 identifier; bytes32[] criteriaProof; }',
  'function fulfillAdvancedOrder(AdvancedOrder advancedOrder, CriteriaResolver[] criteriaResolvers, bytes32 fulfillerConduitKey, address recipient) payable returns (bool fulfilled)',
])

const price = rawOrder.consideration.reduce((s, c) => s + BigInt(c.startAmount), 0n)
const calls = [
  { to: DEFAULTS.usdtAddress, value: '0',
    data: encodeFunctionData({ abi: erc20Abi, functionName: 'approve', args: [DEFAULTS.seaportAddress, price] }) },
  { to: DEFAULTS.seaportAddress, value: '0',
    data: encodeFunctionData({ abi: seaportFulfillAbi, functionName: 'fulfillAdvancedOrder',
      args: [{ parameters: toViemParams(toOrderParameters(rawOrder)), numerator: 1n, denominator: 1n, signature, extraData: '0x' },
             [], zeroHash, buyer] }) },
]
The ABI block
A description of Seaport's function and its nested structs, so viem knows how to turn our JS object into bytes. It's the same one the probe used on mainnet, so copy it as is.
price
The sum of all consideration amounts. A listing pays two parties (the seller and our 2.5% fee wallet), so the total price is both added together.
Call 1
"Dear USDT contract, allow Seaport to take price." Sent to the USDT address.
Call 2
"Dear Seaport, fill this order." Sent to the Seaport address.
numerator 1, denominator 1
Buy the whole order (1 out of 1), not a fraction.
[]
No criteria resolvers. Those are for "any item from a collection" style offers, which we don't use.
zeroHash
No conduit for the fulfiller. Tokens move through Seaport directly.
buyer
The recipient. The whole point.
toViemParams
A small helper you write. Our existing toOrderParameters keeps numbers as decimal strings (the way the API returns them) and sets totalOriginalConsiderationItems to the consideration length; viem wants bigint, so this converts the numeric fields.
DEFAULTS
Existing constants in the marketplace order client in src/lib (lines 32 to 48): seaportAddress, usdtAddress, domainNftAddress.

Section 9

Purchase status

In one lineTrails tells you about progress and refunds; only our own sale receipt is allowed to say "Done, the domain is yours".

Three sources of truth

SourceHowWhat you get
Widget callbacksonQuote, onSign, onOriginConfirmation, onDestinationConfirmation, onPaymentSuccess, onPaymentErrorThe intentId early, then instant progress, but only while the drawer is open
Trails intent receiptnew TrailsApi(NEXT_PUBLIC_TRAILS_API_KEY).getIntentReceipt({ intentId }) from @0xtrails/api (comes with 0xtrails)Status, refund, transaction hashes; works even after a reload
Our sale receipt (already exists)GET /marketplacev2/orders/transactions/:orderHash, publicThe SALE row with buyer, once the poller indexes it (about 30 to 60 seconds)

Translating Trails status into ours

Trails saysWe show
QUOTED, COMMITTEDattached
EXECUTINGexecuting
SUCCEEDEDsucceeded
REFUNDEDrefunded
FAILED, ABORTED, INVALIDfailed

Keep polling a failed intent for 20 minutes, because FAILED can still turn into REFUNDED.

The five rules

  1. Done only from the chain. Show Done only when our sale receipt has a SALE whose buyer equals the connected address (compare lowercased). Before that, succeeded shows "Purchase confirmed. Preparing your receipt." Trails saying "succeeded" means the money moved; our receipt proves the domain arrived.
  2. Lost race. If the sale receipt shows a different buyer, someone else bought it first. Expect refunded from Trails within seconds.
  3. Refund can hide inside the failed transaction. In probe E7 the refund happened in the same Polygon transaction as the failed purchase. So refundTransaction may be null, with destinationTransaction.status REVERTED and statusReason "call reverted: refund triggered on destination". In that case link destinationTransaction.txnHash as the refund. The refund is the listing price in USDT on Polygon, sent to the buyer.
  4. Polling speed. Every 3 seconds while not finished, every 15 seconds after 5 minutes, stop at a terminal state.
  5. Survive reloads. At onQuote, save {checkoutId, orderHash, intentId, buyer, createdAt} to localStorage. On app load, resume anything under 24 hours old that hasn't finished and show the result as a toast. The /history banner reads the same store until the backend has a list endpoint.
Spike must confirm
The browser must be allowed to call getIntentReceipt with the public key (no CORS block). The SDK itself calls the same API from the browser, so it's expected to work, but verify it.
