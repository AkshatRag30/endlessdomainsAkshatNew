Test process (written 10 Nov 2026)

The exact steps for testing phases 3 to 9 end to end, in the order to run them: free tests first, paid ones after. Results go into the Testing log. Paid runs use real money on Polygon mainnet because Trails has no test network (plan §5).

A. Before starting

  1. Site: dev server running on localhost:3002; .env has NEXT_PUBLIC_TRAILS_ENABLED=true and the key; stage API up (if every page shows "Failed to fetch", stage is down; wait).
  2. Seller wallet (a team wallet that owns Endless domains): list 4 or 5 domains on stage for 0.10 to 0.30 USDT each, up front. One per paid run, because the buyer can't relist a bought name without POL.
  3. Buyer wallet: a fresh MetaMask account with about 2 USDC and about 0.10 USD of ETH on Base, and no POL at all. Log in to the site with your account and connect this wallet.
  4. Browser: DevTools open, Console, "Preserve log" on, filter trails|buying-flow.
  5. Explorers ready: basescan.org (the payment) and polygonscan.com (the purchase or refund).

B. Free tests (no money moves)

  1. Look and layout: on any listing you don't own, Buy Now ▸ "Any token, any chain". Check the review step, then Continue ▸ the payment screen, in light and dark, at phone, tablet and desktop widths. Expect: three cards, Trails wording, the Trails box fits the drawer, no overlap or double scrollbars.
  2. USDT mode unchanged: switch back to USDT. Expect: exactly today's review (balance after, POL fee, "Buy for X USDT").
  3. Back: on the payment screen press Back. Expect: the review with the payment options.
  4. Own listing: with the seller wallet, Buy Now on its own listing ▸ Any token ▸ Continue. Expect: "This is your own listing".
  5. Cancelled signature: in the Trails box get a price, press Pay, then Reject in MetaMask. Expect: still on the Trails box, nothing charged, no toast.
  6. Unpaid quote: get a price, don't pay, close the drawer, reload, open /history. Expect: no banner now, and no toast ever (the saved quote is dropped after 15 minutes).
  7. Trails off: set NEXT_PUBLIC_TRAILS_ENABLED=false, restart the dev server, open Buy Now. Expect: exactly today's drawer, two cards. Set it back to true and restart.

C. Paid tests (about 0.30 USD in fees each; the listing price goes to the team seller wallet)

  1. Run 1, happy path, drawer open: Buy Now ▸ Any token ▸ tick terms ▸ Continue ▸ USDC on Base ▸ Pay ▸ confirm in MetaMask. Expect: Trails box progress ▸ our "Payment in progress" ▸ possibly "Purchase confirmed / Preparing your receipt..." ▸ "name.og is yours" ▸ View Receipt. Then check: receipt page; BUY row on /history; the name in the buyer's My Domains; buyer and seller emails; on Polygonscan the domain went to the buyer, not a Trails wallet.
  2. Run 2, drawer closed: same as run 1, but close the drawer on "Payment in progress". Expect: a "name.og is yours" toast within a few minutes.
  3. Run 3, reload: same, but reload the page on "Payment in progress", then open /history straight away. Expect: "Purchase in progress" banner on /history, then a "name.og is yours" toast, then the banner disappears.
  4. Run 4, lost race (refund): in a second browser, the seller's teammate buys the same listing directly with USDT just after you press Pay in the Trails box. Expect: "Payment refunded" with the amount and a "View refund" link to Polygonscan; the USDT back in the buyer's wallet on Polygon. (Costs a Trails fee with nothing bought; do it once.)
  5. Run 5, WalletConnect: run 1 again from a phone wallet over WalletConnect. Expect: same as run 1.

D. What to send back after each test

  • Screenshots of each screen in the order seen, plus anything that looks wrong.
  • The console lines filtered by trails|buying-flow.
  • For paid runs: the Base payment transaction and the Polygon purchase or refund transaction (links or hashes), and the two emails.
  • Pass or fail for each step, in your own words. Claude records it in the Testing log and only marks what you confirmed.

E. Later, not today

  • "Ending soon" screen needs a listing with under 15 minutes left; only if a short listing can be made.
  • Phase 10 fixes are on hold until your senior answers; after them, a USDT buy regression again.
  • Final step (phase 12): stop the dev server and run next build once yourself; check no page's First Load JS grew.

The four files, and where each comes from in Mohit's doc

  1. checkout.ts, the shapes. Descriptions of the data the feature passes around: a "prepared checkout" (an id, the order, the buyer, an expiry time, the amount, the two calls), the stages a payment can be in (prepared, executing, succeeded, refunded…), and the eight reasons a purchase can be refused.   2. checkoutError.ts, the error. One kind of error carrying a short code like OWN_LISTING. The doc (page 4) says the error carries these codes "so error screens are written once". In phase 7 each code gets its own screen.
  3. buildDestinationCalls.ts, the builder. You give it a listing, the seller's signature, the buyer's wallet and the two contract addresses. It returns the two instructions Trails runs on Polygon: "USDT contract, let Seaport take the price", then "Seaport, buy this order and send the domain to this buyer". Source: doc pages 4 to 6, including the ABI (the description of Seaport's buy function), copied word for word.
  4. buildDestinationCalls.test.ts, the test. Runs automatically with npm test and checks that the builder produces the right bytes.

Where the 14 checks come from

Four come straight from Mohit's doc (pages 6 and 7). The doc gives a real past order, the one actually bought on Polygon in his experiment, and the exact output that worked on the blockchain. The test feeds that order into our builder and compares:

  1. The first 4 bytes are 0xe7acab24, meaning the function is fulfillAdvancedOrder.
  2. The buy instruction is exactly 1,444 bytes long.
  3. Its fingerprint (keccak) is 0x81f1e320…7bd99, which proves every single byte matches.
  4. The approve instruction matches the doc's value exactly.

The doc says in its own words: "Put it in a Vitest test; your builder must reproduce the expected values." These four do exactly that, and passed on the first run.

Ten more were added by us, to protect rules the doc describes in words but doesn't test:

  1. Approve comes first, then the buy, and neither sends any POL. If the order flipped, Seaport would try to take USDT before being allowed to, and the purchase would fail.
  2. Decoding our own bytes gives fulfillAdvancedOrder, never the simpler buy functions. The doc's biggest warning (page 4): fulfillOrder and fulfillBasicOrder send the domain to the Trails wallet.
  3. The recipient inside the bytes is the buyer we passed in. The doc's main point again, tested with the user's own wallet address, not only Mohit's.
  4. It buys the whole order (1 out of 1), with no extra options. The values the doc's code uses.
  5. counter is dropped and the item count is added. What the doc says the conversion does (page 6).
  6. The 77 digit salt number survives without losing digits. Ordinary JavaScript numbers would quietly round it.
  7. The price is 243,750 + 6,250 = 250,000.
  8. A listing priced in another token is refused.
  9. A listing whose price changes over time is refused.
  10. The error type carries its code and still behaves like a normal error.

Did we do exactly what Mohit's doc says?

The core of it, yes: the ABI word for word, the same two calls in the same order, the same buy inputs (the order, an empty list, the zero value, the buyer), the same 1 out of 1 and empty extra data, and the price worked out the same way, by adding up what the seller asked for. The test proves it: the output matches his real transaction byte for byte.

Five small differences, each for a reason:

  1. Where the code lives. The doc puts everything in one file, buying-flow/trails/checkoutSource.ts. Our layering rules put shapes in src/types, pure logic in src/helpers and network calls in src/core/services, so it's split. Decided together in plan §1.2 before any code was written.
  2. The addresses are passed in. The doc's code reads Seaport and USDT addresses from DEFAULTS in src/lib. Helper files may not import from src/lib, so the builder receives them, and phase 5 hands in the same DEFAULTS values. Same result; only where the addresses come from changed.
  3. The old toOrderParameters isn't called. The doc uses it for one small step (remove counter, add the item count). It also lives in src/lib and is built for our older library, ethers. Those same two lines are written inside the builder instead; the matching fingerprint proves the result is identical.
  4. One extra safety check. If a listing isn't priced in a fixed USDT amount, the builder refuses it. Otherwise Trails could deliver the wrong amount, the purchase would fail and the buyer would get a refund minus fees. All our listings are fixed USDT today, so it blocks nothing real. The doc doesn't mention this case.
  5. BigInt(0) instead of 0n. Same value. Our TypeScript settings target an older JavaScript version that doesn't support the short form.

What phase 4 doesn't do yet

It doesn't read the blockchain (checking the seller still owns the domain, the listing is still valid and so on is phase 5), doesn't save anything, doesn't talk to Trails or our backend, and shows nothing on screen. It's only the piece that turns "this listing, this buyer" into the right bytes, plus the test proving those bytes are correct.

Fixes that help both methods

On hold: user checking with senior

Two old problems in the buy flow, found while reading the code for Trails. They affect the normal USDT purchase today, and would affect Trails purchases the same way. Mohit's doc lists both (task 8). Explained to the user 6 Nov; nothing changed yet.

Problem 1: after buying, the site still shows the old picture

How it works today. The site keeps a short memory (a cache) of what it last loaded from the backend, so pages open fast without asking again. That memory is RTK Query, and each kind of data has a label (a "tag"):

  • domain_listing: the marketplace's live listings (getMarketplaceOrders, used by useLiveListings).
  • domain: your own domains and listings on My Domains (getMyDomainsOrders, getDomainListForSeller, the expiry lists).
  • all_domain_listing: older listing and filter endpoints (domainListing.ts, filterDomain.ts).
  • recent_transactions: the live activity feed of recent sales.

Listing and delisting already tell the cache "this is out of date, reload it" (invalidatesTags: ['domain_listing', 'domain'] in domainListing.ts). Buying doesn't. Of the places that open the buy drawer, only the domain details page reacts after a purchase (it reloads its own page via onPurchased={refetch}); the marketplace list, the watchlist and the rest do nothing.

What the buyer sees. They buy a name, close the drawer, and the marketplace still shows it as for sale with a Buy button; My Domains doesn't show the new name yet; the activity feed doesn't show the sale. Clicking Buy again leads to "This listing just ended", which looks like a bug. It only fixes itself after a reload or once the cache expires.

The fix. After any successful purchase, USDT or Trails, tell the cache that domain_listing and domain are out of date (and, if plan Q10 says yes, all_domain_listing and recent_transactions too). Every list on screen then reloads itself.

One timing detail. Our backend learns about a sale from its poller, which watches the chain and takes about 20 to 60 seconds. For a Trails purchase the drawer only says Done once our sale record exists, so reloading at that moment gets fresh data. For a USDT purchase the drawer says Bought as soon as the transaction is mined, which can be before the poller has caught up, so a reload at that instant can still return the old list. The fix should reload once at once, and once more about 30 seconds later, so the second load catches the poller.

Problem 2: the "Transaction fail" screen shows the success message

How it works today. When a USDT purchase doesn't go through, the drawer shows the reject step: title "Reject", heading "Transaction fail", and under it the text from the success screen: "Ownership transferred in the same transaction as the payment. It will appear in your account within 10 to 15 minutes." The Figma frame (1:1051) was drawn with that text copied by mistake, and the code kept it as drawn with a comment flagging it for design. So a buyer whose purchase failed is told the domain is on its way.

Three different situations all land on this one screen (from runPurchase in BuyFlowModal.tsx and confirmPurchase / awaitSettlement in useBuyFlowActions.ts):

  1. Cancelled in the wallet (the buyer pressed Reject in MetaMask). Nothing was sent, nothing was charged.
  2. Failed before sending (the order couldn't be prepared, the pre-check couldn't reach Polygon, or the wallet failed to send). Nothing was charged.
  3. Sent but failed on chain (the transaction was mined but reverted). The domain wasn't bought and no USDT moved, but the gas (POL) was spent. The toast for this case when the drawer is closed already says so: "Gas was spent, but the purchase did not go through."

The fix. Replace the success text with real failure text, one line per situation, so the buyer knows whether anything was charged. The wording is drafted by us and shown to the user for approval before it goes in (same as every other screen). The "Try Again" and "Keep browsing" buttons stay. The title "Reject" and heading "Transaction fail" come from Figma too and read oddly; whether to change them is a question for the user.

Does this touch Trails? Not directly: Trails has its own failed and refunded screens (phase 8). But it's the same drawer, and Mohit's doc asks for this fix as part of the work.

In plain words

  • Problem 1: the site remembers lists to load pages fast, but nobody tells it to forget them after you buy something, so you keep seeing the domain for sale and your My Domains looks unchanged until you reload.
  • Problem 2: when a purchase fails, the screen says the domain is on its way, because its text was copied from the success screen by mistake.

Plan in plain words

Where Mohit's doc and our code differ

Mohit wrote his doc without looking closely at our repo. These are the six places where it guessed differently, and what we do instead. None of them is a problem; they only change how a step is done. Plan §1.2.

  • Env map. The doc says register the Trails settings in next.config.ts as well as .env. Not needed: any setting named NEXT_PUBLIC_ is available everywhere automatically, and we already rely on that for the Polygon RPC setting. One file to edit, not two.
  • Versions. The doc is right about what is installed (viem 2.41.2, react query 5.90.12, wagmi 2.19.5). package.json still lists old minimums (^2.7.10, ^5.66.0), so when we upgrade we also update those numbers to match what we actually need.
  • Vitest. The doc asks for a Vitest test. Vitest is a tool that runs automatic checks on code, and the project has never had one installed. We install it first; our Trails test becomes the first automated test in the repo.
  • next build. The doc counts a passing build as part of done. Running a build while the dev server runs broke every page with 500 errors on 9 Oct, so Claude checks with TypeScript, ESLint, tests and the dev server, and at the very end the user stops the dev server and runs next build once.
  • Folders. The doc puts its main Trails file inside the design system next to the drawer UI. Our rule (30 Oct) is that design system folders only draw, and that file fetches data and reads the blockchain. So the same code is sorted into the right folders: types/trails, helpers/trails, core/services/trails, hooks/trails and the design system trails folder. Every folder is named trails, so the doc's "only trails folders import Trails" rule still works.
  • Live checks. The doc wants seven safety checks before buying. Our loadOrder() already does four (signature exists, not sold or cancelled, time window valid, not your own listing). For Trails we add the missing ones: at least 15 minutes left, seller still owns the domain, Seaport still allowed to move it, seller hasn't cancelled everything. Added only on the Trails path, so the normal USDT buy can't break.

Pushing the lock file, and what DevOps needs

Decided 5 Nov 2026. Plan §7.

  • Both files, one commit. Phase 2 changed package.json and package-lock.json. The lock file records the exact version of every package, including the hundreds underneath ours. The deploy server installs from it with npm ci, which is strict: push package.json without the lock file and the two disagree, so the deploy fails. Push neither and the server builds without Trails. Push both together and it installs exactly what we tested.
  • Who it's for. DevOps (the deploy pipeline). Not the backend team: the backend is a separate repo with its own packages.
  • What DevOps needs that isn't in git. .env is gitignored, so uat needs NEXT_PUBLIC_TRAILS_API_KEY (the uat key), NEXT_PUBLIC_TRAILS_ENABLED=true and NEXT_PUBLIC_TRAILS_PILOT_WALLETS (empty on uat) in its AWS environment, like the Polygon RPC setting. They're baked in at build time, so the uat build must run after they're set. Prod only with Mohit's approval and staff wallets in the pilot list.
  • First commit holds: package.json, package-lock.json, vitest.config.ts, src/types/trails/, src/helpers/trails/, src/constants/trails.ts. Never committed: node_modules, .env, CLAUDE.md, dev-docs/, the spike page.
