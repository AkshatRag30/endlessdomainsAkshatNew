1. The idea in one line

The buyer pays with whatever token and chain they have (POL, BNB, USDT on BSC, ETH…). Trails converts it to USDT on Polygon and buys the domain on the buyer's behalf through Seaport. The domain goes straight to the buyer's wallet and the seller gets USDT, exactly like a normal buy.

3. Step by step, in technical terms

1

Drawer opens: is Trails allowed?

GET /marketplacev2/trails/config → { enabled, available, minPriceUsdt, maxPriceUsdt, route }.

The "Pay with any token" option shows only when all of these hold (isTrailsAvailable, helpers/trails/checkoutGate.ts): our env switch NEXT_PUBLIC_TRAILS_ENABLED=true and an API key; the server says enabled and available; the price is inside min and max. The server decides who may use it and fails closed.

2

Wallet proof (only if the old one is stale)

GET /marketplacev2/orders/auth/wallet-nonce → free MetaMask signature → POST /marketplacev2/orders/auth/prove-wallet. Needed because the backend always treats the wallet in the login as the buyer, never a wallet we send.

3

Prepare the checkout

POST /marketplacev2/trails/checkouts with { orderHash }.

  • The server checks the listing is still live on Polygon: not cancelled or filled, the seller still owns the domain and has approved Seaport, it doesn't expire soon, the price is in range, and it isn't your own listing.
  • The server builds two Polygon calls: approve(Seaport, price) on USDT, then fulfillAdvancedOrder(order, [], 0x0, buyer) on Seaport.
  • It returns checkoutId, buyer, expiresAt (15 minutes), destination (chain 137, USDT, amount in 6 decimal units), calls, route.
  • Frontend safety check: if the returned buyer isn't the connected wallet, it stops (backendCheckoutSource.ts).
4

The widget makes a quote

We hand the widget the destination (USDT on Polygon, the amount) and the two calls as actions. The buyer picks a token and chain; the widget asks Trails' API for a quote, which comes with an intentId. We set disablePassthrough, so every payment has an intent we can track, even USDT already on Polygon.

5

Attach the quote

POST /marketplacev2/trails/checkouts/{checkoutId}/intent with { intentId }. The server checks the quote really contains our two calls with the right amount. Answers: attached (carry on), mismatch (stop), expired (prepare again).

6

Buyer presses Pay

One wallet transaction on the buyer's own chain sends their token to Trails' intent wallet. Trails swaps and bridges to USDT on Polygon, then runs approve + fulfillAdvancedOrder in one Polygon transaction. Seaport pays the seller, takes the 2.5% fee and sends the domain NFT to the buyer.

7

Tracking until it's done

GET /marketplacev2/trails/checkouts/{checkoutId} every 5 s, every 15 s after 5 minutes (watchCheckout.ts). The backend refreshes from Trails and from our own sale record by itself.

  • Statuses: prepared → attached → executing → succeeded. Other endings: refunded, failed, expired, mismatch.
  • The final answer carries destinationTxHash, plus sale.fillTxHash on success or refund details if Trails gave the money back.
  • After a reload: the checkout is kept in localStorage, so tracking resumes; GET /marketplacev2/trails/checkouts?status=… lists the buyer's checkouts, and History shows a notice.

4. Why fulfillAdvancedOrder (the key technical point)

It's the only Seaport function with a recipient argument. Trails' wallet is the one paying, so a plain fulfillOrder or fulfillBasicOrder would send the domain to Trails' wallet. Our early probe saw exactly that happen. So buildDestinationCalls.ts only ever uses fulfillAdvancedOrder with the buyer as recipient, and the approve must come first or Seaport's USDT pull reverts.

5. How to demo it in the Network tab

  1. Open DevTools → Network, tick Preserve log.
  2. Click Fetch/XHR and type trails in the filter. That shows our backend's Trails routes and Trails' own API.
  3. Open a listing, choose "Pay with any token", and buy something cheap (like the 0.10 USDT test).

  • Payload and Response tabs on each request; Preview is easier to read.

  • Application → Local Storage: the saved checkout entry that lets tracking survive a reload.

7. Questions seniors usually ask

  1. Who signs what?The buyer signs one deposit transaction on their own chain. Trails' wallet signs the Polygon purchase; Seaport's recipient argument makes sure the domain goes to the buyer.
  2. What if it fails?Trails refunds the buyer, and our tracker shows "Refunded" with the amount.
  3. Where's the trust?Our backend builds and checks the calls, and checks every quote before anything is paid. The frontend never decides who the buyer is.
  4. How do we switch it off?NEXT_PUBLIC_TRAILS_ENABLED on our side, enabled on the server. NEXT_PUBLIC_TRAILS_SOURCE=browser was the rollback to the older browser only version.
  5. Does the seller do anything different?No. It's the same signed Seaport listing; only the payer is different.
