Section 2 · Point 1

Every page got heavier, by about 38 kB

What Mohit said

The resume hook in _app pulls the entire checkout code (Seaport encoder, order checks) into every page, including login and profile. That breaks the doc's "no page's First Load JS grew" rule. Fix: load it lazily, only when a purchase is actually pending.

What the code does

pages/_app.tsx wraps every page on the site. On lines 36 to 39 it imports the resume hook, and line 78 runs it. Following the imports from there:

pages/_app.tsx                                  (every page)
 └ hooks/trails/useTrailsResume.ts
    └ core/services/trails/watchCheckout.ts
       └ core/services/trails/index.ts           getCheckoutSource()
          └ core/services/trails/browserCheckoutSource.ts
             ├ helpers/trails/buildDestinationCalls.ts   viem encoder, Seaport ABI
             ├ core/services/trails/orderChecks.service.ts   ethers, seaport-order-builder-v5
             ├ helpers/trails/orderChecks.ts
             └ lib/marketplace-order-client.ts

So the code that builds a purchase (encoding the Seaport call, checking the order on chain) is loaded on every page, even though the resume hook only needs the code that reads a purchase's status. And it's loaded for everyone, even when nothing is pending, which is almost always.

Why it matters, in plain words

Every visitor downloads extra code on every page, including pages that have nothing to do with buying. Mohit's doc set a rule that the Trails work must not make any page's first download bigger. Only the buy drawer's own Trails widget was loaded lazily (that part is fine: TrailsWidget.tsx is loaded with next/dynamic).

The fix

  1. On app load, do only a tiny check: read localStorage and see if any purchase is pending. That code is a few lines with no libraries.
  2. Only if something is pending, load the watching code with import(), which makes it a separate file the browser fetches on demand.
  3. Split the "read the status" part (Trails API call plus our sale receipt) away from the "prepare a purchase" part (encoder, order checks), so even the on demand file stays small.

This is best done together with point 2, because both change where tracking lives.

To confirm after the fix: you run next build once (dev server stopped) and compare First Load JS for a page like /login with the dark-mode branch. It should match again.

Section 3 · Point 2

Purchase tracking stops if the buyer navigates away

What Mohit said

Tracking lives inside the drawer, which belongs to each page. If the buyer closes it mid purchase and clicks to another page, or starts a second purchase, polling stops: no result toast, and the History banner says "in progress" until a full reload. Fix: move tracking to app level.

What the code does

  • The polling for an open purchase lives in hooks/trails/useTrailsCheckout.ts, which the buy drawer uses. The drawer is placed by each page separately: pages/index.tsx, pages/details/[orderId].tsx and pages/watchlist/index.tsx.
  • Line 41 of useTrailsCheckout.ts stops polling when the drawer goes away. Moving to another page removes the old page and its drawer, so polling stops.
  • Lines 44 to 53: starting a new purchase calls stop() first, so the previous purchase stops being watched. The comment on lines 24 to 26 even says so.
  • The app level resume (useTrailsResume.ts, lines 22 to 34) runs once, when the app first loads. Moving between pages doesn't reload the app, so nobody picks the purchase back up until a full reload.
  • The History banner (useTrailsPendingCheckouts.ts) just reads the saved list every 15 seconds. The entry is only removed by a watcher when the purchase ends, and no watcher is running, so the banner keeps saying "in progress".

Why it matters, in plain words

The purchase itself still completes on chain, money and domain are safe. But the buyer is left without the "is yours" (or refund) message, and History tells them it's still running when it's long finished. Your 10 Nov tests didn't hit this because the buyer stayed on the same page each time.

The fix

  1. One app level tracker, started from _app, that owns every running purchase and polls it, whatever page the buyer is on. It shows the end message itself.
  2. The drawer stops owning the polling. When the widget quotes, the drawer hands the purchase to the tracker and only listens to it for its own screens (progress, done, refunded).
  3. The tracker watches several purchases at once, so starting a second one no longer stops the first.
  4. When a purchase ends, the tracker removes it from the saved list straight away, so the History banner clears without a reload.
  5. The tracker's polling code is loaded only when it has something to watch (point 1).

Fits the layering rules (CLAUDE.md §8): the list of running purchases and the polling stay in core/services, the hook in hooks/trails, the end message is drawn in _app like today.

Testing it needs a paid run: start a Trails purchase, press "Keep browsing", go to another page, and check the "is yours" message appears and the History banner clears. That's the same run as the "closed drawer" test already on the list, so no extra cost.

Section 4 · Point 3

The refund screen wording

What Mohit said

It states "Trails' conversion fees aren't refunded" as fact, which Trails hasn't confirmed. It also says the USDT was "sent back", which misleads someone who paid in, say, BNB on BSC. The doc's wording, "not converted back to your original token", needs to go in.

What the code says today

  • Refund screen in the drawer, BuyFlowModal.tsx line 840: "The purchase couldn't complete, so X USDT was sent back to your wallet on Polygon. Trails' conversion fees aren't refunded."
  • Refund message (toast) when the drawer isn't showing it, data/trails/copy.ts line 14: "X USDT was sent back to your wallet on Polygon."

This was already flagged: the progress doc's "Double check before this ships" box lists "Trails' conversion fees aren't refunded" as a claim to confirm with Mohit. His answer is: don't claim it.

Why it matters, in plain words

"Sent back" sounds like the buyer gets back what they paid. If they paid in BNB on BSC, they actually get USDT on Polygon, a different token on a different network. They might look in the wrong wallet or think money is missing. And the fees sentence is a promise about money that nobody confirmed.

Section 5 · Point 4

Slippage tolerance: 5% vs 0.5%

What Mohit said

Slippage tolerance is set to 5%; the probe used 0.5%.

What the code does

core/services/trails/browserCheckoutSource.ts line 19: SLIPPAGE_TOLERANCE = 0.05 (5%). The comment says it's Trails' own widget default and waits on Mohit (plan question Q13). That part is true: the 0xtrails package uses 0.05 when no value is passed. But Mohit's doc gave no value, and the spike page (pages/trails-spike.tsx, local only) used '0.005' (0.5%), which matches the probe he means.

Why it matters, in plain words

Slippage tolerance is how far the price may move between the quote and the moment Trails swaps the buyer's token. At 5%, Trails may use up to 5% more of the buyer's token than the price looked like; at 0.5%, the buyer is much better protected. The trade off: with a token whose price jumps a lot, a tight 0.5% can make the swap fail more often, which then ends in a refund.

The fix

Change the one line to 0.005, mark Q13 answered by Mohit, and do the next paid run at 0.5% to check quotes still go through. All three real purchases so far ran at 5%.

Section 6 · Point 5

A committed but unpaid intent is polled forever

What Mohit said

An intent the buyer committed to but never paid is polled forever, and again after every reload within 24 hours.

What the code does

The rules that decide when to stop polling are in helpers/trails/intentStatus.ts:

  • Lines 24 and 25: Trails' QUOTED and COMMITTED both become our status attached.
  • Line 103 (isFinal): only QUOTED has a cut off ("stop once the quote is 15 minutes old").
  • A COMMITTED intent falls through to isTerminal (line 53), which says "not finished" for attached. So it never stops: every 3 seconds for 5 minutes, then every 15 seconds for as long as the tab is open.
  • The saved entry stays for 24 hours (isResumable, line 121), and useTrailsResume starts polling it again on every reload in that time.

Same gap, smaller: line 35 treats any status Trails might add in future as "still running", which also never ends.

Why it matters, in plain words

A buyer who signed in the widget but never actually paid leaves the site asking Trails about it every 15 seconds, all day, in every tab and after every reload. No money is at risk, but it's wasted requests against our Trails key, and it could keep a History banner or later message alive for a purchase that never happened.

The fix

  1. Treat COMMITTED like QUOTED: if the payment hasn't landed after a cut off, stop, and end it quietly as "abandoned" (no message, same as an unpaid quote today).
  2. On reload, skip entries that were never paid and are past that cut off, instead of polling them for 24 hours. The saved entry already records whether the payment landed (paid).
  3. Give unknown statuses the same overall time limit as failures (20 minutes).
  4. Add tests for each case next to the existing 66.

One choice: the cut off. 15 minutes matches the quote's life today. A payment from Ethereum mainnet on a busy day can take longer to land, so 30 minutes is the safer choice. Once the payment lands Trails moves to EXECUTING, so the cut off never affects a real paid purchase.

Section 7 · Point 6

Every widget event is written to the browser console

What Mohit said

Every widget event is written to the browser console; earlier reviews made us strip that kind of logging.

What the code does

  • buying-flow/trails/TrailsWidgetLoader/TrailsWidget.tsx line 41: logEvent prints a [trails] widget … line for all seven widget events (quote, sign, sign rejected, origin confirmed, destination confirmed, success, error). It was added on 10 Nov to find out which events fire, after the first purchase got stuck.
  • Six of the seven print the whole event data, which can include the buyer's wallet address and transaction details. That's more than noise.
  • Error lines also exist: [trails] status check failed (watchCheckout.ts line 38), [trails] order chain reads failed (orderChecks.service.ts line 43), and three [buying-flow] trails … lines in BuyFlowModal.tsx (498, 798, 803). The drawer already printed errors this way before Trails (five console.error lines in the old file).

The fix

Remove logEvent and its seven calls; the widget callbacks themselves stay. It has done its job: we know onOriginConfirmation doesn't always fire, and that's handled.

For the error lines: they follow the drawer's existing style, so I'd keep them, unless Mohit wants those gone too. Worth one line in your reply to him.

Why the status requests continue after a cancel

After a cancel the widget offers "Try again" on the same quote, so our tracker keeps checking: GetIntent (status) and, while Trails says "executing", GetIntentReceipt (did money move?). Both 200; every 3 s, then every 15 s after 5 minutes; they stop for good 15 minutes after Pay (30 until changed later on 11 Nov), with no message. It's needed because a cancel doesn't guarantee no money moves: the buyer can press Try again, a wallet request can still be waiting and get approved later (run 3), or a deposit can be slow to land. Without watching, the buyer could pay and see nothing, not even a refund message. Full plain words story: progress doc, "Review fixes".
