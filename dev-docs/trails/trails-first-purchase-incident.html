Section 2

How it was meant to work

Phase 8 of the plan built what happens after the buyer presses Pay inside the Trails box. The design, before 10 Nov:

Trails boxPrice quotedTrails gives the payment an id ("intent id"). We save it in the browser.
WalletBuyer paysMetaMask sends the buyer's token on their chain.
Trails box ▸ our drawer"Payment landed"The box fires an event (onOriginConfirmation). Only then did our drawer start checking and switch screens.
Our drawerProgress ▸ DoneWe check Trails and our sale record every few seconds, then show Done and View Receipt.

The red step is the weak link: everything after it depended on one event from a package we don't control.

Reference: plan §4 phase 8; progress doc phase 8 entry; Mohit's doc page 8 ("Widget callbacks … onOriginConfirmation … instant progress while the drawer is open").

Section 4

Problem 1: the drawer stayed on the payment screen

What the user saw

  • Paid in MetaMask, the wallet confirmed.
  • The drawer kept showing the Trails box with its Pay button. No "Payment in progress", no "is yours", no View Receipt.
  • The domain was in My Domains anyway.

What actually happened (the evidence)

  1. The browser's saved entry (DevTools ▸ Application ▸ Local storage ▸ trails-checkouts), pasted by the user: 
    checkoutId:  81ab12f0-b091-4edb-8475-2df64fb10409
orderHash:   0x6902dc9f…3faa
intentId:    0x7d0af0c659d7ff0f13c6dde5e2f1af891901073b8ec34b6bcab63bb6057f4f01
buyer:       0x8FD5Fb2dbE512E5eb4C38Ea84E8e8D45b10Be4D0
amount:      "100000"   (0.10 USDT)
domainLabel: "theforceis.unstoppable"
(no "paid" field)
    The intent id and name were saved, so the quote step worked. But there was no paid flag, which our code only sets when the "payment landed" handler runs. So that handler never ran.
  2. Trails' own record, asked directly with our API key (POST https://trails-api.sequence.app/rpc/Trails/GetIntentReceipt): 
    status: SUCCEEDED
originChainId: 56 (BSC)    destinationChainId: 137 (Polygon)
depositTransaction.txnHash: 0x1111000000000000…0000   ← a placeholder, not a real hash
depositTransaction.txnMinedAt: null
destinationTransaction: SUCCEEDED, tokenAmount 100000 (exactly 0.10 USDT)
    Trails converted the BNB and ran our two buying steps on Polygon. The deposit, though, is stored with a placeholder hash and no "mined" time.
  3. Our backend's sale record (GET /marketplacev2/orders/transactions/0x6902dc9f…3faa): a SALE with buyer 0x8FD5…e4D0, price 100000, fill transaction 0x00c55971…825a. So "Done only when our record shows the buyer" would have passed.
  4. The Trails package code (node_modules/0xtrails/dist/src-Cd_X4Rd1.js, the hook that calls onOriginConfirmation): it only fires once it has the origin transaction hash and chain id. With the deposit recorded as a placeholder, that event never reached us.
Root cause

Our drawer depended on one event from the Trails box, and that event doesn't fire for every kind of payment. Everything else (saving the id, Trails' status, our sale record) was correct.

The fix

  1. Start watching at the quote, not after the event. As soon as Trails gives a price and we save the intent id, the drawer starts checking Trails' status in the background (useTrailsCheckout.attachIntent now calls track()). Picking another token gives a new id; the check follows it automatically.
  2. Switch screens from Trails' status. A new rule, hasPaymentLanded(status), is true once Trails says the payment is executing or finished. When it turns true while the Trails box is showing, the drawer switches to "Payment in progress" (BuyFlowModal.tsx, the effect starting at line 348). While it's only a price, the Trails box stays.
  3. Mark the saved entry as paid at the same moment (useTrailsCheckout.ts line 78), so the /history banner and the after-reload check know it's a real payment.
  4. Keep the box's events as extra triggers. If onOriginConfirmation or onPaymentSuccess do fire, they still switch the screen straight away. Signing in the wallet (onSign) restarts the check if it had stopped.
  5. A price never paid is dropped quietly. If the buyer leaves after seeing a price, the check gives up after 15 minutes with no message (isFinal and checkoutOutcome → "abandoned").
  6. Every event from the box is now written to the console as [trails] widget onQuote, onSign, onOriginConfirmation and so on (TrailsWidget.tsx line 41), so the next problem is quick to read.
Confirmed

Run 2 (section 7): progress ▸ Done ▸ View Receipt ▸ receipt page, confirmed by the user. 66 of 66 automated tests pass (2 new for hasPaymentLanded).

References: src/hooks/trails/useTrailsCheckout.ts (lines 66, 78, 96); src/helpers/trails/intentStatus.ts (lines 44, 100 to 103, 113 to 115); src/design-system/composites/marketplace/buying-flow/BuyFlowModal/BuyFlowModal.tsx (lines 348, 356 to 365, 513, 795 to 800); .../trails/TrailsWidgetLoader/TrailsWidget.tsx (line 41); progress doc phase 8, "First real purchase".

Section 5

Problem 2: red GetIntentReceipt 400 lines in the console

What the user saw

  • During run 1: a few red POST https://trails-api.sequence.app/rpc/Trails/GetIntentReceipt 400 (Bad Request) lines, coming from Trails' own file (onramp-D6xxHSLW.js). Our checking hadn't started then, so these were the Trails box's own requests.
  • After the problem 1 fix: the same red line repeating every few seconds, now pointing at our file trailsReceipt.service.ts:23. The user said "I keep getting this in my log".

Investigation

  1. Called the same endpoint for run 1's intent from outside the browser, first plainly, then with the browser's Origin: http://localhost:3002 header, then through the exact client library our code uses (@0xtrails/api). All three answered 200, SUCCEEDED. So run 1's id wasn't the failing one.
  2. The user opened the Network tab on one red request and copied its payload and response: 
    Payload:  { "intentId": "0xe298b26821b77fe2849e43cb712eab1596e9d3498a50692d4d74054ef1f92701" }
Response: { "error": "NotFound", "code": 8000, "status": 400,
            "cause": "intent receipt not found for intentId 0xe298…2701" }
    That id was a new price nobody had paid for yet. A receipt only exists after paying, so Trails says "not found".
  3. Our code already understood "not found" as "only a price, nothing paid" and would stop after 15 minutes. The red lines were Chrome printing every failed request, even ones our code handles. Since the problem 1 fix checks every 3 seconds from the quote, that meant a red line every 3 seconds while the buyer chooses a token.
  4. Asked Trails' other call, GetIntent, about both ids: the unpaid price answered 200, QUOTED; run 1's purchase answered 200, SUCCEEDED. So GetIntent works for both, without an error.
Root cause

We asked for a payment's receipt before a receipt could exist. Not a wrong answer from our code, but a red error in the console on every check.

The fix

  1. getTrailsIntent now asks GetIntent first. If the status is QUOTED or COMMITTED (paid not yet landed), it stops there: no receipt call, no error (trailsReceipt.service.ts lines 13, 30 to 31).
  2. Only once Trails is executing or finished does it also ask GetIntentReceipt for the transaction and refund details (line 32).
  3. A "not found" from either call still counts as "only a price" (line 47), so a made up or expired id is handled quietly.
  4. Our backend's sale record is only fetched once the payment has landed, not on every check while choosing a token (browserCheckoutSource.ts line 107).
Confirmed

Through the same client library: unpaid price ▸ QUOTED, run 1 ▸ SUCCEEDED, made up id ▸ NotFound (handled). In run 2 the user saw no red GetIntentReceipt lines.

References: src/core/services/trails/trailsReceipt.service.ts; src/core/services/trails/browserCheckoutSource.ts line 107; Trails API POST /rpc/Trails/GetIntent and /rpc/Trails/GetIntentReceipt with header X-Access-Key; progress doc phase 8, "Follow up, same day".

Section 9

Found along the way (to decide, not bugs in Trails code)

  1. No way to the receipt after "Keep browsing" (raised by the user). Pressing it on "Payment in progress" closes the drawer; the purchase still finishes and the "is yours" message appears, but the message has no link. Today the receipt is reached from the purchase's row on /history ("View receipt", src/helpers/history/format.ts line 50). The normal USDT purchase has the same gap. Proposed: a "View receipt" link inside that message, for both. Not in Mohit's doc; to check with the senior first.
  2. Receipt page wording for Trails purchases. "You paid 0.10 USDT" and "Payment and transfer settled in the same transaction" describe only the Polygon side; the buyer actually paid POL or BNB through Trails. The "is yours" message has the same nuance.
  3. Rounding at tiny prices. On a 0.10 listing the receipt shows "Seller received 0.10" and "Marketplace fee 0.00"; the real values are 0.0975 and 0.0025.
  4. The "is yours" message has no title (found in run 3, ETH, westbengal.og). The buyer sees only "Ownership transferred…", without "westbengal.og is yours". Our code passes the title, but the site's shared success message (src/design-system/primitives/toast-message/success.tsx) never draws one. Not a Trails bug: the normal USDT purchase and the "Link copied" messages lose their titles the same way. Two fixes: let the success message show a title whenever one is given (fixes all of them; "Link copied" titles start showing too), or only where we ask for it. Waiting for a decision.
  5. A payment popup can outlive the screen that started it (run 3, cause confirmed by the user). The user pressed Pay in the Trails widget, then went back. MetaMask kept the request, and it popped up later while the drawer showed the normal USDT screen. Confirming it still bought the domain and the background tracking finished it, but the buyer sees a payment with no context, and the site can't cancel a wallet request. To decide: a short warning when leaving the widget ("check your wallet for a waiting request"), or leave as is.
  6. The red "another network" notice only offers Switch (run 3). With the wallet on Ethereum, the drawer opens on "USDT from your wallet" and asks to switch to Polygon, even though "Any token, any chain" would work from Ethereum. It could point to that option, or select it automatically. New wording, so to approve first.

All six are in the progress doc's "Double check before this ships" box.

Section 13 · 11 Nov 2026

Follow up: the red GetIntentReceipt 400 lines again

In one lineThe red lines seen on 11 Nov come from the Trails widget's own code, not ours. Yesterday's fix (section 5) still holds. No code change needed.

Context

  • On 11 Nov the user tested the fixes from Mohit's code review (trails-mohit-review.html). The MetaMask browser extension (13.55) could not connect to any site that day: it adds Tron to every connect request and then rejects it, including on app.uniswap.org; a colleague on 13.52 was fine. So the tests ran over WalletConnect with MetaMask on the phone. Unrelated to Trails or our code; logged in the progress doc's double check list.
  • While checking test A (no widget logging), the user saw red POST …/GetIntentReceipt 400 (Bad Request) lines again, on tawhidabdullah.og, quoting USDT0 and then POL on Polygon, without paying.

What these red lines are

When the buyer picks a token, the Trails widget creates a quote (Trails' offer of how much to pay), and every quote gets an id. The widget then asks Trails "is there a receipt for this quote yet?" A receipt only exists once someone has paid, so before paying Trails answers "not found", and Chrome paints every "not found" answer red (400). Why the widget asks isn't visible from outside (most likely to check whether that quote was already paid). It does no harm: nothing breaks and nothing shows on screen.

Investigation

  1. The Initiator call stack of one red request showed only our files (useTrailsCheckout.ts, BuyFlowModal.tsx, TrailsWidget.tsx), which first suggested our code. But Chrome hides library frames by default (the "Show ignore-listed frames" link), so the widget's own code that made the request was hidden. Those visible files only pass the quote along.
  2. The user copied the request's payload: intentId 0xc3ad3afa6afaf76412efbfc7a5fcad1df664d49a6aeb3f4ef03f7939690b3f01. Trails was asked directly, with the key from .env: 
    GetIntent         ▸ 200, status QUOTED
                    createdAt 08:00:55, updatedAt 08:00:55 (never changed),
                    expiresAt 08:15:55 (15 minutes)
GetIntentReceipt  ▸ 400 NotFound, "intent receipt not found"
  3. Our code (trailsReceipt.service.ts) asks for a receipt only when GetIntent says the status is not QUOTED or COMMITTED. This quote was QUOTED the whole time, so our code can't have asked for its receipt. The widget's package does contain its own receipt request.
  4. The quote expired after exactly 15 minutes, which matches our rule for dropping an unpaid quote.
Result

The red lines are the Trails widget's own calls. Our status check works as designed and yesterday's fix holds. Nothing to change in our code.
