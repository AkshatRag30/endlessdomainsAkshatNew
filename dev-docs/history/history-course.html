How the History page (/history, Figma 140:16047) was built, in the order to build it yourself, with every one of the 70 changed files explained and judged: needed or not. Pair it with history-implementation-plan.md (the what) and history-progress.html (the log).

What you'll build

A signed in activity log: a header and seven tabs, a toolbar (search, sort, export), a table of activities that becomes cards on smaller screens, and a right rail with a Summary, Filters and Need help. Everything runs on demo data behind hooks, so real APIs can replace it later without touching a component.

What you need to know first

  • React function components, props and hooks (useState, useEffect, useMemo, useCallback).
  • TypeScript basics: unions, interfaces, Pick, Record, a simple generic.
  • SCSS modules: nesting, @include, &, attribute selectors like [data-status='pending'].
  • Next.js pages router: a file in pages/ is a route.

1

Research before you write code

Files: none. Output: dev-docs/history/history-implementation-plan.md

What I did

Before touching the page I answered one question: which parts of the Figma design can show real data today? That decides what the hooks return and what has to be demo data.

  1. Opened the backend repo (D:\Akshat Endless\backend\backend) and searched every controller for routes about history, activity, transactions, offers, bids and transfers.
  2. Read each match: its guard (login only, or a recently verified wallet), its query parameters and the shape it returns.
  3. Wrote the findings into the plan as a table: endpoint, what it gives, whether it fits.
  4. Decided live versus demo per area, then you asked for demo everywhere for now, so phase 6 (live) is on hold.
The mistake I made here, and how to avoid it

My first check said the listing history endpoint only worked per domain. Your senior was right that it's per user. Two causes: my local backend clone was two weeks old, and I misread an optional parameter as required. Always run git fetch (and git pull if your branch is behind) in the backend repo first, but never edit its files. Then read the DTO (the class with @IsOptional()) rather than guessing from the controller.

Why it matters

Every later file depends on this: the types mirror what the API will return, the hook hides where data comes from, and the Sample data chip tells testers which numbers are fake.

Try itIn the backend repo run git fetch (reading only, no edits), then search src for @Get( lines containing history. For one result, open its DTO and list which query parameters are optional.

Exporting icons

Exporting a whole icon node gave an SVG with a huge page background baked in. The fix was to take the icon's own vector layers (the SVG assets inside it), then rebuild each as a React component with currentColor (module 9).

Habit worth keepingMap each Figma colour to a role by what it does, not by its hex: #171429 text is primary text, black at 53% to 69% is secondary text, the #e2e0ec hairline is a border. That's what makes dark mode work later.

4

Demo data

Files: src/data/history/activities.ts, src/data/history/summary.ts

What I did

Instead of writing 22 full objects, I wrote short seeds and one function that expands them. That keeps the data readable and the rules (reference format, explorer hash, which rows link to a receipt) in one place.

  • The first eight seeds copy Figma's table order (one of each type, statuses alternating) so you can compare the page and the frame row by row.
  • Times are "hours ago", not fixed dates, so Last 7 days and This month always have rows to show.
  • 22 rows in total: 8 on the first page plus 14 more, the number Figma shows.
  • summary.ts holds Figma's exact Summary numbers for This month and scales them for other periods, so switching the select visibly changes the card.
Why demo data lives in its own folderThe repo rule (your sibling page pattern): demo data in src/data/<page>, read only by hooks. When the API arrives you delete the file and change the hook; no component imports demo data directly.

Paging and filtering the rows

Applied filters versus the draft

The Filters card has an Apply button, so there are two copies of the filters: the applied ones the list uses, and the draft the card is editing. The tab is applied filters too, stored in the URL as ?tab= so a reload keeps it.

A subtle pointWhen the applied filters change from elsewhere (you click a tab, or the "9 pending" link), an effect copies them back into the draft. Without it the Filters card would still show the old values and Apply would undo your tab click.

Extending shared components without breaking them

Files: ProfileTabs, SearchInput, FilterDropdown, DefaultButton, WatchlistDomainIdentity

This is the most important skill in the course. Five existing components needed something new. The repo rule: extend additively. Every new prop is optional and its default reproduces the old behaviour exactly, so every existing page keeps working without any change.

Example: making ProfileTabs generic

  • <T extends string = ProfileTab> makes the tab ids generic, defaulting to Profile's ids, so Profile's call doesn't change.
  • Each new prop has a default equal to the old hard coded value.
  • The icon became optional ({Icon && <Icon />}) because History's tabs are text only.

Example: a variant that only reaches mobile dark

Example: an optional behaviour

When onSubmit isn't passed, onKeyDown is undefined, so the Marketplace, My Domains and Watchlist searches behave exactly as before.

Your checklist before changing a shared component

  1. Search for every caller (grep -rn "ProfileTabs" src pages).
  2. Add the prop as optional, with a default that equals today's behaviour.
  3. Run tsc: every caller must still compile untouched.
  4. Look at one existing page that uses it, in both themes. I screenshotted Profile after changing ProfileTabs.
Try itFind the two callers of WatchlistDomainIdentity other than History. Confirm neither passes metaText or showCrown, then reason why their output is unchanged.

Components, built bottom up

Files: everything in composites/history/listings and composites/history/shared

Build order

  1. HistoryPills: the type pill and status chip. Smallest pieces, no dependencies.
  2. HistoryActivityParts: name block, copyable reference, amount, date link. Shared by row and card.
  3. HistoryActivityRow using the parts and the grid mixin.
  4. HistoryActivityCard using the same parts at card size.
  5. HistoryStatusLegend, HistoryToolbar.
  6. HistoryActivityTable: puts rows or cards together with every state.

Building small to large means each piece can be looked at alone, and the big component is just assembly.

One grid for header and rows

275fr and so on keep Figma's proportions at any width; minmax(150px, …) stops a column getting so narrow its content wraps. Both the header and the rows @include history-grid, so they can't drift.

The coloured status strip without an extra element

A ::before pseudo element plus a data-status attribute: no extra markup, and the colour comes from data, not from inline styles (CLAUDE.md §4.5 forbids inline styles for fixed states).

Table or cards

Below 1280px the main column is too narrow for an 817px row, so every activity becomes a card. CSS alone can't swap a table for a different component, which is why this uses the repo's useIsMobile hook, like My Domains.

Beating a shared component's style without !important

CSS modules load in an order you don't control, so a single class could lose to the primitive's own single class. Two classes always win. That's the repo's answer to "no !important" (CLAUDE.md §4.3).

Reusing the Watchlist name block

Try itAdd a sixth column, "Network", to the table. You'll need to touch the grid mixin, the header list in the table and the row. Notice the card doesn't change: that's the benefit of separate row and card components.

Dark mode

Files: every .module.scss in this course

  1. Colours come from role tokens: --color-bg-surface, --color-text-secondary, --color-border-subtle… They already have dark values, so most of the page needed no dark code at all.
  2. One surface rule: the list section is the surface (#141415 in dark) and the rows inside it are the page colour (black), as CLAUDE.md §7.2 says.
  3. Brand fills keep their colours (pill gradients, status strip), each with a "design-specific" comment.
  4. When a value can't be a role, add @include dark { … } as the last thing in the rule.
Caught by a screenshotThe black Listing pill disappeared on the black dark rows. The dark Figma frame draws it as a lifted grey, so a dark block gives it that grey.

Checking your work

Commands you run after every step

  1. Type check: npx tsc --noEmit -p . must print nothing.
  2. Lint only the files you touched: npx eslint pages/history src/hooks/history …. No new warnings.
  3. Banned patterns: search your files for !important, <img, <a and fragments inside .map().
  4. Pure helpers in Node (module 5).
  5. Look at it on your dev server (port 3002): sign in for real, open DevTools' device toolbar, check 390, 834, 1024 and 1440 in both themes.
  6. Click through behaviour: each tab, search plus Enter, clear, sort, Apply, Clear All, "9 pending", Show more, copy, Export, the Filter sheet on mobile.
  7. Regression: open a page that uses a shared component you changed (Profile, Watchlist).

How I took screenshots without a login (optional, advanced)

I drove headless Chrome over the DevTools protocol from a small Node script. Lessons from making it work, useful if you ever automate this:

  • The app logs out a token it can't decode (AutoLogoutHandler uses jwtDecode), so the dummy cookie had to look like a JWT.
  • An expiry years ahead overflowed the browser's setTimeout limit (about 24.8 days), which fired the "session will expire" dialog at once. 20 days ahead worked.
  • Backend calls were blocked so nothing reached the real API; the Next dev overlay then reported those failures and had to be hidden.
  • Git Bash rewrote /history into a Windows path; MSYS_NO_PATHCONV=1 stops that.

For learning, signing in for real and using DevTools is simpler and checks more.

Cheat sheet and glossary

TermMeaning here
PrimitiveA small, page agnostic building block in design-system/primitives (a button, a select).
CompositeA page specific component built from primitives, in design-system/composites/<page>.
BarrelAn index.ts that re exports a folder's components so imports are short.
Additive changeA new optional prop whose default keeps old behaviour; existing callers don't change.
Role tokenA CSS variable named by job (--color-text-secondary) with a light and a dark value.
Demo data / isMockSample rows from src/data; isMock shows the Sample data chip.
Applied vs draftWhat the list shows vs what the Filters card is editing until Apply.
Pure functionSame input, same output, no side effects; testable in Node.
Commandsnpx tsc --noEmit -p . · npx eslint <paths> · localStorage.theme = 'dark'
