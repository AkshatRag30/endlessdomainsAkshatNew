Nov 10, 2026  · ​@Mohit
Summary
Both features extend the Seaport 1.6 marketplace (marketplacev2) that is live today for
UD on Polygon only, and neither needs a new smart contract. Seaport 1.6 is deployed at
the same address on all five target chains, so multi chain is a config and indexing job, not a
contract job. Bulk listing uses Seaport's native bulk order signature, so one wallet
signature can cover many orders on one chain.
Recommended order of work, after Trails ships:
1. Bulk listing for UD on Polygon. No chain work. The drawer already exists on the
unmerged bulk-list  branch; the work is switching it to one signature and adding a
bulk endpoint.
2. Multi chain foundation. Turn the single Polygon config into a per chain and per
collection registry across backend, poller and frontend, including ERC1155 support for
ENS. Nothing user visible changes yet.
3. All providers in one release. UD Base, Freename (Polygon, Base, BNB), SPACE ID .arb
and .bnb, and ENS (unwrapped, wrapped and ENSv2). ENS is the largest piece: two
ERC1155 contracts, mutable ENSv2 token ids, NameWrapper fuses and mainnet gas.
Out of scope here: auctions (the design already marks them Coming Soon), offers, bulk
buy, Solana and non EVM providers, and a smart contract audit (none is needed while we
only use Seaport).
All product questions are decided; the answers and their effect on the plan are in the
Open questions section.
Where the code is today
Single listing works end to end for UD on Polygon, and a bulk drawer is already built on an
unmerged branch, but every layer assumes one chain, one NFT contract, one currency
and one signature per order. Read from marketplace frontend uat  and origin/bulk-
list , backend uat@465c09fe , webui origin/uat@caf8013c .

Bulk listing: product flow
The attached designs describe five screens, and the target is one approval per
unapproved contract plus one signature per chain, whatever the batch size. The flow
below is the designs with the gaps closed.
1. Select names (My Domains, list view). Bulk List in the hero or Quick Actions enters
select mode. Each row's action becomes Select or Selected. Ineligible rows (listed,
sold, expired, expiring within the listing window, chain not enabled, no token id) show
a disabled Select with the reason on hover. The banner reads "N unlisted names in this
view" with List (selected count), Select All N and close. Esc also exits. A batch holds
names from one chain only, so the chain filter must be set before selecting (decision
2).
2. Bulk list drawer. Pricing (applies to all): same price for every name, or set each myself.
The percentage of model estimate option is dropped (decision 5). Listing type: Fixed
price, Auction marked Coming Soon. How long it runs: 7, 30 or 90 days, with one line
saying when they expire and which names end early because the domain expires first.
The names: extension chips with counts, one row per name with editable price and
remove. Summary: domain count, combined asking price, platform fee, you receive if
all sell. CTA reads Approve, then list N when any approval is missing, otherwise List N.
3. One time approval (skipped when every contract in the batch is already approved).
One setApprovalForAll(Seaport)  transaction per unapproved NFT contract. The
modal lists each contract with its chain and estimated gas.
4. Sign. The app builds every order, the wallet shows one Seaport bulk order signature
per chain, the app posts the batch. Progress reads Preparing orders, then Waiting for
signature, then Publishing. The button is Cancel, which closes the flow; it cannot
cancel anything inside the wallet.
5. Done. "N domains are live" with combined asking price, you receive if all sell, and the
expiry. If some names failed server checks, show "N of M are live" with each failed
name, its reason and Try these again (already built on the branch). Buttons: Done and
List more.
Single listing stays as it is. It can later use the same code path with a batch of one.

F1. Rebase the branch. origin/bulk-list  was last merged with dark-mode on 2026-10-

F2. One signature per batch (Seaport bulk order).
1. Build every OrderComponents  first (counter and block time read once per batch, as
the branch already does).
2. Tree height h = max(1, ceil(log2(n))) ; pad the leaves to 2^h  with an empty
OrderComponents . With the cap of 50, h  is 6 (64 leaves).
3. Sign the EIP712 type BulkOrder(OrderComponents[2]...[2] tree)  (one [2]  per
level) against the chain's Seaport domain. Port the tree and type helpers from
Seaport.js ( Eip712MerkleTree ); do not hand write the type strings.
4. Per order signature = 64 byte compact signature, then the 3 byte leaf index, then h
proof hashes of 32 bytes. Each order stores its own signature; Seaport verifies it on
every fill path.
5. Verify locally before posting: rebuild the root from each proof and recover the signer,
mirroring the existing verifyTypedData  check.
6. Post once to the bulk endpoint (B1) and render each item's result.
F3. Keep per name signing as a fallback. Some wallets will fail on a 64 leaf typed data
payload (hardware wallets, some WalletConnect mobile wallets, smart contract wallets).

B2. Bulk signature verification in @endlessdomains/order-builder , shared with the
frontend.
1. Detect a bulk signature by length: 64 or 65 bytes, plus 3, plus a multiple of 32.
Anything else follows today's ECDSA path.
2. Read the leaf index and proof. Leaf = the order hash
( hashStruct(OrderComponents) ). Walk up the tree using the index bits for left or
right.
3. Digest = keccak256(0x1901 ‖ domainSeparator ‖
keccak256(bulkOrderTypehash(h) ‖ root)) , recover, compare to the offerer.
4. Tests against signatures produced by Seaport.js for heights 1, 2 and 6, and one fork
test that fills a bulk signed order on Polygon.
B3. Validation per item, reads batched. Reuse checks 1 to 10 in order.service.ts
unchanged per order. Batch the chain reads through Multicall3: one getCounter  per
maker, one isApprovedForAll  per contract, one ownerOf  (or balanceOf  for ERC1155)
per token. A single RPC failure still returns 503 for the whole batch, as today.
B4. Partial success. A rejected item must not block the rest. Insert accepted orders one
transaction per order (reusing create() ), so an ALREADY_LISTED  race on one name does
not roll back the others. DUPLICATE_ORDER  on a retry of the same signed order counts as
listed, which makes the frontend retry idempotent.
B5. Batch record and bulk cancel. Add batchId  (uuid) to tbl_marketplacev2_orders
and the listing history. Send one seller email per batch, not one per order. Add POST
/marketplacev2/orders/cancel-bulk  taking order hashes plus the on chain cancel  tx
hash. Single cancel follows the same rules (decision 1). Agreed with the backend dev on 16
Nov:
1. The tx hash is a hint, the events are the proof. On request, check only that the hash is
well formed and that every order belongs to the caller, sits on one chain and is active.
Then set the orders to cancel_pending  (hidden from browse) and store the hash. Do
not require the RPC to see the tx; public nodes often cannot see a pending one.
2. Only OrderCancelled  events, matched by order hash, move an order to cancelled.
Wallet speed up and replace send a new tx hash, so matching on the submitted hash
would miss real cancels. If the stored hash's receipt shows a revert, or lands without
cancelling some orders, flag those orders at once.

Traps the devs must design for:
BNB stables use 18 decimals. Every other row uses 6. The order table stores
priceUsdt  as a bigint in 6 decimal units, and order-builder hardcodes USDT_DECIMALS
= 6 . Amounts must be stored with the token address and its decimals.
Expiring names can be sold after they lapse. ENS and SPACE ID transfers revert once
the name expires, so a fill fails safely. UD names can expire too: expiryOf(tokenId)
returns 0 for most names (brad.crypto) but a real date for some newer ones, so UD is
checked per name. The listing must still end before the name's expiry, or a buyer pays
gas for a failed fill. Backend already caps listings at 90 days. It must also cap at expiry
minus a buffer.
ERC721 transfer does not reset records on ENS v1 and SPACE ID. The buyer receives
the registrant NFT, but the registry controller and resolver records stay with the
seller until the buyer calls reclaim  and edits records. The receipt and the buyer's
manage page need a "claim control" step. UD and Freename are the opposite: UD
emits ResetRecords in every transfer (3 Polygon transfers checked), and Freename
emits a matching reset event keyed by the token id before every transfer (2 checked),
so their buyers start with empty records and need no claim step.
NameWrapper fuses. A wrapped name with the CANNOT_TRANSFER  fuse burned can
never be sold. Listing must check fuses and refuse it.
ENSv2 token ids change. When an ENSv2 token id is regenerated, any order signed
against the old id becomes unfillable. Checked on mainnet: the registry burns the old
id and mints the new one as TransferSingle events, then emits
