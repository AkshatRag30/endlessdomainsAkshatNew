1. The ideas behind multi chain, explained simply

What changes in one sentence

Today every name on our marketplace is a UD name on Polygon, paid in USDT0. After this work a name can come from 4 providers on 5 chains, paid in the stablecoin of its own chain. Nothing new is invented: the same Seaport contract already sits at the same address on all five chains.

Chain

A separate blockchain: Polygon (137), Ethereum (1), Base (8453), Arbitrum (42161), BNB (56). A wallet is connected to one chain at a time, so before listing or buying we must ask the wallet to switch to the name's chain.

Collection (NFT contract)

The contract that holds the names. A provider can have several (ENS has three) and one contract can live on several chains (Freename uses the same address on Polygon, Base and BNB). So a name is identified by three things together: chain, contract and token id. Today we use token id alone.

A signature only works on its own chain

Each chain stamps its own id into the message the seller signs. An order signed for Base can never be filled on Polygon. So the order builder must be told the chain every time.

Currency and decimals

Prices are stored as whole numbers of the token's smallest unit. USDT0, USDC and Arbitrum's USD₮0 use 6 decimals (1 dollar = 1,000,000 units). BNB's USDT uses 18 (1 dollar = 1 followed by 18 zeros). Every place that divides by 1,000,000 today would show a BNB price a trillion times too big. Mohit sir decided all prices are shown as USD.

Approval is per contract per chain

Seaport needs permission (setApprovalForAll) once per NFT contract on each chain. A seller with UD Polygon, Freename Polygon and ENS names approves three times. On Polygon that costs cents; on Ethereum a few dollars. Bulk listing already built approvals this way, with one row today.

ERC721 versus ERC1155

Two kinds of NFT. ERC721 is "one token, one owner", used by UD, Freename, SPACE ID and unwrapped ENS. ERC1155 is "a balance of a token", used by wrapped ENS and ENSv2. Seaport writes them differently in the order (item type 2 versus 3), so the builder must know which one.

Token id from a name

Each provider turns a name into a token id differently: namehash (UD, wrapped ENS), labelhash (SPACE ID, unwrapped ENS), a changing id (ENSv2), or no rule at all (Freename, read from chain). The frontend mostly gets ids from the backend; it just has to stop assuming one scheme.

Expiry

UD names mostly never expire, SPACE ID and ENS names do. Decision 8: a listing must end 7 days before the name expires, and a name with under 14 days left can't be listed. Bulk listing already does this for UD on Polygon by reading expiryOf; each provider has a different expiry function.

Claim control

When an ENS v1 or SPACE ID name is sold, the buyer gets the NFT but the old owner still controls its records until the buyer presses "reclaim". So these receipts must tell the buyer to claim control. UD and Freename wipe records on transfer, so they need nothing.

Trails

Trails lets a buyer pay with any token from any chain. Today we always tell Trails to deliver USDT0 on Polygon. After this work, the delivery chain and token become those of the listing.

Trails versus multi chain: what's the difference?

They solve two different sides of a sale. Trails is about the buyer's money. Multi chain is about where the name lives.

Trails (built, merged 18 Nov)

Answers "how can the buyer pay?" Every listing today is a UD name on Polygon priced in USDT0. Without Trails the buyer must already hold USDT0 on Polygon. With Trails they can pay with ETH on Base or USDC on Arbitrum; Trails swaps and bridges behind the scenes and delivers exact USDT0 on Polygon, where Seaport completes the sale. The name never leaves Polygon. Trails only changes where the buyer's money comes from.

Multi chain (this plan)

Answers "where can the name be?" Today the marketplace knows one shop: UD names on Polygon. Multi chain opens more: UD on Base, Freename on three chains, SPACE ID on Arbitrum and BNB, ENS on Ethereum. Each name is listed, signed, approved and sold on its own chain, in that chain's stablecoin. It is about the seller's side.

Where they meet: ticket C4. Trails always delivers to one place today, Polygon USDT0, which is why browserCheckoutSource.ts:84 hardcodes chainId: 137. Once a name can sit on BNB, Trails must deliver USDT on BNB instead, so its delivery point follows the listing's chain.

A simple picture: multi chain decides which city the shop is in. Trails lets the customer pay in any currency from anywhere and converts it into the local currency at the shop's door. Today there is one shop, in Polygon. After this work there are shops in five cities, and Trails needs to know which city to deliver to.

That is why gap 2 matters: Trails is locked to Polygon on our side and on Guru's (MC-09 added a Polygon only guard). Both locks must open together, and only Polygon has had a real Trails buy, so Mohit sir wants one real test buy per chain.

Phase 2: the foundation (nothing visible changes)

C1

Read the chain setup from the backend

Mock firstMedium
In plain words
Today the frontend has its own hardcoded copy of the marketplace setup (DEFAULTS in src/lib/marketplace-order-client.ts): one chain id 137, one Seaport, one USDT, one NFT contract, the fee 250 bps and its recipient. Mohit sir wants it read from GET /marketplacev2/config instead, so the fee shown and the fee charged can never disagree again.
The problem today

Whenever someone lists or buys, 21 files reach into this one object to answer "which chain, which coin, which contract, what fee". That only works because there is exactly one of each today:

export const DEFAULTS = {
  chainId: 137,                      // Polygon
  seaportAddress: '0x0000...eB395',
  usdtAddress: '0xc213...8e8F',      // the one currency
  domainNftAddress: '0xa9a6...9e9f', // the one NFT contract (UD)
  feeRecipient: '0xeF51...5494',
  feeBps: 250,                       // 2.5%
}

The backend keeps its own copy of the same settings and checks every order against it. Two copies must always agree: if the backend changes the fee and nobody edits our file, we show and sign the old fee and the backend rejects the order. Mohit sir notes this drift has already happened once.

Why multi chain breaks it
A seller lists a UD name on Base. Our code grabs DEFAULTS.usdtAddress, which is Polygon's USDT, and puts it in a Base order. That is simply wrong: on Base the price must be in USDC, at a different address. With 8 collections on 5 chains, one hardcoded object can't hold the answers.
What the config returns

Guru's endpoint returns the backend's own settings as lists:

chains:      Polygon 137 → Seaport, USDT0 (6 decimals), fee 2.5%
             Base 8453   → Seaport, USDC (6 decimals), fee 2.5%
             BNB 56      → Seaport, USDT (18 decimals), fee 2.5%  ...
collections: UD on Polygon, ERC721, expires sometimes, no claim needed
             SPACE ID .bnb on BNB, ERC721, 90 day grace, claim needed  ...
listing:     14 day minimum, 7 day buffer, 7/30/90 day durations, max 50

The frontend fetches this once when the page loads. Instead of reading DEFAULTS.usdtAddress, the listing flow asks "this name is on chain 8453, what is its currency?" and gets USDC with 6 decimals.

What we gain
One source of truth: the fee we show is always the fee the backend checks. Switching a chain or provider on becomes a backend setting, not a frontend release (that is how Freename stays off until its token ids exist). The listing rules (14 days, 50 names) come from the same reply instead of also being typed into bulkListing.ts.
Why "mock first"
The endpoint exists on Guru's branch but answered 404 on stage today. We build against a small local JSON with the same shape, holding only today's row (UD on Polygon), so users see no difference. When the endpoint reaches uat we point at it and delete the JSON.
In one line
C1 swaps "the frontend's own hardcoded settings" for "ask the backend what its settings are". Every other ticket stands on it, because each needs to look up its name's chain details.
Today
21 files import DEFAULTS (not 7 as listed): the buy flow, single and bulk listing, approvals, on chain cancel, watchlist, history mapping, token formatting, Trails, and two type files.
What we build
A typed config (types in src/types/), an RTK Query endpoint in src/core/redux, a hook that serves it, and small pure helpers like "find the collection for this chain and contract". Then every DEFAULTS reader moves to it. Until the endpoint exists, the same shape is served from a local JSON with only the UD Polygon row, so nothing changes for users.
Backend
MC-05 built the endpoint on Guru's branch; the shape is known (section 4). Not on stage yet (404 today).
C2

Read from any chain, and one wallet setup

IndependentMedium
In plain words
To read anything on chain (who owns a name, is Seaport approved, when does the name expire) we use getPolygonReadProvider, which only talks to Polygon, with a smart list of backup servers. It becomes getReadProvider(chainId) with the same backup logic per chain. Separately, the wallet popup library (AppKit) is set up seven times in seven files; it should be set up once.
Today

Good news: all of them already list Ethereum, Base, Arbitrum, BNB and Polygon, so no network needs adding. They also list dead test networks (Goerli, Mumbai, Arbitrum Goerli) that can go.
What we build
One read provider per chain with an RPC list per chain (a dedicated RPC env per chain plus public backups), and one shared AppKit setup that the seven places import. Two of the seven live in src/component, which we no longer add code to; we only change their import.
Backend
None. Needs RPC URLs per chain (question 7).
C3

Order builder takes chain, NFT kind and currency

IndependentMedium
In plain words
The code that writes a Seaport order (src/lib/seaport-order-builder-v5.ts) always writes "an ERC721 token for USDT with 6 decimals on Polygon". It must take the chain id, the item type (ERC721 or ERC1155), the currency token and its decimals as inputs. The bulk signature (the tree) also has to use the chain's id.
Today
ItemType.ERC721 is fixed at line 133; the bulk tree in listingOrder.ts and the Trails order checks also assume Polygon.
What we build
Parameters with safe defaults, then tests that sign a Base order, a BNB 18 decimal order and an ERC1155 order and compare with the backend's own package (@endlessdomains/order-builder 0.3.0, MC-04), the same trick that proved bulk signatures.
Backend
None for building; the backend's 0.3.0 package is our reference.
C5

Money amounts use each currency's decimals

Mock firstLarge
In plain words
Everywhere we turn a stored amount into dollars we divide by 1,000,000 (1e6 or USDT_DECIMALS). For BNB's 18 decimal USDT that is wrong by a factor of a trillion. Every one of these must use the order's own decimals, and for 18 decimals we must use exact big number maths, because ordinary JavaScript numbers lose precision there.
Today
16 files: useMyDomainsData, useLiveListings, orderDetails, watchlist, mapApiActivity, summarizeHistory, watchlistItems, profile-settings.service, useBuyFlowActions, and seven the PDF doesn't name: PriceInput, priceFilter, bulkListing, tokenFormat, checkoutGate, trails/usdtAmount, TrailsWidget.
What we build
One pair of helpers, "units to dollars" and "dollars to units", that take decimals, tested with 6 and 18. Every file above calls them. Labels say USD (decision 3), with the token named where a wallet asks for it.
Backend
MC-06 added priceAmount, feeAmount, sellerAmount and priceUsd, and keeps the old priceUsdt names until MC-23. Where currencyDecimals appears in the replies has to be confirmed with Guru.

5. What the PDF misses or gets slightly wrong

1

The hotspot lists are short. DEFAULTS is read in 21 files, not 7. Six decimal maths sits in 16 files, not 10. createAppKit runs 7 times, not 6. The plan will use the full lists.

Grep on bulk-list, 24 Nov, excluding _archive and Guru's test page

2

Trails is Polygon only on both sides. The PDF says "the destination becomes the listing's chain", but the frontend hardcodes 137 and the backend's MC-09 added a Polygon guard. Both have to open together, and only Polygon has ever been tested with a real buy.

core/services/trails/browserCheckoutSource.ts:84

3

The deep link refuses non Polygon names. The PDF notes this for webui's List action (W1), but it lives in our page: pages/seller-hub/my-domains/index.tsx:146 shows "Only Polygon domains can be listed". It must read the chain from ?chainId= and the config.

4

Expiry reads are per provider. Bulk listing reads UD's expiryOf on Polygon through Multicall3. SPACE ID and ENS use other functions (with grace periods), Freename has none, and ENSv2 differs again. This sits between C4 and the ENS ticket and isn't named anywhere.

hooks/my-domains/useBulkListingActions.ts readChainExpiries

5

On chain cancel is Polygon only. Delist (single and bulk) sends Seaport cancel on Polygon. It must go to the order's chain, and on Ethereum the cost is real, so the copy must say so.

useOnChainCancel.ts, onChainCancel.ts

6

Price filter and sort across currencies. helpers/marketplace/priceFilter.ts filters on 6 decimal units. Mixed currencies have to filter and sort on priceUsd, which the backend added in MC-06.

7

Listing rules are still hardcoded. 14 days, 7 days, the 7, 30, 90 durations and the cap of 50 are constants in bulkListing.ts; the config endpoint carries them now, so C1 should read them.

8

The files we must touch break the layering rules today. listingOrder.ts and useListingFlowActions.ts sign and post orders from inside a composite folder (CLAUDE.md §8, plan rows M8 to M10). Multi chain rewrites both, so fixing their place at the same time is cheap. Fixing them is your call (question 6).

9

Old modals still switch to Polygon. src/component/modals/BuyNowModal, DomainListingModal and DomainBulkListingModal still have Polygon network code and are imported from a few places. If any path still opens them, they'd bypass the multi chain flow.

10

Freename can't be listed until M5b ships. Its token ids are stored as null today, and our flows need a token id. Freename should stay switched off in the config until discovery fills ids.

11

Approval copy. The designs' "Approve once, list forever" was already flagged by Mohit sir (design issue 5). With several contracts per seller, the approval step must list each contract with its chain and a real gas estimate. Bulk v2's approval step does that for one row; it needs testing with several.
