How the Profile page gets its data

A friendly, step by step walk through how /profile talks to the backend, where its sample data lives, what the hooks do, how wallet linking works, and how it all links up to the screen. No prior knowledge of the code needed. Every example is copied from the real files on the profile-settings branch, as of 15 October 2026.

Why it's built this way

The Figma design for the Profile page shows a lot: your name and email, a username and bio, how you sign in, your wallets, active sessions, five notification switches, display preferences and account stats. The backend can serve some of that today, and the main Endless Domains site already uses those APIs on its own profile page. The rest doesn't exist on the backend yet.

So the page does two things at once:

  • Where the backend has an API, the page uses the same API as the main site: loading and saving your details, email verification, changing your password, your wallets, and linking a missing wallet.
  • Where it doesn't, the page shows sample data (also called mock data), clearly marked with a "Sample data" chip, so the design can be reviewed now and switched to real data later.

And it does this the same way My Domains and Watchlist do, so anyone who knows those pages already knows this one. (An earlier version had its own extra "service layer" folder; it was removed on 15 October because no other page works like that.)

The big picture

Think of the page like a restaurant.

Component (the customer)A card, a form or a switch on screen. It just wants data and doesn't care where it comes from.
Hook (the waiter)Takes the order, brings the data back, and says "still cooking" (loading) or "sorry" (error). Every card gets its data from a hook.
RTK Query in Redux (the real kitchen)The app's existing way of calling the backend. It also remembers answers (a cache), so the same dish isn't cooked twice.
Sample data store (the practice kitchen)Cooks pretend dishes for the parts the backend can't make yet. It lives in src/data/profile/.
Mapper (the translator)The backend speaks its own shape; the page wants a tidy one. src/helpers/profile/mapUser.ts translates both ways.
Types (the recipe card)Describes exactly what each dish looks like, so both kitchens serve the same plate.

Here's the same thing as layers. Requests go down, data comes back up.

Componentscomposites/profile/…
Tab panels and cards. They call hooks and draw what they get back.
↓ call a hook, like useProfileDetails() or useNotificationSettings()
Hookssrc/hooks/profile/
One file per hook. They handle loading, errors, saving, and turning backend data into the page's shape.
↓ each hook uses one of two sources
Real: RTK Querysrc/core/redux/userProfile.ts
The main site's profile APIs, shared with the rest of the app. Reshaped by src/helpers/profile/mapUser.ts.

The one sentence to rememberComponents → hooks → either Redux (real) or src/data/profile (sample). The component never knows which.

1Decide what the data looks like (types)

First, the shape the page needs, read from the Figma frames field by field. This is the "recipe card", in src/types/profile-settings/index.ts.

src/types/profile-settings/index.ts

export interface ProfileDetails {
  fullName: string
  username: string            // no backend field yet
  email: string
  isEmailVerified: boolean
  canChangeEmail: boolean     // false for Google accounts and verified addresses
  verificationSent: boolean   // "Resend verification" instead of "Verify email"
  phone: { countryCode: string; number: string } | null
  telegram: string
  bio: string
  location: string
  website: string
  avatarUrl: string | null
}

Why start here? Because the real data and the sample data must both arrive in exactly this shape. The backend sends a phone number as one string ("+919876543210"); the page always gets the tidy version ({ countryCode: 'IN', number: '9876543210' }). Step 3 does that tidying.

Small detailThe folder is called profile-settings, not profile, because src/types/Profile.ts already exists and Windows treats profile and Profile as the same name.

2The backend endpoints (Redux, already in the app)

The app already calls the backend through RTK Query. The profile endpoints were mostly there already; this page reuses them and adds only two, next to the others.

WhatEndpointRTK hook
Read the userGET /users/user-multiple-walletuseGetUserProfileQuery (existing)
Save the profilePUT /usersuseSetProfileMutation (existing)
Verify / resend emailPOST /auth/verification-emailuseResendVerificationEmailMutation (added)
Change passwordPUT /auth/change-passworduseChangePasswordMutation (added)

src/core/redux/userProfile.ts (one of the two added endpoints)

changePassword: builder.mutation<unknown, { oldPassword: string; newPassword: string }>({
  query: (body) => ({ url: ChangePasswordApi, method: "PUT", body }),
}),

Using Redux instead of a new way of calling the server buys three things: the login token is attached automatically, the profile request is shared with the header and the wallet connect flow (one request, not three), and everything lives where other developers expect it.

One gotchagetUserProfile has no cache "tag", so saving with setProfile doesn't refresh it on its own. That's why the profile hooks call refetch() after every save. Because the cache is shared, the refetch also updates every other screen showing your name.

3Translate between the backend and the page (the mapper)

src/helpers/profile/mapUser.ts holds small pure functions (no React, easy to test), the same idea as src/helpers/marketplace/watchlist.ts for the watchlist.

src/helpers/profile/mapUser.ts (reading)

export function mapUserToDetails(user: User): ProfileDetails {
  return {
    fullName: user.name ?? '',
    username: '',                       // no backend column yet
    email: user.email ?? '',
    isEmailVerified: user.isEmailVerified,
    // The main site's rule: Google accounts and verified addresses can't change their email.
    canChangeEmail: !user.isRegisteredWithGoogle && !(user.email && user.isEmailVerified),
    verificationSent: (user.sentEmailCount ?? 0) > 0,
    // "+919876543210" → { countryCode: 'IN', number: '9876543210' }
    phone: user.phoneNumber ? parsePhoneString(user.phoneNumber, COUNTRIES, DEFAULT_COUNTRY_CODE) : null,
    telegram: user.telegram ?? '',
    bio: '', location: '', website: '', avatarUrl: null,
  }
}

src/helpers/profile/mapUser.ts (saving: the same body the main site sends)

export function toUpdateUserBody(saved: ProfileDetails, next: ProfileDetails) {
  const body = {
    name: next.fullName,
    phoneNumber: next.phone?.number ? toPhoneString(findCountry(next.phone.countryCode).dial, next.phone.number) : '',
    telegram: next.telegram,
    isVerified: saved.isEmailVerified && saved.email !== next.email ? 'false' : 'true',
  }
  if (next.email) body.email = next.email   // the backend rejects an empty email
  return body
}

The same file also turns the user into sign in methods and wallets, and works out which wallet the account can still link:

// One EVM and one Solana wallet per account (the seniors' rule).
export function missingWalletNetworks(wallets) {
  const missing = []
  if (!wallets.some((w) => w.network === 'evm_network')) missing.push('evm')
  if (!wallets.some((w) => w.network === 'solana')) missing.push('solana')
  return missing
}

4b. store.ts: one shared memory for the sample data

If two parts of the page show the same sample data, they must agree. So the sample data lives in one shared store that every hook reads, built exactly like the watchlist's sample store in src/data/marketplace/watchlist.ts. React's useSyncExternalStore re-renders every component that reads an area when that area changes.

src/data/profile/store.ts

let state: ProfileMockState = {
  extras: { username: '', bio: '', location: '', website: '', avatarUrl: null },
  summary: mockAccountSummary,
  sessions: mockSessions,
  walletSettings: mockWalletSettings,
  notifications: mockNotificationSettings,
  preferences: mockPreferences,
}

// Replace one area (never change it in place), then tell every listener.
export function setProfileMock(key, next) {
  state = { ...state, [key]: next }
  listeners.forEach((listener) => listener())
  return next
}

// The live value of one area, for a hook.
export function useProfileMock(key) {
  const read = () => state[key]
  return useSyncExternalStore(subscribe, read, read)
}

extras holds the profile fields the backend has no column for (username, bio, location, website, photo). They start empty for a real account. The whole store resets on a hard reload, like the watchlist's sample data, and the form says so in a note.

5The hooks (the waiters)

Every card gets its data from a hook in src/hooks/profile/, one hook per file, like src/hooks/my-domains/. Every data hook returns the same basic shape, QueryResult, which the domain overview and watchlist hooks use too:

data       // the data, or undefined while loading
isLoading  // true the first time → show a skeleton
isError    // true if loading failed → show an error banner with Retry
refetch    // the Retry button calls this

5a. A real hook: useSignInMethods

src/hooks/profile/useSignInMethods.ts

export function useSignInMethods() {
  const query = useGetUserProfileQuery()              // the shared, cached request
  const user = query.data?.result
  const data = useMemo(() => (user ? mapUserToSignInMethods(user) : undefined), [user])
  return {
    data,
    isLoading: query.isLoading,
    isError: query.isError,
    refetch: () => { query.refetch() },
    canDisconnectGoogle: false,                       // no endpoint yet
  }
}

5b. A real hook that saves: useProfileDetails

This one mixes the real account fields with the sample extras, and its save sends each part to the right place:

src/hooks/profile/useProfileDetails.ts (save)

5c. A sample hook: useNotificationSettings

src/hooks/profile/useNotificationSettings.ts

export function useNotificationSettings() {
  const area = useProfileMockArea('notifications')       // QueryResult from the store
  const { run: update, isSaving } = useProfileAction(async (patch) => {
    await mockSaveDelay()                                  // feels like a network call
    return setProfileMock('notifications', { ...getProfileMock('notifications'), ...patch })
  })
  return { ...area, isMock: true, update, isSaving }
}

The two small helpers keep every sample hook this short:

  • useProfileMockArea(key) uses the shared useMockQuery (from the domain overview hooks) for a short first load, so skeletons show and get tested, then returns the live value from the store.
  • useProfileAction(fn) wraps a save with an isSaving flag, for "Saving…" and disabled buttons.

When this area's endpoint ships, only the inside of this hook changes: useProfileMockArea becomes an RTK query, setProfileMock becomes a mutation, and isMock becomes false. The card using it doesn't change.

5d. useProfileDraft: the Profile form's edits

The Profile form keeps a draft (your unsaved copy) next to the saved version from useProfileDetails. It compares them to know if anything changed (which enables Save and powers "Discard unsaved changes?"), checks each field with src/helpers/profile/validation.ts, and on Save sends only the changed fields through useProfileDetails().save.

6Linking a wallet (useLinkWallet)

Each account can have one EVM wallet and one Solana wallet. The Wallets tab offers whichever is missing. Linking uses the same endpoints as the main site's profile page:

  1. You click Add Another Wallet (or Add EVM Wallet / Add Solana Wallet when neither is linked).
  2. The hook creates the AppKit wallet pop up with both the EVM (wagmi) and Solana adapters, and opens it for the right network.
  3. EVM: once your wallet is connected, it asks the backend for a one time code (GET /web3-auth/generate-nonce), asks your wallet to sign it, and sends the signature to POST /web3-auth/verify, which adds the wallet to your signed in account.
  4. Solana: once your wallet is connected, it sends its address and your user id to POST /web3-auth/solana-add-wallet.
  5. On success the Wallets tab refetches your profile, shows a toast, and the new wallet appears (the tab badge counts it too). Closing the pop up without connecting cancels.

Why not the normal wallet connect?The marketplace's usual wallet connect calls the sign in endpoints (/web3-auth/login), which can switch you to another account or create a new one. Linking must add the wallet to your account, so it uses the main site's link endpoints instead.

7The components (the customers)

Each tab has a "panel" component that calls the hooks and decides what to draw. The cards inside (switches, rows, forms) only receive values and callbacks as props. Here's the Notifications tab, simplified:

composites/profile/notifications/NotificationsTabPanel/NotificationsTabPanel.tsx

const notifications = useNotificationSettings()   // sample
const details = useProfileDetails()                // real (for Telegram)

const handleToggle = async (key, value) => {
  const previous = local
  setLocal({ ...local, [key]: value })            // 1. show it at once
  try {
    await notifications.update({ [key]: value })  // 2. save
  } catch (error) {
    setLocal(previous)                            // 3. failed? put it back
    ToastMessage(TOAST_TYPE.ERROR, "Couldn't save that alert", getUserFriendlyToastMessage(error, 'Please try again.'))
  }
}

if (notifications.isLoading) return <SettingsCardSkeleton rows={4} />
if (notifications.isError)   return <NoticeBanner … Retry calls notifications.refetch />
return <NotificationSwitches settings={local} onToggle={handleToggle} isSample={notifications.isMock} />

Notice the panel uses one sample hook and one real hook side by side, and treats them the same way. Errors from either become readable sentences through the app's existing getUserFriendlyToastMessage.

Two journeys

Saving your name (real data)

  1. You open /profile. ProfileTabPanel calls useProfileDraft, which calls useProfileDetails.
  2. useProfileDetails calls useGetUserProfileQuery(). If the header already loaded your profile, the answer comes from the cache; otherwise RTK Query sends GET /users/user-multiple-wallet. You see skeletons until it arrives.
  3. mapUserToDetails turns the answer into the page's shape, and the form fills in.
  4. You change your name. The draft now differs from the saved copy, so Save changes lights up.
  5. You press Save. useProfileDraft checks the fields, then calls save with only the changed field.
  6. save sends PUT /users with the body from toUpdateUserBody, then refetches your profile.
  7. The fresh profile flows back through the cache to the form, the header and anywhere else your name shows. A toast says "Your profile is saved."

Turning off "Product news" (sample data)

  1. You open the Notifications tab. useNotificationSettings calls useProfileMockArea('notifications'): a short loading moment, then the values from the store.
  2. You flip the switch. The panel shows it off straight away and calls update({ productNews: false }).
  3. The hook waits briefly, then setProfileMock replaces the notifications area in the store and tells every listener.
  4. Every component reading notifications re-renders with the new value. The card keeps its "Sample data" chip. A hard reload brings the Figma values back.

Recipes

Recipe A: the backend shipped notifications. How do I make that card real?

  1. Add the endpoints to RTK Query in src/core/redux/ (and the URLs to src/core/enum/api-endpoint.enum.ts / src/constants/Api.ts), like the existing ones.
  2. In src/hooks/profile/useNotificationSettings.ts, replace useProfileMockArea('notifications') with the query and setProfileMock with the mutation. If the backend's shape differs, add a mapper in src/helpers/profile/.
  3. Set isMock to false (the chip disappears) and remove notifications from src/data/profile/store.ts and fixtures.ts.
  4. Run the type check. The panel and cards don't change.

Recipe B: every card is real. How do I delete the sample data?

  1. When no hook imports src/data/profile/ any more, delete the folder.
  2. Delete useProfileMockArea.ts and the SampleDataChip primitive.
  3. Run the type check; it points at anything left over.

Recipe C: trying the error states

  • Change password: a wrong current password comes back from the backend as 401 and shows "Your current password is incorrect." under the field.
  • A card failing to load: each card shows its own error with Retry; the rest of the page keeps working.
  • Delete account (sample): the button stays disabled until you type your username (or your email, while there's no username).

FAQ

Why not just call the backend from the components?

Then every component would repeat loading, errors, saving and reshaping. Hooks do it once, and swapping sample data for real data only touches the hook.

Will real users see John Doe?

No. Profile details are real. Sample values only appear on cards marked "Sample data", and the profile's extra fields (username, bio, location, website, photo) start empty for a real account.

Why do my bio and username disappear when I reload?

The backend can't store them yet, so they live in the page's sample store. The form shows a note about this. They'll be saved for real once the backend adds those fields.

Why does changing my password sign me out?

The main site does the same: you sign in again with the new password.

Where is the theme (light/dark) saved?

On your device, through src/context/ThemeContext.tsx, the same as the header toggle.

Where's the full list of files and the history?

In dev-docs/profile/profile-settings-progress.html. The plan, with the decisions and next steps, is dev-docs/profile/profile-settings-implementation-plan.md (start at §14).
