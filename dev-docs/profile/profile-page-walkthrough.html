The 30 second version

"I built the Profile and Settings page at /profile from the Figma section, with five tabs and a right rail, in light and dark. I first built it on sample data so the design could be reviewed, then restructured it to match how My Domains and Watchlist are built, and then connected it to the same APIs the main site's profile page uses. Everything the backend supports is real now. Everything else is clearly marked as sample data, with a list of what the backend still needs to add."

The full story, in order

  1. Planning (14 Oct)Started from the Figma frames, light and dark. Wrote a plan: a map of every frame, what already existed to reuse, the data each tab needs, which APIs existed and which didn't, and phases. Decided the route (/profile?tab=…), that a first visit follows the device theme, and that missing data would be sample data for now.
  2. FoundationsThe route, one "My Profile" item in the sidebar and bottom nav, the header card, the five tabs with keyboard support, and the shell placement (the rail sits under the content on tablet).
  3. Form piecesBuilt the inputs the design needed: text field, password field with a strength meter, phone field with country codes, switch, settings row, avatar upload. Where something already existed, extended it instead of duplicating: the dropdown got a form "field" variant, the button got a new size, the segmented toggle got a pill variant. Every extension is additive, so existing pages didn't change.
  4. The tabs, one phase eachProfile form with live preview, save, discard and the unsaved changes guard; the right rail; Security (sign in methods, change password, sessions); Wallets; Notifications; Preferences with System / Light / Dark following the device.
  5. QAChecked all five tabs in light and dark at phone, tablet and desktop (40 screenshots), error states, keyboard and focus, and code rules (no !important, no inline styles). Fixed what came up, like the keyboard Tab order reaching the rail before the content.
  6. Restructure (15 Oct)Noticed the first version had its own "service layer" folder no other page uses. Restructured to match My Domains and Watchlist: real data through the existing Redux endpoints, sample data in src/data/profile, one hook per file on the shared useMockQuery / QueryResult, mapping in src/helpers/profile, errors through the existing error helper.
  7. Real APIs (15 Oct)Studied the main site's profile page and used the same endpoints: load and save the profile, email verification, change password (signs you out after, like the main site), the wallet list. Wallet linking follows the seniors' rule: one EVM and one Solana wallet; Add Another Wallet links whichever is missing. Copied the main site's rules, like locking the email for Google accounts and verified addresses.
  8. Right rail check (15 Oct)Checked whether the rail can be real: domains owned and listed can come from the call My Domains uses; sales need the backend to confirm one endpoint on stage; member since needs one field added to the user response; export and delete have no endpoint. Recorded in the plan (§14.6); not built yet.

The layers, in plain words

LayerWhat it isWhere

The one sentenceComponents draw; tab panels call hooks; hooks get data either from Redux (real, the main site's APIs) or from src/data/profile (sample); mappers translate the backend's shape into the page's. The same structure as My Domains and Watchlist.

Questions you'll likely get

Why Redux?
The app already uses RTK Query, and the profile endpoints were already there. Reusing them means one shared, cached request with the header and wallet connect, and the login token is handled automatically. Only two endpoints were added (verification email, change password); nothing existing changed.
What's still fake?
Username, bio, location, website and photo (no backend column; kept until reload, with a note); account stats; sessions; wallet network settings; notifications; preferences (the theme itself is real, on the device); export and delete. Each such card shows a "Sample data" chip. The list for the backend team is in the plan, §8.2.
Can the right rail be real?
Domains owned and listed, yes, today, from GET /marketplacev2/orders/my-domains (the My Domains call). Completed sales and volume sold probably, once the backend confirms status=SOLD works on stage. Member since needs createdDateTime added to the user response. Export and delete have no endpoint. Plan §14.6.
Did you test it?
Type check, lint and helper tests are clean. Browser tests with the APIs simulated: load, save (the exact body sent was checked), verify email, wrong password, change password to the login page, Telegram disconnect, the Google email lock, all three wallet states, and Add opening the wallet pop up; all five tabs in light and dark at phone and desktop. Not yet: a real login on stage, and a real wallet signature.
Anything you'd do differently?
Check how the sibling pages are built before designing the data layer; the first version had its own service layer and had to be restructured. Also, the cached profile doesn't refresh on its own after a save (no cache tag), so the hooks refetch it.
Did anything else in the app change?
Only small additive changes to shared pieces: the page shell, dropdown, buttons, info card, segmented toggle, the theme context, the endpoints enum, two Redux endpoints and the navigation item. Other pages were rechecked. The backend and main site repos are untouched.
