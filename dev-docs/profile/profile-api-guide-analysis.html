3. Gaps in his integration

Fixed on 26 Oct (uncommitted): items 1, 2, 4, 5, 6 and 7 below. Items 3 and 8 remain.

  1. Account summary is fetched twice. ProfileTabPanel and ProfileRail each call useAccountSummary, and the hook has no shared cache, so every page load sends the same request twice.
  2. Errors are silent. The new summary and notification hooks catch errors without logging them, unlike the other pages, which log with a [page] prefix.
  3. Notification channels don't persist. The email and Telegram switches live in React state only, so they reset on every reload, while the card no longer shows the Sample data chip.
  4. Username is checked only on save. The user finds out a name is taken only after pressing Save.
  5. Data request status isn't shown. GET /users/requests is never called, so after requesting an export or deletion the user can't see that it's open.
  6. Member since can be blank. A null memberSince becomes an empty string; check how the card shows it.
  7. Redirect only works with a token in the body. If a caller passes no access_token, the request goes without Bearer and gets a 401.
  8. A test page ships in the app. /dev/sprint1-test is included in the build and only hidden by NEXT_PUBLIC_MPV2_SPRINT1_TEST. Confirm the variable is off in production.

4. Where it differs from our conventions

The new calls go through src/core/services/profile-settings.service.ts, which has its own fetch wrapper. The rest of the Profile page uses RTK Query in src/core/redux/ (plan §14.3), and the marketplace v2 pages use callBackend. Going around both means no shared cache (the double summary call above) and no automatic refresh after a save elsewhere on the site. It works, but it's a second data layer to maintain. A later clean up could move these calls into RTK Query endpoints, keeping the hooks' return shapes so components don't change.

5. Mistakes in the guide

  1. Photo limit is 2 MB, not 3 MB. The 3 MB is only the upload buffer. His frontend code correctly uses 2 MB.
  2. The account summary has no "domain statuses". It returns member since, domains owned, listed, volume sold and completed sales.
  3. The "where the marketplace uses it" column named files we didn't have this morning. They exist now that his commit is merged (profile-settings.service and its functions).

6. How "sign out other sessions" works

  1. This browser stays signed in because the new tokens are saved into the cookies (his code does this).
  2. Not instant on other devices. The backend keeps one refresh token per user. Other devices fail at their next refresh, but their current access token keeps working until it expires.
  3. History is safe. The wallet verification is carried into the new token.

7. Parts of the Profile page with no API

  1. Active sessions list (device, location, last active) and signing out one session. Still sample.
  2. Wallet settings: settlement network, hide other wallets, disconnect a wallet, set the primary wallet. Still sample.
  3. Sign in methods: disconnect Google, set a password for a Google or wallet only account.
  4. Notification channels (email and Telegram switches). Now in memory only, see section 3.
  5. Privacy and display preferences. Display can stay in the browser.

8. Does this help the History page?

Not really. The account summary gives all time sales totals only, with no time period and no "spent" figure. The History Summary card still needs its own summary endpoint with a period.

12. The uat build problem (26 Oct 2026)

In short: the frontend uat branch doesn't build since commit c6cda71 (26 Oct, 13:00). Two files contain leftover git stash conflict markers, and one of them lost four lines. His follow up 7302216 ("Resolved the conflict", 13:56) didn't touch those files, so uat was still broken. Our dark-mode branch had the fix.

Resolved, 26 Oct 16:37: he merged our dark-mode into uat (f92a37e); the markers are gone, the four lines are back, staging deployed (/dev/sprint1-test and /history answer 200).

What is broken, and where

  1. src/core/enum/api-endpoint.enum.ts, around line 47: conflict marker lines (<<<<<<< Updated upstream, =======, >>>>>>> Stashed changes) around the new endpoint names.
  2. src/core/redux/userProfile.ts, around line 58: the same markers around resendVerificationEmail and changePassword. The file also lost the ChangePasswordApi and ResendVerificationEmailApi imports at the top and the useResendVerificationEmailMutation and useChangePasswordMutation exports at the bottom. Change password and resend verification on the Profile page depend on them.

Fix on uat: delete the marker lines, keeping the code between them (the "Updated upstream" side is empty), then put the two imports and two exports back. Our dark-mode merge 39dc0f5 has exactly this.

How it happened: a stash popped onto another branch

  1. His changes were built on our Profile work, which lives only on dark-mode (our commit db9b41d, 16 Oct). That version has the two imports, the two hooks and the Solana endpoint line.
  2. He ran git stash, switched to uat (which never had our Profile work) and ran git stash pop.
  3. Git merged the stash onto uat with dark-mode as the base. Where he had edited next to lines uat lacks, git couldn't decide and wrote markers (the 6 errors). Where he hadn't edited, the lines were in the base but missing on uat, so git read that as "uat deleted them" and quietly dropped them (the 4 lost lines).
  4. It was committed and pushed without a build or type check.

To avoid it: after a stash pop, search for <<<<<<< and run npx tsc --noEmit before committing. Don't pop a stash made on one branch onto another; commit it on its own branch and merge.

Why staging still works

Staging (stagemarketplace.endlessdomains.io) still serves a build from before c6cda71. Checked 26 Oct: /dev/sprint1-test answers 404, while any build with c6cda71 would answer 200 (the page shows "Not available" when its switch is off). The home page and /watchlist answer 200, /profile redirects to sign in.

Staging deploys through AWS CodeDeploy (appspec.yml): copy the code, npm install, scripts/build_frontend.sh runs npm run build, and only then scripts/start_frontend.sh restarts the app with pm2. So either the deploy ran and failed at the build step (the restart never happened, the old version kept running; most likely), or staging hasn't been deployed since. The CodeDeploy history in the AWS console will say which. Until uat builds, no new change reaches staging.
