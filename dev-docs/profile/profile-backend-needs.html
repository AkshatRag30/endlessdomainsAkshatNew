Profile page: what we still need from the backend

27 Oct 2026 · Frontend branch dark-mode · Checked against backend uat at ebcc85b9 (PR #994, the profile APIs)

Where we are. The Profile and Settings page is built with all five tabs (Profile, Security, Wallets, Notifications, Preferences) and the right rail, in light and dark, on mobile, tablet and desktop. Most of it already runs on real APIs: profile fields, username, photo, verification email, change and forgot password, EVM and Solana wallet linking, the five alert switches, the account summary, and export and deletion requests.

The parts below still show sample data or are missing behaviour, because the backend has no API for them yet. For each one this report explains what it is, why users need it, what happens today, and exactly what we would need from the backend.

2. Disconnect a wallet

Remove a linked EVM or Solana wallet

Not supported

Product decision, 27 Oct 2026: not supported for now. The Disconnect button is commented out; each wallet only has Copy. Nothing is needed from the backend. The notes below are kept for if it ever comes back.

What it is

A Disconnect action on each wallet in the Connected Wallets card.

Why we need it

A user can link a wallet but can never remove one. Because the rule is one EVM wallet plus one Solana wallet per account, a user who loses a wallet, has it compromised, or simply moves to a new one is stuck: the old wallet stays on the account and there is no slot for the new one. That is a real security and support problem, not just a missing nicety.

Today

The Disconnect button is sample only. Linking is real (EVM nonce and verify, Solana signed nonce).

What we need from the backend

  • DELETE /users/wallets/:id (or by address and network) that removes the wallet from the user.
  • A rule for the last sign in method: if the wallet is how the user signs in and they have no email password or Google, refuse the request so nobody locks themselves out (Google and wallet accounts have no password to fall back on).
  • An answer on what happens to listings and pending orders tied to that wallet when it is removed.

3. Privacy settings and the public portfolio

Public portfolio and Show my sales history

Asked 27 Oct

Status, 27 Oct 2026: asked of the backend, waiting on the answer. This stays in the plan.

What it is

Two switches on the Preferences tab. Public portfolio: anyone with the link can see the user's names. Show my sales history: completed sales appear on the public profile.

Why we need it

These switches control what other people can see, so they only mean something if the backend stores them and the public portfolio API obeys them. A switch that only lives in the browser would tell the user their sales are hidden while anyone can still see them, which is worse than having no switch at all. The public portfolio is being built now, so this is the right moment to build the privacy rules into it from the start rather than add them later.

Today

No public portfolio endpoint and nowhere to store these settings. The switches are sample data. Until both pieces exist we suggest showing the card with the switches disabled and a "Coming soon" note.

What we need from the backend

  • Storage: GET, PATCH /users/privacy returning { publicPortfolio: boolean, showSalesHistory: boolean }, or the same two fields on the user response and PUT /users.
  • Defaults for new users (a product decision; our suggestion is portfolio public, sales history hidden).
  • Enforcement inside the public portfolio API: when the portfolio is off, everyone except the owner gets "private" or not found; when sales history is off, sales are left out of the response entirely. Hiding them only in the frontend is not enough, since anyone can call the API directly.
  • The public link: confirm it is based on the username (for example /u/username) and what happens to old links when a username changes.
  • The exact list of what the public page shows (listed names, unlisted names, prices, sales) so the switch descriptions match reality. Ownership on chain is public anyway, so "private" can hide our page but cannot stop a block explorer lookup; the copy should not promise more than that.

4. Notification channels

Email and Telegram switches

Not supported

Product decision, 27 Oct 2026: not supported for now. The Telegram row is commented out; the card shows Email only. Nothing is needed from the backend. The notes below are kept for if it ever comes back.

What it is

The five alert switches decide what the user hears about and already save through PATCH /users/notifications. The channel switches decide where those alerts go: email, Telegram, or both.

Why we need it

If a user turns email off, they expect to stop getting emails. Without a saved channel choice the backend never learns about it and keeps sending, which is annoying at best and a trust problem at worst.

Today

The channel switches live only in the page's memory. Turn email off, reload, and it is back on.

What we need from the backend

  • Add channels: { email: boolean, telegram: boolean } to GET and PATCH /users/notifications.
  • The notification sender respects it.
  • Confirm Telegram delivery uses the Telegram handle already saved on the profile, and what happens when that is empty.

5. Active sessions

Session list, sign out one session, real sign out of others

Not supported

Product decision, 27 Oct 2026: not supported for now. The Active Sessions card is commented out, and its Sign out everywhere else button with it. Nothing is needed from the backend. The notes below are kept for if it ever comes back.

What it is

A list on the Security tab of every device signed in to the account (device, location, last active, which one is this device), with a Sign out button per row.

Why we need it

It is how a user notices a login they do not recognise and shuts it down. Accounts here hold domains and linked wallets with real money behind them, so this is a meaningful security feature.

Today

The list is sample data. "Sign out other devices" is real (POST /auth/logout/others), but because there is one refresh token per user, other devices are only blocked at their next refresh. Their current access token keeps working until it expires, so an attacker keeps access for that window.

What we need from the backend

  • GET /auth/sessions returning [{ id, device, location, lastActive, current }].
  • DELETE /auth/sessions/:id that ends that one session immediately.
  • POST /auth/logout/others revoking other access tokens immediately, not at expiry.

6. Sign in methods

Nothing needed: Google and wallet accounts are password free

Not needed

What it is

The How You Sign In card on the Security tab lists email and password, Google and wallet sign in. It is real, read from GET /users/user-multiple-wallet.

Product decision (27 Oct 2026)

A user who signs in with Google or a wallet cannot use a password. We do not offer setting one, so no "set a password" API is needed. For the same reason Disconnect Google is dropped: with no password to fall back on, disconnecting Google would lock the user out.

What the page does

Email and password accounts get the Change Password form (real, PUT /auth/change-password). Google and wallet accounts see a note instead: "You sign in with Google or a wallet, so this account has no password. Keep using that method to sign in." The Google row has no Disconnect button.

7. Default settlement network

Which chain payouts land on

Not supported

Product decision, 27 Oct 2026: not supported for now. The whole Default Network card (settlement network and hide other wallets) is commented out. Nothing is needed from the backend. The notes below are kept for if it ever comes back.

What it is

The Default Network card on the Wallets tab lets the user choose the network their sale proceeds and payments settle on.

Why we need it

Without it the user has no say in where their money arrives, and has to find out after the fact.

Today

Sample only. The card also has a "Hide domains from other wallets" switch. Its Figma text says "Only show names held in the primary wallet above", but the design has no way to choose a primary wallet, so the backend and design need to agree on what this switch should hide before we wire it.

What we need from the backend

  • GET, PATCH /users/wallet-settings with { settlementChainId }, and the list of chains a user may pick.
  • Confirmation that payouts actually use it, otherwise the card should not exist.

8. Data requests

Cancel an open request

Not happening

Product decision, 27 Oct 2026: no cancel. A sent export or deletion request cannot be withdrawn from the page, and nothing is needed from the backend. The notes below are kept for context.

What it is

Export my data and Request account deletion in the Your Data card each send a request to the support team (POST /users/requests). The card now shows each request's status from GET /users/requests ("Requested · our team will contact you" or "Completed").

Why we need it

Once a request is sent the user cannot take it back. That matters for deletion: someone taps it by mistake, or changes their mind the next day, and today the only option is to contact support and hope the team sees it in time. For export it hardly matters.

What we need from the backend

  • One answer first: does support wait or check anything before deleting an account? If they act straight away, a cancel option becomes much more important.
  • Optional: DELETE /users/requests/:id to withdraw a request while it is open. If not, we will show "Changed your mind? Contact support to cancel." with the support contact under an open deletion request.
  • Confirm open and done are the only statuses, and whether support emails the user when a request is done.

9. Account summary by period

Totals for a chosen period

Not happening

Product decision, 27 Oct 2026: no period filter. The summary stays lifetime totals, and nothing is needed from the backend. The notes below are kept for context.

What it is

The account summary (GET /marketplacev2/orders/summary) already powers the Profile rail. The History page has a Summary card with a period choice (this month, this year).

Why we need it

Without a period the History summary can only show lifetime totals, whatever period the user picks.

What we need from the backend

  • Optional from and to (or period) on the summary, plus a total spent alongside volume sold.

10. Display preferences

Theme, currency, language, date and time format

Optional

What it is

The Display card on the Preferences tab.

Why we need it

These only affect how the page looks to the user themselves, so they work fine saved in the browser, and the theme already does. The only gain from storing them on the account is that they follow the user to another device. Nice to have, not essential.

What we need from the backend

  • Nothing, unless we decide they should follow the user. Then GET, PATCH /users/preferences with { theme, currency, language, dateFormat, timeFormat }.
