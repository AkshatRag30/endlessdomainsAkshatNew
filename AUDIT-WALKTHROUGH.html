One issue, one commit, one clear message.

A few habits that will keep this safe given how sensitive some of these are:

Rotate secrets outside of Claude Code entirely. Issues S1, S2, and S3 involve real credentials. Let it show you a diff before committing. For anything in the Critical or High rows, read the actual diff. These are small changes, so this costs you two minutes and saves you from a silent regression.

S1 — The Google OAuth secret is exposed to every browser

Critical Both

Files: .env · next.config.ts:7 · pages/_app.tsx:23

In plain words: Google gives you two different things when you set up sign-in: a client ID, which is meant to be public, and a client secret, which is meant to stay on your server and never be seen by users. Somewhere along the way, the secret got put into the variable meant for the public ID. You can tell because it starts with GOCSPX-, which is Google's marker for a secret — a real client ID always ends in .apps.googleusercontent.com.

Because this value flows through next.config.ts into the app's public env block, and then into a component that runs in the browser, that secret is sitting in plain text inside every page your users load. Anyone can open devtools and read it.

Why it matters

Whoever has this secret can potentially impersonate your app when talking to Google's OAuth servers. It also means your Google sign-in flow was probably never wired correctly in the first place, since a secret doesn't work where a client ID is expected.

How to fix it

1. Go rotate this secret in Google Cloud Console right now, outside of any coding session — treat it as already leaked, because it is.
2. Put the real client ID in a variable named NEXT_PUBLIC_GOOGLE_CLIENT_ID.
3. Keep the actual secret only on your backend — it should never be referenced in next.config.ts's public env block at all.
4. After the swap, actually click through Google sign-in once and confirm it still works.

Prompting Claude Code

Once you've rotated the secret yourself, tell Claude Code something like: "In next.config.ts and pages/_app.tsx, we're passing a Google OAuth client secret into the public env block where a client ID belongs. Replace it with NEXT_PUBLIC_GOOGLE_CLIENT_ID reading the real client ID, and make sure nothing server-side leaks into the client bundle. Show me the diff before applying."

Split: the frontend side (Claude Code's job) is removing the secret from the public env block and swapping in the real client ID. The backend side is making sure whatever server-side flow needs the actual secret — token exchange, if you use one — reads it from a server-only environment variable that never touches next.config.ts's public block. If your OAuth flow is entirely client-side today with no backend token exchange at all, that's worth a separate conversation about whether it should be.

S2 — The .env file itself is tracked in git

Critical Mostly resolved already Frontend

Files: .env · .env-cmdrc · .gitignore

In plain words: Any file tracked by git gets saved into the project's permanent history — every commit, forever, even if you delete the file tomorrow. The audit found that both .env and .env-cmdrc were tracked, and that .gitignore had no rule to stop it.

What's changed since the audit: checking the repo directly, .env is no longer tracked, and .gitignore now includes an .env* rule. .env-cmdrc, however, is still tracked — that one's still open.

Why it matters

Even after removing a file from the current commit, it's still recoverable from git history unless that history is rewritten — which is a separate, more involved conversation. The safest assumption is that every value that was ever in a tracked env file should be treated as seen and rotated.

How to fix it

Remove .env-cmdrc from tracking the same way .env already was, and add a .env.example file that lists the variable names with no real values, so new developers know what to set without any secrets living in git.

Prompting Claude Code

"`.env-cmdrc` is still tracked in git even though `.env` was already removed. Untrack it with `git rm --cached`, confirm the gitignore rule covers it, and generate a `.env.example` with the same keys as `.env-cmdrc` but blank values." Then separately, decide with your team whether the old committed values are sensitive enough to justify rewriting git history — that's worth a standalone conversation, not a quick fix.

Split: the frontend side is deleting the hardcoded key and pointing the call at a new proxy endpoint instead. The backend side is actually building that proxy endpoint, since that's where the key needs to live now. Neither half is complete without the other — the frontend change is unsafe to ship until the backend endpoint exists.

S4 — Login tokens are stored where any script on the page can read them

Critical Still present Both, backend-led

Files: src/core/services/cookies.service.ts · used in auth-component, wallet-signup, google-signup

export const setCookieValue = (key: string, value: string) => {
  setCookie(key, value) // no httpOnly, no secure, no sameSite, no expiry
}

In plain words: There are two tokens that keep a user logged in: a short-lived access token, and a long-lived refresh token that can mint new access tokens for a long time. Right now both are stored in a way that any JavaScript running on the page — including a script injected through some unrelated bug, or a compromised third-party script like the ones in S8 — can read directly.

The safe version of a cookie has a flag called httpOnly, which means JavaScript literally cannot read it, only the browser can send it along with requests. That flag is missing here.

Why it matters

If any script on the page ever misbehaves, it can walk away with the refresh token — meaning a persistent, long-lived session hijack, not just a one-time nuisance.

How to fix it

Best fix: have the backend set these cookies directly on the auth response with httpOnly; Secure; SameSite=Lax. The frontend then never touches the token values at all — it just relies on the browser to send the cookie automatically.

If the backend can't change quickly: at minimum add secure and sameSite: 'strict' when setting the cookie from the frontend, plus a short expiry on the access token.

One important guardrail: don't set the cookie's domain to cover the whole .endlessdomains.io apex to make cross-subdomain login easier. Sibling subdomains count as "same site" for cookie purposes, so a bug on any other subdomain could then steal your marketplace tokens too.

Prompting Claude Code

"cookies.service.ts sets auth cookies with no httpOnly, secure, or sameSite flags. I want to move cookie-setting to the backend response instead of the frontend calling setCookie directly — walk me through what changes on the frontend once the backend sets httpOnly cookies, and what becomes dead code here." Treat this as a two-sided change and loop in whoever owns the API before applying anything.

Split: the real fix — setting httpOnly cookies on the auth response — can only happen on the backend, since httpOnly cookies are set through server response headers, not by frontend JavaScript. Claude Code's job here is the frontend cleanup once that's live: removing the manual setCookieValue calls for tokens and letting the browser handle the cookie automatically. The interim frontend-only fix (secure + sameSite: 'strict') is a real improvement but doesn't fully close the gap on its own — flag that to whoever owns the backend as the priority conversation.

S6 — Protected pages are only guarded in the browser, and inconsistently

High Frontend

Files: src/component/ProtectedRoute.tsx · pages/profile/*

In plain words: There are two ways to check "is this user allowed to see this page." One happens on the server before anything is sent to the browser — fast, and the unauthorized content never leaves your server. The other happens in React after the page has already loaded in the browser, and just redirects away once it notices the user isn't logged in.

Right now, most of /profile/* only has the second kind. That means the page's HTML and JavaScript are sent to anyone who requests them; the redirect only happens after the page has already rendered once, for a moment.

Two pages do this correctly already — pages/register/index.tsx and pages/profile/domains/index.tsx — using a server-side cookie check. The rest of /profile/* don't. There are also two getServerSideProps functions written for exactly this purpose that are silently dead code, because Next.js only runs that function from files inside pages/, and these live in component files instead.

Why it matters

Assuming your actual API still checks permissions correctly server-side, this isn't a full break-in — but it is an unnecessary exposure and a confusing user experience (briefly seeing a page you shouldn't).

How to fix it

A single middleware.ts file at the project root, checking for the access token cookie and redirecting to login, replaces all of the scattered per-page logic in one place:

import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
import { Cookie_Key } from '@/core/enum/cookie.enum'

export function middleware(req: NextRequest) {
  if (!req.cookies.get(Cookie_Key.ACCESS_TOKEN)) {
    return NextResponse.redirect(new URL('/login', req.url))
  }
  return NextResponse.next()
}

export const config = { matcher: ['/profile/:path*'] }

Then delete the two dead getServerSideProps exports that never run.

Prompting Claude Code

"We only guard /profile/* routes client-side through ProtectedRoute.tsx, and two getServerSideProps exports in component files are dead code since Next.js ignores them outside pages/. Add a root middleware.ts that redirects unauthenticated requests to /profile/* before they render, matching the pattern already used correctly in pages/register/index.tsx. Then remove the dead exports." This is a well-contained, single-purpose change — good first real fix to try.

This entire fix lives in the frontend repo — middleware.ts is a Next.js concept, no backend change needed. The one assumption worth double-checking with whoever owns the API is that it still enforces its own authorization independently of this cookie check — the middleware stops the page from rendering, but it shouldn't be the only thing standing between a request and the data it returns.

S7 — The "log back in automatically" flow can loop forever or crash

High Both

File: src/core/services/error.service.ts:38-52

In plain words: When a request fails because your session expired, the app is supposed to quietly fetch a new access token using the refresh token, then retry the original request so the user never notices. Two things are missing: nothing stops the app from retrying endlessly if the refresh call itself keeps failing, and nothing checks that the refresh response actually has the shape it expects before reading a field off it — so a failed refresh can throw a confusing crash instead of a clean "please log in again."

There's a deeper problem underneath this one: the URL this refresh call hits is built from environment variables that are never actually defined anywhere (see P11), so the URL literally comes out as undefined/undefined/undefined/.... This flow has likely never worked at all.

Why it matters

Right now users probably just get logged out when their session expires, rather than experiencing an infinite loop — but only because the URL is broken. Fixing P11 without also fixing this could introduce the loop for the first time.

How to fix it

Fix the URL problem in P11 first. Then add a flag so a refresh is only attempted once per failed request, validate that the response actually contains what you expect before reading it, and if it doesn't, send the user to a clean logout instead of letting an error bubble up.

Prompting Claude Code

"Once P11's env vars are fixed, error.service.ts's 401 refresh-and-retry logic needs a single-retry guard and a shape check on the refresh response before touching .accessToken. Walk me through the current flow first, then propose the fix." Sequence this strictly after P11 — fixing it first would just move where things break.

Split: the retry guard and response validation are entirely frontend work, Claude Code can do this alone. But it only matters once the refresh endpoint itself is reachable — that depends on P11's env vars (frontend) resolving to a real URL, and on the backend's refresh endpoint actually returning the shape the frontend expects. If the refresh endpoint has never been hit successfully, it's worth confirming with the backend team what a real response from it looks like before writing the validation logic.

S8 — Outside scripts are loaded with no safety pin

High Frontend

File: src/template/layout/index.tsx:114-119

In plain words: The site loads jQuery, Font Awesome, and Chart.js straight from third-party CDNs. Each of these is a full script that runs with full access to your page, the same as your own code. There's a browser feature called Subresource Integrity that lets you say "only run this file if it matches this exact fingerprint" — none of these scripts have it. One of them, Chart.js, isn't even pinned to a version, so the exact code it loads can change without any deploy on your side.

Why it matters

If any of those CDNs is ever compromised, or that unpinned Chart.js URL starts serving something different, it runs with the same trust as your own code — on a site where users sign real wallet transactions.

How to fix it

Best option: install these as normal npm packages so they're versioned and reviewed like everything else in your dependency tree. If any must stay on a CDN, pin an exact version and add the integrity and crossorigin attributes. Chart.js specifically looks removable outright since you already use Recharts elsewhere (see P6).

Prompting Claude Code

"layout/index.tsx loads jQuery, Font Awesome, and Chart.js from CDNs with no integrity attribute and Chart.js has no version pin at all. Check whether Chart.js is used anywhere real or if Recharts already covers it, then propose replacing these CDN tags with npm installs or pinned+integrity CDN tags." Good to pair with S9 since they touch the same file.

S10 — No basic security headers are set at all

High Frontend

File: next.config.ts — no headers() function exists

In plain words: There's a small set of response headers that tell the browser things like "don't let this page be embedded inside another site's frame" and "don't guess file types, trust what the server says." None of them are set right now.

The framing one matters specifically here: users sign wallet transactions on this site. A convincing lookalike page that frames your buy flow inside an invisible iframe — a classic clickjacking setup — would be dangerous precisely because the transaction looks legitimate to the user.

Why it matters

These headers cost nothing to add and close off a real, well-known attack category.

How to fix it

This is close to a five-minute, zero-risk change:

async headers() {
  return [{
    source: '/:path*',
    headers: [
      { key: 'X-Content-Type-Options', value: 'nosniff' },
      { key: 'X-Frame-Options', value: 'SAMEORIGIN' },
      { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
      { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
    ],
  }]
}

A stricter Content-Security-Policy is worth doing too, but needs more testing given the CDN scripts and wallet SDKs in play — start it in report-only mode rather than enforcing mode.

Prompting Claude Code

"Add a headers() function to next.config.ts setting X-Content-Type-Options, X-Frame-Options, Referrer-Policy, and Permissions-Policy across all routes." This one is safe enough to just ask for directly — low risk, well-defined, good first change to build confidence with.

Fully doable in the frontend repo through next.config.ts. If you're sitting behind a CDN or reverse proxy in front of Next.js, that's a second, optional place these headers could also be set at the infra layer — but it's not required if next.config.ts handles it.

E1 — Every page can serve just "Loading..." to anyone who isn't already logged in

Critical Partially patched Frontend

File: src/component/AppContent.tsx:7

In plain words: Next.js can render a page in two places: once on the server, before it's ever sent to the browser, and then again in the browser once React "wakes up." Search engines mostly rely on getting real, meaningful HTML from that first server render.

The app tracks whether a user is logged in using a value that starts out as null and only gets set to something real inside a useEffect — and effects never run on the server. So on the very first server render, for every page, that value is still null, and the code responds by throwing away the entire page and rendering just <p>Loading...</p> instead. No title, no headings, no content — for anyone, including search engine crawlers, on the very first paint.

There were originally three separate places doing a version of this: AppContent.tsx, ProtectedRoute.tsx, and a manual isClient check wrapping the entire body of pages/index.tsx.

What's changed since the audit: looking at the current file, AppContent.tsx now has an escape hatch — isAlwaysRenderableRoute(ROUTER.pathname) — that skips the loading gate for certain routes. That's real progress, but it means the fix is route-by-route rather than structural: any route not on that exempt list still gets blanked out on first render. The underlying pattern (waiting on a client-only effect before rendering anything) is still there.

Why it matters

Google does execute JavaScript eventually, so you're not completely invisible to it — but JavaScript-rendered indexing is slower and less reliable than getting real HTML immediately. Every other crawler — Bing, link-preview bots for social platforms, AI crawlers — typically doesn't wait around the way Google sometimes does, and sees nothing but "Loading...".

How to fix it properly

The durable fix is to read the authentication cookie during server-side rendering, so authenticated has a real value the very first time the page renders — never null. Then the page itself should always render its real content; only small, auth-dependent widgets inside the page (like a "welcome back" banner) should have their own tiny loading state, not the entire page tree.

Prompting Claude Code

"AppContent.tsx currently only renders real content for routes in isAlwaysRenderableRoute, and blanks every other route to just Loading... until a client-side effect resolves authenticated. I want to fix this at the root instead of exempting more routes one at a time — read the auth cookie during SSR so authenticated has a real value on the first render everywhere, then remove the route exemption list entirely since it becomes unnecessary. Show me the plan before changing anything." This is the single highest-value fix in the whole list — worth a focused session on its own, not squeezed in alongside something else.

Entirely a frontend fix — reading a cookie during getServerSideProps and deciding what to render is all Next.js code in this repo. No backend change is required, since the access token cookie already exists; the frontend just needs to check for it earlier, on the server, instead of waiting for a client effect.

E2 — There's no robots.txt and no sitemap

Critical Still missing Frontend

In plain words: Confirmed directly — neither file exists in public/. A robots.txt tells crawlers what they're allowed to look at, and a sitemap is essentially a list of every page you want indexed. Without either, search engines have to discover your pages by accident, through links, rather than being handed a clear map — and your domain listing and seller portfolio pages, which are the pages that actually matter for organic traffic, have no discovery path at all.

Worth noting: a robots.txt living on your main apex domain doesn't cover this marketplace subdomain — each host needs its own.

How to fix it

Add a public/robots.txt pointing at https://marketplace.endlessdomains.io/sitemap.xml, generate an actual sitemap (a library like next-sitemap, or a dynamic route, both work) including your seller portfolio and domain detail pages, and register this subdomain as its own property in Google Search Console.

Prompting Claude Code

"There's no robots.txt or sitemap anywhere in this project. Add a public/robots.txt pointing at our sitemap, and set up next-sitemap (or a dynamic sitemap route) that includes /seller-portfolio/[slug] pages and domain detail pages." Straightforward, low-risk, high-value — good candidate to do right after E1.

The robots.txt and sitemap files themselves are frontend work. Registering the property in Google Search Console isn't a code change at all — it's an account-level step, usually done by whoever manages your marketing or SEO tooling, and can happen independently of the code fix.

E3 — There's no _document.tsx file

P3 — 22 megabytes of font files, almost none of it needed

P11 — The app may be pointed at the staging API, and several endpoints resolve to literally nothing
