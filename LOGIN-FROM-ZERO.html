Login, from absolute zero

A complete walkthrough of how POST /api/v1/auth/login works in the Endless Domains backend. Every keyword is explained, every line is annotated, and at the end you build the same thing yourself, file by file.

0. How to use this guide

Do not try to read this in one sitting. Read section 1 to get the shape of the whole thing, then keep section 2 open as a dictionary whenever a word confuses you. Section 4 is the main event: open each real file in VS Code next to this page and follow along line by line. Section 7 is where the learning actually locks in, because you will type the whole thing yourself in a fresh project.

All real file paths are relative to D:\Akshat Endless\backend\backend\. When you see a code block with a grey path above it, that is the real file it was copied from. Some long files are trimmed, and trimmed parts are marked with // ....

You already know more than you thinkAs a frontend developer you have already called this endpoint with fetch or axios, stored a token, and sent it in a header. This guide is simply the other side of that same conversation.

1. The big picture

Think of the backend as a hotel reception desk. A guest walks up and hands over an ID card (email and password). The receptionist looks the guest up in the register (the database). If the guest exists, is not banned, has confirmed their booking (verified email), and the ID matches, the receptionist hands over two keycards. One opens the room but stops working after a short time (the access token). The other is only for going back to reception to get a fresh room card (the refresh token). From that point on, the guest never shows their ID again; they just tap the room card.

The four layers

Almost every feature in this backend, login included, is split into the same four layers. Each layer has exactly one job, and each one only talks to the layer directly beneath it.

ControllerReceives the HTTP request, hands the body to the service, wraps the answer. No thinking.
ServiceAll the business rules: is the user blocked, is the password right, make tokens.
RepositoryThe only place that talks to the database. Runs queries, returns rows.
EntityA TypeScript class that describes one database table and its columns.

The full journey in one picture

Browser sends POST /api/v1/auth/login with email, password, source
↓
main.ts setup CORS check, JSON body parsing, security headers, global validation pipe
↓
LogInDto rules check the body. Bad body means a 400 error and the journey ends here.
↓
AuthController.login() passes the DTO to the service
↓
AuthService.login() normalize email, find user, check deleted, blocked, verified, compare password, create tokens, save hashed refresh token, fire background events
↓
UserService and UserRepo run the actual SQL against tbl_user in PostgreSQL
↓
Response { message: "Login Success", result: { user, accessToken, refreshToken } } goes back with status 201

2. Every word you need

This is the dictionary. Skim it once now, then come back whenever a word in section 4 feels fuzzy.

Web words

Server
A program that runs forever, waits for requests, and answers them. Our server is a Node.js program started by npm run start:dev. It listens on a port (a numbered door on the machine, for example 3001).
HTTP request
A message from a client to a server. It has a method (GET, POST, PUT, DELETE), a URL (which resource), headers (extra info like Authorization or Content-Type), and optionally a body (the data, usually JSON).
HTTP response
The server's answer. It has a status code (a number saying how it went), headers, and a body.
Status codes
200 OK. 201 Created (NestJS uses this by default for every POST, which is why login returns 201). 400 Bad Request, the client sent something invalid. 401 Unauthorized, you are not who you claim, or not logged in. 403 Forbidden, you are known but not allowed. 404 Not Found. 500 Internal Server Error, the server itself crashed.
Endpoint / route
One method plus one URL that the server knows how to handle, for example POST /api/v1/auth/login. GET /api/v1/auth/login would be a different endpoint (and does not exist).
JSON
JavaScript Object Notation. Text that looks like a JS object: {"email":"a@b.com"}. The request body arrives as plain text and has to be parsed into a real object.
Middleware
A function that runs on every request before your route code. It can inspect, modify, or reject the request. CORS, body parsing, and Helmet are all middleware.
CORS
Cross Origin Resource Sharing. Browsers block a page on siteA.com from reading responses from siteB.com unless siteB explicitly allows siteA. Our backend keeps a list of allowed frontend origins.
Header Authorization: Bearer <token>
The standard way to send a token. "Bearer" means "whoever bears (carries) this token is allowed in".
Express
The low level Node.js web framework that NestJS runs on top of. NestJS adds structure; Express does the actual HTTP handling underneath.

TypeScript words

class
A blueprint for objects. class LogInDto { email: string } describes the shape of a login body.
interface
A type only description, a contract. It disappears when TypeScript compiles to JavaScript, so it cannot be used at runtime. That detail matters later (section 5).
public / private / readonly
public means anyone can access it. private means only code inside the class can. readonly means it can be set once and never reassigned.
constructor
The special method that runs when an object is created. In NestJS, constructor parameters are how a class asks for its dependencies.
async / await / Promise
Anything slow (database, network, hashing) returns a Promise, a placeholder for a value that arrives later. await pauses this function until the value arrives, without freezing the whole server. A function using await must be marked async, and it automatically returns a Promise. Promise<Response> means "a Promise that will eventually hold a Response".
Promise.all([a, b])
Start both slow things at once and wait until both are done. Faster than awaiting one after the other.
Generic <T>
A type parameter. BaseAbstractRepository<User> means "the base repository, but working with User objects". Same idea as useState<string>() in React.
Decorator @Something()
A function that attaches extra information (metadata) to a class, method, property, or parameter. Decorators do not run your logic; they label things so a framework can find them later. @Post('login') labels a method as "handler for POST login". This is the single most important idea in NestJS.
enum
A fixed named set of values. AuthSuccessMessage.LOG_IN_SUCCESS is just the string 'Login Success' with a safe name.
throw
Stop the current function immediately and send an error up to whoever called it. If nobody catches it, NestJS does, and turns it into an HTTP error response.
Spread ...
{ ...payload, refreshToken } copies every property of payload into a new object and adds refreshToken.

NestJS words

Module @Module()
A box that groups related code. It declares its controllers, its providers (services, repos, strategies), what it imports from other modules, and what it exports for other modules to use. AuthModule is the box for everything auth.
Controller @Controller('auth')
A class whose methods handle HTTP routes. The string is the URL prefix for every route in it.
Route decorators @Get @Post @Put @Delete
Mark a method as the handler for that HTTP method on that path.
Parameter decorators @Body() @Query() @Param() @Req()
Tell NestJS what to pass into a parameter: the JSON body, the ?a=b query string, a :id URL piece, or the whole raw request.
Provider / @Injectable()
Any class that NestJS can create and hand to other classes. Services, repositories, strategies are providers. @Injectable() marks a class as something NestJS is allowed to construct.
Dependency Injection (DI)
Instead of a class doing new UserService() itself, it lists what it needs in its constructor and NestJS supplies it. NestJS creates one shared instance (a singleton) of each provider and reuses it everywhere. Benefits: classes stay loosely connected, and in tests you can swap in fakes.
Injection token @Inject('AuthServiceInterface')
The name a provider is registered under. This codebase registers services under string names (tokens) instead of using the class directly. The module says "the token 'AuthServiceInterface' should be filled with the class AuthService".
Pipe
Code that runs on incoming parameters before the handler, to validate or transform them. ValidationPipe checks DTOs.
Guard @UseGuards()
Code that decides "is this request allowed to reach the handler at all?" Returns yes or no. Used for authentication.
Exception classes
BadRequestException (400), UnauthorizedException (401), ForbiddenException (403), NotFoundException (404), InternalServerErrorException (500). Throw one and NestJS sends that status with your message.
DTO (Data Transfer Object)
A class that describes the shape of data coming in or going out. With class validator decorators on it, it doubles as validation rules.
ConfigService
A NestJS service for reading configuration values such as secrets. this.configService.get('JWT_ACCESS_TOKEN_SECRET').
EventEmitter2 / @OnEvent()
A publish and subscribe system. emit('name', data) announces something happened. Any method decorated with @OnEvent('name') runs in response. The emitter does not wait for the listeners.
Passport / Strategy
Passport is a popular Node library for authentication. A strategy is one way of authenticating (JWT, Google, and so on). NestJS wraps it with PassportStrategy and AuthGuard.

Database words

PostgreSQL
The database. Data lives in tables (like spreadsheets): columns are fields, rows are records. Users live in tbl_user.
SQL
The language for talking to the database: SELECT * FROM tbl_user WHERE email = 'x' LIMIT 1.
ORM / TypeORM
Object Relational Mapper. Lets you work with TypeScript objects and it writes the SQL for you. repo.findOne({ where: { email } }) becomes the SELECT above.
Entity @Entity()
A class that maps to a table. Each @Column() property is a column.
Repository (TypeORM)
An object TypeORM gives you for one entity, with methods like find, findOne, save, update, delete.
Repository (this codebase)
A wrapper class like UserRepo that holds the TypeORM repository and adds named query methods like findByEmail. Two different things share the word, which confuses everyone at first.
UUID
A long random id like 3f2b...9c1e. Every row's id here is a UUID, not 1, 2, 3.
Index
A lookup structure that makes searching a column fast, like a book index. tbl_user has an index on email so login lookups stay quick.
Unique constraint
The database refuses two rows with the same value in that column. Email is unique, so duplicate signups fail at the database level.

Security words

Hashing
A one way scramble. hash("mypassword123") gives $2b$10$Xk9.... You cannot turn the hash back into the password. To check a password, you hash the attempt the same way and compare.
Salt
Random data mixed in before hashing, so two users with the same password get different hashes. bcrypt stores the salt inside the hash string, so you never handle it yourself.
bcrypt
A deliberately slow password hashing algorithm. Slow is good: it makes guessing millions of passwords expensive for an attacker. The 10 in bcrypt.hash(pw, 10) is the "cost" (2 to the power 10 rounds).
argon2
A newer, stronger hashing algorithm. This codebase uses it for hashing refresh tokens.
JWT (JSON Web Token)
A string in three parts separated by dots: header.payload.signature. The header and payload are just base64 encoded JSON, readable by anyone (paste one into jwt.io). The signature is computed from the header, payload, and a secret key. If anyone edits the payload, the signature no longer matches and the server rejects it.
Payload / claims
The data inside the JWT. Here it is { userId, iat, exp }: who the user is, issued at, expires at.
Secret
The key used to sign and verify JWTs. If it leaks, anyone can forge tokens. Stored in AWS Secrets Manager, never in code.
Access token
Short lived JWT sent with every protected request.
Refresh token
Longer lived JWT used only to get a new access token. Its hash is stored in the database so the server can revoke it.
Stateless authentication
The server does not need to look anything up to trust an access token; the signature proves it. That is why JWTs are fast, and also why you cannot easily "cancel" one before it expires.

4. The journey, line by line

Step 0: The frontend sends the request

Somewhere in the frontend, a login form does something like this:

const res = await axios.post(`${API}/api/v1/auth/login`, {
  email: 'Akshat.Rag@gmail.com',
  password: 'mypassword123',
  source: 'marketplace',
});

What actually travels over the network is plain text:

POST /api/v1/auth/login HTTP/1.1
Host: api.endlessdomains.io
Origin: https://marketplace.endlessdomains.io
Content-Type: application/json

{"email":"Akshat.Rag@gmail.com","password":"mypassword123","source":"marketplace"}

Every line matters. POST is the method. /api/v1/auth/login is the path. Origin is the website the browser is on, which CORS checks. Content-Type: application/json tells the server how to parse the body. The final line is the body.

Step 1: main.ts prepares every request

main.ts is the first file that runs when the server starts. It builds the app and attaches the middleware every request will pass through.

src/main.ts (trimmed) 
const app = await NestFactory.create(AppModule);       // build the whole app from the root module
app.enableCors({ origin: (origin, callback) => { /* allow list check */ }, credentials: true });
app.setGlobalPrefix('api/v1');                             // every route now starts with /api/v1
app.use(bodyParser.json({ limit: '50mb' }));                // turn JSON text into req.body object
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
app.use(helmet());                                           // add security headers to every response
app.use(cookieParser());
// ...
await app.listen(PORT);                                      // open the door and start waiting
PieceMeaning
NestFactory.create(AppModule)Read AppModule, follow all its imports (including AuthModule), create every provider, register every controller route.
enableCorsIf the Origin header is not on the allow list, reject. That is why calling the API from a random site fails in the browser.
setGlobalPrefix('api/v1')Prepends /api/v1 to every route. The v1 lets the team release a v2 later without breaking old clients.
bodyParser.jsonWithout this, req.body would be undefined. It reads the raw text and runs JSON.parse on it.
whitelist: trueRemove any body property that the DTO does not declare. A sneaky "isAdmin": true is dropped silently.
transform: trueTurn the plain body object into a real instance of the DTO class, and convert types where possible (string "5" to number 5 for query params).
helmet()Adds headers that make browsers stricter, protecting against some common attacks.
listen(PORT)The server is now running and waiting for requests.

Step 2: NestJS finds the right method

When the server started, NestJS scanned every controller and built a routing table from the decorators. For login it combined three pieces of text:

'api/v1' (global prefix) + 'auth' (from @Controller('auth')) + 'login' (from @Post('login')) = POST /api/v1/auth/login → AuthController.login()

So when our request arrives, NestJS looks up the table, finds a match, and knows exactly which method to call.

If someone sends {"email":"notanemail","password":"123"}, the ValidationPipe stops the request and NestJS replies automatically:

{
  "statusCode": 400,
  "message": ["email must be an email", "password must be longer than or equal to 8 characters", "source should not be empty", "source must be a string"],
  "error": "Bad Request"
}
Key takeawayYou never write if (!body.email) throw ... by hand in NestJS. Put the rules on the DTO and the pipe enforces them before your code runs.

Step 5: The service does the real work

This is the heart of login. Here is the whole method, then we take it apart in pieces.

src/components/auth/auth.service.ts (lines 93 to 139) 
async login(logInDto: LogInDto): Promise<ReturnLoginDto> {
    const logger = new Logger(AuthService.name + '-login');
    const normalizedEmail = normalizeEmail(logInDto.email);
    const user = await this.userService.getByEmail(normalizedEmail);
    if (!user) {
        logger.error(UserErrorMessage.USER_DOES_NOT_EXIST + '-' + logInDto.email);
        throw new UnauthorizedException(UserErrorMessage.INVALID_ATTEMPT);
    }
    if (user.isDeleted) {
        throw new UnauthorizedException('Your account has been deleted. Please contact support for assistance.');
    }
    if (user.isBlocked) {
        throw new UnauthorizedException('Your account has been blocked. Please contact support for assistance.');
    }
    const passwordFromDB = await this.userService.getPasswordByUserId(user.id);
    if (!passwordFromDB) {
        logger.error(UserErrorMessage.USER_DOES_NOT_EXIST + '-' + logInDto.email);
        throw new ForbiddenException(UserErrorMessage.INVALID_ATTEMPT);
    }
    if (!user.isEmailVerified) {
        logger.error(UserErrorMessage.EMAIL_NOT_VERIFIED_YET + '-' + logInDto.email);
        throw new BadRequestException(UserErrorMessage.EMAIL_NOT_VERIFIED_YET);
    }
    await this.userService.updateTheUserSource(user.id, logInDto.source);
    await this.verifyPassword(logInDto.password, passwordFromDB);
    const returnLoginDto = new ReturnLoginDto();
    returnLoginDto.user = user;
    const tokens = await this.getTokens(user.id);
    returnLoginDto.accessToken = tokens.accessToken;
    await this.userService.setCurrentRefreshToken(tokens.refreshToken, user.id);
    returnLoginDto.refreshToken = tokens.refreshToken;
    this.eventEmitter.emit(`userlogin.UpdateDomainDetailTable`, new UpdateDomainDetailTableAfterLoginEvent(user.id));
    this.eventEmitter.emit('reputation.login', { userId: user.id });
    return returnLoginDto;
}

5aThe service's constructor

Before login can use this.userService or this.jwtService, those have to be injected. The constructor of AuthService asks for them:

Only the project's own interface based services need string tokens. The secrets are read once at startup and kept in private fields.

5cNormalizing the email

const normalizedEmail = normalizeEmail(logInDto.email);
src/@core/utils/email-normalizer.util.ts 
export function normalizeEmail(email: string): string {
    if (!email) return '';
    const trimEmail = email.trim().toLowerCase();
    const emailParts = trimEmail.split('@');
    if (emailParts.length !== 2) return trimEmail;
    let [localPart, domain] = emailParts;
    if (domain === 'gmail.com' || domain === 'googlemail.com') {
        localPart = localPart.replace(/\./g, '');         // remove all dots
        const plusIndex = localPart.indexOf('+');
        if (plusIndex > -1) localPart = localPart.substring(0, plusIndex);  // cut "+anything"
        domain = 'gmail.com';
    }
    return `${localPart}@${domain}`;
}

Gmail delivers Akshat.Rag+promo@gmail.com and akshatrag@gmail.com to the same inbox. Without normalization, one person could create many accounts (handy for abusing coupons or affiliate rewards). So " Akshat.Rag+promo@Gmail.com " becomes "akshatrag@gmail.com", exactly matching what was stored at registration. This is a pure function: same input, same output, no database, no side effects. Those are the easiest kind of code to test.

5dFinding the user

const user = await this.userService.getByEmail(normalizedEmail);
src/components/user/user.service.ts (line 153) 
async getByEmail(email: string): Promise<ReturnUserDto> {
    const user = await this.userRepo.findByEmail(email);
    if (user) {
        return await this.toReturnUserDto(user);
    }
    throw new UnauthorizedException(UserErrorMessage.INVALID_ATTEMPT);
}

Notice AuthService does not talk to the database. It asks the user service, because users belong to the user module. Each module owns its own data. The user service then asks its repository (step 6), and if a row comes back, converts it with toReturnUserDto, a function that copies safe fields (id, email, name, flags) into a new object and deliberately leaves out password and currentHashedRefreshToken. If no row comes back, it throws a 401 with the message 'Invalid User Name or Password'.

5eChecking the account state

if (user.isDeleted) throw new UnauthorizedException('Your account has been deleted...');
if (user.isBlocked) throw new UnauthorizedException('Your account has been blocked...');

These are guard clauses: check for a bad condition early and exit immediately. This keeps the happy path flat instead of nested in many if/else blocks. isDeleted comes from the shared base entity (soft delete: the row stays but is marked deleted). isBlocked is set by admins.

5fFetching the password hash separately

const passwordFromDB = await this.userService.getPasswordByUserId(user.id);
src/components/user/user.service.ts (line 195) 
async getPasswordByUserId(userId: string): Promise<string> {
    return await (await this.userRepo.findOneById(userId)).password;
}

Since the safe user object has no password, the service fetches the full row again by id and returns only the password hash. Two queries instead of one, but the hash never ends up in an object that might be sent to the browser. If the hash is missing (a user who signed up with Google or a wallet has no password), login refuses with 403.

5gEmail must be verified

if (!user.isEmailVerified) throw new BadRequestException(UserErrorMessage.EMAIL_NOT_VERIFIED_YET);

After registering, users get an email with a link. Clicking it sets isEmailVerified = true. Until then, login returns 400 with 'Email Not Verified Yet', and the frontend can show a "resend verification" button.

5hRecording which site they came from

src/components/user/user.service.ts (line 394) 
async updateTheUserSource(userId: string, source: string): Promise<void> {
    const user = await this.userRepo.findOneById(userId);
    if (!user) throw new NotFoundException(UserErrorMessage.USER_DOES_NOT_EXIST);
    if (source === 'main_site') user.isMainSiteUser = true;
    if (source === 'marketplace') user.isMarketplceUser = true;
    await this.userRepo.save(user);
}

The same accounts work on the main site and the marketplace. This flips a flag so the team knows which product each user has used. save(user) writes the changed row back to the database (an UPDATE). Note this runs before the password check; see section 8.

private async verifyPassword(plainTextPassword: string, hashedPassword: string): Promise<void> {
    const isPasswordMatching = await bcrypt.compare(plainTextPassword, hashedPassword);
    if (!isPasswordMatching) {
        throw new UnauthorizedException(UserErrorMessage.INVALID_ATTEMPT);
    }
}

The database holds something like $2b$10$N9qo8uLOickgx2ZMRZoMye..., never the real password. That string contains the algorithm (2b), the cost (10), the salt, and the hash. bcrypt.compare pulls the salt out, hashes the typed password with it, and checks if the results are identical. It returns true or false; it never "decrypts" anything.

The error message is 'Invalid User Name or Password' on purpose. If it said "wrong password", an attacker would learn that the email exists, which helps them target accounts. That idea is called avoiding user enumeration.

private means only code inside AuthService can call this. It is a helper, not part of the public API of the service.

The refresh token is hashed with argon2 before storing, for the same reason passwords are hashed: if the database leaks, the attacker cannot use what they find. Only one hash is stored per user, so logging in on a second device replaces it, and the first device's refresh token stops working.

5. How the pieces get wired together

The most magical feeling part of NestJS is that nobody writes new AuthService(...). Here is exactly how it happens.

src/components/auth/auth.module.ts (trimmed) 
@Module({
    imports: [JwtModule.register({}), ConfigModule, UserModule, EventEmitterModule.forRoot(), /* ... */],
    providers: [
        { provide: 'AuthServiceInterface', useClass: AuthService },
        AccessTokenStrategy,
        RefreshTokenStrategy
    ],
    controllers: [AuthController],
    exports: [
        { provide: 'AuthServiceInterface', useClass: AuthService }
    ]
})
export class AuthModule { }
KeyMeaning
importsOther modules whose exported providers this module wants. Importing UserModule is why AuthService can inject 'UserServiceInterface'. JwtModule provides JwtService.
providersThings this module can create. { provide: 'AuthServiceInterface', useClass: AuthService } means "when someone asks for the token 'AuthServiceInterface', build an AuthService". Listing a bare class like AccessTokenStrategy is shorthand for { provide: AccessTokenStrategy, useClass: AccessTokenStrategy }.
controllersControllers to scan for routes.
exportsProviders other modules may use if they import AuthModule.

Why string tokens like 'AuthServiceInterface'?

The controller wants to depend on the interface, not the concrete class, so the class could be swapped (for example, a fake in tests). But TypeScript interfaces vanish at runtime, so NestJS cannot use an interface as a key. The workaround is a string name. The interface gives you types in the editor, and the string gives NestJS a runtime key. That is the whole reason this pattern exists.

The order NestJS builds things

1. AppModule imports TypeOrmModule.forRootAsync (database connection) and AuthModule.
↓
2. AuthModule imports UserModule, which has TypeOrmModule.forFeature([User]), giving a TypeORM Repository<User>.
↓
3. NestJS builds UserRepo (needs Repository<User>), then UserService (needs 'UserRepoInterface').
↓
4. Builds AuthService (needs 'UserServiceInterface', JwtService, ConfigService, ...).
↓
5. Builds AuthController (needs 'AuthServiceInterface') and registers its routes.
The error you will definitely seeNest can't resolve dependencies of the AuthService (?, JwtService, ...). The ? marks the missing one. It almost always means the module that provides it is not in imports, or the provider is not in that module's exports, or the token string has a typo.

6. After login: guards and refresh

Using the access token

The frontend stores the tokens and sends Authorization: Bearer <accessToken> with protected requests. Protected routes look like this:

@UseGuards(AccessTokenGuard)
@Get('logout')
async logout(@Req() req: Request) {
    const userId = req.user['userId'];
    // ...
}
src/@core/common/guards/access-token.guard.ts 
@Injectable()
export class AccessTokenGuard extends AuthGuard('jwt') {}
src/components/auth/strategies/access-token.strategy.ts 
@Injectable()
export class AccessTokenStrategy extends PassportStrategy(Strategy, 'jwt') {
    constructor() {
        super({
            jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
            secretOrKey: process.env.JWT_ACCESS_TOKEN_SECRET
        });
    }
    validate(payload: JwtPayload): JwtPayload {
        return payload;
    }
}

The guard's name 'jwt' links it to the strategy with the same name. When the request arrives, the strategy pulls the token from the Authorization header, verifies the signature with the access secret and checks exp. If anything fails, the response is 401 and the handler never runs. If it passes, validate runs, and whatever it returns is placed on req.user. That is how every protected handler knows who is calling, with zero database lookups.

Refreshing

When the access token expires, the frontend calls GET /api/v1/auth/refresh-token with the refresh token in the header. That route uses RefreshTokenGuard and the 'jwt-refresh' strategy, which verifies with the refresh secret and also attaches the raw token to req.user. Then:

src/components/auth/auth.service.ts 
async refreshTokens(userId: string, refreshToken: string, ...): Promise<TokenResponseDto> {
    const refreshTokenFromDB = await this.userService.getHashedRefreshTokenByUserId(userId);
    if (!refreshTokenFromDB) throw new UnauthorizedException('Access Denied');
    const refreshTokenMatches = await verifyHash(refreshTokenFromDB, refreshToken);
    if (!refreshTokenMatches) throw new UnauthorizedException('Access Denied');
    const tokens = await this.getTokens(userId, verifiedWalletInfo);
    await this.userService.setCurrentRefreshToken(tokens.refreshToken, userId);
    return new TokenResponseDto(tokens.accessToken, tokens.refreshToken);
}

A valid signature is not enough here; the token must also match the hash stored in the database. That is what makes logout work: logout sets the stored hash to null, so the old refresh token is dead even though its signature is still valid. Each refresh issues a new pair and stores the new hash, which is called token rotation.

9The auth service

src/auth/auth.service.ts 
import { BadRequestException, Injectable, UnauthorizedException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcrypt';
import { UsersService } from '../users/users.service';
import { LoginDto } from './dto/login.dto';

@Injectable()
export class AuthService {
  constructor(
    private readonly usersService: UsersService,
    private readonly jwtService: JwtService,
    private readonly config: ConfigService,
  ) {}

  async register(email: string, password: string) {
    const existing = await this.usersService.findByEmail(email.trim().toLowerCase());
    if (existing) throw new BadRequestException('User already exists');
    const user = await this.usersService.create(email.trim().toLowerCase(), password);
    return { id: user.id, email: user.email };
  }

  async login(dto: LoginDto) {
    // 1. normalize
    const email = dto.email.trim().toLowerCase();

    // 2. find user, same vague message for every failure
    const user = await this.usersService.findByEmail(email);
    if (!user || !user.password) throw new UnauthorizedException('Invalid email or password');

    // 3. compare password FIRST, before revealing anything about the account
    const ok = await bcrypt.compare(dto.password, user.password);
    if (!ok) throw new UnauthorizedException('Invalid email or password');

    // 4. account state
    if (user.isDeleted) throw new UnauthorizedException('Account deleted');
    if (user.isBlocked) throw new UnauthorizedException('Account blocked');
    if (!user.isEmailVerified) throw new BadRequestException('Email not verified');

    // 5. tokens
    const tokens = await this.getTokens(user.id);
    await this.usersService.setRefreshToken(user.id, tokens.refreshToken);

    // 6. return safe data only
    return { user: { id: user.id, email: user.email }, ...tokens };
  }

  async logout(userId: string) {
    await this.usersService.setRefreshToken(userId, null);
  }

  private async getTokens(userId: string) {
    const payload = { userId };
    const [accessToken, refreshToken] = await Promise.all([
      this.jwtService.signAsync(payload, {
        secret: this.config.get('JWT_ACCESS_SECRET'),
        expiresIn: this.config.get('JWT_ACCESS_EXPIRES'),
      }),
      this.jwtService.signAsync(payload, {
        secret: this.config.get('JWT_REFRESH_SECRET'),
        expiresIn: this.config.get('JWT_REFRESH_EXPIRES'),
      }),
    ]);
    return { accessToken, refreshToken };
  }
}

Compare this with the real one. The structure is the same. The differences are deliberate improvements: the password is checked before revealing whether the account is blocked or unverified (so a stranger cannot learn account state without knowing the password), and nothing is written to the database until the password is correct.

8. Quirks in the real code

Reading real code means noticing what is a little off. None of these are emergencies, but spotting them is a sign you understand the flow. Discuss them with the team before changing anything.

The if (!user) check never runsuserService.getByEmail already throws when no user is found, so the if (!user) block right after it in login is unreachable.
The source flag is written before the password checkupdateTheUserSource runs before verifyPassword, so a failed login with the wrong password still writes to the user row.
Account state is revealed before the password checkAnyone who knows an email can learn whether that account is deleted, blocked, or unverified, without knowing the password, because those checks come first and have distinct messages.
Three queries for one usergetByEmail, getPasswordByUserId, and updateTheUserSource each fetch the same row. One query could do it.
One refresh token per userLogging in on a new device invalidates the old device's refresh token. This may be intended, but be aware of it when debugging "I got logged out" reports.
success and statusCode are never setThe Response class declares them, but nothing assigns them, so they never appear in JSON. The project's CLAUDE.md says an interceptor fills them; there is none. On the frontend, rely on the HTTP status code.
expiresIn is declared but never filledReturnLoginDto.expiresIn exists but login never sets it. The frontend can decode exp from the access token instead.
