CRUD, from absolute zero

The sequel to LOGIN-FROM-ZERO.html. You now have users who can log in. Next you'll let them create, read, update and delete their own data. This is the work you'll do most often as a backend engineer.

0. Before you start

This guide builds on the login-practice project from section 7 of the login guide. You need it running, with register, login and the /auth/me route working, before you continue. If /auth/me returns your user id when you send a Bearer token, you're ready.

We'll build a domain listings feature, a tiny version of the Endless Domains marketplace. A logged in user can list a domain for sale with a price, see everyone's listings, edit their own, and remove their own. It is small enough to finish in an evening and realistic enough that every concept you'll meet at work shows up.

Same rule as beforeType everything by hand in your practice project. Keep the real backend repo open only for reading and comparing.

1. What CRUD really means

CRUD stands for Create, Read, Update, Delete, the four things you can do with stored data. Almost every feature in the Endless Domains backend is CRUD in a costume. The cart lets you add, view and remove items. Favorites lets you add, view and remove domains. Listings, coupons, watchlist and affiliate keys all follow the same pattern. Once you can build one cleanly, you can build all of them.

In a REST API, each CRUD operation maps to an HTTP method and a URL pattern. Learn this table by heart; the whole industry uses it.

OperationHTTPURLSQL underneathSuccess status
CreatePOST/listingsINSERT201 Created
Read manyGET/listings?page=1&limit=10SELECT ... LIMIT OFFSET200 OK
Read oneGET/listings/:idSELECT ... WHERE id =200 OK
UpdatePATCH/listings/:idUPDATE ... WHERE id =200 OK
DeleteDELETE/listings/:idDELETE or soft delete UPDATE200 OK (or 204 No Content)

Notice that the URL names the thing (a plural noun, listings), and the HTTP method says what to do with it. You don't write /createListing or /deleteListing. Some older routes in this backend break that rule, and that's fine to notice, but new code should follow it.

PUT versus PATCH

PUT means "replace the whole thing with what I send". If you leave out a field, it should be cleared. PATCH means "change only the fields I send". Frontends almost always want PATCH, because an edit form usually changes one or two fields. We'll use PATCH.

2. New words for this guide

The login guide's dictionary still applies. These are the new terms you'll meet here.

Resource
The "thing" an endpoint is about. Here, a listing. Each resource gets a URL.
Path parameter :id
A variable piece of the URL. In /listings/7f3a..., the id is the path parameter. Read it with @Param('id').
Query parameter ?page=2
Optional settings after the ?, used for filtering, sorting and paging. Read them with @Query(). They always arrive as strings, which matters a lot (see pagination).
Pagination
Returning a large list in small pages instead of all at once. limit is how many per page. skip (or offset) is how many rows to skip, which equals (page - 1) * limit.
Relation
A link between two tables. Each listing belongs to one user, and one user has many listings. In the database this is a foreign key column, ownerId, that holds a user's id.
Foreign key
A column whose value must exist as an id in another table. The database refuses a listing whose ownerId points to a user who doesn't exist.
@ManyToOne / @OneToMany
TypeORM decorators that describe a relation. "Many listings to one user."
Soft delete
Instead of removing a row, set isDeleted = true (or a deletedAt date) and hide it from queries. The data can be recovered and history stays intact. This backend's BaseEntity has isDeleted for exactly this.
Hard delete
Actually remove the row with DELETE. Gone for good.
Ownership / authorization
Authentication asks "who are you?" and login answers it. Authorization asks "are you allowed to do this?" For example, may this user edit this particular listing? This guide is mostly about authorization.
ParseUUIDPipe
A built in NestJS pipe that rejects a path parameter that isn't a valid UUID, before your code runs.
PartialType
A helper that takes a DTO and makes every field optional. That's perfect for an update DTO built from the create DTO.
@Type(() => Number)
A class transformer decorator that converts a value to a number before validation. Needed for query params, because they arrive as strings.
findAndCount
A TypeORM method that returns [rows, totalCount] in one call. It's what pagination needs.
Idempotent
Doing it twice has the same effect as doing it once. GET, PUT and DELETE should be idempotent; POST usually is not, because two POSTs create two rows.
Unit test / mock
A test of one class in isolation. Its dependencies are replaced with mocks, fake objects that you control.

The entity

src/components/domain/domain-favorite/enity/domain-favorite-entity.entity.ts 
@Entity({ name: 'tbl_fav_domain' })
export class DomainFavoriteEntity extends BaseEntity {
    @Column({ nullable: false }) domain_name: string;
    @Column({ nullable: false }) domain_provider: string;
    @Column({ nullable: false }) user_id: string;
    @Column({ unique: true, nullable: false }) fav_unique_identifier: string;
}

user_id is a plain string column, not a real relation. It works, but the database won't stop a favorite from pointing at a user who doesn't exist. fav_unique_identifier is domainName~provider~userId glued together with a unique constraint, a trick that stops the same user favoriting the same domain twice.

The controller

src/components/domain/domain-favorite/domain-favorite.controller.ts (trimmed) 
@Controller('domain/favorite')
export class DomainFavoriteController {
    constructor(
        @Inject('DomainFavoriteServiceInterface')

    ) {}

    @Post()

    @UseGuards(AccessTokenGuard)

        const userId = req.user['userId'];
        return new Response(DomainFavSuccessMessage.FAVORITE_DOMAIN_ADD_SUCCESSFUL,

    }

    @Delete(':favDomainId')
    @UseGuards(AccessTokenGuard)
    public async deleteFromFavDomain(@Param('favDomainId') favDomainId: string, @Req() req: Request) { /* ... */ }

    @Get()
    @UseGuards(AccessTokenGuard)
    public async getFavDomainByUser(@Req() req: Request) { /* ... */ }
}

Three ideas to notice. First, @HttpCode(HttpStatus.OK) overrides the default 201 for POST with 200. Second, every route reads req.user['userId'], which the access token guard put there, so the user id always comes from the token, never from the body. Third, @Param('favDomainId') pulls the id out of the URL.

The repository

src/components/domain/domain-favorite/domain-favorite-repo.service.ts (trimmed) 
async findAllFavoriteDomainByUserId(userId: string): Promise<DomainFavoriteEntity[]> {
    try {
        return this.favDomainRepo.find({ where: { user_id: userId } });
    } catch (e) {
        this.customLoggerService.error('error===>', e);
        throw new InternalServerErrorException('Something went wrong');
    }
}

async addIfNotExistsByUserId(favDomain: DomainFavoriteEntity): Promise<void> {
    await this.favDomainRepo.createQueryBuilder().insert().values(favDomain).orIgnore().execute();
}

async removeFavDomainByUserIdAndFavDomainId(userId: string, favDomainId: string[]): Promise<void> {
    await this.favDomainRepo.createQueryBuilder().delete()
        .where('user_id = :userId', { userId: userId })
        .andWhere('id in (:...id)', { id: favDomainId })
        .execute();
}

.orIgnore() means "if this would break the unique constraint, quietly do nothing". That makes adding a favorite safe to repeat (idempotent). The delete is a good pattern: the WHERE includes both the item id and the user id, so a user can never delete someone else's favorite even if they guess its id. :...id expands an array into IN ('a','b','c').

What favorites teaches, and what it skips

Good patterns to copyThe user id always comes from the token. The delete filters by owner. Adding a favorite twice is safe because of the unique key and orIgnore.
Things to do differentlyThere is no Update, so it's really CRD, not CRUD. The list has no pagination. Delete always says success, even when nothing matched. The try in findAllFavoriteDomainByUserId never catches anything, because return this.favDomainRepo.find(...) returns the promise without await; if the query fails, the rejection escapes the try before it can be caught (more in section 11). user_id is not a real foreign key.

Our listings feature will keep the good patterns and fix every item in that second box.

4. Design before code

Experienced engineers spend ten minutes on paper before touching code. Answer these four questions for every CRUD feature.

Question 1: What does the data look like?

ColumnTypeRules
iduuidGenerated
domainNamevarcharRequired, lowercase, like coffee.eth
pricenumeric(12,2)Required, above 0, in USD
descriptionvarchar(500)Optional
statusenumactive, paused or sold. Default active
ownerIduuid, foreign key to tbl_user.idSet from the token, never from the body
isDeletedbooleanSoft delete flag, default false
createdAt, updatedAttimestamptzAutomatic

There's also one business rule: a domain can have only one active listing at a time.

Question 2: What endpoints, and who may call them?

EndpointWhoPurpose
POST /listingsLogged inCreate a listing owned by me
GET /listingsAnyoneBrowse active listings with search, sort and pages
GET /listings/mineLogged inMy listings in every status
GET /listings/:idAnyoneOne listing's details
PATCH /listings/:idOwner onlyChange price, description or status
DELETE /listings/:idOwner onlySoft delete

Question 3: What can go wrong?

The body might be invalid (400). The user might not be logged in (401). The listing might not exist or might be deleted (404). The user might not own it (403). The domain might already have an active listing (409 Conflict). The id in the URL might not be a UUID (400). Writing these down now means you won't forget them later.

Question 4: What does each response look like?

Use the same envelope as the real backend, { message, result }. Paginated lists put the items and the paging info inside result.

5.2Entity and relation

src/listings/listing-status.enum.ts 
export enum ListingStatus {
  ACTIVE = 'active',
  PAUSED = 'paused',
  SOLD = 'sold',
}
src/listings/listing.entity.ts 
import {
  Column, CreateDateColumn, Entity, Index, JoinColumn, ManyToOne,
  PrimaryGeneratedColumn, UpdateDateColumn,
} from 'typeorm';
import { User } from '../users/user.entity';
import { ListingStatus } from './listing-status.enum';

@Entity({ name: 'tbl_listing' })
@Index(['status', 'isDeleted'])
export class Listing {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column()
  domainName: string;

  @Column({ type: 'numeric', precision: 12, scale: 2,
    transformer: { to: (v: number) => v, from: (v: string) => Number(v) } })
  price: number;

  @Column({ length: 500, nullable: true })
  description: string | null;

  @Column({ type: 'enum', enum: ListingStatus, default: ListingStatus.ACTIVE })
  status: ListingStatus;

  @Column()
  ownerId: string;

  @ManyToOne(() => User, { onDelete: 'CASCADE' })
  @JoinColumn({ name: 'ownerId' })
  owner: User;

  @Column({ default: false })
  isDeleted: boolean;

  @CreateDateColumn({ type: 'timestamptz' })
  createdAt: Date;

  @UpdateDateColumn({ type: 'timestamptz' })
  updatedAt: Date;
}
PieceMeaning
@Index(['status', 'isDeleted'])The public list always filters on these two columns, so index them together.
type: 'numeric', precision: 12, scale: 2Exact decimal with up to 12 digits, 2 after the point. Never store money as a float; 0.1 + 0.2 is not 0.3 in floating point.
transformerPostgreSQL returns numeric columns as strings ("25.00") so no precision is lost. This converts them back to a JS number on read. Fine for practice; real payment code often keeps them as strings or uses a decimal library.
type: 'enum', enum: ListingStatusThe database itself refuses any status not in the list.
@Column() ownerIdThe plain foreign key column. Handy because you can filter on it without loading the user.
@ManyToOne(() => User)"Many listings belong to one user." Creates a real foreign key constraint. The arrow function avoids import order problems between files that reference each other.
onDelete: 'CASCADE'If the user row is hard deleted, the database deletes their listings too.
@JoinColumn({ name: 'ownerId' })"Use the ownerId column I already declared as the foreign key", instead of TypeORM inventing its own column.
owner: UserLets you load the user object with the listing when you ask for it (relations: ['owner']). It is not loaded by default.
Compare with the real codeThe favorites entity uses a plain user_id string without @ManyToOne. Ours gives you a real foreign key, so the database guards your data even if your code has a bug.

5.3DTOs

You need three: one for the create body, one for the update body, and one for the list query string.

src/listings/dto/create-listing.dto.ts 
import { Transform } from 'class-transformer';
import { IsNotEmpty, IsNumber, IsOptional, IsPositive, IsString, Matches, MaxLength } from 'class-validator';

export class CreateListingDto {
  @Transform(({ value }) => (typeof value === 'string' ? value.trim().toLowerCase() : value))
  @IsString()
  @IsNotEmpty()
  @Matches(/^[a-z0-9-]+\.[a-z0-9]+$/, { message: 'domainName must look like name.tld' })
  domainName: string;

  @IsNumber({ maxDecimalPlaces: 2 })
  @IsPositive()
  price: number;

  @IsOptional()
  @IsString()
  @MaxLength(500)
  description?: string;
}
DecoratorMeaning
@Transform(...)Clean the value before validation: trim spaces, lowercase. " Coffee.ETH " becomes "coffee.eth". Works because the global pipe has transform: true.
@Matches(regex)Must match the pattern: letters, digits or dashes, then a dot, then a TLD.
@IsNumber({ maxDecimalPlaces: 2 })A real JSON number, not the string "25", with at most 2 decimals.
@IsPositive()Greater than zero.
@IsOptional()If the field is missing or null, skip the other checks for it.
@MaxLength(500)Matches the column length so the database never rejects it.

Notice what is not in this DTO: ownerId, status, id, isDeleted. The client must never control those. Because of whitelist: true, if someone sends "ownerId": "someone-else", it is stripped before your code sees it. This protection is called preventing mass assignment.

src/listings/dto/update-listing.dto.ts 
import { PartialType } from '@nestjs/mapped-types';
import { IsEnum, IsOptional } from 'class-validator';
import { CreateListingDto } from './create-listing.dto';
import { ListingStatus } from '../listing-status.enum';

export class UpdateListingDto extends PartialType(CreateListingDto) {
  @IsOptional()
  @IsEnum(ListingStatus)
  status?: ListingStatus;
}

PartialType(CreateListingDto) copies every field and its validation rules from the create DTO and makes them all optional. So you can send only { "price": 30 }, but if you send a price, it must still be a positive number. Then we add status, which you can change on update but not set on create. If you later add a field to CreateListingDto, the update DTO picks it up automatically.

src/listings/dto/list-listings-query.dto.ts 
import { Type } from 'class-transformer';
import { IsIn, IsInt, IsOptional, IsString, Max, MaxLength, Min } from 'class-validator';

export class ListListingsQueryDto {
  @IsOptional() @Type(() => Number) @IsInt() @Min(1)
  page: number = 1;

  @IsOptional() @Type(() => Number) @IsInt() @Min(1) @Max(50)
  limit: number = 10;

  @IsOptional() @IsString() @MaxLength(100)
  search?: string;

  @IsOptional() @IsIn(['newest', 'price_asc', 'price_desc'])
  sort: 'newest' | 'price_asc' | 'price_desc' = 'newest';
}

This one matters more than it looks. ?page=2 arrives as the string "2". @Type(() => Number) turns it into the number 2 so that @IsInt passes and your math works. Without it, (page - 1) * limit would still work by accident in JS, but page + 1 would give "21". = 1 and = 10 are defaults when the parameter is missing. @Max(50) stops someone asking for a million rows at once and slowing your database down. @IsIn limits sort to known values, so nobody can inject an arbitrary column name.

5.4Repository

src/listings/listings.repo.ts 
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Listing } from './listing.entity';
import { ListingStatus } from './listing-status.enum';
import { ListListingsQueryDto } from './dto/list-listings-query.dto';

@Injectable()
export class ListingsRepo {
  constructor(@InjectRepository(Listing) private readonly repo: Repository<Listing>) {}

  create(data: Partial<Listing>): Promise<Listing> {
    return this.repo.save(this.repo.create(data));
  }

  findActiveById(id: string): Promise<Listing | null> {
    return this.repo.findOne({ where: { id, isDeleted: false } });
  }

  findActiveByDomain(domainName: string): Promise<Listing | null> {
    return this.repo.findOne({ where: { domainName, status: ListingStatus.ACTIVE, isDeleted: false } });
  }

  findMine(ownerId: string): Promise<Listing[]> {
    return this.repo.find({ where: { ownerId, isDeleted: false }, order: { createdAt: 'DESC' } });
  }

  async findPublicPage(q: ListListingsQueryDto): Promise<[Listing[], number]> {
    const qb = this.repo.createQueryBuilder('l')
      .where('l.isDeleted = false')
      .andWhere('l.status = :status', { status: ListingStatus.ACTIVE });

    if (q.search) {
      qb.andWhere('l.domainName ILIKE :search', { search: `%${q.search}%` });
    }

    if (q.sort === 'price_asc') qb.orderBy('l.price', 'ASC');
    else if (q.sort === 'price_desc') qb.orderBy('l.price', 'DESC');
    else qb.orderBy('l.createdAt', 'DESC');

    return qb.skip((q.page - 1) * q.limit).take(q.limit).getManyAndCount();
  }

  async update(id: string, data: Partial<Listing>): Promise<Listing> {
    await this.repo.update({ id }, data);
    return this.repo.findOneOrFail({ where: { id } });
  }

  async softDelete(id: string): Promise<void> {
    await this.repo.update({ id }, { isDeleted: true });
  }
}
PieceMeaning
this.repo.create(data)Builds a Listing object in memory. It does not touch the database. The name is confusing; think of it as "new Listing with these fields".
this.repo.save(entity)Runs INSERT (or UPDATE if it has an existing id) and returns the row with its generated id and dates.
isDeleted: false everywhereSoft delete only works if every read filters out deleted rows. Forgetting this once leaks "deleted" data. That's why it lives in the repo, written once per method.
createQueryBuilder('l')Start building SQL by hand, with l as a short alias for the listing table.
:status, :searchParameters. TypeORM sends the values separately from the SQL text, so a search like '; DROP TABLE is treated as plain text, not code. Never glue user input into the SQL string yourself; that's how SQL injection happens.
ILIKE '%coffee%'Case insensitive "contains". % means "anything here".
.skip(...).take(...)OFFSET and LIMIT. Page 3 with limit 10 skips 20 rows and takes 10.
getManyAndCount()Runs two queries: the page of rows, and the total count ignoring skip and take. Returns [rows, total].
repo.update({ id }, data)A direct UPDATE ... SET ... WHERE id = .... It returns how many rows changed, not the row, so we fetch it again.
findOneOrFailLike findOne but throws if nothing is found.
Compare with the real codeThe real backend would make ListingsRepo extends BaseAbstractRepository<Listing> and register it under a string token like 'ListingRepoInterface'. Once yours works, try converting it to that style as an exercise; you'll understand the real codebase much better afterwards.

5.5Service

src/listings/listings.service.ts 
import { ConflictException, ForbiddenException, Injectable, NotFoundException } from '@nestjs/common';
import { ListingsRepo } from './listings.repo';
import { Listing } from './listing.entity';
import { ListingStatus } from './listing-status.enum';
import { CreateListingDto } from './dto/create-listing.dto';
import { UpdateListingDto } from './dto/update-listing.dto';
import { ListListingsQueryDto } from './dto/list-listings-query.dto';

@Injectable()
export class ListingsService {
  constructor(private readonly listingsRepo: ListingsRepo) {}

  // CREATE
  async create(dto: CreateListingDto, ownerId: string): Promise<Listing> {
    const existing = await this.listingsRepo.findActiveByDomain(dto.domainName);
    if (existing) throw new ConflictException('This domain already has an active listing');
    return this.listingsRepo.create({ ...dto, ownerId });
  }

  // READ many (public)
  async findPublic(q: ListListingsQueryDto) {
    const [items, total] = await this.listingsRepo.findPublicPage(q);
    const lastPage = Math.max(1, Math.ceil(total / q.limit));
    return {
      items,
      paginationInfo: {
        total,
        page: q.page,
        limit: q.limit,
        lastPage,
        nextPage: q.page < lastPage ? q.page + 1 : null,
        prevPage: q.page > 1 ? q.page - 1 : null,
      },
    };
  }

  // READ many (mine)
  findMine(ownerId: string): Promise<Listing[]> {
    return this.listingsRepo.findMine(ownerId);
  }

  // READ one
  async findOne(id: string): Promise<Listing> {
    const listing = await this.listingsRepo.findActiveById(id);
    if (!listing) throw new NotFoundException('Listing not found');
    return listing;
  }

  // UPDATE
  async update(id: string, dto: UpdateListingDto, userId: string): Promise<Listing> {
    const listing = await this.findOwned(id, userId);

    if (listing.status === ListingStatus.SOLD) {
      throw new ConflictException('A sold listing cannot be edited');
    }
    if (dto.status === ListingStatus.ACTIVE && listing.status !== ListingStatus.ACTIVE) {
      const other = await this.listingsRepo.findActiveByDomain(listing.domainName);
      if (other && other.id !== id) throw new ConflictException('Another active listing exists for this domain');
    }
    return this.listingsRepo.update(id, dto);
  }

  // DELETE (soft)
  async remove(id: string, userId: string): Promise<void> {
    await this.findOwned(id, userId);
    await this.listingsRepo.softDelete(id);
  }

  // shared helper: exists AND belongs to this user
  private async findOwned(id: string, userId: string): Promise<Listing> {
    const listing = await this.findOne(id);
    if (listing.ownerId !== userId) throw new ForbiddenException('You do not own this listing');
    return listing;
  }
}

Read it as a list of business rules. Each rule is one guard clause that throws. The private findOwned helper is the heart of authorization: update and delete both go through it, so the ownership rule is written once and can't be forgotten on one path. { ...dto, ownerId } copies the validated fields and adds the owner from the token, so the client never chooses the owner.

5.6Controller

src/listings/listings.controller.ts 
import {
  Body, Controller, Delete, Get, Param, ParseUUIDPipe, Patch, Post, Query, Req, UseGuards,
} from '@nestjs/common';
import { AccessTokenGuard } from '../auth/access-token.guard';
import { ListingsService } from './listings.service';
import { CreateListingDto } from './dto/create-listing.dto';
import { UpdateListingDto } from './dto/update-listing.dto';
import { ListListingsQueryDto } from './dto/list-listings-query.dto';

@Controller('listings')
export class ListingsController {
  constructor(private readonly listingsService: ListingsService) {}

  @UseGuards(AccessTokenGuard)
  @Post()
  async create(@Body() dto: CreateListingDto, @Req() req) {
    return { message: 'Listing created', result: await this.listingsService.create(dto, req.user.userId) };
  }

  @Get()
  async findPublic(@Query() query: ListListingsQueryDto) {
    return { message: 'Listings fetched', result: await this.listingsService.findPublic(query) };
  }

  @UseGuards(AccessTokenGuard)
  @Get('mine')
  async findMine(@Req() req) {
    return { message: 'My listings fetched', result: await this.listingsService.findMine(req.user.userId) };
  }

  @Get(':id')
  async findOne(@Param('id', ParseUUIDPipe) id: string) {
    return { message: 'Listing fetched', result: await this.listingsService.findOne(id) };
  }

  @UseGuards(AccessTokenGuard)
  @Patch(':id')
  async update(@Param('id', ParseUUIDPipe) id: string, @Body() dto: UpdateListingDto, @Req() req) {
    return { message: 'Listing updated', result: await this.listingsService.update(id, dto, req.user.userId) };
  }

  @UseGuards(AccessTokenGuard)
  @Delete(':id')
  async remove(@Param('id', ParseUUIDPipe) id: string, @Req() req) {
    await this.listingsService.remove(id, req.user.userId);
    return { message: 'Listing deleted', result: null };
  }
}
Route order matters@Get('mine') must come before @Get(':id'). Routes are matched top to bottom, and :id matches any text, including the word "mine". If :id came first, GET /listings/mine would be treated as "find the listing with id mine". Here ParseUUIDPipe would then fail with a confusing 400 error.

Notice that the guard is on each method rather than on the whole class, because two of the routes are public. If every route needed login, you could put @UseGuards(AccessTokenGuard) once above the class instead.

6. Each operation, deep dive

Now follow each request from start to finish, the same way the login guide did.

POST Create

Request POST /api/v1/listings, header Authorization: Bearer ..., body {"domainName":" Coffee.ETH ","price":25,"ownerId":"hacker"}
↓
Guard verifies the token and sets req.user = { userId: "u1" }. No token means 401.
↓
ValidationPipe strips ownerId (not in the DTO), transforms the name to coffee.eth, checks the regex and the price.
↓
Service checks for an existing active listing (409 if found), then saves { domainName, price, ownerId: "u1" }.
↓
Database INSERT INTO tbl_listing (...) VALUES (...) RETURNING id, status, isDeleted, createdAt, updatedAt
↓
Response 201 with the new listing, including its generated id and default status: "active".
The race conditionIf two requests for coffee.eth arrive at the exact same millisecond, both can pass the "existing?" check before either inserts. The bulletproof fix is a partial unique index in the database: CREATE UNIQUE INDEX ON tbl_listing ("domainName") WHERE status = 'active' AND "isDeleted" = false. Then catch the PostgreSQL error code 23505 and turn it into a 409. The real backend uses this exact code: look for PostgresErrorCode.UNIQUE_VIOLATION in auth.service.ts register. Code checks give users friendly messages; database constraints give you real guarantees. Use both.

GET Read list, with pagination

Request: GET /api/v1/listings?page=2&limit=5&search=coffee&sort=price_asc

The ValidationPipe turns the query string into a ListListingsQueryDto with real numbers, and the repo builds this SQL:

SELECT * FROM tbl_listing l
WHERE l."isDeleted" = false
  AND l.status = 'active'
  AND l."domainName" ILIKE '%coffee%'
ORDER BY l.price ASC
LIMIT 5 OFFSET 5;

SELECT COUNT(*) FROM tbl_listing l WHERE -- same filters, no LIMIT/OFFSET

The response:

{
  "message": "Listings fetched",
  "result": {
    "items": [ { "id": "...", "domainName": "coffeeshop.eth", "price": 12.5, ... } ],
    "paginationInfo": { "total": 13, "page": 2, "limit": 5, "lastPage": 3, "nextPage": 3, "prevPage": 1 }
  }
}

The frontend uses nextPage and prevPage to enable the pager buttons, or lastPage to draw page numbers. The real backend does the same with its paginateResponse(data, total, paginationRequest) helper in src/@core/utils/helper.ts, and getPaginationSkipByPageAndLimit(page, limit) which is literally (page - 1) * limit. Open those two functions now; you'll recognize every line.

Offset pagination's weaknessSkipping 100,000 rows still makes the database walk past them, and if new rows are inserted while someone pages, items can shift between pages. Big feeds use cursor pagination instead ("give me 10 after the item with this createdAt"). Offset is completely fine at this scale; just know the other exists.

GET Read one

Request: GET /api/v1/listings/not-a-uuid gives a 400 from ParseUUIDPipe, before the database is asked anything. Without the pipe, PostgreSQL itself would throw "invalid input syntax for type uuid", which NestJS would turn into a confusing 500. With a valid UUID that doesn't exist, or that is soft deleted, the service throws 404. Both cases look identical to the client, which is what you want: a deleted listing should simply not exist from the outside.

PATCH Update

Request: PATCH /api/v1/listings/7f3a... with body {"price": 30}

The order of checks inside update is deliberate:

  1. Does it exist? If not, 404. (findOne inside findOwned.)
  2. Is it mine? If not, 403. (findOwned.)
  3. Is the change allowed? Sold listings are frozen, and reactivating must not create a second active listing. If not, 409.
  4. Apply it. Only the fields present in the DTO are updated. {"price": 30} becomes UPDATE tbl_listing SET price = 30, "updatedAt" = now() WHERE id = '7f3a...'. The description and status are untouched.
The empty bodyA body of {} passes validation (everything is optional) and leads to an update with nothing to set, which TypeORM rejects with an error. Easy fix as an exercise: in the service, if Object.keys(dto).length === 0, throw a BadRequestException('Nothing to update').

DELETE Delete

Request: DELETE /api/v1/listings/7f3a...

Same first two checks as update (exists, mine), then UPDATE tbl_listing SET "isDeleted" = true WHERE id = .... The row stays in the table but every read method filters it out. Calling DELETE again returns 404, because from the outside it no longer exists.

Soft deleteHard delete
RecoverableYes, flip the flag backNo
History and reportsKept, so sales history still points to real rowsLost, and foreign keys may break
RiskForgetting isDeleted: false in one query leaks deleted dataAccidental permanent loss
Privacy laws (user asks "erase me")Not enough on its ownRequired for personal data

This backend uses soft delete by default via BaseEntity.isDeleted, but the favorites module uses a hard DELETE. Both are valid; pick deliberately.

7. Ownership and security

CRUD bugs are the most common security bugs in real APIs. They even have a name: IDOR, Insecure Direct Object Reference. It means "I changed the id in the URL and got someone else's data". These are the rules that prevent it.

Rule 1: Identity comes from the token, never from the clientUse req.user.userId. Never accept userId or ownerId in a body, query or path for "my" resources. The real favorites controller follows this rule on every route.
Rule 2: Check ownership on every writeEvery update and delete must confirm the row belongs to the caller. Either load it and compare (our findOwned), or put the owner in the WHERE clause (the favorites delete does WHERE user_id = :userId AND id IN (...)). The second style is also safe against race conditions.
Rule 3: Whitelist what the client may setDTOs list exactly the allowed fields, and whitelist: true drops everything else. Never do repo.save(req.body).
Rule 4: Validate every input, including path and queryParseUUIDPipe for ids, a query DTO with @Max on limit, @IsIn for sort fields.
Rule 5: Parameterize every queryUse :name placeholders in QueryBuilder. Never put user input directly into SQL text.
403 or 404 for "not yours"?We return 403, which is honest and easy to debug. Some teams return 404 instead so outsiders can't even confirm that an id exists. For private data, like a user's orders, 404 is the safer choice. For public data like listings, where anyone can already see the listing, 403 is fine.

10. Your first unit test

The real backend has Jest set up and only a couple of spec files, so learning this puts you ahead. A unit test checks the service alone, with the repository replaced by a fake. This is where dependency injection pays off: you hand the service a fake repo instead of a real database.

src/listings/listings.service.spec.ts 
import { Test } from '@nestjs/testing';
import { ConflictException, ForbiddenException, NotFoundException } from '@nestjs/common';
import { ListingsService } from './listings.service';
import { ListingsRepo } from './listings.repo';
import { ListingStatus } from './listing-status.enum';

describe('ListingsService', () => {
  let service: ListingsService;
  const repo = {
    create: jest.fn(),
    findActiveById: jest.fn(),
    findActiveByDomain: jest.fn(),
    update: jest.fn(),
    softDelete: jest.fn(),
  };

  beforeEach(async () => {
    jest.resetAllMocks();
    const moduleRef = await Test.createTestingModule({
      providers: [ListingsService, { provide: ListingsRepo, useValue: repo }],
    }).compile();
    service = moduleRef.get(ListingsService);
  });

  it('creates a listing owned by the caller', async () => {
    repo.findActiveByDomain.mockResolvedValue(null);
    repo.create.mockImplementation(async (data) => ({ id: 'l1', ...data }));

    const result = await service.create({ domainName: 'coffee.eth', price: 25 }, 'u1');

    expect(result.ownerId).toBe('u1');
    expect(repo.create).toHaveBeenCalledWith({ domainName: 'coffee.eth', price: 25, ownerId: 'u1' });
  });

  it('refuses a second active listing for the same domain', async () => {
    repo.findActiveByDomain.mockResolvedValue({ id: 'other' });
    await expect(service.create({ domainName: 'coffee.eth', price: 25 }, 'u1'))
      .rejects.toBeInstanceOf(ConflictException);
  });

  it('returns 404 for a missing listing', async () => {
    repo.findActiveById.mockResolvedValue(null);
    await expect(service.findOne('x')).rejects.toBeInstanceOf(NotFoundException);
  });

  it('blocks updates from someone who is not the owner', async () => {
    repo.findActiveById.mockResolvedValue({ id: 'l1', ownerId: 'u1', status: ListingStatus.ACTIVE });
    await expect(service.update('l1', { price: 1 }, 'intruder')).rejects.toBeInstanceOf(ForbiddenException);
    expect(repo.update).not.toHaveBeenCalled();
  });
});
PieceMeaning
describe / itA group of tests, and one test. The string reads like a sentence describing the behaviour.
jest.fn()A fake function that records how it was called and returns whatever you tell it to.
{ provide: ListingsRepo, useValue: repo }"When the service asks for ListingsRepo, give it this fake object." This is exactly the same mechanism as useClass in the real modules.
mockResolvedValue(x)Make the fake async function resolve to x.
rejects.toBeInstanceOf(...)Assert that the promise failed with that exception type.
expect(repo.update).not.toHaveBeenCalled()Prove that the intruder never reached the database write. This is the most important assertion in the file.

11. Common beginner mistakes

Returning a promise inside try without await 
try { return this.repo.find(...); } catch (e) { /* never runs on DB errors */ }
The function returns the pending promise, then leaves the try block. When the promise rejects later, the catch is no longer there to catch it. Write return await this.repo.find(...) inside try blocks. The real findAllFavoriteDomainByUserId has exactly this bug.
Taking the user id from the body@Body() dto with dto.userId lets anyone act as anyone. Always use req.user.userId.
Forgetting isDeleted: false in one querySoft deleted rows reappear in one screen and nobody knows why. Keep every read in the repo, and filter there.
Putting :id routes above fixed routesGET /listings/mine gets swallowed by GET /listings/:id.
Query params treated as numbers without @Typepage + 1 becomes "21". Use @Type(() => Number) in the query DTO.
No upper limit on limit?limit=1000000 makes your database work hard and your response huge. Always cap it.
Money as float@Column('float') for prices leads to 19.999999. Use numeric.
Business logic in the controllerThe moment you write if in a controller, ask whether it belongs in the service.
Using synchronize: true outside practiceIt can drop columns with real data. Production uses migrations.
