Section 0

Why this page exists Basic

In one lineA throwaway test page that proves the Trails payment box works inside our buy drawer before we spend days building the real screens around it.

Think of it like test fitting a new part in a machine before rebuilding the machine around it. Mohit's doc asked for four answers before anyone builds the real "pay with any token" feature:

CheckThe questionWhere in the fileResult 5 Nov
(a)Will the Trails box accept our own two instructions and give a price?Lines 113 to 147 (the box), 131 (onQuote)Pass
(b)Did Trails keep our instructions byte for byte, with the domain going to the buyer?Lines 179 to 195Pass
(c)Does the box sit nicely in our drawer, light and dark, phone and desktop?Lines 260 to 262 (our Modal)Dark desktop OK, rest pending
(d)Can the browser ask Trails "how is this payment doing?" directly?Lines 197 to 211Pass

The page uses an old order from Mohit's experiments ("probe order 99"). It's already sold, so it can never be bought again. That makes it safe for getting a price, but it also means you must never press the final Pay button: the buying step would fail on chain and Trails would refund you minus fees.

A Seaport order is the seller's signed promise: "I give this, I want that, between these times." Field by field:

23

orderHash: the order's unique fingerprint. Not used in this file, kept because it's part of the doc's fixture.

24

recipient: the buyer from Mohit's original test. Only used for the encoding check (section 14), because the doc's expected bytes were made with this buyer.

25

signature: the seller's wallet signature over the order. Proves the seller agreed. 65 bytes.

27

offerer: the seller.

28

zone: an optional referee contract that can approve or block sales. All zeros means "no referee".

29

offer: what the seller gives. itemType: 2 means an NFT (ERC721). The token is Mohit's test NFT contract (not our domain contract), and 99 is the NFT's number. Amount 1.

30 to 33

consideration: what the seller wants back, as a list. itemType: 1 means an ERC20 token; the token address is USDT on Polygon. 243,750 goes to the seller and 6,250 to our fee wallet. USDT has 6 decimals, so these are 0.24375 and 0.00625 USDT, together 250,000 = 0.25 USDT. 6,250 is 2.5% of 250,000: our fee.

34

orderType: 0: "full open": the whole order must be bought at once, by anyone.

35 to 36

startTime, endTime: Unix time (seconds since 1 Jan 1970). The order is valid between them, about 7 days.

37, 39

zoneHash, conduitKey: extra settings for the referee and for a "conduit" (a helper that moves tokens). All zeros: not used.

38

salt: a huge random number that makes every order unique, even two otherwise identical ones.

40

counter: the seller's "cancel everything" counter at signing time. It is part of what was signed but is not sent when buying (section 9).

42

as const: tells TypeScript "this object never changes, and remember each value exactly". It also lets line 61 read the exact shape of the order.

Why numbers are strings here. JavaScript's normal numbers can't hold exact values above about 9 quadrillion. The salt has 77 digits. So the API (and the PDF) write big numbers as text, and we turn them into BigInt later (section 8).

Section 6

Lines 51 to 59: the ABI Advanced

In one lineA description of Seaport's buy function and the data shapes it takes, so viem knows how to turn our JavaScript object into bytes.
52const seaportFulfillAbi = parseAbi([
53  'struct OfferItem { uint8 itemType; address token; uint256 identifierOrCriteria; uint256 startAmount; uint256 endAmount; }',
54  'struct ConsiderationItem { … same five … ; address recipient; }',
55  'struct OrderParameters { address offerer; address zone; OfferItem[] offer; ConsiderationItem[] consideration; … ; uint256 totalOriginalConsiderationItems; }',
56  'struct AdvancedOrder { OrderParameters parameters; uint120 numerator; uint120 denominator; bytes signature; bytes extraData; }',
57  'struct CriteriaResolver { uint256 orderIndex; uint8 side; uint256 index; uint256 identifier; bytes32[] criteriaProof; }',
58  'function fulfillAdvancedOrder(AdvancedOrder advancedOrder, CriteriaResolver[] criteriaResolvers, bytes32 fulfillerConduitKey, address recipient) payable returns (bool fulfilled)',
59])

ABI stands for Application Binary Interface: the contract's "menu", listing each function and the exact type of each input. It's needed because the blockchain only sees bytes; the ABI is the agreement about which bytes mean what.

52

parseAbi reads these human readable lines (Solidity style) and builds the ABI object viem needs. Mohit's probe used exactly these lines on mainnet, so we copy them word for word.

53 to 57

A struct is a named group of fields, like a TypeScript interface. Types: uint8, uint120, uint256 are whole numbers of 8, 120, 256 bits; address is 20 bytes; bytes32 is exactly 32 bytes; bytes is any length; [] means a list.

56

AdvancedOrder wraps the order with numerator/denominator (what fraction to buy, we always use 1/1 = all of it), the seller's signature, and extraData (unused, empty).

57

CriteriaResolver: for "buy any NFT from a collection" style orders. We don't use it, so we pass an empty list.

58

The function itself. Its last input, address recipient, is the whole reason we use this function: it says who gets the NFT.

The rule this protects. With Trails, the one paying Seaport is a Trails wallet, not the buyer. Seaport's simpler functions (fulfillOrder, fulfillBasicOrder) always give the NFT to whoever paid, so the domain would get stuck in the Trails wallet. Only fulfillAdvancedOrder lets us name the buyer as the recipient.

Section 8

Lines 64 to 80: toViemParams Advanced

In one lineTurns every number stored as text into a real BigInt, because viem insists on BigInt for blockchain numbers.
65const toViemParams = (p: WireParams) => {
66  const w = p as unknown as Omit<RawOrder, 'counter'> & { totalOriginalConsiderationItems: number }
67  return {
68    offerer: w.offerer as Hex,
70    offer: w.offer.map((i) => ({ itemType: i.itemType, token: i.token as Hex, identifierOrCriteria: BigInt(i.identifierOrCriteria), … })),
71    consideration: w.consideration.map((i) => ({ …, recipient: i.recipient as Hex })),
73    startTime: BigInt(w.startTime),
76    salt: BigInt(w.salt),
78    totalOriginalConsiderationItems: BigInt(w.totalOriginalConsiderationItems),
79  }
80}
65

An arrow function that takes the "wire" order (the shape from toOrderParameters).

66

The trickiest TypeScript line in the file. toOrderParameters was written for ethers (our older blockchain library), so its types talk about ethers' BigNumber. Our data is plain strings. as unknown as X is a double cast: "trust me, treat this as X". Omit<RawOrder, 'counter'> means "the order shape minus counter", and & { … } adds the new field. It changes nothing at runtime; it only tells TypeScript what's really there.

68

as Hex: tells TypeScript this string is a 0x… value, which viem's types require for addresses.

70 to 71

.map(…) makes a new list by converting each item. Each item keeps its fields, with the number fields wrapped in BigInt(…).

73 to 78

The same BigInt treatment for times, salt and the item count. itemType and orderType stay normal numbers because viem accepts small numbers for uint8.

Phase 4 moves this function into src/helpers/trails/buildDestinationCalls.ts, with a proper test. The spike has its own copy so it doesn't depend on unfinished work.

Section 9

Lines 82 to 97: buildCalls, the heart of the file Advanced

In one lineBuilds the two instructions Trails will run on Polygon: "let Seaport take 0.25 USDT" and "buy order 99 for this buyer".
82const buildCalls = (buyer: Hex) => {
83  const rawOrder = FIXTURE.rawOrder
84  const price = rawOrder.consideration.reduce((s, c) => s + BigInt(c.startAmount), BigInt(0))
85  const approveData = encodeFunctionData({ abi: erc20Abi, functionName: 'approve', args: [DEFAULTS.seaportAddress as Hex, price] })
86  const fulfillData = encodeFunctionData({
87    abi: seaportFulfillAbi,
88    functionName: 'fulfillAdvancedOrder',
89    args: [
90      { parameters: toViemParams(toOrderParameters(rawOrder as never)), numerator: BigInt(1), denominator: BigInt(1), signature: FIXTURE.signature, extraData: '0x' },
91      [],
92      zeroHash,
93      buyer,
94    ],
95  })
96  return { price, approveData, fulfillData }
97}
82

Takes one input, the buyer's address, because that's the only thing that changes between buyers.

84

The price. reduce walks the list and keeps a running total: start at BigInt(0), add each item's amount. 243,750 + 6,250 = 250,000. We add up the consideration instead of trusting a separate "price" field, so the amount always matches what Seaport will actually charge. (BigInt(0) is written instead of 0n because the project's TypeScript target is older.)

85

Call 1, approve. Tokens can't be taken from a wallet without permission. approve(spender, amount) on the USDT contract says "Seaport may take up to 250,000 from me". "Me" will be the Trails wallet when this runs. encodeFunctionData turns this into bytes.

86 to 95

Call 2, buy. The four inputs of fulfillAdvancedOrder, in order:

1 (line 90): the AdvancedOrder. toOrderParameters drops counter and adds totalOriginalConsiderationItems (here 2), which is what Seaport wants when buying. Then toViemParams converts the numbers. rawOrder as never is a cast to satisfy the ethers typed helper; never fits any type. Then 1/1 (buy all), the seller's signature, and empty extraData.

2 (line 91): [], no criteria resolvers.

3 (line 92): zeroHash, no conduit for the buyer side, tokens move through Seaport directly.

4 (line 93): buyer, the recipient. The domain goes here.

96

Returns all three so the page can show the price and hand both calldatas to Trails.

Proven correct. With Mohit's buyer, this produces exactly the doc's selector, 1,444 bytes and keccak. It was checked in Node and again in your browser (all four lines true).
Section 10

Line 99: a safe stringify Middle

99const stringify = (v: unknown) => JSON.stringify(v, (_k, x) => (typeof x === 'bigint' ? x.toString() : x), 2)

JSON.stringify turns an object into text, but it crashes on BigInt values ("Do not know how to serialize a BigInt"). The second argument is a "replacer" that runs on every value: if it's a BigInt, turn it into a string, otherwise leave it. The 2 indents the output by two spaces so it's readable. _k is the key, unused, and the underscore says so on purpose.

115

Section 18

What calldata really looks like Advanced

In one lineA selector, then each input padded to 32 bytes, in order.

The approve calldata is short enough to read by hand. It's 68 bytes:

095ea7b3 0000000000000000000000000000000000000068f116a894984e2db1123eb395 000000000000000000000000000000000000000000000000000000000003d090
4 bytes

Selector 095ea7b3: the first 4 bytes of the keccak fingerprint of the text approve(address,uint256). Every contract that has an approve function with these inputs uses the same selector.

32 bytes

Input 1, spender: the Seaport address 0x0000000000000068F116…B395, padded on the left with zeros to fill 32 bytes.

32 bytes

Input 2, amount: 3d090 in hex = 250,000 in decimal = 0.25 USDT. Also padded to 32 bytes.

The buy calldata follows the same rules, but its inputs contain lists and variable length bytes (the signature), so it's longer. Those parts are stored after the fixed part, with "offsets" saying where each one starts. That's how it reaches 1,444 bytes. You never write this by hand; that's viem's job. The fingerprint check is how we know viem and the ABI produced it right.

Trails' bundle (1,860 bytes) is another call to its own helper contract, with our two calls placed inside it as inputs. That's why a plain "contains" search could find our bytes inside it in check (b).

Section 21

Test yourself

Why can't we use Seaport's simpler fulfillOrder?

It sends the domain to whoever pays Seaport, which with Trails is the Trails wallet. Only fulfillAdvancedOrder has a recipient input.

Why is the encoding check built with Mohit's buyer instead of yours?

The expected fingerprint was made with his buyer. Any other address changes the bytes, so only his can be compared with the answer key.

What would "BLOCKED" in check (d) have meant?

The browser threw a TypeError, so Trails' API doesn't allow requests from our site. We'd need the backend to ask Trails for status instead.

Why does approve come before the buy call?

Seaport pulls the USDT from the Trails wallet during the buy. Without the approval first, that pull is refused and the buy reverts.

What does 3d090 mean?

250,000 in hex, which is 0.25 USDT because USDT has 6 decimals.

Why is the Trails box loaded with dynamic and ssr: false?

It needs the browser (no server rendering), and it's big, so it goes in its own chunk that only downloads when the drawer opens. No other page gets heavier.
