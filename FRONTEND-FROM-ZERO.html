2. The big picture

The login guide compared the backend to a hotel reception desk. Let's walk around to the guest's side of that hotel. The browser is the guest. The Next.js server is the concierge in the lobby who hands every guest a printed floor plan the moment they arrive, so they can see the building straight away. The JavaScript bundle is the staff who then walk in and make the floor plan come alive: doors open, lights switch on, buttons work. The NestJS backend is still the reception desk, now in a different building, which the staff phone whenever they need real information, like which domains are for sale or whether your keycard is still valid.

From typing the URL to seeing the listings table

1. Browser You type the marketplace address. The browser sends GET / to the Next.js server, along with any cookies it has for that site, including access_token if you logged in before.
↓
2. Next.js server, _app.tsx Before drawing anything, App.getInitialProps runs on the server and reads the access_token cookie from the request. It doesn't verify the token; it only checks that one exists, and passes initialAuthenticated: true or false down.
↓
3. Server render Next.js runs your React components once on the server and turns them into an HTML string: the header, the sidebar, the empty listings table showing skeleton rows. Hooks that fetch data don't run here, because effects only run in a browser.
↓
4. HTML arrives The browser paints that HTML immediately. You can see the page, but nothing is clickable yet. The HTML also contains <script> tags pointing at JavaScript bundles, files with your compiled components in them.
↓
5. Hydration The bundles download and React runs the same components again in the browser, then attaches event handlers to the HTML that's already on screen instead of drawing it again. That attaching step is called hydration. If the browser's first render produces different HTML from the server's, React warns about a hydration mismatch.
↓
6. Effects run Now useEffect callbacks fire for the first time. AppContent checks for a main site session, AuthProvider rereads the cookie, AutoLogoutHandler schedules expiry timers, and RTK Query's useGetMarketplaceOrdersQuery inside useLiveListings sends GET /marketplacev2/orders?limit=28 to the backend.
↓
7. Backend answers NestJS replies with JSON, { message, result: { items, nextCursor, categoryCounts } }. RTK Query stores it in the Redux store, the hook's data changes, and React rerenders the page.
↓
8. Listings table useLiveListings maps each row into a MarketplaceListing, pages/index.tsx filters them, and LiveListingsTable swaps its skeleton rows for real ListingRows. That's the moment you see domains.

Clicking a link after that works differently. next/link doesn't ask the server for a whole new HTML page. It downloads only the JavaScript for the next page and swaps it in, which is why navigation inside the app feels instant. That's called client side navigation. In this app getInitialProps runs again on each of those navigations too, this time in the browser.

AuthProviderOur own context, src/context/AuthContext.tsx. Holds authenticated, login() and logout().
WagmiProviderFrom wagmi. Knows which wallet is connected and on which chain.
QueryClientProviderFrom @tanstack/react-query. Holds a React Query cache. wagmi needs it; our own code doesn't use it (section 7).

Order matters, because a component can only use a provider that sits above it. AutoLogoutHandler sits inside all five, so it could use any of them. 3. Every word you need

This is the dictionary. Skim it once now, then come back whenever a word later on feels fuzzy. Where a word shows up in the real code, the entry says where.

Web words

Browser
The program that fetches pages and runs their JavaScript. Everything a user clicks happens here, on their machine, not on our servers.
Server
A program that waits for requests and answers them. This project has two kinds: the Next.js server that sends HTML pages (started with npm run dev, which this repo runs on port 3002), and the NestJS backend that sends JSON data.
Port
A numbered door on a machine. localhost:3002 means "this computer, door 3002".
Origin
The scheme, host and port together, like http://localhost:3002. Two URLs with different ports are different origins. The browser sends it in an Origin header, and CORS decisions are made on it.
HTML
The text that describes what's on the page. Next.js produces it from your components.
JavaScript bundle
A file the build tool produces by combining your components and the libraries they import. The browser downloads bundles to make the page interactive.
DOM
The live tree of elements the browser builds from HTML. React updates the DOM for you; you almost never touch it directly.
Cookie
A small named value the browser stores per site and sends back automatically with every request to that site. This repo stores access_token and refresh_token in cookies.
httpOnly cookie
A cookie the server sets with the HttpOnly flag. JavaScript can't read it at all, which protects it from stolen script attacks. The cookies our frontend sets are not httpOnly (section 9).
localStorage / sessionStorage
Key value storage in the browser that only JavaScript uses; it's never sent to a server automatically. sessionStorage is cleared when the tab closes. This repo uses localStorage for the idle timer and sessionStorage for a token_expired flag.

JavaScript and TypeScript words

Promise
A placeholder for a value that arrives later, like a network response. It's either pending, fulfilled with a value, or rejected with an error.
async / await
await pauses the current function until a Promise settles, without freezing the page. A function using await must be marked async, and it always returns a Promise itself.
try / catch / finally
catch runs if anything in try throws (including a rejected awaited Promise). finally runs either way, which is why hooks here put setLoading(false) in it.
Destructuring
const { data, isLoading } = useQuery(...) pulls named properties out of an object into variables. const [a, setA] = useState() does the same for an array.
Spread ...
{ ...prev, [key]: value } copies every property of prev into a new object, then overrides one. You'll see this everywhere state is updated.
Optional chaining ?. and ??
res?.result gives undefined instead of crashing when res is missing. x ?? fallback uses fallback only when x is null or undefined.
Type / interface
TypeScript descriptions of a value's shape. They vanish when the code compiles, so they can't check anything at runtime. interface WatchlistEntry in useWatchlist.ts is one.
Generic <T>
A type parameter. useState<string | null>(null) says "this state holds a string or null".
enum
A named set of constants. Cookie_Key.ACCESS_TOKEN is just the string 'access_token' with a safe name.
Module and barrel file
Each file is a module with its own imports and exports. A barrel is an index.ts that only passes along exports from other files, so you can import many components from one path.

React words

Component
A function that returns what should be on screen. PrimaryButton, ListingRow and every page are components. Names must start with a capital letter.
JSX
The HTML looking syntax inside components, like <Link href="/">Home</Link>. It compiles to plain function calls.
Props
The inputs a parent passes to a component, like function arguments. <ListingRow listing={listing} favorited={true} /> passes two props.
children
A special prop holding whatever you put between a component's opening and closing tags.
State
Data a component remembers between renders, created with useState. Changing state is what makes React redraw.
Render
React calling your component function to find out what it should show right now.
Rerender
Calling it again because its state, its props or a context it reads changed. Every rerender runs the whole function body again from the top.
Hook
A function whose name starts with use that lets a component use React features (state, effects, context). Hooks must be called at the top level of a component, never inside an if or a loop, so React can match them up between renders.
Effect
Code that runs after a render to sync with something outside React: fetching data, timers, event listeners. Written with useEffect.
Dependency array
The list after an effect, useEffect(fn, [a, b]). React reruns the effect only when one of those values changed since the last render. [] means "only after the first render".
Cleanup
A function you return from an effect. React calls it before running the effect again and when the component disappears. It's where you clear timers and remove listeners.
Ref
A box, created with useRef, whose .current value survives rerenders but doesn't cause one when changed. Good for timer ids and DOM elements.
Memo
Remembering a computed result between renders. useMemo remembers a value; useCallback remembers a function.
Context
A way to share a value with every component below a point in the tree without passing props through each level. AuthContext is one.
Provider
The component that supplies a context's value to everything inside it, like <AuthContext.Provider value={...}>.
Custom hook
Your own function starting with use that calls other hooks. useWatchlist and useLiveListings are custom hooks.
Controlled input
An input whose value comes from React state (value={formValue.email}) and changes only through onChange. The login form in this repo is controlled. An uncontrolled input keeps its own value in the DOM and you read it when needed, which is what react-hook-form does by default.
Event handler
A function React calls when something happens, passed as onClick, onChange, onSubmit. Pass the function itself (onClick={toggle}), don't call it (onClick={toggle()}).
Key
A unique, stable id you give each item in a list (key={listing.id}) so React can tell items apart when the list changes.
Strict Mode
A development only mode where React runs effects twice on purpose to expose missing cleanups. This repo's next.config.ts doesn't set reactStrictMode, so it's off here; a fresh app usually has it on.

Next.js words

Pages Router
Next.js's original routing system: every file in the pages folder becomes a URL. This repo uses it. (The newer App Router uses an app folder; it isn't used here.)
Route / dynamic route
A URL the app answers. A file named with brackets, like pages/details/[orderId].tsx, is dynamic: it answers /details/anything and you read anything from router.query.orderId.
_app.tsx
The component that wraps every page. Providers and global CSS go here.
_document.tsx
The outer HTML shell (<html>, <head>, <body>). Rendered only on the server; no event handlers work in it.
Middleware
A function in middleware.js at the project root that runs on the server before a page is served, and can redirect or block the request.
SSR
Server side rendering: producing HTML on the server for each request.
Hydration
React attaching event handlers to server made HTML in the browser (section 2).
getInitialProps / getServerSideProps / getStaticProps
Functions a page (or _app) can export so Next.js fetches data before rendering. Section 12 explains each and which ones this repo uses.
next/link and next/router
Link is the in app link component. useRouter() gives you the current path and query, plus push and replace to navigate in code.
next/image
Next's Image component, which this repo's CLAUDE.md requires instead of a plain <img>.
Environment variable
A setting supplied from outside the code, like the API address, read with process.env.NAME. Values differ per machine or server (local, stage, production).
NEXT_PUBLIC_ variables
Next.js copies any variable whose name starts with NEXT_PUBLIC_ straight into the browser bundle at build time. Anything else stays on the server, unless it's listed under env in next.config.ts, which this repo does. Either way, assume anything that reaches the browser is public.

State management words

Redux store
One big JavaScript object that holds shared app state, plus the rules for changing it. Created in src/core/redux/store.ts.
Slice
One named section of the store with its own starting value and update functions. userProfileSlice owns state.userProfile.
Action
A plain object describing something that happened, like { type: 'userProfile/setUserProfile', payload: data }. Redux Toolkit writes these for you.
Reducer
A function that takes the current state and an action and returns the next state. Redux Toolkit lets you write it as if you were mutating (state.profile = action.payload) and safely turns that into a new object.
dispatch
Sending an action to the store: dispatch(setUserProfile(data)).
Selector
A function that reads a piece of the store: useSelector((state) => state.userProfile.profile). The component rerenders when that piece changes.
Thunk
A function you dispatch instead of an action, for async work that dispatches real actions when done. This repo doesn't write its own thunks; RTK Query uses them internally.
RTK Query
The data fetching tool built into Redux Toolkit. You describe endpoints once (createApi) and get hooks like useGetMarketplaceOrdersQuery that fetch, cache and track loading for you. Most of this repo's Redux code is RTK Query.
React Query
A separate library (@tanstack/react-query) that does the same job as RTK Query without Redux. Installed and provided here, but only wagmi uses it.
Query key
React Query's name for one cached piece of data, an array like ['listings', 'list', { page: 1 }]. Same key, same cache entry.
Cache
Remembered responses, so a second component asking for the same data gets it instantly instead of sending another request.
Mutation
A request that changes data on the server (POST, PATCH, DELETE), as opposed to a query that reads.
Invalidation
Marking cached data as out of date so it gets fetched again. RTK Query does it with tags (invalidateTags(['domain'])); React Query with invalidateQueries.

API words

HTTP request and response
A request has a method (GET, POST, PATCH, PUT, DELETE), a URL, headers and maybe a JSON body. A response has a status code, headers and a body. The login guide's web words cover these in more depth.
Status code
200 OK, 201 Created (NestJS's default for every POST), 400 bad input, 401 not logged in or token expired, 403 logged in but not allowed, 404 not found, 409 conflict, 500 the server broke.
fetch
The browser's built in function for HTTP requests. It only rejects on network failure; a 401 or 500 still resolves, so you must check response.ok yourself.
axios
A popular library for HTTP requests. Unlike fetch, it rejects automatically on any status outside 200 to 299 and parses JSON for you.
Interceptor
An axios function that runs on every request before it's sent, or on every response before your code sees it. api.service.ts registers a request interceptor that adds the token.
JSON
The text format requests and responses use. response.json() turns it into an object.
Bearer token
The header Authorization: Bearer <token>. "Bearer" means "whoever carries this is allowed in".
Access token / refresh token
The two JWTs login returns. The short lived access token goes on every protected request. The long lived refresh token is only used to get a new pair. See the login guide's step 8.
Envelope
Our backend wraps every success in the same shape, { message, result }, so your data is always in result.
CORS
Cross Origin Resource Sharing. A browser on http://localhost:3002 may only read responses from the API on another origin if the API says that origin is allowed. Section 9 shows the real list.
Debounce
Waiting until the user stops typing for a moment before acting, so you search once instead of on every keystroke.
Race condition
Two requests in flight where the older one finishes last and overwrites the newer result. Typing fast in a search box is the classic way to cause one.

Web3 words

Wallet
An app or browser extension (MetaMask, Coinbase Wallet) that holds your blockchain keys and signs things on your behalf. Its public address looks like 0x8A7F...3c9D.
Signature
Proof that the owner of an address approved a specific message. Wallet login signs a one time text with a nonce (a random number used once) in it.
Chain / network
Which blockchain: Ethereum, Polygon, Arbitrum and so on. Our listings live on Polygon (chain id 137).
wagmi
A React hooks library for wallets: useAccount() tells you the connected address, useSignMessage() asks the wallet to sign.
Connector
wagmi's adapter for one kind of wallet connection: injected browser wallets, WalletConnect, Coinbase and so on.
Reown AppKit
The ready made "Connect wallet" modal (formerly called Web3Modal), built on top of wagmi. createAppKit sets it up and useAppKit().open() shows it.
ethers
An older, lower level blockchain library (version 5 here). This repo uses it for signing and for reading the chain alongside wagmi.

tsconfig.json (paths) 
"paths": {
  "@/*": ["./src/*"],
  "@newstyles/*": ["./src/design-system/styles/*"],
  "@legacy-styles/*": ["./public/assets/css/*"],

middleware.js

middleware.js (trimmed) 
import { NextResponse } from 'next/server';
import { Cookie_Key } from '@/core/enum/cookie.enum';

export function middleware(request) {
    // ... an IP allow list, all commented out ...
    if (request.nextUrl.pathname.startsWith('/profile')) {
        const token = request.cookies.get(Cookie_Key.ACCESS_TOKEN)?.value;
        if (!token) {
            return NextResponse.redirect(new URL('/login', request.url));
        }
    }
    return NextResponse.next();
}

Middleware runs on the server before the page is served. If you request /profile without an access_token cookie, it answers with a redirect to /login and your page code never runs. NextResponse.next() means "carry on normally". The surprise: there's no pages/profile in this repo any more (the old profile pages live in src/_archive/profile), so today this check guards a URL that would 404 anyway. Every real protection happens in ProtectedRoute instead (section 9).

6. Every hook, deeply

useState

const [pendingTokenId, setPendingTokenId] = useState<string | null>(null)

From useWatchlist. useState(initial) returns a pair: the current value and a function to replace it. Calling the setter schedules a rerender in which pendingTokenId has the new value. The <string | null> says what the state may hold.

Updating based on the previous value

src/hooks/marketplace/useWatchlist.ts (lines 93 and 99) 
setEntries((prev) => prev.filter((entry) => entry.id !== existing.id))
// ...
if (res?.result) setEntries((prev) => [...prev, res.result])

When the new state depends on the old one, pass a function. React calls it with the latest value, even if other updates are queued. That matters here because toggle runs after an await, by which point the entries variable it closed over might be stale. Notice also that neither line changes the array in place: filter and [...prev, x] both build a new array. React compares state by reference, so mutating with prev.push(x) would look like "nothing changed" and skip the rerender.

Why state updates aren't instant

const [count, setCount] = useState(0)
const handleClick = () => {
  setCount(count + 1)
  console.log(count)        // still 0: this render's count never changes
  setCount(count + 1)       // also sets 1, not 2, because count is still 0 here
  setCount((c) => c + 1)    // this one does build on the queued value
}

Each render gets its own snapshot of state. count is a plain constant inside that render. The setter doesn't change it; it asks React for a new render where count will be different. React also batches several updates in one event into a single rerender.

useEffect

An effect runs after React has put the render on screen. The dependency array decides when it runs again. The simplest real example is useIsMobile:

src/utils/UseIsMobile.tsx 
import { useEffect, useState } from "react";

export function useIsMobile(breakpoint = 768) {
    const [isMobile, setIsMobile] = useState(false);

    useEffect(() => {
        const checkScreenSize = () => setIsMobile(window.innerWidth <= breakpoint);

        checkScreenSize(); // check on mount
        window.addEventListener("resize", checkScreenSize);

        return () => window.removeEventListener("resize", checkScreenSize);
    }, [breakpoint]);

    return isMobile;
}
LineWhat it does and why
useState(false)Starts as "not mobile". On the server there's no window, so the hook can't know yet; it must pick something.
useEffect(() => { ... }, [breakpoint])Runs after the first render in the browser, and again only if breakpoint changes.
checkScreenSize()Measure once immediately, so the value is right straight away.
addEventListener("resize", ...)Measure again whenever the window size changes.
return () => removeEventListener(...)The cleanup. Without it, every mount would add another listener that never goes away: a memory leak, and setState calls on components that no longer exist.
window.innerWidth <= breakpointNote the <=: useIsMobile(767) means "767px or narrower".
Dependency arrayWhen the effect runs
none: useEffect(fn)After every render. Rarely what you want.
[]Once, after the first render. AppContent uses this to check the session once.
[a, b]After the first render, then whenever a or b is different from last time (compared with Object.is, so a new object or array counts as different even with the same contents).

The double run in Strict Mode

In development, React's Strict Mode mounts each component, runs its effects, runs their cleanups, then runs the effects again. It's on purpose: if your effect breaks when run twice, it was missing a cleanup. This repo's next.config.ts doesn't turn on reactStrictMode, so you won't see it here, but your practice app in section 13 will probably have it on, and you'll see requests fire twice in development. That's expected; production runs them once.

The infinite loop mistake

// WRONG: runs after every render, sets state, which causes a render, which runs it again...
useEffect(() => {
  setFilters({ ...filters, page: 1 })
})

// WRONG: an object created during render is "new" every time, so the effect always reruns
const query = { search, page }
useEffect(() => { fetchListings(query).then(setData) }, [query])

The fix for both is the same thought: list only the values the effect really depends on, as primitives where possible ([search, page]), and never set state unconditionally inside an effect that depends on that same state. Section 16 has more.

useMemo and useCallback

src/hooks/marketplace/useWatchlist.ts (lines 77 and 78)

useMemo(fn, deps) runs fn and remembers the result until a dependency changes. Here it builds a Set of watched keys only when entries changes, so checking a heart is a fast .has() instead of searching the array for every row. useCallback(fn, deps) remembers the function itself, so isWatched is the same function object between renders unless watchedKeys changed. That matters when a function is passed to a child or listed in another hook's dependency array: a fresh function every render would look like a change every time.

But filtered is a brand new array built on every render, and watchlist is the hook's return object, also new every render. So this memo recomputes every single time and saves nothing. Not a bug, just wasted intent. Section 15 lists it.

Custom hooks

A custom hook is just a function that starts with use and calls other hooks. It lets you pull logic out of a component and reuse it. The smallest real one:

src/utils/useDebounce.ts 
export const useDebounces = (value: string, delay: number = 300) => {
  const [debouncedValue, setDebouncedValue] = useState(value);
  useEffect(() => {
    const handler = setTimeout(() => setDebouncedValue(value), delay);
    return () => clearTimeout(handler);
  }, [value, delay]);

  return debouncedValue;
};

Every time value changes, the effect's cleanup cancels the previous timer and starts a new one. Only when the user stops typing for delay milliseconds does a timer survive long enough to update debouncedValue. useListingFilters uses it for the listings search box. Each component that calls a custom hook gets its own copy of that hook's state; hooks share logic, not data. That's exactly why useWatchlistCount needs an event to learn about changes made by a useWatchlist somewhere else (section 10).

Why one app ended up with all of these

Honestly: history. The older parts of the app (the legacy components, profile, the old watchlist) were built around Redux slices, plain fetch helpers and RTK Query. The redesign added hooks that call callBackend and keep their own useState, because those flows also talk to wallets and needed finer control. React Query arrived as a requirement of wagmi version 2, not as a choice for our data. None of the four is wrong; having all of them means a new person has to learn every pattern, and data about the same thing can live in two places (the old RTK Query watchlist endpoints in src/core/redux/watchlist.ts next to the new useWatchlist).

How to choose for new codeStart with local useState. If two siblings need it, lift it to their common parent. If data comes from the server, don't hand roll useState plus useEffect: use the server state tool the area already uses (RTK Query in this repo's Redux areas). Reach for Context only for small, rarely changing app wide values (who's logged in, theme). Reach for a Redux slice only when unrelated parts of the app read and write the same client data. And whichever you choose, match the code around you; a consistent repo beats a clever one.

export async function callBackend(path: string, options: { method?: 'GET' | 'POST' | 'DELETE'; body?: unknown } = {}) {
  const token = getCookieValue(Cookie_Key.ACCESS_TOKEN)
  const res = await fetch(`${DEFAULTS.backendBaseUrl}${path}`, {
    method: options.method ?? 'GET',
    headers: { 'Content-Type': 'application/json', ...(token ? { Authorization: `Bearer ${token}` } : {}) },
    body: options.body ? JSON.stringify(options.body) : undefined,
  })
  const json = await res.json().catch(() => ({}))
  if (!res.ok) {
    const message = json?.message ? (Array.isArray(json.message) ? json.message.join(', ') : json.message) : `Request failed (${res.status})`
    throw new BackendError(message, json?.code)
  }
  return json
}
PieceMeaning
DEFAULTS.backendBaseUrlJust baseUrl again, the same API address everything uses.
...(token ? { Authorization } : {})Adds the header only when a token exists. Spreading an empty object adds nothing.
JSON.stringify(options.body)fetch wants text; axios does this for you, fetch doesn't.
res.json().catch(() => ({}))Some responses have no JSON body. Instead of crashing, use an empty object.
Array.isArray(json.message)NestJS validation errors send message as an array of strings; other errors send one string. This handles both.

    JSON.parse(error).message.map((err: any) => {

    })

  1. 401 with a refresh token: call GET /auth/refresh-token with the refresh token as the Bearer (the backend's RefreshTokenGuard, see the login guide's section 6), save the new pair, and return it. The fetch helper sees result and retries once.   2. Anything else: parseError reads the NestJS error body { statusCode, message, error } and throws the message string (for a validation array, only the first one).

So the real chain is: request fails → a helper throws a message → your hook or component catches → you call ToastMessage. If you forget the last step, the user sees nothing.

Step 3: deciding "am I logged in?"

There's no "current user" object in the frontend's auth state at all, only a yes or no, and it's decided by one rule: an access_token cookie exists. It's checked in three places:

  1. On the server, every request: App.getInitialProps reads the cookie from the incoming request and passes initialAuthenticated to AuthProvider, so even the server rendered HTML knows.
  2. In the browser, once: AuthProvider's effect rereads the cookie.
  3. After login: login() flips it to true.

Nobody checks whether the token is valid at this point. An expired token still counts as "logged in" until something removes it, which is the job of the expiry machinery in step 5.

Why CORS errors happen, and the real allowed list

The browser enforces CORS, not the server. When a page on http://localhost:3002 calls an API on another origin, the browser first checks the API's answer (for non simple requests, with a preflight OPTIONS request) to see whether that origin is allowed. If not, it hides the response from your code and logs a CORS error, even though the server may have run the request. The backend decides who's allowed:

backend: src/main.ts (lines 26 to 56, trimmed)

    "https://endlessdomains.io",

];

app.enableCors({
    origin: (origin, callback) => {
        if (!origin) return callback(null, true);
        if (allowedOrigins.includes(origin)) {
            callback(null, true);
        } else {
            console.warn(`Blocked CORS request from origin: ${origin}`);
            callback(new Error(`Origin ${origin} not allowed by CORS`));

    },
    credentials: true,
    methods: "GET,HEAD,PUT,PATCH,POST,DELETE,OPTIONS",
    allowedHeaders: "Content-Type, Authorization, X-Requested-With",
});

That's why this frontend runs on port 3002 ("dev": "next dev -p 3002" in package.json): http://localhost:3002 is on the list. Run it on 3001 or 127.0.0.1:3002 and every call fails with a CORS error, because those are different origins. credentials: true is what allows credentials: 'include' calls to send cookies. allowedHeaders lists Authorization, which is required for the Bearer header to be allowed across origins. And !origin is allowed because tools like curl and Postman send no Origin at all, which is why a request can work in Postman and fail in the browser.

The hydration tradeoff CLAUDE.md describes

Hydration only works smoothly if the browser's first render produces the same HTML the server did. The server has no screen width, so useIsMobile can't know it there. It returns false on the server and in the browser's first render (so they match and hydration is clean), and only then does its effect measure the window and switch to true on a phone. The visible result is a brief desktop layout before the mobile one. CLAUDE.md accepts this and asks everyone to use the same hook rather than invent another approach in one component. The tempting "fix", reading window.innerWidth directly during render, would crash on the server (window is not defined), and checking typeof window during render would make server and client HTML differ, which is exactly a hydration mismatch. The usual clean alternative is plain CSS media queries for anything that only changes styling, which is what the design system's @include mobile mixins do. JavaScript detection is only needed when the component tree itself differs.

13.3An axios instance with an interceptor that refreshes once

src/lib/api.ts 
import axios, { AxiosError, InternalAxiosRequestConfig } from 'axios'
import { clearTokens, getAccessToken, getRefreshToken, saveTokens } from './cookies'

export const API_URL = process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:3001/api/v1'

/** Every success from our NestJS backend looks like this. */
export interface ApiEnvelope<T> {
  message: string | string[]
  result: T
}

/** Fired when the session can't be saved, so the app can forget the user. */
export const SESSION_EXPIRED_EVENT = 'practice:session-expired'

export const api = axios.create({
  baseURL: API_URL,
  headers: { 'Content-Type': 'application/json' },
})

// 1. Before every request: attach the access token, if we have one.
api.interceptors.request.use((config) => {
  const token = getAccessToken()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 2. After every failed response: on a 401, refresh once and retry once.
const NO_REFRESH = ['/auth/login', '/auth/register', '/auth/refresh-token']
let refreshPromise: Promise<string | null> | null = null

async function refreshAccessToken(): Promise<string | null> {
  const refreshToken = getRefreshToken()
  if (!refreshToken) return null
  try {
    // A plain axios call, not `api`, so this request never goes through our own interceptors.
    const res = await axios.get<ApiEnvelope<{ accessToken: string; refreshToken: string }>>(`${API_URL}/auth/refresh-token`, {
      headers: { Authorization: `Bearer ${refreshToken}` },
    })
    saveTokens(res.data.result.accessToken, res.data.result.refreshToken)
    return res.data.result.accessToken
  } catch {
    return null
  }
}

type RetriableConfig = InternalAxiosRequestConfig & { _retried?: boolean }

api.interceptors.response.use(
  (response) => response,
  async (error: AxiosError) => {
    const original = error.config as RetriableConfig | undefined
    const isAuthCall = NO_REFRESH.some((path) => original?.url?.startsWith(path))
    if (error.response?.status !== 401 || !original || original._retried || isAuthCall) {
      return Promise.reject(error)
    }
    original._retried = true

    // Many requests can 401 at the same moment. They all wait for ONE refresh.
    if (!refreshPromise) {
      refreshPromise = refreshAccessToken().finally(() => {
        refreshPromise = null
      })
    }
    const newToken = await refreshPromise

    if (!newToken) {
      clearTokens()
      if (typeof window !== 'undefined') window.dispatchEvent(new Event(SESSION_EXPIRED_EVENT))
      return Promise.reject(error)
    }
    original.headers.Authorization = `Bearer ${newToken}`
    return api(original)
  },
)

/** The HTTP status of a failed request, if there was a response at all. */
export function statusOf(err: unknown): number | undefined {
  return axios.isAxiosError(err) ? err.response?.status : undefined
}

/** Turns any error into one sentence for a toast. */
export function getErrorMessage(err: unknown, fallback = 'Something went wrong.'): string {
  if (axios.isAxiosError(err)) {
    if (!err.response) return 'Cannot reach the server. Is the backend running on port 3001?'
    const data = err.response.data as { message?: string | string[] } | undefined
    if (Array.isArray(data?.message)) return data.message.join(', ')
    if (typeof data?.message === 'string') return data.message
  }
  if (err instanceof Error && err.message) return err.message
  return fallback
}
PieceMeaning
process.env.NEXT_PUBLIC_API_URLCopied into the bundle at build time because of the NEXT_PUBLIC_ prefix. Restart npm run dev after changing .env.local.
ApiEnvelope<T>A generic type for { message, result }. ApiEnvelope<Listing> means result is a Listing.
axios.create({ baseURL })Our own instance. Calls become api.get('/listings') and the base URL is added for you. Unlike the real repo, the interceptors live on this instance, not on axios's global default, so they can't surprise code elsewhere.
interceptors.request.useRuns before every request. Reads the cookie each time, so a newly saved token is used straight away.
interceptors.response.use(ok, fail)The first function sees successes (we pass them through), the second sees failures.
NO_REFRESHA 401 from login means "wrong password", not "expired token". Trying to refresh there would be wrong, and refreshing the refresh call would loop forever.
_retriedA flag we stick on the request config. If the retried request 401s again, we give up instead of looping. That's the "once" in "refresh once".
refreshPromiseIf five requests fail together, the first starts a refresh and the other four await the same Promise. Without this, five refreshes would race, and with token rotation four of them would fail.
.finally(() => refreshPromise = null)Clear it when done, so a later expiry can refresh again.
return api(original)Send the original request again with the new header. The caller never knows a refresh happened.
SESSION_EXPIRED_EVENTThe interceptor can't use hooks (it's not a component), so it announces the problem with a browser event and AuthProvider listens. The same trick as WATCHLIST_CHANGED_EVENT in the real repo.
getErrorMessageOne function that understands NestJS errors (message as a string or an array) and network failures, like the real callBackend's message handling.
The refresh endpoint is a level up in the login guideYour practice backend only has GET /auth/refresh-token if you did the "Refresh endpoint with a second strategy" level up in the login guide's section 7. This code assumes you built it like the real backend: refresh token as the Bearer, answer { message, result: { accessToken, refreshToken } }. Without it, the refresh call 404s, refreshAccessToken returns null, and the user is logged out cleanly on the first 401. Either way nothing crashes.

Compared with the real code: the real repo has three refresh paths (section 9) and only the fetch helpers refresh on a 401. Here every request made through api gets the same behavior, written once.

      .get<ApiEnvelope<{ userId: string }>>('/auth/me')
      .then((res) => {
        if (!cancelled) dispatch(userLoggedIn({ id: res.data.result.userId }))
      })
      .catch(() => {
        if (!cancelled) {
          clearTokens()
          dispatch(userLoggedOut())
        }
      })
    return () => {
      cancelled = true
    }
  }, [dispatch])

  // The interceptor gave up refreshing: forget the user and their cached data.
  useEffect(() => {
    const onExpired = () => {
      dispatch(userLoggedOut())
      queryClient.clear()
    }
    window.addEventListener(SESSION_EXPIRED_EVENT, onExpired)
    return () => window.removeEventListener(SESSION_EXPIRED_EVENT, onExpired)
  }, [dispatch, queryClient])

  const login = useCallback(
    async (email: string, password: string) => {
      const res = await api.post<ApiEnvelope<LoginResult>>('/auth/login', { email, password })
      const { user: loggedIn, accessToken, refreshToken } = res.data.result
      saveTokens(accessToken, refreshToken)
      dispatch(userLoggedIn({ id: loggedIn.id, email: loggedIn.email }))
    },
    [dispatch],
  )

  const logout = useCallback(async () => {
    try {
      await api.get('/auth/logout') // clears the refresh token hash on the server
    } catch {
      // Already logged out on the server, or offline. Log out locally anyway.
    }
    clearTokens()
    dispatch(userLoggedOut())
    queryClient.clear()
    router.replace('/login')
  }, [dispatch, queryClient, router])

  const value = useMemo(() => ({ user, status, login, logout }), [user, status, login, logout])
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>
}

export function useAuth() {
  const context = useContext(AuthContext)
  if (!context) throw new Error('useAuth must be used inside AuthProvider')
  return context
}
PieceMeaning
the first useEffectThe session check. A cookie existing isn't proof of anything, so ask GET /auth/me (the guarded route from the login guide). If the access token expired, the interceptor refreshes first, and the user never notices.
let cancelled = false ... cancelled = trueThe cleanup sets a flag so a response arriving after unmount, or after Strict Mode's first discarded run, is ignored. This is the simplest way to avoid "setting state for a component that's gone".
res.data.result.userIdYour practice /auth/me returns req.user, which is the JWT payload { userId, iat, exp }, so the email isn't available after a reload, only right after login.
queryClient.clear()Throws away every cached query, so the next user on this browser can't see the previous user's data. Same reason the real logout calls resetApiState().
login returns a Promise and throws on failureThe context doesn't show toasts. The login page decides what to say, keeping this file free of UI.
api.get('/auth/logout')The real logout endpoint, which nulls the stored refresh hash on the server. The real marketplace calls /auth/logout-cookies instead (section 9).
useCallback and useMemoKeep login, logout and value stable, so consumers rerender only when user or status really change. The real AuthContext skips this.

Compared with the real code: the real AuthProvider only knows "token cookie exists: yes or no" and has no user object; it also sits above the Redux provider. Yours sits inside both the Redux and React Query providers, because it uses both. Its login takes credentials and does the request, while the real login() only flips a boolean after the form has already done the work.

13.10The list page: search, sort and pages in the URL

First a small generic debounce hook, the same idea as the real useDebounces:

src/hooks/useDebounce.ts 
import { useEffect, useState } from 'react'

export function useDebounce<T>(value: T, delay = 400): T {
  const [debounced, setDebounced] = useState(value)
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay)
    return () => clearTimeout(timer)
  }, [value, delay])
  return debounced
}

Now the page. The idea: the URL is the source of truth for page, search and sort. That makes the back button, refreshing and sharing a link all just work. The search box keeps a temporary draft while you type, and pushes it into the URL after a pause.

src/pages/listings/index.tsx 
import Link from 'next/link'
import { useRouter } from 'next/router'
import { useCallback, useEffect, useState } from 'react'
import { keepPreviousData, useMutation, useQuery, useQueryClient } from '@tanstack/react-query'
import { toast } from 'react-toastify'
import { useAuth } from '@/context/AuthContext'
import { useDebounce } from '@/hooks/useDebounce'
import { getErrorMessage } from '@/lib/api'
import {
  deleteListing, fetchListings, formatUsd, listingKeys,
  type Listing, type ListingSort, type ListingsPage, type ListingsQuery,
} from '@/lib/listingsApi'

const PAGE_SIZE = 10
const SORTS: { value: ListingSort; label: string }[] = [
  { value: 'newest', label: 'Newest first' },
  { value: 'price_asc', label: 'Price: low to high' },
  { value: 'price_desc', label: 'Price: high to low' },
]

type RawQuery = Record<string, string | string[] | undefined>
const first = (value: string | string[] | undefined) => (Array.isArray(value) ? value[0] : value) ?? ''

/** Reads page, search and sort from the URL, with safe defaults for anything missing or wrong. */
function readQuery(raw: RawQuery): ListingsQuery {
  const page = Math.max(1, Number(first(raw.page)) || 1)
  const sortRaw = first(raw.sort)
  const sort = SORTS.some((s) => s.value === sortRaw) ? (sortRaw as ListingSort) : 'newest'
  return { page, limit: PAGE_SIZE, search: first(raw.search), sort }
}

export default function ListingsPage() {
  const router = useRouter()
  const queryClient = useQueryClient()
  const { user } = useAuth()
  const query = readQuery(router.query)
  const { page, search, sort } = query

  // Writes page, search and sort back to the URL, leaving defaults out to keep it tidy.
  const updateUrl = useCallback(
    (changes: Partial<Pick<ListingsQuery, 'page' | 'search' | 'sort'>>) => {
      const next = { page, search, sort, ...changes }
      const urlQuery: Record<string, string> = {}
      if (next.search) urlQuery.search = next.search
      if (next.sort !== 'newest') urlQuery.sort = next.sort
      if (next.page > 1) urlQuery.page = String(next.page)
      return router.replace({ pathname: router.pathname, query: urlQuery }, undefined, { shallow: true })
    },
    [router, page, search, sort],
  )

  // The search box: null means "show what the URL says".
  const [draft, setDraft] = useState<string | null>(null)
  const debouncedDraft = useDebounce(draft, 400)

  useEffect(() => {
    if (draft === null || debouncedDraft !== draft) return // still typing
    if (debouncedDraft === search) {
      setDraft(null)
      return
    }
    updateUrl({ search: debouncedDraft, page: 1 }).then(() => {
      setDraft((current) => (current === debouncedDraft ? null : current))
    })
  }, [draft, debouncedDraft, search, updateUrl])

  const listingsQuery = useQuery({
    queryKey: listingKeys.list(query),
    queryFn: ({ signal }) => fetchListings(query, signal),
    enabled: router.isReady,
    placeholderData: keepPreviousData,
  })

  const deleteMutation = useMutation({
    mutationFn: (id: string) => deleteListing(id),
    onMutate: async (id) => {
      // Stop any refetch that could overwrite our optimistic change.
      await queryClient.cancelQueries({ queryKey: listingKeys.lists() })
      // Remember every cached page, so we can undo.
      const previous = queryClient.getQueriesData<ListingsPage>({ queryKey: listingKeys.lists() })
      // Remove the listing from every cached page right now.
      queryClient.setQueriesData<ListingsPage>({ queryKey: listingKeys.lists() }, (old) =>
        old
          ? {
              ...old,
              items: old.items.filter((item) => item.id !== id),
              paginationInfo: { ...old.paginationInfo, total: old.paginationInfo.total - 1 },
            }
          : old,
      )
      return { previous }
    },
    onError: (err, _id, context) => {
      // Roll back: put every page back exactly as it was.
      context?.previous.forEach(([key, data]) => queryClient.setQueryData(key, data))
      toast.error(getErrorMessage(err, 'Could not delete the listing.'))
    },
    onSuccess: () => toast.success('Listing deleted.'),
    onSettled: (_data, _err, id) => {
      queryClient.removeQueries({ queryKey: listingKeys.detail(id) })
      queryClient.invalidateQueries({ queryKey: listingKeys.all })
    },
  })

  const handleDelete = (listing: Listing) => {
    if (window.confirm(`Delete ${listing.domainName}? This cannot be undone.`)) {
      deleteMutation.mutate(listing.id)
    }
  }

  const info = listingsQuery.data?.paginationInfo

  return (
    <main className="page">
      <h1>Domain listings</h1>
      <div className="toolbar">
        <input
          type="search"
          placeholder="Search domains"
          aria-label="Search domains"
          value={draft ?? search}
          onChange={(e) => setDraft(e.target.value)}
        />
        <select aria-label="Sort" value={sort} onChange={(e) => updateUrl({ sort: e.target.value as ListingSort, page: 1 })}>
          {SORTS.map((option) => (
            <option key={option.value} value={option.value}>{option.label}</option>
          ))}
        </select>
      </div>

      {listingsQuery.isPending ? (
        <p className="muted">Loading listings…</p>
      ) : listingsQuery.isError ? (
        <div className="error-box">
          <p>{getErrorMessage(listingsQuery.error)}</p>
          <button type="button" onClick={() => listingsQuery.refetch()}>Try again</button>
        </div>
      ) : listingsQuery.data.items.length === 0 ? (
        <p className="muted">{search ? `No listings match "${search}".` : 'No listings yet. Be the first to sell one.'}</p>
      ) : (
        <table style={{ opacity: listingsQuery.isPlaceholderData ? 0.6 : 1 }}>
          <thead>
            <tr><th>Domain</th><th>Price</th><th>Status</th><th /></tr>
          </thead>
          <tbody>
            {listingsQuery.data.items.map((listing) => (
              <tr key={listing.id}>
                <td><Link href={`/listings/${listing.id}`}>{listing.domainName}</Link></td>
                <td>{formatUsd(listing.price)}</td>
                <td>{listing.status}</td>
                <td>
                  {user?.id === listing.ownerId && (
                    <div className="actions">
                      <Link href={`/listings/${listing.id}/edit`}>Edit</Link>
                      <button type="button" className="danger" onClick={() => handleDelete(listing)}>Delete</button>
                    </div>
                  )}
                </td>
              </tr>
            ))}
          </tbody>
        </table>
      )}

      {info && info.lastPage > 1 && (
        <div className="pager">
          <button type="button" className="secondary" disabled={!info.prevPage} onClick={() => info.prevPage && updateUrl({ page: info.prevPage })}>
            Previous
          </button>
          <span>Page {info.page} of {info.lastPage}</span>
          <button type="button" className="secondary" disabled={!info.nextPage} onClick={() => info.nextPage && updateUrl({ page: info.nextPage })}>
            Next
          </button>
        </div>
      )}
    </main>
  )
}

The URL as state

PieceMeaning
readQuery(router.query)Every render reads page, search and sort from the URL. Anything a user typed into the address bar is treated as untrusted: a bad sort falls back to 'newest', a bad page to 1.
first(...)router.query.search can be a string, an array (?search=a&search=b) or missing. This picks one string.
router.replace(..., { shallow: true })Change the URL without adding a history entry for every keystroke or sort change, and without rerunning data functions. Use push instead if you want each page change to be its own back button step.
updateUrl in useCallbackIt's a dependency of the search effect. Depending on page, search and sort (plain strings and numbers), not on the query object, keeps it from changing on every render, which would rerun the effect every render.
enabled: router.isReadyOn the first render the router may not have read the URL yet; fetching then would load page 1 and then immediately page 3. Wait until it's ready.

Debounced search, without fighting the URL

While you type, draft holds your text and the box shows it. useDebounce waits for a 400ms pause. When the debounced value catches up with the draft, the effect writes it into the URL (resetting to page 1, because page 3 of a new search makes no sense), and when the URL has updated, it sets draft back to null so the box follows the URL again. The current === debouncedDraft check makes sure that if you kept typing during the URL update, your newer text isn't thrown away. And because the box shows the URL whenever draft is null, the back button restores old searches by itself.

The query: caching, race conditions and cancelling

queryKey: listingKeys.list(query) gives every combination of page, search and sort its own cache entry. That one decision solves the race condition from section 8. If you type "cof" and then "coffee", the two responses go into two different cache entries, and the page only ever shows the entry for the current key, so a slow "cof" response can never overwrite "coffee". On top of that, because queryFn passes React Query's signal to axios, the "cof" request is actually cancelled once nothing is waiting for it (you'll see it marked as cancelled in the Network tab). placeholderData: keepPreviousData keeps showing the old page while the next one loads, instead of flashing "Loading", and isPlaceholderData lets us fade it slightly so the user knows it's updating. Inline style is fine here, since opacity is computed at runtime; in the real design system you'd use a class.

The four states, and the optimistic delete

isPending (no data yet), isError (with a retry button), empty (with a message that depends on whether you searched) and success: the same four states as the real details page. React Query's result type is a union, so after the isPending and isError checks TypeScript knows data exists, which is why listingsQuery.data.items needs no ?.

Mutation stepWhat happens
onMutateRuns before the request. Cancel in flight list fetches (they'd overwrite our change), snapshot every cached list page, then remove the listing from all of them. The row vanishes instantly: that's an optimistic update, showing success before the server confirms it.
return { previous }Whatever onMutate returns arrives in the other callbacks as context.
onErrorThe server said no (403 not yours, 404 already gone, network down). Put every snapshot back, which is the rollback, and explain with a toast.
onSettledRuns after success or failure. Drop the deleted listing's detail cache and invalidate everything about listings, so the real data from the server replaces our guess.
window.confirmA plain confirmation, the same choice the real handleDelist makes.

Compared with the real code: the real useWatchlist updates only after the server answers (not optimistic), keeps its own useState list, and uses a window event to tell the badge. Here one cache plus invalidateQueries does all three jobs. And the real marketplace filters search on the client side over already fetched rows, while this page sends search to the backend's ILIKE query.

13.14Finally, a useListings hook

The list page works, but it's long, and half of it is "how to talk to the URL and the cache", not "what to draw". Move that half into a custom hook. The page gets shorter, and the logic becomes reusable and testable.

src/hooks/useListings.ts 
import { useRouter } from 'next/router'
import { useCallback, useEffect, useState } from 'react'
import { keepPreviousData, useMutation, useQuery, useQueryClient } from '@tanstack/react-query'
import { toast } from 'react-toastify'
import { useDebounce } from '@/hooks/useDebounce'
import { getErrorMessage } from '@/lib/api'
import { deleteListing, fetchListings, listingKeys, type ListingSort, type ListingsPage, type ListingsQuery } from '@/lib/listingsApi'

export const PAGE_SIZE = 10
export const LISTING_SORTS: { value: ListingSort; label: string }[] = [
  { value: 'newest', label: 'Newest first' },
  { value: 'price_asc', label: 'Price: low to high' },
  { value: 'price_desc', label: 'Price: high to low' },
]

type RawQuery = Record<string, string | string[] | undefined>
const first = (value: string | string[] | undefined) => (Array.isArray(value) ? value[0] : value) ?? ''

function readQuery(raw: RawQuery): ListingsQuery {
  const page = Math.max(1, Number(first(raw.page)) || 1)
  const sortRaw = first(raw.sort)
  const sort = LISTING_SORTS.some((s) => s.value === sortRaw) ? (sortRaw as ListingSort) : 'newest'
  return { page, limit: PAGE_SIZE, search: first(raw.search), sort }
}

/** Everything the listings page needs: URL state, debounced search, the query and an optimistic delete. */
export function useListings() {
  const router = useRouter()
  const queryClient = useQueryClient()
  const query = readQuery(router.query)
  const { page, search, sort } = query

  const updateUrl = useCallback(
    (changes: Partial<Pick<ListingsQuery, 'page' | 'search' | 'sort'>>) => {
      const next = { page, search, sort, ...changes }
      const urlQuery: Record<string, string> = {}
      if (next.search) urlQuery.search = next.search
      if (next.sort !== 'newest') urlQuery.sort = next.sort
      if (next.page > 1) urlQuery.page = String(next.page)
      return router.replace({ pathname: router.pathname, query: urlQuery }, undefined, { shallow: true })
    },
    [router, page, search, sort],
  )

  const [draft, setDraft] = useState<string | null>(null)
  const debouncedDraft = useDebounce(draft, 400)

  useEffect(() => {
    if (draft === null || debouncedDraft !== draft) return
    if (debouncedDraft === search) {
      setDraft(null)
      return
    }
    updateUrl({ search: debouncedDraft, page: 1 }).then(() => {
      setDraft((current) => (current === debouncedDraft ? null : current))
    })
  }, [draft, debouncedDraft, search, updateUrl])

  const listingsQuery = useQuery({
    queryKey: listingKeys.list(query),
    queryFn: ({ signal }) => fetchListings(query, signal),
    enabled: router.isReady,
    placeholderData: keepPreviousData,
  })

  const deleteMutation = useMutation({
    mutationFn: (id: string) => deleteListing(id),
    onMutate: async (id) => {
      await queryClient.cancelQueries({ queryKey: listingKeys.lists() })
      const previous = queryClient.getQueriesData<ListingsPage>({ queryKey: listingKeys.lists() })
      queryClient.setQueriesData<ListingsPage>({ queryKey: listingKeys.lists() }, (old) =>
        old
          ? {
              ...old,
              items: old.items.filter((item) => item.id !== id),
              paginationInfo: { ...old.paginationInfo, total: old.paginationInfo.total - 1 },
            }
          : old,
      )
      return { previous }
    },
    onError: (err, _id, context) => {
      context?.previous.forEach(([key, data]) => queryClient.setQueryData(key, data))
      toast.error(getErrorMessage(err, 'Could not delete the listing.'))
    },
    onSuccess: () => toast.success('Listing deleted.'),
    onSettled: (_data, _err, id) => {
      queryClient.removeQueries({ queryKey: listingKeys.detail(id) })
      queryClient.invalidateQueries({ queryKey: listingKeys.all })
    },
  })

  return {
    query,
    listingsQuery,
    searchText: draft ?? search,
    setSearchText: setDraft,
    setSort: (value: ListingSort) => updateUrl({ sort: value, page: 1 }),
    goToPage: (value: number) => updateUrl({ page: value }),
    deleteListing: deleteMutation.mutate,
  }
}

14. Debugging like a professional

Most frontend bugs are answered by one question: what actually went over the wire? Learn to answer it in ten seconds and you'll stop guessing.

The Network tab

Open DevTools (F12), choose Network, tick Preserve log (so redirects don't wipe it) and filter by Fetch/XHR. Click a request and read it top to bottom:

WhereWhat to check
Headers, GeneralRequest URL: is it the host and path you expected, including /api/v1? Request Method: GET versus POST versus PATCH. Status Code: the backend's answer.
Headers, Request HeadersIs Authorization: Bearer ... there? Is Origin what you think (http://localhost:3002)? Is Content-Type: application/json set for bodies?
Headers, Response HeadersAccess-Control-Allow-Origin (missing means CORS will block it), Set-Cookie (the server setting cookies).
PayloadThe body and query string you actually sent. This is where you'd see a PATCH carrying fields you didn't mean to send, or a price sent as "25" instead of 25.
Preview, ResponseThe JSON that came back. For errors, NestJS's { statusCode, message, error } tells you exactly what failed.
TimingSlow requests, and whether time went to waiting for the server or downloading.
Cookies (on the request)Which cookies were sent. With credentials: 'include' you'll see the domain cookies here.

Two power moves: right click a request and choose Copy as cURL to replay it in a terminal (now you know whether the problem is the browser or the server), and look for an OPTIONS request before a failing one, which is the CORS preflight.

The Application tab

Under Application, Cookies, pick the site to see access_token and refresh_token, their expiry and flags. You can edit or delete them here, which is the fastest way to test "what happens when the token is gone?". Paste a token into a JWT decoder (jwt.io, or atob on its middle part in the Console) to read its exp; that's what _app.tsx's minute check compares against. Local storage shows lastActivityTimestamp from the idle timer, and Session storage shows token_expired.

The Console

Errors are red, warnings yellow. Click the file link on the right of a message to jump to the line in the Sources tab. This repo prefixes many logs with a tag like [marketplace] or [my-domains], so filtering the console by that tag shows just one feature's story. Remember production builds strip console.log (but keep console.error) because of compiler.removeConsole, so a log you see locally won't exist in production.

Five ways to call the APIFetch helpers, axios with a global interceptor, callBackend, RTK Query and a raw fetch, each with its own token, error and refresh behavior (section 8). Only the fetch helpers refresh on a 401.
postApiCall ignores its own optionsIt builds headers and axiosConfig (with withCredentials) and then calls axios.post(url, formData) without them. It works only thanks to the global interceptor, and withCredentials is never applied.
putApi retries as a POSTOn a successful refresh after a 401, putApi calls postApi(url, formData), so the retry goes out with the wrong method. (Only the dev test page calls putApi today.)
postApi never checks response.okAn error body comes back as if it were success, so callers crash on response.result.user instead of seeing the real message.

16. Common beginner mistakes

Not checking response.ok with fetch 
// WRONG: a 401 or 500 still "succeeds" here
const data = await (await fetch(url)).json()
setListings(data.result.items)   // crashes: an error body has no result

// FIXED
const res = await fetch(url)
const data = await res.json().catch(() => ({}))
if (!res.ok) throw new Error(data.message ?? `Request failed (${res.status})`)
setListings(data.result.items)
This is exactly the postApi quirk.
Mutating state 
// WRONG: same array, React sees no change
entries.push(newEntry)
setEntries(entries)

// FIXED: a new array, built from the latest value
setEntries((prev) => [...prev, newEntry])
Expecting state to update immediately 
// WRONG
setPage(2)
fetchPage(page)   // still the old page

// FIXED: use the value you just computed, or let an effect or query key react to the change
const next = 2
setPage(next)
fetchPage(next)
The effect that loops forever 
// WRONG: a new object every render, so the effect runs every render
const filters = { search, page }
useEffect(() => { load(filters) }, [filters])

// FIXED: depend on primitives
useEffect(() => { load({ search, page }) }, [search, page])
Forgetting the cleanup 
// WRONG: every mount adds a listener that never goes away
useEffect(() => {
  window.addEventListener('resize', onResize)
}, [])

// FIXED
useEffect(() => {
  window.addEventListener('resize', onResize)
  return () => window.removeEventListener('resize', onResize)
}, [])
Compare useIsMobile, which does it right.
Ignoring stale responses 
// WRONG: if id changes quickly, an old response can land last
useEffect(() => {
  fetchListing(id).then(setListing)
}, [id])

// FIXED: cancel the old request when id changes
useEffect(() => {
  const controller = new AbortController()
  fetchListing(id, controller.signal).then(setListing).catch(() => {})
  return () => controller.abort()
}, [id])
Or let React Query key the cache by id (section 13.11).
Calling a hook conditionally 
// WRONG
if (!user) return null
const { data } = useQuery(...)   // runs on some renders, not others

// FIXED: hooks first, early returns after (or an inner component)
const { data } = useQuery({ ..., enabled: !!user })
if (!user) return null
Calling the handler instead of passing it 
// WRONG: runs toggle during render, every render
<button onClick={toggle(listing.id)}>

// FIXED
<button onClick={() => toggle(listing.id)}>
Using the index as a key in a list that changes 
// WRONG: delete row 2 and row 3's state jumps to row 2
{listings.map((listing, i) => <ListingRow key={i} listing={listing} />)}

// FIXED
{listings.map((listing) => <ListingRow key={listing.id} listing={listing} />)}
Reading browser only values during render 
// WRONG: crashes on the server, or causes a hydration mismatch
const isMobile = window.innerWidth < 768

// FIXED: read it after mount
const isMobile = useIsMobile(767)
Sending a number as a string 
// WRONG: the backend's @IsNumber() rejects "25" with a 400
await api.post('/listings', { domainName, price: priceInput.value })

// FIXED
await api.post('/listings', { domainName, price: Number(priceInput.value) })
Putting secrets in NEXT_PUBLIC_ variables 
# WRONG: this ends up inside the JavaScript every visitor downloads
NEXT_PUBLIC_ADMIN_API_KEY=abc123

# FIXED: public values only; secrets stay on a server you control
NEXT_PUBLIC_API_URL=http://localhost:3001/api/v1
Treating frontend guards as security 
// WRONG: hiding the button is not protection
{isOwner && <button onClick={remove}>Delete</button>}
// ...and the backend deletes whatever id it receives

// FIXED: hide it for good UX, AND have the backend check ownership
// (findOwned in the CRUD guide returns 403 for everyone else)
Using a plain anchor for in app links 
// WRONG: a full page reload, every bit of state lost
<a href="/watchlist">Watchlist</a>

// FIXED
<Link href="/watchlist">Watchlist</Link>
