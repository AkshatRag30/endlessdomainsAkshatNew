1

Decide where the shared state lives

Five unrelated files and one modal host all need to read and write "which domain is being bought, is a popup open." That state has to live somewhere all of them can reach. Two candidates existed in this codebase already, and the choice mattered enough to check properly rather than default to whichever felt more familiar.

What was checked

src/context/AuthContext.tsx, the one place this app already does exactly this kind of thing, a single piece of session state with actions exposed through a custom hook, useAuth, backed by a provider mounted once in pages/_app.tsx.

src/core/redux/slice/userProfileSlice.ts and src/core/redux/store.ts, to see what Redux is actually used for in this app, real server backed data: the profile, the wallet address, domain listings, analytics mutations.

Decision

Use a Context, following AuthContext.tsx, not a Redux slice

"Which domain is mid purchase and is a popup open" isn't server data and doesn't need to survive a reload, it's a flow control flag. That's exactly the shape AuthContext already exists for in this app, and there's no equivalent pattern for it in Redux, everything in Redux here is real fetched or cached application data. Copying the existing pattern beats inventing a new one or bending Redux to a job it isn't used for anywhere else in this codebase.

One placement flag raised here, resolved in step 3: AuthProvider sits outside the Redux Provider in _app.tsx. The new buy intent provider can't sit in that same spot, because it needs evmWalletAddress from Redux via useSelector, so it has to be mounted inside the Redux Provider instead.

2

Build the hook

New file: src/context/BuyIntentContext.tsx. Exports useBuyIntent() and a BuyIntentProvider, following the exact shape of AuthContext/useAuth from step 1.

What it does

Reproduces the four step gate ladder pulled directly from domain-item/page.tsx lines 144 to 170, the reference implementation: check the login token, check the saved wallet address, check the wallet is actually connected, and either open the wallet popup or open the buy popup and fire the tracking call. One function, buy(domain), runs the whole thing.

Added onWalletConfirmed(), which resumes the buy flow for whichever domain was selected once the wallet actually connects, matching what every one of the five files did today through WalletConect's onConfirm callback.

✓ Typecheck clean immediately after creating this one file, before touching anything else.
3

Build the single modal host

New file: src/component/buy-intent-modal-host/index.tsx. One BuyNowModal, one WalletConect, driven entirely by useBuyIntent().

Decision

Added a BuyableDomain type, in src/types/BuyModal.ts

The five files don't agree on what a domain looks like: one calls the id field id, another calls it domain_id; one calls the network field currency, others call it assetContract; keywords show up as a raw array in some places and already joined into a string in others. Rather than have the shared host guess which name applies, one clear shape was defined once, and each file maps its own local names into it at the call site during migration.

Safety check performed before consolidating

Mounting WalletConect once instead of once per card is the actual fix for the performance finding in the review, but that only works if nothing else depends on it remounting. Searched every usage first: it's actually used in six places, not five, the sixth being domain-self-item/index.tsx, the seller's own listing management page, which uses it for confirming a delist, a completely different action. That file is outside this phase's scope and was left untouched.

Also checked whether calling createAppKit(...) only once was safe. It's already called independently in three other unrelated places in this app today, wallet-signup/index.tsx, wallet-connect/index.tsx itself, and profile-form/AddWalletAddress.tsx, which means the app already tolerates it being called more than once. Going from five calls down to one for the buy flow specifically has no hidden coupling.

Wired into pages/_app.tsx

BuyIntentProvider and BuyIntentModalHost were mounted right next to the two other app wide helpers already sitting there, AutoLogoutHandler and InitProvider, and placed inside the Redux Provider, resolving the placement flag from step 1.

✓ Typecheck clean. Lint clean, only pre-existing "any" warnings matching the style already used in BuyNowModalProps.

Decision, flagged before editing

Dropped an extra refetchProfile() call this one file had

This file's toggleModal() also refetched the user's profile before opening the wallet popup, a side effect none of the other four files had. Checking wallet-connect/index.tsx directly showed WalletConect already runs its own profile query internally, making this extra refetch redundant rather than load bearing. Replicating one file's extra behavior into the shared hook would have undermined the point of consolidating, so it was dropped, not carried forward as a special case.

Testing this phase

The migration above was verified by the type checker and linter as it was built, but none of that proves the app actually works in a browser. This section covers what came out of actually running it, first three local blockers that had nothing to do with the buy gate at all, then what got confirmed working, then a handful of real findings that turned out to belong to other parts of the app, not this one.

Local environment blockers, found before any of this could even be tested

Blocker 1, fixed

Every single API call was 404ing, homepage and grid both showed nothing

NEXT_PUBLIC_API_URL in the local .env was missing a /v1 segment. Confirmed by loading the app in a headless browser and watching every network call fail, then confirmed the fix by comparing against the actual working staging deployment, which calls the same host with /v1 in the path. Not caused by phase 1, this value was already wrong before this session started.

Blocker 2, fixed

Three of five top nav links pointed nowhere

MAIN_SITE_URL was missing from .env entirely, so Domains, Parked Domains, and Domain Appraisal all resolved to undefined/.... Fixed with the real value confirmed against the working deployment's actual link hrefs, https://stage.endlessdomains.io, rather than guessed.

Blocker 3, added then removed

SITE_URL turned out not to be the actual problem

Added briefly to fix a missing "Portfolio URL" line on the Profile page, then removed once testing showed the real cause was something else entirely, see the user hash finding below. Kept out of .env since it wasn't proven necessary.

Confirmed working

Verified

Real domains render on the homepage and grid once the env blockers above were fixed, and every API call lands on /v1 with normal 200 or 401 responses, no more 404s.

No JavaScript errors anywhere on page load, checked with a headless browser's console output, not just visually.

Clicking Buy Now on a grid card while logged out shows "Please log in to purchase the domain." and nothing else happens, confirmed in a real browser, proving the migrated hook's login check works end to end, not just in the type checker.

The homepage inline trending section, the one file that used to skip the wallet check entirely, was specifically retested and now behaves the same as the other four surfaces.

Found while testing, confirmed not this phase's problem

Each of these came up while working through the test checklist. Every one was traced to an actual cause rather than assumed, and every one lands outside phase 1, either a different file entirely, the backend, or the untouched transaction handler that phase 2 covers.

Backend, account state

Your account's user hash comes back null, blocking your own seller portfolio

The /users/user-hash call returns {"result": null} for this account, on stage as well as locally. That's why the "Portfolio URL" row never shows in your own Profile page, the code is doing exactly what it should given what the backend sent. No /seller-portfolio/... URL exists for this account until the backend assigns it a hash, nothing fixable from this repository.

Backend bug, different file

"Unlisted" showing 0 domains on the My Domains page

Traced to pages/profile/domains/index.tsx, the "My Domains" page from the header dropdown, a file phase 1 never touched. The get-domains-summary-by-user response itself is contradictory: "totalUnlisted": 5 right next to "data": []. The backend's own count logic and its own list logic disagree with each other inside one response. Confirmed this isn't the frontend's double filter causing it, filtering an empty array just gives an empty array either way.

Backend hygiene

A debug string leaking into a real error message

The session check endpoint returned "User not authenticated sdgsdgsdgf", a placeholder string that shouldn't be in a production-facing message. Worth reporting alongside the finding above, same backend, same staging deploy.

Confirmed harmless

add-analytics returning 429 during testing

Traced via its own stack trace to BuyIntentContext.tsx's tracking call, fired from the grid card. It's fire and forget, nothing awaits it or checks its result, so a rate limited tracking call can't and doesn't block the buy flow, confirmed the popup still opened normally when this happened. Most likely caused by the volume of automated and manual testing hitting the same staging API today, not a logic bug.

Real bug, but phase 2's file

The actual purchase fails with an on chain revert

Clicking Buy inside the popup throws call revert exception ... method="getRequiredNativeAmount(uint256)", caught by BuyNowModal.tsx's single generic catch block and shown as "Something went wrong. Please try again.", the exact "every failure reads the same" finding the original review already documented. This file was not touched by phase 1. Most likely cause: this domain's listing exists in the backend's database but not, or not correctly, on the actual smart contract for the connected chain, a data mismatch common on staging environments where backend and on chain state are seeded separately. Phase 2 would make the error message honest instead of generic, it would not make a listing that doesn't really exist on chain purchasable.
