Start here: eight ideas everything else depends on

Nothing on this page requires prior React or TypeScript experience, but it does assume these eight ideas. They're small, and once they click, the rest of the document reads like plain English instead of a foreign language. If they're already familiar, skip straight to the hook. Every example in this section is a short, made up snippet built only to demonstrate the idea, it isn't from this codebase, it's marked "illustrative example" so it's never confused with the real, verified code that fills the rest of the page.

0.1  A component is just a function that draws part of the screen

Everything visible in this app, a button, a card, an entire page, is built out of components. A component is a normal JavaScript function, with one rule: it has to hand back a description of what should appear on screen. React takes that description and turns it into real, visible pixels.

a tiny made up exampleillustrative example
1function Greeting() {
2 return <h1>Hello there</h1>;
3}
in plain englishGreeting is a function like any other. Instead of returning a number or a string, it returns a description of an on screen heading. Somewhere else, React will call this function and put that heading on the page.

0.2  JSX: writing tags inside JavaScript

That <h1>Hello there</h1> above looks like HTML, but it's sitting directly inside a JavaScript function. That combination is called JSX. It's not a separate language, it's a shorthand that gets converted into plain JavaScript before it ever runs. The one thing worth knowing early: curly braces, { }, are the escape hatch. Anywhere inside JSX, wrapping something in { } means "stop treating this as a tag, this is real JavaScript, evaluate it and show the result."

a tiny made up exampleillustrative example
1function Greeting() {
2 const name = "Akshat";
3 return <h1>Hello, {name}</h1>;
4}
in plain englishThe word name inside those braces is not text on the page, it's a real variable. React runs it, gets back the string "Akshat", and drops that into the sentence. If it had been written without the braces, as literal text name, the page would show the word "name," not the value.

0.3  Props: data handed down from parent to child

A component can accept input, the same way a function accepts arguments. In React, that input is called a prop, short for "property." Whoever renders the component decides what to hand it, and the component reads it back out through destructuring, which is covered in 0.6 below.

a tiny made up exampleillustrative example
1function Greeting({ name }: { name: string }) {
2 return <h1>Hello, {name}</h1>;
3}
4
5<Greeting name="Akshat" />
in plain englishLine 5 is where Greeting actually gets used, and name="Akshat" is the prop being handed in, exactly the way an argument gets handed into a normal function call. Inside the component on line 1, that same value shows up as the variable name. This is the entire relationship between a parent component and a child component: the parent writes the tag with some attributes, the child receives those attributes as props.

0.4  State: a value a component remembers, and re-renders when it changes

A plain variable inside a function forgets itself the moment the function finishes running. That's a problem for a component, because React calls a component's function over and over, once per render, and a normal variable would reset to its starting value every single time. useState is React's way around that: it gives a component a value that survives between renders, and a way to change that value that automatically tells React "something changed, please redraw this."

a tiny made up exampleillustrative example
1function Counter() {
2 const [count, setCount] = useState(0);
3 return (
4 <button onClick={() => setCount(count + 1)}>
5 Clicked {count} times
6 </button>
7 );
8}
Basics: reading const [a, b] = useState(0)

useState(0) starts a stored value at 0 and hands back exactly two things, always in this order: the current value, and a function for changing it. The square brackets on the left, [count, setCount], are array destructuring, a shortcut for pulling items out of an array by position instead of writing const count = result[0]; const setCount = result[1]; on two separate lines. The names count and setCount aren't special keywords, they're just the names chosen for this particular pair, any two names would work, but "value" and "setValue" is the convention this whole codebase follows, for example selectedDomain and setSelectedDomain later in this document.

Calling setCount(count + 1) does two things: it updates the remembered value, and it tells React to run this component's function again so the screen catches up. That second part is the entire difference from a plain variable, plain variables never trigger a redraw.

0.5  Arrow functions: the () => {} shorthand

JavaScript has more than one way to write a function. This codebase almost always uses the arrow function style, () => { ... }, instead of the older function () { ... } style. They do the same job, an arrow function is just shorter to write and reads naturally as "given these inputs, produce this output."

the same function, two stylesillustrative example
1// older style
2function add(a, b) {
3 return a + b;
4}
5
6// arrow function style, used throughout this codebase
7const add = (a, b) => {
8 return a + b;
9};
in plain englishRead const add = (a, b) => { ... } as "make a variable called add, and its value is a function that takes a and b." Every time this document shows something like const buy = (domain) => { ... }, it's the exact same shape, a variable that holds a function.

0.6  Destructuring: unpacking an object in one step

0.4 showed destructuring an array. The far more common version in this codebase is destructuring an object, pulling named fields straight out of it instead of writing const x = someObject.x on a separate line for every field.

without destructuring, then with itillustrative example
1const domain = { id: 12, domainName: "example.com" };
2
3// without destructuring
4const id = domain.id;
5const domainName = domain.domainName;
6
7// with destructuring, same result, one line
8const { id, domainName } = domain;
in plain englishLine 8 says "look inside domain, and give me two new variables named id and domainName, filled with whatever those fields hold." This shows up constantly in this walkthrough, including in every component's own function signature, the ({ children }: { children: ReactNode }) pattern in section 1 is exactly this, destructuring happening right where the props arrive.

0.7  Import and export: how files share code

Every file in this project is its own little world, isolated by default. export is how a file marks something as available to be used elsewhere, and import is how another file asks to borrow it. Without these two keywords, no two files could ever talk to each other.

two files, one sharing with the otherillustrative example
1// file: math.ts
2export const double = (n: number) => n * 2;
3
4// file: app.ts
5import { double } from "./math";
6console.log(double(4)); // 8
Basics: named export vs. the @/ path

Writing export const, as on line 2, is a named export, the file is sharing something under a specific name, double, and the importer must ask for that exact name inside curly braces, as on line 5. Every piece of shared code in this walkthrough, useBuyIntent, BuyIntentProvider, BuyableDomain, is a named export, which is why every import of them uses that same curly brace form.

The path on line 5, "./math", means "the file called math, in this same folder." Real files in this codebase instead import using paths like "@/core/redux/store". The @/ isn't a real folder, it's an alias set up once in tsconfig.json that always means "start from the src folder," no matter how deeply nested the importing file is. It exists purely so imports don't turn into long chains of ../../../ as files get nested deeper.

0.8  TypeScript: describing a shape before the code runs

Plain JavaScript never checks what shape a piece of data has until the moment the code actually runs, by which point a mistake is a live bug. TypeScript is JavaScript with an extra layer on top: it lets a file describe the exact shape something must have, and then a separate tool, the type checker, reads the whole project and flags anywhere that shape is violated, before the app ever runs. Every file in this codebase ending in .ts or .tsx (rather than plain .js or .jsx) is written in TypeScript.

a shape, and a mistake it catchesillustrative example
1interface Domain {
2 id: number;
3 name: string;
4}
5
6const good: Domain = { id: 1, name: "example.com" }; // fine
7const bad: Domain = { id: 1 }; // error: missing "name"
in plain englishAn interface is not a real, running value, it never appears in the finished JavaScript at all. It's purely a promise checked ahead of time: "anything typed as Domain must have an id that's a number and a name that's a string." Line 7 never gets a chance to run and fail in front of a real user, the mistake gets caught the moment the code is written, underlined in the editor, the same way a red squiggly line flags a misspelled word.
Why this matters for the hook rule ahead

One React rule shows up constantly starting in the very next section: hooks, any function starting with use, must always be called in the same order, every single render, and only from the top level of a component, never inside an if, a loop, or a function defined inside the component. React keeps track of hooks purely by the order they were called in, not by name, so calling one conditionally would make React lose track of which stored value belongs to which useState call between one render and the next, corrupting state in a way that's genuinely confusing to debug. Every hook call in this walkthrough sits at the very top of its component specifically because of this rule.

The whole file in one paragraph, no jargon

Going through it in the order it runs

Lines 1-11 Every import pulls in one thing this file needs from somewhere else. This is exactly how JavaScript modules share code, nothing here is special to React, it's the same mechanism from idea 0.7 above. The last one, line 11, imports the shared shape defined in part 3 below, BuyableDomain, that's what lets this file describe exactly what a "domain" object must look like.

Concept: the @/ path

Paths like @/core/redux/store aren't relative file paths (../../core/redux/store), they're an alias configured once in tsconfig.json that always means "start from the src folder." It exists purely so imports don't turn into long chains of ../../../ as files get nested deeper.

Lines 13-22 This is a TypeScript interface, a description of a shape, not real code that runs, exactly as introduced in idea 0.8. It says: anything claiming to be a BuyIntentContextType must have exactly these nine fields, with exactly these types. Nothing is created yet, this is a contract that gets enforced everywhere the type is used later in the file. Read each field's type as a small English sentence: line 15, isBuyModalOpen: boolean, means "this must be exactly true or exactly false, nothing else." Line 18, buy: (domain: BuyableDomain) => void, means "this must be a function that accepts one argument shaped like BuyableDomain, and doesn't hand anything back," void is TypeScript's word for "returns nothing."

Concept: why describe the shape first

Writing the interface before the logic is a deliberate order. It forces answering "what does this actually need to expose to the rest of the app" before writing a single line of the real behavior. Every field on line 14 to 21 became a field because some other file, the modal host or one of the five migrated files, genuinely needed to read or call it. Nothing extra got added "just in case."

Line 24 createContext is the one React function that actually creates a Context. Think of it as creating an empty radio channel that doesn't broadcast anything yet. The <BuyIntentContextType | null> part is a generic, the blank introduced in the glossary above, it tells TypeScript "whatever gets broadcast on this channel will either match that interface, or be null." The starting value, the thing in the parentheses, is null, because nothing is actually being provided yet at this point in the file, that only happens later, inside the Provider.

Basics: reading BuyIntentContextType | null

The vertical bar | in TypeScript means "or." BuyIntentContextType | null reads as "either a real object matching that interface, or the literal value null, and nothing else is allowed." This shows up constantly in this codebase, for example walletAddress: string | null on line 17 means the wallet address is either a real string or null, never, say, a number or undefined.

Lines 26-32 This is the custom hook every other file actually calls. useContext(BuyIntentContext) tunes in to the channel created above and returns whatever the nearest Provider is currently broadcasting. If nothing above this component in the tree is providing it, useContext returns the fallback from createContext, which was null. That's exactly what the if (!context) check is for.

Basics: what the ! means

In JavaScript, ! means "not," it flips a value to its opposite boolean. !context reads as "is context falsy," true when context is null, undefined, false, 0, or an empty string, and false otherwise. This exact pattern, if (!something) { handle it; return; }, appears so many times in this file that it's worth memorizing once here: it always means "if this thing is missing or empty, deal with that and stop."

Why throw instead of just returning null

A simpler version of this hook could just return context directly and let every caller deal with the possibility of null. That would mean every single one of the five migrated files would need its own if (!buy) return null style guard, or risk a confusing crash three components away from the actual mistake. Throwing here, loudly, the moment the hook is misused, turns "forgot to wrap this page in the Provider" into an error message that points straight at the real problem, immediately, in development, instead of a silent bug discovered later.

Line 39 This is the actual component that will wrap the app. { children }: { children: ReactNode } is destructuring the one prop this component accepts, and typing it, ReactNode is TypeScript's built in type for "anything React can render," which is exactly what a component that just wraps other components needs to accept.

Concept: components that just wrap other components

A Provider component's whole job is usually to set some data up, and then render whatever was passed inside it, untouched. That's what {children} on line 105 does, it's the placeholder for "whatever JSX was nested between the opening and closing <BuyIntentProvider> tags in _app.tsx."

Lines 40-45 Four hooks called right at the top, before any of this component's own logic, exactly matching the ordering rule explained at the end of the Start Here section. This is a hard rule in React, not a style choice, hooks must always run in the same order on every render, so they always go at the top of a component, never inside an if or a loop. Three of these, useRouter, useAppKitProvider, and useSelector, aren't new, they're the exact same hooks the five files used to call individually, just called here once instead of five times.

Lines 47-49 Three separate useState calls, one each for the domain being bought, whether the buy popup is open, and whether the wallet popup is open. Each call returns a pair, the current value and a function to change it, that's why the syntax is const [value, setValue] = useState(...), the array destructuring pattern from idea 0.4. Whenever one of the setter functions runs, React re-renders this component and everything reading from its Context.

Why three separate values instead of one object

These three pieces of state are logically related but change independently, closing the buy popup shouldn't touch which domain is selected, for instance. Three small, named useState calls read clearly and each update is simple. One combined object would mean every update has to spread the rest of the object to avoid wiping out the other fields, more ceremony for no real benefit at this size.

Lines 51-53 A small helper function, defined right inside the component. buy(), the function every single call site actually calls

The same function, told as a story with no code at all

Imagine buy as a single receptionist standing between every "Buy Now" button in the app and the actual purchase screen. Someone clicks a button somewhere. The receptionist asks question one: are you logged in? If not, she tells you to log in, and the conversation ends right there, nothing else happens. If yes, she asks question two: do you have a wallet address saved to your account? If not, she tells you, sends you to your profile page to add one, and the conversation ends there too. If yes, she writes down which domain you wanted, in case she needs to remember it later. Then question three: is your wallet actually connected right now, in this browser, at this moment? If not, she opens the "connect your wallet" popup and waits, she still remembers which domain you wanted. If yes, she logs that you clicked, and finally opens the real purchase popup. Every single check happens in that exact order, every single time, no matter which button was clicked.

Lines 56-60 Read the login cookie. If it's missing, show a message and return, which in a function with no return type just means "stop running this function right here." Nothing after this line executes.

Lines 62-66 Same shape, second check: does this account have a wallet address saved. If not, show a different message and send the browser to the profile page with router.push, then stop.

Concept: the early return pattern

Every check in this function follows the same shape: check a condition, and if it fails, handle it and return immediately, rather than nesting the rest of the function inside an else. This is called an early return or guard clause. The benefit shows up as the function gets longer, each check reads top to bottom as "rule out this problem, then this one, then this one," instead of a pyramid of nested if blocks getting narrower with every check.

Line 68 This line runs unconditionally once both checks above have passed, setSelectedDomain(domain) remembers which domain is being bought no matter what happens next, because both possible next steps, opening the wallet popup or opening the buy popup, need to know which domain it was.

Lines 70-73 The third check: is a wallet actually connected right now. If not, open the wallet popup and stop, this domain stays remembered from line 68, waiting for onWalletConfirmed to pick the flow back up.

Lines 75-76 Only reached if every check above passed. Fire the tracking call, then open the buy popup. This is the one path where analytics gets recorded, which is the entire point of this hook existing, every surface that calls buy() gets this for free, instead of five separate places remembering to add it themselves.

A component's return can only hand back one single thing, not two separate elements side by side. Lines 11-19 One call to useBuyIntent(), and object destructuring pulls out exactly the seven pieces this component actually needs. This is the entire connection between "the decision" and "the rendering," everything below this line is just wiring those seven values into two existing components' props.

Line 23 {selectedDomain && ( ... )} is how conditional rendering works in JSX without writing a full if statement. If selectedDomain is null, JavaScript's && short circuits and the whole expression evaluates to null, which React simply renders as nothing. If it's a real object, truthy, the right hand side, the actual <BuyNowModal>, gets rendered. This is also why BuyNowModal only appears here at all, before any domain has ever been selected, there's nothing to show it data for, so it doesn't render.

Basics: why && works as an on/off switch

&& normally means "and" in an if condition, but in JavaScript it also has a second behavior: a && b checks a first, and if a is falsy, it stops right there and the whole expression becomes a, it never even looks at b. Only if a is truthy does it move on and become b. That's called short circuiting, and it's exactly what turns selectedDomain && (<BuyNowModal .../>) into "show the modal only if a domain has actually been picked."

Line 33 BuyNowModal expects its keywords prop as one comma separated string, but the shared BuyableDomain type stores keywords as a real array, string[]. .join(", ") is a plain JavaScript array method that turns an array into a string, gluing every item together with ", " between them. This is the one spot where the shared shape gets converted into the exact shape one specific old component still expects.

Basics: .join() in one line

["fast", "cool", "short"].join(", ") produces the single string "fast, cool, short". It's a method that exists on every array, and it always works the same way, put the separator in the parentheses, get one string back out.

Line 44 selectedDomain?.id uses optional chaining. Without the ?, reading .id off a null value would throw an error and crash the page. With it, if selectedDomain is null, the whole expression just evaluates to undefined instead of crashing. This matters here specifically because WalletConect, unlike BuyNowModal above it, is rendered unconditionally, it has to exist before a domain is ever selected, so this line has to survive selectedDomain being empty.

The pattern this file follows

A "host" component's whole job is to sit exactly once in the tree, read from a Context, and turn that state into real rendered UI. It owns no state of its own, everything it reads comes from the hook. Anywhere five different files each need to conditionally show the same kind of popup, this same shape, one hook for the decision, one host for the rendering, is worth reaching for again.

The shared type

Not a new file, an addition to an existing one, but worth its own stop because of what it prevents.

src/types/BuyModal.ts
what was added
18// The one shape every buy surface has to normalize its own domain data into
19// before calling buy(domain). The five call sites don't agree today on field
20// names (id vs domain_id, currency vs assetContract, keywords joined vs raw),
21// this is where that gets settled, once, instead of five different ways.
22export interface BuyableDomain {
23 id: any;
24 domainName: string;
25 network: string;
26 tokenId: string;
27 pricePerToken?: number | string;
28 description: string;
29 keywords: string[];
30 endTime?: any;
31 usdAmount: any;
32}
Why this had to exist before the migration could start

Before this, five files each had their own idea of what a domain object looks like, one called the id field id, another called it domain_id, one called the network field currency, others called it assetContract. The shared buy(domain) function has no way to know which name each caller happens to use. Rather than have that shared code guess or handle every possible name, this interface names the one shape it will always accept, and every migrated file's job became "translate your local names into this shape right before calling buy," a small, visible, one line-per-field conversion at each call site instead of a hidden guessing game inside shared code.

Concept: the ? after a field name

pricePerToken?: number | string means this field is optional, an object can be a valid BuyableDomain with or without it. Compare that to domainName: string with no ?, which is required, TypeScript will refuse to compile a call to buy(...) that's missing it. This is exactly what makes the type useful as a safety net, not just documentation, forgetting a required field becomes a compile error instead of a bug discovered by a user clicking a broken button.

Basics: what any actually means, and why three fields use it

Every other type seen so far, string, boolean, string[], is TypeScript checking that the value really is that shape. any is the opposite, it tells TypeScript "stop checking this field entirely, allow literally anything here." It's not a good default, it's closer to a pressure valve. On lines 23, 30, and 31, id, endTime, and usdAmount are typed any specifically because the five source files disagree on whether these come through as a number, a string, or a differently shaped date, and pinning down the real type for all five at once was out of scope for this phase. It's a known, visible trade off, not an oversight, the sort of thing worth tightening later once every caller's real data shape is confirmed.

Basics: nesting is like envelopes inside envelopes

Picture each pair of tags as a physical envelope, and whatever sits between the opening and closing tag as what's sealed inside it. <BuyIntentProvider> is now one envelope, and inside it are two things sealed together: the envelope containing every real page, <AppContent />, and the envelope holding the two popups, <BuyIntentModalHost />. Anything sealed inside an envelope can see what that envelope is carrying, in React's case that means "can call useContext and read the value that envelope is broadcasting." Nothing sealed in a different, unrelated envelope can. This physical picture is the entire reason placement in this tree matters as much as it does.

Concept: JSX nesting is the whole app's wiring diagram

Every component wrapped inside another component's tags can read anything that outer component provides through Context, and nothing outside it can. <AppContent>, which renders whichever actual page the user is on, now sits inside <BuyIntentProvider>, that's the only reason any page in the entire app is able to call useBuyIntent() at all. <BuyIntentModalHost /> sits inside it too, as a sibling to AppContent, for the exact same reason, it needs to read the same Context.

Why this exact spot in the tree, not higher or lower

This had to go inside the Redux <Provider store={store}>, not outside it, because the hook reads evmWalletAddress with useSelector, and useSelector only works inside the Redux Provider. It also had to go somewhere that wraps AppContent, since that's what actually renders every page. Right next to AutoLogoutHandler and InitProvider matched how this app already handles "one thing that needs to exist once, for the whole app," rather than inventing a new convention.

Removed, and exactly why each one was safe to remove

useState calls for showModal, isModalOpen, and selectedDomainId, plus the functions toggleModal, handleShow, handleClose, and closeModel, all deleted. Basics: what "the type checker and the linter" actually are

Two separate automated tools were run after every single file change in this phase, and neither one is guesswork. The type checker, run with the command tsc --noEmit, reads every .ts and .tsx file in the project and confirms every value matches the shape TypeScript expects it to have, exactly the kind of checking described in idea 0.8, catching things like a deleted variable that's still referenced somewhere. The linter, ESLint, separately checks for things that compile fine but are still worth flagging, an import that's brought in but never used, for instance. Running both after a deletion, rather than trusting memory, is what turns "I think this is safe to delete" into "the tools confirm nothing else in this file still needs it."

The migration recipe, in general terms

Find every piece of state and every function whose only job was feeding the thing you just centralized. Delete the thing you centralized from this file's JSX. Replace its trigger, the button's onClick here, with a call into the new shared hook, translating this file's own field names into the shared shape at that exact call site. Then let the type checker and linter tell you what's now unused, rather than guessing, and remove exactly that, nothing more.

The general recipe, for next time

Strip away the domain specifics and this is a reusable shape for any situation where the same logic has been copy pasted across several files and needs to become one. None of these eight steps require anything beyond the ideas covered in this document, so this recipe is meant to actually be picked up and reused, not just read once.

  1. Find the reference implementation. Usually one of the duplicated copies already does it best, or most completely, use that one as the source of truth for what the shared version should do, don't design from scratch.
  2. Decide where shared state should live by looking at what this codebase already does for something structurally similar, a login flag, a theme setting, before reaching for Context or Redux or anything else out of habit.
  3. Write the interface before the logic. List exactly what the rest of the app needs to read and call, that list becomes the Context's type, and nothing gets added that isn't actually needed somewhere real.
  4. Build the hook and its Provider together, following whichever existing pattern was chosen in step 2, with the real behavior living inside the Provider, not scattered across callers.
  5. Build one host if what's being consolidated includes something visual, a modal, a popup, a banner, so it renders once instead of once per caller.
  6. Define a shared shape for the data if the callers don't already agree on field names, and translate into it at each call site rather than guessing inside the shared code.
  7. Migrate one file at a time. Swap the trigger, delete what only existed to drive the old version, and let the type checker and linter, not memory, tell you exactly what's safe to remove.
  8. Wire the Provider in at the right spot in the app's root, wrapping whatever needs to read it, and nested inside whatever it itself depends on.
If this is the first time doing this kind of work

Don't try to hold all eight steps in your head before starting. Open the reference file from step 1 first, read it slowly, and just ask one question at a time: what does this piece of state actually control, what would break if it disappeared, what's the smallest new file that could hold it. The hook and the host in this document look tidy now, but they came from repeatedly asking exactly those small questions about five messy files, one at a time, not from seeing the whole shape in advance.
