How the buy and listing transactions were actually rewritten

This is the companion to the Buy Gate Walkthrough, same purpose, different subject. That one explained how five files became one shared hook. This one explains how the two places that actually move money and sign transactions, buying a domain and listing one, went from "tell everyone it worked before checking" to "only tell anyone once the chain has actually confirmed it." It stops at every piece of new or changed code, explains what it does, why it's written that way, and what the underlying idea is, assuming nothing about prior experience with async code or blockchain transactions.

Four files changed, none of them new: src/component/modals/BuyNowModal.tsx, src/component/modals/DomainListingModal.tsx, src/component/modals/SubmitButton.tsx, and src/component/domain-self-item/index.tsx. This phase is different from the last one in one important way worth saying plainly up front: this code sends real transactions to a real wallet and a real smart contract, so testing it properly takes a funded wallet and a listing that genuinely exists on chain, and at the time of writing that live testing hadn't been run yet, only the type checker and linter had. That's covered honestly in the Phase 2 Paper Trail, this document is about the code itself, not the test results.

Start here: seven ideas this phase leans on

The Buy Gate Walkthrough's "start here" section covered components, props, state, and TypeScript basics. None of that is repeated here. This section covers what's specific to this phase instead: code that waits for things, code that can genuinely fail in ways a login check never could, and code that talks to a blockchain instead of a normal server. If these are already familiar, skip to the buy handler. Every example here is a short, made up snippet built only to demonstrate the idea, clearly marked, and not part of this codebase.

0.1  Synchronous code runs in order, asynchronous code waits

Most of the code in a typical function runs the instant the line before it finishes, top to bottom, with no gaps. Some operations can't work that way: asking a wallet to sign something, or asking a blockchain for data, take real time, sometimes several seconds, and the browser can't just freeze the whole page waiting. JavaScript's answer is the async and await keywords. A function marked async is allowed to pause and resume itself without blocking anything else running on the page while it waits.

a tiny made up exampleillustrative example
1async function getBalance() {
2 const balance = await wallet.getBalance();
3 console.log(balance);
4}
in plain englishLine 2 doesn't move on to line 3 the instant it's read. It pauses this function right there, lets the rest of the page keep working normally, and only continues once the wallet actually answers. await is only legal inside a function marked async, that's the deal, in exchange for being allowed to pause, the function has to admit up front that it might take a while.

0.2  A Promise is a placeholder for a value that isn't ready yet

Every async function, whether it says so or not, actually hands back a Promise, not the real value directly. A Promise is an object with exactly one job: eventually settle into either a real value, or an error. await is what unwraps a Promise back into the plain value underneath it, that's the entire relationship between the two, async functions produce Promises, await consumes them.

Basics: why this matters for reading this phase's code

Every line in this phase that starts with await, connecting to a wallet, reading a contract's data, sending a transaction, waiting for it to confirm, is a Promise being unwrapped. Seeing await is the signal "this line takes real time, and everything after it only runs once this specific thing finishes," it's the single most repeated pattern in both rewritten files.

0.3  try, catch, and throw, and why throw is different from returning false

try { ... } marks a block of code that might fail. catch (error) { ... } only runs if something inside that try block actually failed, and it receives whatever went wrong as error. throw is how a piece of code, anywhere, at any depth, hands an error up to the nearest catch that's listening for it, even if that catch lives in a completely different function that called this one.

2 throw new Error("something broke");
3}

5async function run() {
6 try {
7 await riskyStep();
8 } catch (error) {
9 console.log("caught it:", error.message);
10 }
11}
Why this distinction mattered in this actual rewrite

Before this phase, one function in DomainListingModal.tsx, approval(), handled a cancelled wallet prompt by quietly returning false instead of throwing. That meant the code calling it had to remember to check for that specific false value, and it didn't, it just kept going as if approval had succeeded. Changing that one function to throw instead means the mistake becomes structurally impossible, code that calls an async function without handling what it throws doesn't silently continue, it stops, right there, exactly where the failure happened. That's the real, practical reason "throw, don't return false" is one of this phase's central fixes, not a style preference.

0.4  A smart contract call is either a free read or a real transaction

Every interaction with the marketplace contract in this codebase falls into one of two very different categories. Reading its stored data, like asking "what's the required payment for this listing," costs nothing and returns instantly, it's just asking a question. Actually changing something it stores, buying a listing or creating one, is a real transaction: it needs a signature from the connected wallet, it costs a fee, and the result isn't known instantly, it has to be confirmed by the network first.

Concept: same JavaScript syntax, two very different operations

contract.getRequiredNativeAmount(priceInUSD) and contract.buy(...) look almost identical in the code, both are just await contract.someFunction(...). The difference is entirely in what that function does on chain, one is defined as a read in the contract's own code, the other as a write. Nothing in the JavaScript syntax marks that difference, it has to be known about the specific contract function being called.

0.5  BigNumber: why this code can't just use normal JavaScript numbers for money

JavaScript's built in number type starts silently losing precision past about 9 quadrillion, and token amounts are usually expressed in tiny fractional units, wei, the smallest possible unit of native currency, where 1 whole token equals 1 followed by 18 zeros of these units. A price like "2.5 tokens" becomes an 18 digit integer once converted to wei, comfortably past where plain JavaScript numbers can be trusted. ethers.js works around this with its own BigNumber type, which can represent numbers of any size exactly, at the cost of needing its own methods, .add(), .mul(), .lt(), instead of the normal +, *, < operators.

a tiny made up exampleillustrative example
1// wrong: silently loses precision for large enough values
2const total = price + fee;
3
4// right: BigNumber's own method, exact no matter how large
5const total = price.add(fee);
in plain englishAnywhere this phase's code writes .mul(102).div(100) instead of * 1.02, or .lt(...) instead of <, or .add(...) instead of +, that's this exact reason, the values involved are BigNumbers, not plain numbers, and BigNumbers only understand their own method names.

0.6  A transaction hash, a receipt, and a confirmation are three different moments

It's easy to assume "the transaction was sent" and "the transaction succeeded" are the same moment. They aren't, and conflating them is exactly what this phase's rewrite fixes in both files. Sending a transaction returns a hash almost immediately, that's just proof it was broadcast, not proof it worked. Only once a block actually includes it does a receipt exist, and only that receipt's status field says whether it truly succeeded or reverted. A transaction can be mined, meaning included in a block, and still have failed on chain, that's exactly what a status of 0 means.

Why this is the single most repeated fix across this whole phase

Every one of the four files touched in this phase had some version of the same bug: treating "the transaction was sent" as if it meant "the transaction succeeded," and telling the backend, or the user, before actually checking. The fix, everywhere it appears, is the same three step shape: send the transaction, await its receipt, then check receipt.status === 1 before doing anything that can't be undone, like saving to a database or showing a success message.

0.7  Gas, in one paragraph

Every transaction that changes something on a blockchain costs a fee, called gas, paid in that network's native currency, separately from whatever the transaction itself is sending or paying for. Buying a domain for, say, 0.5 of a token also costs some additional, smaller amount of that same native currency just for the transaction to run at all. A wallet needs enough balance to cover both, the price and the gas, or the transaction can't go through, and checking a wallet's balance against only the price, ignoring gas, is exactly the kind of check that looks correct until the numbers are close.

0.8  Event logs: a permanent note a contract attaches to a transaction

A smart contract can declare that whenever a certain thing happens, creating a new listing, for instance, it will emit an event, a small, permanent, structured note recorded alongside the transaction. That note ends up inside the transaction's own receipt, in a list called logs. Anyone with the contract's ABI, its description of what functions and events it has, can decode those logs back into readable data afterward, including data that was never returned directly from the function call itself.

Concept: why bother reading a log instead of just asking again

Once a listing is created, its id could be looked up with a second, separate call asking the contract "what's the id for this token now." But that second call reads whatever the contract's current, live state is, at the exact moment it's asked, which can be a fraction of a second after the creating transaction, a small window where the answer can be stale or not yet consistent. The transaction's own receipt, on the other hand, is a fixed, permanent record of exactly what that specific transaction did, including whatever it emitted. Reading the id from there is asking "what did this exact transaction record," not "what does the contract currently say," a meaningfully different, more reliable question.

src/component/modals/BuyNowModal.tsx

Why the fallback still exists at all

If the event log genuinely doesn't have the id, for any reason, this function returns null, and the code that called it, back in the main handler, falls back to the older getListingId() contract call. The event log is the better, more reliable source, covered in idea 0.8, but keeping the fallback means a listing still has a path to succeed even if that specific read ever comes back empty.

localStorage is the browser's own small, simple storage that survives a page reload, unlike a normal variable. Basics: an honest boundary, stated plainly

This function guarantees a failed or unsynced listing's data survives, sitting in the browser's storage with everything needed to retry it later, its full field data and its transaction hash. It does not guarantee anything ever actually retries it, nothing in this codebase currently reads this queue back out. Building that piece, an automatic retry worker or a screen listing pending saves, is a real decision about how that should work, not something to invent by guessing while rewriting a transaction handler.

The general recipe, for next time

Strip away the specifics of buying and listing domains, and this is a reusable shape for rewriting any function that performs a real, hard to undo action, a payment, a database write, anything that can't just be quietly retried without a person noticing.

  1. Guard against a second call before anything else runs. One flag, checked and set at the very top of the function, before it does anything, is enough to make a double click structurally impossible instead of just unlikely.
  2. Handle a wrong precondition inline, and confirm it actually changed rather than stopping and asking the user to retry manually. After fixing it, whether that's a network switch or something else entirely, check the fixed state again before trusting it and moving on.
  3. Never confirm success from the act of sending, only from the result of waiting. A hash, an id, a submitted flag, none of them mean the same thing as a checked, confirmed outcome. Get the real result first, always.
  4. Tell anyone external, a backend, a database, a different system, only after that confirmation, and let that call's own failure surface for real instead of getting caught and silently ignored.
  5. Replace one flat catch with real classification. A deliberate cancellation, a known kind of failure, and a genuinely unexpected error are three different situations, and they deserve three different messages, not one that's technically true and practically useless.
  6. When something confirmed can't yet be fully recorded, say so honestly and hold onto it, rather than either lying that it worked or discarding it. It's fine to leave the retry mechanism itself for a separate, deliberate decision, as long as the data survives long enough to make that decision later.
  7. Prefer reading a result from the actual record of what happened, a transaction's own receipt and its logs, over asking again afterward, a second, separate question can race the very event it's trying to observe.
  8. Leave a genuinely open question open, marked clearly in a comment, rather than resolving it by guessing. Not knowing whether a fee is refunded, or exactly how retried data should be replayed, is honest, quietly assuming an answer either way isn't.
