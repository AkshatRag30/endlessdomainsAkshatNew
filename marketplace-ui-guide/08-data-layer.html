Phase 08 · Systems

Where the data comes from, and how it's shaped

Every composite in phases 03 through 07 rendered something. This phase is about the layer underneath all of them — the types that describe what a domain listing or a sidebar item actually is, and the mock data that plays the role of a real API response until there is one.

1The two-folder split, and why it exists

src/types/marketplace/ what the shape of the data is (interfaces, no values) src/data/marketplace/ what today's actual data is (real values, matching those interfaces)

Every domain gets one file in each folder, named to match: types/marketplace/domain.ts defines MarketplaceListing, data/marketplace/domains.ts exports an array of real objects shaped like it. This split matters more than it looks like it should, because it's what makes phase 10's real-API migration a contained, predictable change: a component that imports MarketplaceListing from the types folder and receives an array of them as a prop doesn't know or care whether that array came from a hardcoded file or a network response — only the data folder's contents need to change.

2A type that was designed to be replaced later, on purpose

types/marketplace/domain.ts
/**
 * Frontend-facing domain/listing models for the marketplace redesign.
 *
 * These deliberately mirror the real `DomainListing` (src/types/DomainList.ts)
 * and `TrendingDomain` (src/types/Domain.ts) fields where they overlap
 * (domainName, chain/assetContract, pricePerToken -> priceEth, usdAmount ->
 * priceUsd), so a future API adapter is a rename/reshape, not a redesign.
 */

export interface MarketplaceListing {
  id: string
  domainName: string
  extension: string
  isPremium?: boolean
  chain: Chain
  priceEth: number
  priceUsd: number
  appraisedValueEth: number
  appraisedTrend: 'high' | 'low' | 'neutral'
  isPromoted?: boolean
  isFavorited?: boolean
}
Why name fields to match an existing, unrelated type instead of whatever reads best in isolation

This project already has real domain types elsewhere in the codebase (DomainListing, TrendingDomain) used by pages outside this preview. priceEth here isn't an arbitrary name choice — it's deliberately close to that existing pricePerToken field, and priceUsd to usdAmount, specifically so that whoever eventually wires this page to a real endpoint is doing a mechanical rename/reshape between two similar, already-understood shapes, rather than inventing a mapping from scratch. A type built for a one-off preview can afford to name things however's clearest in isolation; a type meant to become real infrastructure benefits from staying close to the vocabulary the rest of the codebase already uses for the same concept.

Notice which fields are optional (?) and which aren't. isPremium, isPromoted, and isFavorited are all optional booleans — a listing that doesn't specify them is simply treated as false/not set wherever a component reads them (listing.isPremium && in ListingDomainCell, for instance). id, domainName, chain, and the price/appraisal fields are all required — there's no sensible rendering of a listing card without a name or a price, so TypeScript is made to enforce that every mock (and later, every real API response mapped into this shape) actually has them.

3Mock data as a small generator function, not a hand-typed array

28 listings, each with a domain name, a chain, a price, an appraised value and trend, a premium flag, and a promoted flag, all internally consistent (a "high" appraisal trend actually has a higher appraised value than price, for instance) — hand-writing 28 object literals would be both tedious and a place bugs hide. Instead, domains.ts writes one array of just the interesting part (the name stems) and a function that derives everything else:

data/marketplace/domains.ts
const NAME_STEMS = [
  'cryptowave', 'pixelforge', 'nebulax',
  'thisisanextremelylongdomainnamefortestingpurposes', // test fixture, see below
  'voidrunner', 'aetherlink', 'quantumleap',
  // ...24 more...
]

function buildListings(): MarketplaceListing[] {
  const chains = [POLYGON, ETHEREUM, ARBITRUM, BSC]

  return NAME_STEMS.map((stem, index) => {
    const isHighAppraisal = index % 2 === 0
    const priceEth = Number((8 + (index % 7) * 1.35).toFixed(2))

    return {
      id: `listing-${index + 1}`,
      domainName: stem,
      extension: '.ud',
      isPremium: index % 3 === 0,
      chain: chains[index % chains.length],
      priceEth,
      priceUsd: Math.round(priceEth * 2820),
      appraisedValueEth: isHighAppraisal ? priceEth : Number((priceEth * 0.75).toFixed(2)),
      appraisedTrend: isHighAppraisal ? 'high' : 'low',
      isPromoted: index < 8,
      isFavorited: false,
    }
  })
}

export const mockListings: MarketplaceListing[] = buildListings()
export const mockPromotedListings = mockListings.filter((l) => l.isPromoted)

Every derived field is computed from index, using modulo (%) to cycle through a small set of variations — index % 4 walks through all four chains in order and wraps back to Polygon after BSC, index % 2 === 0 alternates high/low appraisal every other listing, index % 3 === 0 marks every third listing premium. None of it is random (no Math.random() anywhere), which matters for two reasons: the exact same 28 listings render every time the page loads, so a screenshot taken today still matches one taken tomorrow, and every value is reproducible enough to reason about by just reading the formula, rather than needing to run the code to know what listing 15 looks like.

mockPromotedListings, the array phase 05's marquee actually renders, isn't a second hand-picked list — it's .filter()ed straight out of mockListings by the same isPromoted flag every other component would read. There is exactly one array of listings in the whole app; every other export in this file is a view over it.

A one-line data change, made in exactly one place, for a UI bug that needed real content to reproduce

When the mobile listings table's domain-name horizontal scroll (phase 06) needed verifying, the existing 27 name stems were all short enough to fit inside 172px without ever needing to scroll — there was no way to see the bug, let alone confirm the fix, without a name long enough to actually overflow. The fix was adding one deliberately oversized stem, with a comment explaining exactly why it's there and why it's positioned 4th in the array rather than last (so it lands on the table's first page of 14, visible without an extra "Show more" click). This is what "test fixture" means in a mock-data file: a value chosen specifically to exercise an edge case, not just to look plausible.

4Navigation data: a flag that exists purely to prevent a bug

Phase 04 covered the sidebar's isPlaceholder guard against multiple nav items appearing active at once. The type it depends on lives here:

types/marketplace/navigation.ts
export interface SidebarNavItem {
  id: string
  label: string
  href: string
  count?: number
  badge?: string // e.g. 'soon'
  /** True when href has no real destination yet — points at '/' until built */
  isPlaceholder?: boolean
}

This is worth noticing as a general shape: a field on a type doesn't have to represent something the design shows on screen at all. isPlaceholder is invisible to a user entirely — it exists solely so that application logic (that active-state check in SidebarSection) has something real to branch on, instead of trying to infer "is this a real destination" from the href string itself (which would have been far more fragile, since every placeholder item currently happens to share the exact same href).

The same file also still defines HeroCategoryChip, unused anywhere in the current components — the leftover from phase 05's wrong assumption about the hero's floating category chips being separate positioned elements. It's a small, harmless reminder that not every type that gets written ends up used, and that's fine; deleting it isn't necessary, but recognizing it as dead when you encounter it (rather than assuming it must be wired up somewhere you haven't found yet) is a useful reading skill on its own.

5What to remember from this phase

  • Keep type definitions (the shape) and mock data (today's actual values) in separate, matching files — it's what makes swapping mock data for a real response a change in one place.
  • When a mock type will eventually be mapped from a real API, name its fields close to the real type's existing vocabulary, not just whatever reads cleanest in isolation — it turns the future mapping into a mechanical rename instead of a redesign.
  • Generate structured mock data from a small seed array plus a deterministic formula (modulo on index, not Math.random()) rather than hand-typing every object — it's shorter, internally consistent, and reproducible across renders.
  • Derive filtered views (mockPromotedListings) from the one source array instead of maintaining a second hand-written list that can drift out of sync.
  • A type field doesn't have to represent anything visible — a flag that exists purely to make application logic (like an active-state check) correct is a legitimate, sometimes necessary part of a data model.
  • When a UI bug needs a specific kind of content to reproduce (an overflow, an edge case), add that content to the mock data deliberately, with a comment explaining why it's there — don't just eyeball whether existing data happens to trigger it.
