Phase 02 · Foundations

Primitives: the small reusable pieces

One folder, src/design-system/primitives/, holding everything too small to be its own "section" but used by several sections. Learn these once, recognize them everywhere.

1What makes something a primitive

The rule this codebase follows: if a piece of UI has no idea what page it's on — it just takes props and renders — it's a primitive. A Badge doesn't know if it's showing a domain extension or a status; it just renders whatever text and color variant you hand it. Compare that to a composite (phases 03–07), which knows exactly what it is — MarketplaceHero is only ever the marketplace hero, never anything else.

2Badge: the variant-prop pattern

This is the simplest possible example of a pattern you'll see in almost every primitive: one component, a variant prop, and a CSS class per variant.

src/design-system/primitives/badges/badge/Badge.tsx
export interface BadgeProps {
  variant?: 'neutral' | 'accent' | 'success' | 'warning' | 'danger'
  children: React.ReactNode
}

export const Badge = ({ variant = 'neutral', children }: BadgeProps) => (
  <span className={`${styles.badge} ${styles[variant]}`}>
    {children}
  </span>
)

The className is built by string-joining two CSS Module classes: the base .badge (shared layout — padding, border-radius, font) and one variant class that only changes color. styles[variant] is a plain JavaScript computed property lookup — when variant is 'success', styles[variant] reads the same as styles.success.

Badge.module.scss
.badge {
  display: inline-flex;
  align-items: center;
  padding: 1px var(--space-2);
  border-radius: var(--radius-full);
  font-family: var(--font-satoshi);
  font-size: var(--text-small-12);
}
.success { background: #e7f6ee; color: #12a05c; }
.danger  { background: var(--color-error-soft-bg); color: var(--color-error); }

Every badge-like primitive in this project follows this exact shape: ChainBadge (a chain name + dot, colored per chain), ExtensionBadge (the small .ud pill next to a domain name), and TrendIndicator (an up/down arrow + label for price trends) are all the same pattern with different content and variants.

3Buttons: the clip-path notch technique

Look closely at any button in this design and the corners aren't simple rounded rectangles — they're chamfered, cut at an angle, like a stop sign with only some corners cut. That shape comes from CSS clip-path: polygon(...), and it's worth understanding in detail because it reappears in half a dozen unrelated components later (the header's hamburger chip, the mobile drawer's Explore row, the bottom nav's icon chips).

src/design-system/primitives/buttons/primary-button/Primarybutton.module.scss
$clip: polygon(
  10px 0%, calc(100% - 20px) 0%, 100% 20px,
  100% calc(100% - 10px), calc(100% - 10px) 100%, 10px 100%,
  0% calc(100% - 10px), 0% 10px
);

.button {
  clip-path: #{$clip};
  background: var(--color-gray-medium);   // fallback, covered by ::before below
}

.button::before {
  content: "";
  position: absolute;
  inset: 1px;                       // 1px smaller than the button — this is what makes the border look like a ring
  clip-path: #{$clip};              // same cut shape, so the fill matches the outer edge exactly
  background: var(--color-blue-primary);
  transition: all 0.3s ease;
}

clip-path: polygon(...) describes a shape as a sequence of x/y coordinate pairs, one per corner, tracing the outline clockwise from the top-left. Each pair like 10px 0% means "10 pixels in from the left, at the top edge" — by giving two coordinates near each corner instead of one, the corner gets cut diagonally instead of meeting at a point. Mixing px and calc(100% - 10px) is what makes the shape scale correctly at any button width while keeping the corner cuts a constant, fixed size instead of stretching with the button.

Why a separate ::before instead of styling .button directly

The visible fill color lives on a ::before pseudo-element sitting 1px inside the real button edge, not on the button itself. That 1px gap is what reads as a crisp border/glow around the fill. Hover and active states then only need to swap this one layer's background and box-shadow, leaving the outer shape untouched — which is also why button text has to be wrapped in a real child element (a <span>), given z-index: 1 so it paints above the ::before layer instead of underneath it.

A smaller version of the same shape, $clip-sm, backs the .sm size variant used for compact buttons like "Buy Now" in the listings table. Color variants (.transparent, .dark, .error, .green) each just override what the ::before layer's background is, the shape math never changes.

4FilterDropdown: the open/close/outside-click pattern

This one small component teaches a pattern reused later by the mobile ticker's own dropdown (phase 07) almost line for line. It's a button that toggles a floating list, and closes itself when you click anywhere else on the page.

src/design-system/primitives/inputs/filter-dropdown/FilterDropdown.tsx
const [open, setOpen] = useState(false)
const rootRef = useRef<HTMLDivElement>(null)

useEffect(() => {
  const handleClickOutside = (e: MouseEvent) => {
    if (rootRef.current && !rootRef.current.contains(e.target as Node)) {
      setOpen(false)
    }
  }
  document.addEventListener('mousedown', handleClickOutside)
  return () => document.removeEventListener('mousedown', handleClickOutside)
}, [])

Three moving parts: a boolean open state, a ref attached to the component's outermost wrapper element, and one document-level click listener registered in a useEffect. The listener checks whether the click's target is inside the wrapper (rootRef.current.contains(...)) — if it's not, the click happened somewhere else on the page, so the dropdown closes. Clicking the trigger button itself doesn't accidentally close-then-reopen, because the trigger is inside the wrapper too, so a click on it is "inside" and the outside-click handler does nothing; the button's own onClick is what actually toggles it.

Why the listener is added in useEffect, and removed in its cleanup

If you attached this listener directly in the component body instead of inside useEffect, it would re-attach a new listener on every single re-render without ever removing the old one — a memory leak, and eventually the click handler firing multiple times per click. The empty dependency array [] means "run this setup once, when the component first mounts," and the function useEffect returns is the cleanup that runs when the component unmounts, removing the exact listener that was added.

The trigger button's label always shows the fixed filter name ("Price", "Chain"), never the current selection — the open panel below is what shows which option is picked, via an optionActive class comparing each option's value to the current value prop.

5Sparkline: wrapping a charting library safely

The little mini-charts on metric cards (phase 07) aren't hand-drawn SVG — they're Recharts, wrapped in a small primitive so the rest of the app never imports Recharts directly.

src/design-system/primitives/charts/sparkline/Sparkline.tsx
export const Sparkline = ({ data, color = 'var(--color-blue-primary)', height = 40, variant = 'area' }: SparklineProps) => {
  const gradientId = `sparkline-${useId().replace(/:/g, '')}`

  return (
    <div style={{ height }}>
      <ResponsiveContainer width="100%" height="100%">
        {variant === 'bar' ? (
          <BarChart data={data}><Bar dataKey="value" fill={color} /></BarChart>
        ) : (
          <AreaChart data={data}>
            <defs><linearGradient id={gradientId}>...</linearGradient></defs>
            <Area dataKey="value" stroke={color} fill={`url(#${gradientId})`} />
          </AreaChart>
        )}
      </ResponsiveContainer>
    </div>
  )
}

Two details that matter beyond "it draws a chart." First, variant: 'area' | 'bar' exists because the real design isn't uniform — the Sales metric card genuinely uses a bar chart while every other metric uses a filled line, a real distinction in the Figma file, not a stylistic choice made up for this project. Second, useId() generates a unique gradient id per chart instance — SVG gradient ids are global to the whole page's DOM, so without a unique id, two sparklines on the same page would silently share (and visually corrupt) each other's gradient fill.

src/design-system/primitives/charts/sparkline/index.ts
import dynamic from 'next/dynamic'
export default dynamic(() => import('./Sparkline'), { ssr: false })
Why this is loaded with next/dynamic and ssr: false

Recharts measures the real DOM (element widths/heights) to lay out a chart, and there is no DOM on the server during server-side rendering — it would either crash or render nothing useful. next/dynamic with ssr: false tells Next.js to skip this component entirely on the server and only render it after the page has hydrated in a real browser, where the DOM actually exists to measure.

6What to remember from this phase

  • A primitive takes props and renders — it never imports mock data or knows what page it's on.
  • Variant props map to CSS Module classes via a computed property lookup, styles[variant].
  • Chamfered corners are clip-path: polygon() on both the button and a 1px-inset ::before fill layer, not an image or a border trick.
  • A dropdown that closes on outside-click needs a ref, a document-level listener added in useEffect, and that listener removed in the effect's cleanup function.
  • Anything that measures the DOM (charts, most third-party visualization libraries) needs next/dynamic(..., { ssr: false }).
