Phase 10 · Systems · Final phase

What has to change to make this real

Everything up to this point was built so that this phase could be short. If phase 08's boundary held, replacing mock data with a real API touches the data layer and nothing else — every component in phases 03 through 07 keeps working unmodified.

1The project already has a working RTK Query pattern — reuse it, don't invent a second one

This app doesn't need a new data-fetching approach designed for this page. src/core/redux/domainListing.ts already injects real domain-listing endpoints into a shared RTK Query API slice, and that exact shape is what this page's endpoints should follow:

src/core/redux/domainListing.ts (existing, real)
export const DomainListApi = myApi.injectEndpoints({
  endpoints: (builder) => ({
    GetAllDomainListing: builder.query<DomainAllListingResponse, { offset: number, limit: number }>({
      query: ({ offset, limit }) => ({
        url: `${GetAllDomainListingApi}?offset=${offset}&limit=${limit}`,
        method: "GET",
      }),
      transformResponse: (response) => response,
      providesTags: ["all_domain_listing"],
    }),
    // ...more endpoints on the same injected slice...
  }),
})

export const { useGetAllDomainListingQuery, ... } = DomainListApi

injectEndpoints adds new query/mutation endpoints onto one shared API slice (myApi) rather than creating a separate store per feature — every endpoint gets caching, tag-based invalidation, and an auto-generated React hook (useGetAllDomainListingQuery) for free, all wired through the same Redux store the rest of the app already uses. A new marketplaceListings.ts file following this exact shape, injecting a GetMarketplaceListings endpoint the same way GetAllDomainListing is injected here, is the natural next step — not a new library, not a new pattern, the same one already proven out elsewhere in this codebase.

2The migration, mapped one data file at a time

Mock file (today)BecomesComponents affected
data/marketplace/domains.tsA query hook, e.g. useGetMarketplaceListingsQuery()LiveListingsTable, PromotedDomainsSection
data/marketplace/activity.tsA query hook + a live channel (see section 4)LiveActivityPanel, LiveActivityTicker
data/marketplace/analytics.tsA query hook, polled or pushedMarketActivityPanel, MarketMetricCard
data/marketplace/navigation.tsMostly stays static (it's site structure, not user data) — only count fields become liveMarketplaceSidebar, MobileDrawerMenu
data/marketplace/categories.tsA query hook, or stays static if categories rarely changeListingCategoryTabs

Every row in that table is a change to one file in src/data/marketplace/, or the introduction of one new hook file next to it. No row requires touching a composite's .tsx or .module.scss — that's the entire payoff of phase 08's split between "what the shape of the data is" (the types, which don't need to change) and "what today's actual values are" (the mock data, which gets replaced).

3A concrete before/after: LiveListingsTable

Here's what actually changes in the component that currently receives mock data as a prop from the page:

pages/design-preview/marketplace.tsx — today
import { mockListings } from '@/data/marketplace/domains'
import { filterListings } from '@/hooks/marketplace/useListingFilters'

const { filters, debouncedSearch } = useListingFilters()
const filtered = filterListings(mockListings, debouncedSearch, filters)

<LiveListingsTable listings={filtered} />
pages/design-preview/marketplace.tsx — after wiring a real endpoint
import { useGetMarketplaceListingsQuery } from '@/core/redux/marketplaceListings'

const { filters, debouncedSearch } = useListingFilters()
const { data, isLoading, isError } = useGetMarketplaceListingsQuery({
  search: debouncedSearch,
  extension: filters.extension !== 'any' ? filters.extension : undefined,
  chain: filters.chain !== 'any' ? filters.chain : undefined,
})

{isLoading && <ListingsTableSkeleton />}
{isError && <p>Couldn't load listings.</p>}
{data && <LiveListingsTable listings={data.listings} />}

LiveListingsTable itself, and everything inside it — ListingRow, the two-pane mobile split, the favorited-state logic — is completely untouched by this diff. Its prop is still listings: MarketplaceListing[]; it never knew or cared whether that array came from a hardcoded file or a network response. What changes above the component boundary: filterListings's pure client-side .filter() (fine for 28 static rows, wrong for a real dataset) moves server-side as query parameters, so search/extension/chain filtering scales with the real dataset instead of requiring every row to ship to the browser first. And isLoading/isError states, which don't exist at all for a synchronous mock array, need real UI — a skeleton and an error message are the two states the current preview has literally never had to show, because mock data never fails and is never in-flight.

4What doesn't map cleanly, and needs a real decision before it's just a data swap

"Live" ticker and activity feed need an actual live transport, not just a query

LiveActivityTicker and LiveActivityPanel are named "live" for a reason the mock data doesn't have to reckon with: the real version needs new activity to appear without a page refresh. A one-shot useQuery fetched once on page load doesn't do that. This needs either polling (pollingInterval is a built-in RTK Query option, the simplest option) or a push transport (WebSocket/SSE) if genuinely sub-second updates matter for this feed. That's a real architectural decision, not a mechanical rename, and it belongs to whoever owns the backend for this feature to weigh in on before it's built.

Buy Now and the favorite heart are currently decorative

Every "Buy Now" button across ListingRow, ListingRestCells, and PromotedDomainCard carries the same comment: visually real, not wired to BuyNowModal or any wallet call. The real app already has a BuyNowModal and wallet-transaction flow elsewhere in the codebase (outside this preview) — wiring these buttons means calling into that existing flow, not building a new one. The favorite/watchlist heart icon currently toggles a local Set<string> that forgets itself on refresh; the real app already has a watchlist slice (src/core/redux/watchlist.ts) that this should read from and dispatch to instead, so a favorited domain actually persists per user rather than resetting every time the page reloads.

Chain icons and a few Figma-exact colors are placeholders too

domains.ts says so directly: the four Chain constants point at icon paths (/assets/img/chains/*.svg) that don't exist as real assets in this project yet, because ChainBadge was built before anyone sourced real chain logos. This is a smaller gap than the two above, but the same principle applies: it's a known, labeled placeholder, not a silent one, findable by anyone who greps for the same comment that's already there.

5The whole guide, in one sentence

Every phase before this one was really in service of this one observation: a UI built out of small, single-purpose components, styled with tokens instead of magic numbers, fed data through one narrow, typed boundary, and made responsive by rendering every layout and letting CSS choose — is a UI where "make it real" is a change to a handful of files at the edge, not a rewrite of everything in the middle. That's the actual, reusable skill this guide was trying to teach past this one page: build the boundary first, and the migration takes care of itself.

6What to remember from this phase, and from the whole guide

  • Reuse an existing data-fetching pattern already proven in the codebase (RTK Query's injectEndpoints, here) rather than introducing a second approach for one page.
  • A clean mock-data-behind-a-hook-boundary means most of a real-API migration is confined to src/data/marketplace/ and a new hooks/endpoints file — components keep their same typed props and don't change.
  • Moving from mock to real data introduces states mock data never had to show — loading, error, empty — and those need real UI, not just a data source swap.
  • Not everything is a mechanical rename: a feed that's actually meant to be live needs a real live transport decision (polling vs. push), and "visually real but not wired up" buttons need to be connected to the flows that already exist elsewhere in the app, not rebuilt from scratch.
  • A labeled placeholder (a comment saying exactly what's fake and why) is what makes a future migration tractable — the alternative, an unlabeled placeholder that looks finished, is what turns a one-file data swap into an investigation.
