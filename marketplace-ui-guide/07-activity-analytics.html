Phase 07 · Sections

Live activity and market analytics

Two right-rail panels, one that becomes a totally different component shape on mobile, and one that renders two totally different layouts from the exact same data and got that toggle backwards the first time.

1LiveActivityPanel vs. LiveActivityTicker: same data, two different components

The right rail's "recent activity" feed has a full desktop presentation — a row of filter tabs (All/Sale/Listing/Drop) above a scrollable list of activity rows — and a completely different mobile presentation: a single-line auto-scrolling ticker with a dropdown instead of tabs, because there's no room for four separate tab buttons in a 30px-tall bar. Rather than one component trying to be both, they're two separate components, LiveActivityPanel and LiveActivityTicker, CSS-toggled exactly like phase 04's sidebar/drawer pair.

LiveActivityTicker.tsx
/**
 * Mobile-only, replaces LiveActivityPanel (CSS-hidden at mobile) with a
 * condensed always-scrolling ticker instead of the full tabs + list panel.
 * Same duplicate-pass marquee technique PromotedDomainsSection already
 * runs. The chevron next to "Live activity" is a real dropdown trigger,
 * opens the same All/Sale/Listing/Drop filter as a dropdown instead of a
 * row of tabs since there's no room for four buttons in a 30px bar.
 */

Two things worth pulling out of that comment. First, the ticker's scrolling row reuses the exact duplicate-pass marquee technique from phase 05 — two identical .pass blocks inside one .track, animated by exactly half its own width. Once you've built that trick once, it's the same three lines of CSS reasoning every other place a row needs to auto-scroll seamlessly. Second, the filter itself is the same four options in both components, just presented as tabs when there's room and collapsed into a dropdown when there isn't — the same filtering concept, two different UI shapes for two different amounts of space.

The dropdown: phase 02's outside-click pattern, in a real composite

LiveActivityTicker.tsx
const [open, setOpen] = useState(false)
const rootRef = useRef<HTMLDivElement>(null)

useEffect(() => {
  const handleClickOutside = (e: MouseEvent) => {
    if (rootRef.current && !rootRef.current.contains(e.target as Node)) {
      setOpen(false)
    }
  }
  document.addEventListener('mousedown', handleClickOutside)
  return () => document.removeEventListener('mousedown', handleClickOutside)
}, [])

This is the identical shape phase 02 walked through for FilterDropdown — a ref on the dropdown's own root element, a document-level listener that closes the menu the instant a click lands anywhere not inside that ref, and a cleanup function that removes the listener when the component unmounts. Recognizing "I need a click-away-to-close menu" as the same solved problem, rather than inventing a new approach each time, is exactly the payoff of having learned the primitive once.

The hydration bug, and why the fix is one attribute, not a rewrite

LiveActivityTicker.tsx
function formatRelativeTime(iso: string): string {
  const seconds = Math.floor((Date.now() - new Date(iso).getTime()) / 1000)
  if (seconds < 30) return 'now'
  // ...minutes/hours/days...
}

<span className={styles.time} suppressHydrationWarning>
  {formatRelativeTime(item.occurredAt)}
</span>
Why the exact same code can print two different things on server and client

Next.js renders every page's initial HTML once on the server, then React "hydrates" that same markup in the browser — attaching event handlers and taking over from where the server left off. For that handoff to work invisibly, the HTML React generates on the client during hydration has to match, character for character, what the server already sent down. mockTickerItems' occurredAt field is computed with Date.now() when the module first loads — and the server evaluates that module at a different wall-clock instant than the browser does moments later. formatRelativeTime is deterministic given its input, but its input (the gap between now and occurredAt) is not the same value on both sides, so "3s ago" on the server can legitimately render as "4s ago" once the client re-runs the same function a moment later.

suppressHydrationWarning is React's own sanctioned escape hatch for exactly this situation — a value that is expected and acceptable to differ between server and client render, most commonly a timestamp. It's a targeted attribute on the one element whose text is allowed to drift, not a workaround for an actual bug: the underlying values are both "correct," they're just correct at two different instants. Reaching for suppressHydrationWarning is only the right move when you can explain why the mismatch is expected, the way this comment does — using it to silence a hydration warning you don't understand would hide a real bug instead.

2LiveActivityPanel keeps moving: turning a static list into a vertical marquee

LiveActivityPanel — the desktop/tablet feed, not the mobile ticker — started out as an ordinary manually-scrollable list: a fixed-height box, overflow-y: auto, scroll it yourself with your mouse wheel or trackpad. The design calls for it to feel alive instead — constantly, gently scrolling on its own, the way a real trading ticker never sits still. That's a genuinely different piece of behavior from anything phase 05 covered, but it turns out to need none of the same new ideas: it's the exact same duplicate-pass marquee trick from PromotedDomainsSection, just running vertically instead of horizontally.

LiveActivityPanel.tsx
const SECONDS_PER_ITEM = 2.5

const trackStyle = {
  '--loop-seconds': `${items.length * SECONDS_PER_ITEM}s`,
} as React.CSSProperties

<div className={styles.list}>
  <div className={styles.track} style={trackStyle}>
    {[0, 1].map((pass) => (
      <div className={styles.pass} key={pass} aria-hidden={pass === 1}>
        {items.map((item) => <ActivityItem key={`${item.id}-${pass}`} item={item} />)}
      </div>
    ))}
  </div>
</div>

If phase 05's marquee is still fresh, every line of this should already read as familiar: the list of items renders twice, back to back, inside .track; the animation's speed is computed from how many items there actually are (SECONDS_PER_ITEM) rather than a fixed number, so the feed doesn't visibly speed up or slow down just because a filter tab happens to leave more or fewer rows on screen; and that computed duration crosses from JavaScript into CSS through an inline style object, landing as the custom property --loop-seconds that the stylesheet reads back with var(--loop-seconds, 20s). The one thing that's actually new is the axis.

LiveActivityPanel.module.scss
.list {
  position: relative;
  max-height: 260px;
  overflow: hidden;
  mask-image: linear-gradient(180deg, transparent, black 20px, black calc(100% - 20px), transparent);
}

.track {
  display: flex;
  flex-direction: column;
  animation: activity-marquee var(--loop-seconds, 20s) linear infinite;

  .list:hover & { animation-play-state: paused; }
}

@keyframes activity-marquee {
  from { transform: translateY(0); }
  to   { transform: translateY(-50%); }
}

Everything about the horizontal version transfers over just by swapping which axis each property talks about: flex-direction: row becomes column (phase 00, section 8, is the place to review what that swap does to a flex container if it's not automatic yet), translateX becomes translateY, and the 90deg left-to-right fade gradient from PromotedDomainsSection becomes a 180deg top-to-bottom one. The seamless-loop math is identical either way: two identical copies stacked end to end, animated by exactly negative one copy's own size (50% of the doubled total), so the moment the loop restarts, what's on screen is pixel-identical to frame zero.

Why the old manual-scroll behavior didn't just disappear

The stylesheet keeps a prefers-reduced-motion branch that restores exactly the original behavior — overflow-y: auto, no animation, the duplicate second pass hidden — the same accessibility fallback phase 05's marquee already establishes as the standard for any continuously-moving content in this codebase. A visitor with that setting enabled never sees the feed move on its own; they get the plain, original scrollable list back, unchanged from before this section existed.

One practical note if you ever need to confirm a change like this actually works: a single static screenshot can't show a continuous animation moving, no matter how carefully you inspect it — you're comparing one frozen instant to itself. What a screenshot can confirm is that the underlying markup and compiled CSS are correct — the .track element exists with the right --loop-seconds value baked in, and the @keyframes rule compiled without errors — which is verifiable evidence even though it isn't a picture of motion itself.

3MarketActivityPanel: one component, two entirely different chart layouts

This is the most dramatic "render both, CSS decides" case in the whole page. On desktop, Market Activity is four small metric cards stacked vertically. On tablet and mobile, it's a single large chart with a row of tabs above it to pick which metric the chart is currently showing. These aren't two arrangements of the same markup — the tablet/mobile version has a chart, a value readout, and a badge that simply don't exist in the desktop card list at all. Both are still rendered by the same component, from the same underlying data:

MarketActivityPanel.tsx
const [timeRange, setTimeRange] = useState<MarketTimeRange>('24h')
const [selectedMetricId, setSelectedMetricId] = useState(mockMarketMetrics[0].id)
const selectedMetric = mockMarketMetrics.find((m) => m.id === selectedMetricId) ?? mockMarketMetrics[0]

return (
  <div className={styles.panel}>
    <div className={`${styles.cards} ${styles.cardsOnly}`}>
      {mockMarketMetrics.map((metric) => <MarketMetricCard key={metric.id} metric={metric} timeRange={timeRange} />)}
    </div>

    <div className={styles.expanded}>
      {/* metric tabs, big value readout, Sparkline chart — all driven by `selectedMetric` */}
    </div>
  </div>
)

selectedMetricId only matters to the expanded (tablet/mobile) layout — the card list ignores it entirely and just maps over every metric at once, since there's room to show all four simultaneously as small cards. timeRange, by contrast, is shared: the same toggle button group (rangeToggle, built once and reused in both places rather than duplicated) controls which time window both layouts read from, so switching to 7d on either layout stays in effect if the viewport is ever resized across the breakpoint.

The cascade-order bug: two rules, opposite intents, same specificity

This component's stylesheet carries an unusually direct comment about a real bug, worth reading in full because the mechanism (not just the fix) is the actual lesson:

MarketActivityPanel.module.scss
.cards {
  display: flex;
  flex-direction: column;
  gap: var(--space-2);
}

// These two rules must come AFTER .cards above: the card-list element
// carries both .cards and .cardsOnly, and .cards's own display:flex is
// unconditional — with equal specificity, whichever rule is declared
// later in the file wins the cascade at any width where both apply.
// Declared first (as this used to be), .cardsOnly's display:none
// silently lost to .cards's display:flex at every width, which is
// exactly why the old stacked cards never actually hid.
.cardsOnly {
  @include tablet-down { display: none; }
}

.expanded {
  display: none;
  @include tablet-down { display: flex; }
}
CSS specificity ties are broken by source order, not by which rule "sounds like" it should win

Both .cards and .cardsOnly are single-class selectors — identical specificity. When two rules with identical specificity both apply to the same element and disagree about a property (here, display), CSS doesn't pick the "more conditional-looking" one or the one that seems more specific in intent. It picks whichever one is written later in the stylesheet, full stop. The card list element has both classes on it (className={`${styles.cards} ${styles.cardsOnly}`}), so at tablet-down widths there were genuinely two rules in play: .cards saying "always flex" and .cardsOnly saying "none below tablet." With .cardsOnly declared first in the file, .cards's later, unconditional rule simply overwrote it for every property they both touched, at every screen width, so the card list never actually disappeared — it just sat rendered underneath the new expanded chart, both visible at once.

This was found by fetching the browser's actual computed CSS for the element and reading the declaration order that won, not by staring at the source file guessing which rule "should" apply. That's generally the fastest way to debug a cascade conflict once a fix that looks obviously correct in the source doesn't take effect: ask the browser what actually won, don't keep re-reading the file.

The expanded chart reuses Sparkline exactly as phase 02 described it

MarketActivityPanel.tsx
<Sparkline
  data={selectedMetric.series[timeRange]}
  variant={selectedMetric.id === 'sales' ? 'bar' : 'area'}
  height={120}
/>

Nothing new here — this is the same variant-prop pattern from phase 02, just fed a different slice of data (selectedMetric.series[timeRange]) depending on which metric tab and which time range are currently selected. The Sales metric renders as bars, every other metric renders as a filled area line, purely by passing a different string into the same component.

4MarketMetricCard: the small building block behind the card list

Each of the four desktop cards is a MarketMetricCard — a label, a formatted value, a trend badge, and (depending on the metric) a tiny inline sparkline. It's not covered in its own section here because there's genuinely nothing new in it past what phases 01 and 02 already established: design tokens for spacing and color, Badge's variant prop for the up/down indicator, and Sparkline again at a much smaller height. Once the primitives are solid, most composites really are this short to explain.

5What to remember from this phase

  • A continuous-motion pattern (the marquee) transfers cleanly from a horizontal case to a vertical one by swapping the axis-specific properties in lockstep — flex direction, translate axis, fade-gradient angle — while the seamless-loop math (duplicate, animate by exactly negative one copy's size) stays identical.
  • When two layouts genuinely differ in structure, not just size, build them as separate components/blocks and let a media query pick between them — the same pattern from phase 04, now seen with a real desktop-vs-tablet/mobile split instead of desktop-vs-mobile.
  • Share the state that both layouts need to agree on (like a time-range toggle) by lifting it to their common parent and passing the same control into both, rather than building it twice.
  • A value computed from the current time (Date.now()) at module load will differ between server and client render — that's an expected hydration mismatch, and suppressHydrationWarning on just that element is the correct, targeted fix, not a rewrite.
  • Two same-specificity CSS rules that disagree are resolved by source order alone — the one declared later in the file wins, regardless of which one "sounds" more specific to the reader. When a display toggle doesn't seem to take effect, check declaration order before assuming the selector itself is wrong.
  • When a CSS fix that looks correct doesn't take effect, check the browser's actual computed styles for the element rather than re-reading the source file again.
