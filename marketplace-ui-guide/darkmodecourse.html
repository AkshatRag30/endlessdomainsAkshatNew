Hand coding dark mode for the marketplace

A complete, beginner friendly course that rebuilds the dark mode of this Next.js marketplace from nothing, the same way it was actually done: tokens first, a flash free theme switch, primitives, the shell, then one page at a time. Every snippet comes from this repo. Read it top to bottom once, then keep it open while you code.

Start here

What you will build, what you need to know first, and how to use this course.

What you will build

By the end, the marketplace has a sun and moon toggle in the header. Clicking it switches every page between the light design you have today and a dark design based on the Figma file. The choice survives a reload, there is no white flash when a dark page loads, light mode keeps looking the way it does now, and the whole thing hides behind a switch in the environment until it is finished.

What you should already know

  • Basic HTML and CSS: selectors, classes, the box model, colours in hex (#141415) and rgba (rgba(255, 255, 255, 0.7)).
  • Basic React: components, props, useState, useEffect.
  • How this repo is laid out: SCSS modules next to components, design tokens in src/design-system/styles/tokens.scss, breakpoint mixins in _mixins.scss.

How the course is organised

Modules 1 to 4 are thinking and planning: no code changes yet. Modules 5 to 12 are the build, in the exact order it was done. Modules 13 to 16 are about checking your work, working safely with a team, and the mistakes that were made so you can avoid them. Each module ends with a short exercise.

The one sentence version

Give every colour a job name (a "role"), make every component use the job name instead of a raw colour, then redefine what each job name means when the page is in dark mode.

1

The ideas behind dark mode

Six small ideas. Once these click, everything else is just applying them carefully.

1.1 Dark mode is not "invert the colours"

If you simply flipped white to black, brand blue would turn orange, photos would look like negatives and shadows would glow. Real dark mode is a second, deliberate palette: a near black page, slightly lighter cards, white text at a few opacities, and the brand colours kept (sometimes adjusted so they stay readable).

Same structure, same hierarchy, different values. That is the whole game.

1.2 CSS custom properties (CSS variables)

A custom property is a named value you define once and reuse anywhere:

:root {
  --color-text-primary: #171429;
}

.title {
  color: var(--color-text-primary);
}

Two things make them perfect for theming. First, they are live: if you change the value later, every place that uses it updates instantly, with no rebuild. Second, they cascade: a more specific selector can redefine the same name for part of the page.

:root { --color-text-primary: #171429; }               /* light */
:root[data-theme='dark'] { --color-text-primary: #fff; } /* dark  */

Now .title never changes. It always says "use the primary text colour". Which colour that is depends on an attribute on the <html> element.

Why not Sass variables?

Sass variables like $text: #171429 are replaced with plain values when the stylesheet compiles. The browser never sees the name, so it cannot switch it at runtime. Use Sass for build time things (breakpoints, mixins) and CSS custom properties for anything that changes with the theme.

1.3 One attribute on <html> controls everything

We put data-theme="dark" (or light) on the root element. Every dark rule in the codebase starts with :root[data-theme='dark']. Switching theme is then one line of JavaScript:

document.documentElement.setAttribute('data-theme', 'dark')

A data attribute beats a class like .dark because it is explicit, it cannot collide with a utility class, and it can hold more than two values later (for example a high contrast theme).

1.4 Specificity, in one paragraph

When two rules set the same property, the more specific selector wins. Count it as (ids, classes and attributes and pseudo classes, elements). .item is (0,1,0). .item:hover is (0,2,0). :root[data-theme='dark'] .item is (0,3,0) because :root counts as a pseudo class and [data-theme] as an attribute. Remember this; it causes a real bug in module 10.

1.5 The flash problem

React runs after the browser has already painted the HTML. If you read the saved theme in a useEffect, a user who chose dark sees the light page for a split second, then it snaps to dark. This "flash of the wrong theme" looks broken. The fix (module 5) is a tiny script inside the <head> that sets the attribute before the first paint.

1.6 color-scheme and contrast

color-scheme: dark tells the browser to draw its own parts dark too: scrollbars, unstyled inputs, date pickers. And contrast is the rule that keeps text readable: normal text needs a contrast ratio of at least 4.5 to 1 against its background, icons and large text at least 3 to 1. You will compute this in module 9.

Exercise

In your browser devtools on any page, select <html>, add style="--test: red", then on any element set color: var(--test). Change --test to blue and watch it update live. That is the mechanism this entire course relies on.

Audit the codebase

Before you change anything, find out how many colours exist, where they live and what they do.

2.1 Count the hardcoded colours

Run these from the repo root (Git Bash works on Windows):

# every hex colour in SCSS, most used first
grep -rhoiE '#[0-9a-f]{3,8}\b' src/design-system --include=*.scss \
  | tr A-Z a-z | sort | uniq -c | sort -rn | head -40

# every rgba() value
grep -rhoE 'rgba?\([^)]*\)' src/design-system --include=*.scss \
  | tr -d ' ' | sort | uniq -c | sort -rn | head -30

# which palette tokens are used, and how often
grep -rhoE 'var\(--color-[a-z0-9-]+' src/design-system --include=*.scss \
  | sort | uniq -c | sort -rn | head -40

This repo had about 660 hardcoded colours across 101 files, outside tokens.scss. The top results tell you the real light palette: #171429 for main text, #7e7a93 and #a6a1bb for muted text, #eeedf3 and #e2e0ec for borders, white for cards.

2.2 Find the heaviest files

cd src/design-system/primitives
for f in $(find . -name "*.scss" | sort); do
  n=$(grep -cE '#[0-9a-fA-F]{3,8}\b|rgba?\(|var\(--color-' "$f")
  [ "$n" -gt 0 ] && echo "$n $f"
done | sort -rn

Work heaviest first: it gives you the most coverage early and surfaces the tricky cases.

2.3 Learn what each colour does

For each frequent value, look at the property it sits on:

grep -rniE "^\s*[a-z-]+:.*#171429" src/design-system --include=*.scss | head

If it is always color:, it is text. If it is border, it is a divider. This tells you which role it will become (module 4).

Do not change code yet

The audit is only reading. The temptation is to start replacing as you look. Resist it: you cannot name roles well until you have seen all the colours.

Read the design in Figma

Turn the dark Figma frames into a list of colours with jobs.

3.1 Map every dark frame to its light twin

The file keeps each dark frame next to its light version. Write the pairs down once; you will keep coming back to them. This project's map lives in darkmodeplan.html (home 93:53454, My Domains 93:49561, watchlist 93:89796, listing flow 93:77717, buying flow 93:91182, login 93:38530, 404 93:89003).

3.2 Three ways to read colours

  1. Selection colors. Select a whole frame. The right panel lists every colour used inside it with its opacity. Click one to see which layers use it. This is the fastest way to see a page's palette.
  2. Dev Mode (Shift D). Click a single layer and read its fill, border, opacity and text colour in the Inspect panel.
  3. Variables. If the designer made Figma variables, they are your tokens. In this file there were none (the designer used black and white at different opacities), so the token scale had to be designed by us.

3.3 What you will find, and what to do with it

  • Lots of near duplicates. The dark frames used about 45 distinct colours: white at 100, 88 and 83%, gray #141414, #171717, #19191a. Group them: 100/88/83% are all "primary text".
  • Leftovers from light mode. Real files have mistakes: a black label on a dark background, a light gray divider, a white drawer. List them as questions for the designer (the plan lists 11) instead of copying them.
  • Translucent panels. Figma often uses "white at 5%" over black. That is about #0d0d0d. Decide whether to keep translucency or use a solid colour (we chose solid, see 4.4).
Large frames

If a tool or plugin says a frame is too big to inspect, open its child frames one by one (the header, the sidebar, one card). Each section is easier to read than the whole page.

4

Design the token system

Name a small set of roles, give each its current light value, and plan its dark value.

4.1 Palette tokens versus role tokens

tokens.scss already had palette tokens: --color-blue-primary, --color-gray-dark, --color-white-primary. They describe what a colour is. A role token describes what a colour does: --color-text-secondary, --color-bg-surface.

Only role tokens change between themes. "White" is always white; but "the card background" is white in light and #141415 in dark. If a component uses var(--color-white-primary) for its background, dark mode cannot touch it without breaking every other use of white.

4.2 The 27 roles in this project

GroupRoles
Surfaces--color-bg-page, --color-bg-surface, --color-bg-surface-active, --color-bg-option-selected
Text--color-text-primary, -secondary, -tertiary, -disabled, -mono-muted, -on-dark
Borders--color-border-subtle, -strong, -emphasis
Controls and brand--color-control-selected-bg, --color-control-selected-text, --color-accent, --color-badge-extension
Status--color-status-success, -success-text, -success-bg, -error, -error-text, -error-bg, -warning, -warning-bg
Data--color-data-primary, --color-data-secondary

4.3 Give each role today's light value

This is the trick that makes the whole migration safe: the role's light value is the colour the site already uses most for that job (from your audit). So adding the roles changes nothing visually.

src/design-system/styles/tokens.scss (end of :root)

  // ══ Semantic theme roles ═══════════════════════════════════════
  // Components use these roles instead of raw colours or the palette
  // tokens above, so dark mode only has to redefine this block.

  // ── Surfaces ──
  --color-bg-page: var(--color-gray-page-bg);     // page and drawer background
  --color-bg-surface: var(--color-white-primary); // every card, table, row, panel
  --color-bg-surface-active: var(--color-gray-light); // hover, active, nested tiles

  // ── Text ──
  --color-text-primary: #171429;   // headings, values, body copy
  --color-text-secondary: #7e7a93; // labels, supporting copy
  --color-text-tertiary: #aba7bc;  // hints, captions, placeholders

  // ── Borders ──
  --color-border-subtle: #eeedf3;  // dividers, card outlines
  --color-border-strong: #e2e0ec;  // inputs, option cards, toggles
  /* …and the rest of the 27 */

4.4 Rules that keep the list short

  • One surface everywhere. The Figma used about seven card backgrounds. We replaced them all with one solid #141415 on a black page, plus one shade for hover (#2f2f2f). Nested cards are separated by a border, not a second shade. It looks calm, and it is three surface tokens instead of ten.
  • White at fixed opacities for text and borders. Text 100/70/50/25%, borders 10/30/57%. Translucent text blends with whatever it sits on, so it works on both the page and the surface.
  • Map, don't multiply. A new colour gets mapped to the nearest existing role. Add a role only when nothing fits and you have asked the team.
Why "near shades map to the role"

Light mode used #171429, #070707 and pure black for main text. Mapping all three to --color-text-primary shifts a few texts by a shade nobody notices, but gives one consistent light mode and one token to switch. The alternative (keeping each exact light colour) needs extra overrides for every near shade. The team chose to map, and every visible shift was logged.

Exercise

Take your exercise list from module 3 and assign every dark colour to one of the 27 roles. Anything that does not fit goes into a "no role" list; you will decide those per page later.

5

The theme switch

Store the choice, apply it before first paint, expose it to React, and hide it behind a flag.

5.1 The feature flag

A half finished dark mode must not reach users. Put everything behind an environment variable. Variables starting with NEXT_PUBLIC_ are baked into the browser bundle at build time, so you must restart the dev server after changing .env.

# .env (local only)
NEXT_PUBLIC_DARK_MODE=true

5.2 The context: one source of truth

src/context/ThemeContext.tsx

export type Theme = 'light' | 'dark'

export const isDarkModeEnabled = process.env.NEXT_PUBLIC_DARK_MODE === 'true'
export const THEME_STORAGE_KEY = 'theme'

// Browser UI colour (mobile address bar) per theme
export const THEME_COLOR: Record<Theme, string> = { light: '#ffffff', dark: '#000000' }

// Runs inline in <head> before first paint, so a saved dark choice never flashes light.
export const themeInitScript = `(function(){try{var t=localStorage.getItem('${THEME_STORAGE_KEY}');
if(t==='dark'||t==='light')document.documentElement.setAttribute('data-theme',t)}catch(e){}})()`

export const ThemeProvider = ({ children }: { children: React.ReactNode }) => {
  const [theme, setThemeState] = useState<Theme>('light')

  // The init script already set the attribute; this only syncs React state to it.
  useEffect(() => {
    if (!isDarkModeEnabled) return
    if (document.documentElement.getAttribute('data-theme') === 'dark') setThemeState('dark')
  }, [])

  const setTheme = useCallback((next: Theme) => {
    if (!isDarkModeEnabled) return
    document.documentElement.setAttribute('data-theme', next)
    try { localStorage.setItem(THEME_STORAGE_KEY, next) } catch {}
    setThemeState(next)
  }, [])

  const toggleTheme = useCallback(() => setTheme(theme === 'dark' ? 'light' : 'dark'), [theme, setTheme])
  return <ThemeContext.Provider value={{ theme, setTheme, toggleTheme }}>{children}</ThemeContext.Provider>
}

export const useTheme = () => useContext(ThemeContext)

Read it slowly. Note three details:

  • Every localStorage access is inside try. In private windows or with blocked storage it can throw; the page must still work.
  • React state starts as 'light' on purpose. The server cannot know the user's choice, so the first render must match on server and client, otherwise React complains about a hydration mismatch. The effect then catches up.
  • Things that must be right on the first paint (like the toggle's knob position) should not depend on React state at all. They read the attribute through CSS (module 6).

5.3 The no flash script

pages/_document.tsx

import { isDarkModeEnabled, themeInitScript } from "@/context/ThemeContext";

<Head>
  {isDarkModeEnabled && <script dangerouslySetInnerHTML={{ __html: themeInitScript }} />}
  …
</Head>

_document renders only on the server and its <head> runs before the body is painted, which is exactly when the attribute must be set. The script is tiny and has no imports because it runs before your bundle loads.

5.4 Wire it up

  • Wrap the app in <ThemeProvider> in pages/_app.tsx.
  • In the main layout, make the theme colour meta tag follow the theme: <meta name="theme-color" content={THEME_COLOR[theme]} />.
  • In tokens.scss, start the dark block: :root[data-theme='dark'] { color-scheme: dark; }.
Default theme

We default to light and only switch when the user picks dark. Following the operating system (matchMedia('(prefers-color-scheme: dark)')) is a one line change in the init script, and it is a product decision, so it was left as an open question for the team.

Exercise

With the flag on, open devtools, run localStorage.setItem('theme','dark'), reload, and confirm <html data-theme="dark"> is already there in the Elements panel before React finishes. Then turn the flag off and confirm the script is gone from the page source.

6

Build the toggle

A small accessible switch whose look comes entirely from CSS.

6.1 Markup: a real switch

src/design-system/primitives/toggles/theme-toggle/ThemeToggle.tsx

<button
  type="button"
  role="switch"
  aria-checked={isDark}
  aria-label="Dark mode"
  className={styles.toggle}
  onClick={toggleTheme}
>
  <span className={styles.knob} aria-hidden="true" />
  <span className={`${styles.slot} ${styles.sun}`}><SunIcon /></span>
  <span className={`${styles.slot} ${styles.moon}`}><MoonIcon /></span>
</button>

role="switch" with aria-checked tells screen readers this is an on/off control, not a plain button.

6.2 Icons that change colour

The sun and moon were exported from Figma as SVG paths, then pasted as inline SVG with fill="currentColor". currentColor means "use this element's CSS color", so CSS can recolour the icon per theme. An <img src="sun.svg"> could not do that.

6.3 State from CSS, not React

ThemeToggle.module.scss (simplified)

.toggle {
  --toggle-pill: var(--color-black-primary);
  --toggle-knob: var(--color-white-primary);
  background: var(--toggle-pill);
}

:global(:root[data-theme='dark']) .toggle {
  --toggle-pill: var(--color-white-primary);
  --toggle-knob: var(--color-black-primary);
}

.knob { left: 2.625px; background: var(--toggle-knob); transition: left 0.2s ease; }
:global(:root[data-theme='dark']) .knob { left: 31.75px; }

Two lessons here. Local custom properties (--toggle-pill) let you flip a whole component by redefining two names. And :global(...) is how a CSS module refers to something outside the module (the html attribute) without the build renaming it.

Why not use theme from React for the knob?

React state is 'light' until the effect runs. If the knob position came from state, a dark user would see the knob jump from sun to moon on load. Reading the attribute through CSS makes it correct on the very first paint.

6.4 Place it behind the flag

{isDarkModeEnabled && <ThemeToggle />}

Figma only showed the dark state of the toggle, so the light state mirrors it (black pill, white knob on the sun). When a design is missing, make the most symmetric choice and write it down as a question for the designer.

Exercise

Add @media (prefers-reduced-motion: reduce) { transition: none; } to the knob and test it with the "Emulate CSS prefers-reduced-motion" option in devtools rendering settings.

7

Migrate the primitives

Make every shared building block read its colours from roles, with no visible change.

7.1 The golden rule: decide by what the colour does

The same hex value can need different roles. White can be a card background (surface, becomes dark) or text on a blue button (stays white). Never search and replace blindly.

Becomes a role
  • Card, row, panel, input, dropdown, modal backgrounds
  • Headings, labels, values, placeholders
  • Dividers, outlines, input borders
  • Success, error, warning text and fills
  • Chart lines and fills, links, focus
Stays as it is
  • Brand fills (the blue Buy Now button, the green and charcoal variants)
  • White text on those brand fills
  • Every colour inside box-shadow, glows, drop shadows
  • Decorative gradients
  • Colours computed from data in TSX

7.2 Before and after

primitives/modal/Modal.module.scss

/* before */
.panel  { background: var(--color-white-primary); }
.header { border-bottom: 1px solid #eeedf3; }
.title  { color: #171429; }
.close  { color: #7e7a93; }
.close:hover { background: var(--color-gray-light); }

/* after */
.panel  { background: var(--color-bg-surface); }
.header { border-bottom: 1px solid var(--color-border-subtle); }
.title  { color: var(--color-text-primary); }
.close  { color: var(--color-text-secondary); }
.close:hover { background: var(--color-bg-surface-active); }

Light mode is identical (every value matched its role's light value). Dark mode now works for free once the dark values exist.

7.3 Write a rulebook before you start

For about 500 colour lines, consistency matters more than speed. Write the mapping down once (it lived in a short file during the build) and follow it everywhere:

  • Dark text (#171429, black, #1a1a1a, black above 60%) → --color-text-primary
  • Mid text (#7e7a93, gray primary, gray dark, black 45 to 59%) → --color-text-secondary
  • Light text and placeholders (#aba7bc) → --color-text-tertiary; mono timestamps #a6a1bb → --color-text-mono-muted
  • Light dividers (#eeedf3, black 3 to 10%) → --color-border-subtle; input borders (#e2e0ec) → --color-border-strong
  • Colours with no fitting role → leave them and add them to a "no role" list

7.4 Log every visible shift

When a near shade maps to its role, write it down: file, old value, new value. For example, the error red moved from #dc3545 to #ef4444 in several places. If someone later says "this looks different", the log answers them in seconds.

Know when a near shade is not near

The disabled price input was #7c7c7c. The disabled role is #b2b2b2, which is visibly lighter. That is not a near shade, so it used the secondary role instead. Use your eyes, not only the rule.

Exercise

Migrate one small primitive (Checkbox or Breadcrumb) on a branch. Take a screenshot before and after in light mode and compare them side by side. They should look the same.

8

Icons and images

Make sure nothing disappears on black, and swap images without a flash.

8.1 Sort every icon into a group

  • Already fine: react-icons and inline SVG components use currentColor, so they follow the text colour automatically.
  • Will vanish: single colour SVG files drawn in black or dark gray. On a black page they are invisible. This repo had ten (calendar, clock, eye, bookmark, share, info, the breadcrumb arrow and slash…).
  • Multicolour with dark parts: logos and illustrations. They need a dark version.
  • Coloured icons: check their contrast on the dark surface (module 9).

8.2 Turn a dark SVG file into a currentColor component

Do not retype paths by hand. A small script read each SVG file, replaced fill="black" with fill="currentColor", kept Figma's opacity, and wrote React components:

primitives/icons/overview-icons/OverviewIcons.tsx (one of eight)

export const EyeIcon = ({ width = 15, height = 15, ...rest }: OverviewIconProps) => (
  <svg width={width} height={height} viewBox="0 0 15 15" fill="none" aria-hidden="true" {...rest}>
    <path d="M1.40625 7.5C1.40625 7.5 3.75 3.28125 …" stroke="currentColor" strokeWidth="1.21875" />
  </svg>
)

Then swap the image for the component and give the caller a colour:

// before
<Image src="/assets/img/domain-overview/eye.svg" width={15} height={15} className={styles.eyeIcon} />
// after
<EyeIcon width={15} height={15} className={styles.eyeIcon} />

/* SCSS */
.eyeIcon { color: var(--color-text-primary); }

8.3 Icons used as CSS backgrounds: use a mask

The breadcrumb slash was a background: url(slash.svg). A background image cannot use currentColor. A mask can: the SVG becomes a stencil and the background colour shows through it.

&::after {
  background: var(--color-text-primary);
  mask: url('/assets/img/breadcrumb/slash.svg') center / 3.75px 9.75px no-repeat;
}

8.4 Swap images with CSS, never with JavaScript

For the white logo, render both images and let CSS show one:

<Image src={logo} … className={styles.logoLight} />
<Image src="/endless-logo-white.svg" alt="" aria-hidden="true" … className={styles.logoDark} />

.logo {
  .logoDark { display: none; }
  @include dark {
    .logoLight { display: none; }
    .logoDark  { display: block; }
  }
}

If you picked the image with theme === 'dark' ? … : … in React, the light logo would flash first for dark users (same reason as module 5).

Make the dark asset from the light one when you can

The white logo was made by copying endless-logo.svg and changing its eight fill="black" to fill="white". Same size and shape, so the header does not shift between themes. Figma's export had a different canvas size and would have moved things.

Exercise

Find any icon in the repo used as <Image src="....svg"> that is drawn in black, convert it into a currentColor component, and check it in both themes.

tokens.scss

  --color-bg-page: #000000;
  --color-bg-surface: #141415;
  --color-bg-surface-active: #2f2f2f;

  --color-text-primary: #ffffff;
  --color-text-secondary: rgba(255, 255, 255, 0.7);
  --color-text-tertiary: rgba(255, 255, 255, 0.5);
  --color-text-disabled: rgba(255, 255, 255, 0.25);

  --color-border-subtle: rgba(255, 255, 255, 0.1);
  --color-border-strong: rgba(255, 255, 255, 0.3);
  --color-border-emphasis: rgba(255, 255, 255, 0.57);

  --color-control-selected-text: #000000;

Only roles are redefined. Palette tokens like --color-blue-primary keep the same value in both themes, which is exactly why brand fills stay put.

9.2 How to compute contrast

Contrast compares the relative brightness (luminance) of two colours. You can compute it in Node in a few lines:

const L = hex => {
  const c = [1, 3, 5].map(i => parseInt(hex.slice(i, i + 2), 16) / 255)
    .map(v => v <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4)
  return 0.2126 * c[0] + 0.7152 * c[1] + 0.0722 * c[2]
}
const ratio = (a, b) => { const [x, y] = [L(a), L(b)].sort((p, q) => q - p); return (x + 0.05) / (y + 0.05) }

console.log(ratio('#2639ed', '#141415').toFixed(2)) // 2.53  → too low for text
console.log(ratio('#6b7bff', '#141415').toFixed(2)) // 5.17  → passes

9.3 When the brand colour fails

The brand blue #2639ED is 2.53 to 1 as text on the dark surface. Text needs 4.5. So the accent role (used for links and blue text) gets a lighter blue in dark, while brand fills (buttons) keep #2639ED because they use the palette token, not the role. One decision, logged, and flagged for the designer. The same check showed the Polygon logo (2.6) needs a lighter variant on its page.

Exercise

Use the snippet to check rgba(255,255,255,0.5) tertiary text on #141415. (Hint: blend it first: 50% white over #141415 is about #8a8a8a.) Is it fine for captions? For body text?

10

The dark mixin

A clean way to write the few rules that only apply in dark, and the traps around it.

10.1 Why you need it

Most components need nothing beyond role tokens. A few need a different colour in dark that no role expresses. Sidebar section titles are gray in light but white in dark; listing rows are white in light but black in dark (while other surfaces stay #141415). For those, add a component level dark rule instead of a new token.

src/design-system/styles/_mixins.scss

@mixin dark {
  :global(:root[data-theme='dark']) & {
    @content;
  }
}
.title {
  color: var(--color-text-secondary);

  @include dark {
    color: var(--color-text-primary); // Figma dark: section titles are white
  }
}

10.2 Trap one: the override beats your hover

.item {
  color: var(--color-text-secondary);
  &:hover { color: var(--color-text-primary); }       /* (0,2,0) */
  @include dark { color: var(--color-text-tertiary); } /* (0,3,0) wins, even on hover! */
}

The dark rule is more specific than .item:hover, so in dark the row never brightens on hover. Fix: repeat the hover inside the dark block.

  @include dark {
    color: var(--color-text-tertiary);
    &:hover { color: var(--color-text-primary); }
  }

10.3 Trap two: declarations after nested rules

Sass now warns when you write a plain declaration after a nested block. Always put @include dark { … } at the end of a rule, after every property.

/* wrong */
.row { background: …; @include dark { … } border-radius: 3px; }
/* right */
.row { background: …; border-radius: 3px; @include dark { … } }

10.4 Trap three: the mixin needs a parent

The mixin uses &, so it only works inside a selector. Writing @include dark { .glowLight { … } } at the top of a file fails with "Top level selectors may not contain the parent selector". Nest it inside each rule instead.

Also remember the import: a module that uses the mixin needs @import '@newstyles/_mixins.scss'; at the top.

The most important rule of this module

Use dark overrides to change colours only. Do not restyle components to match the dark Figma (turning the blue active tab into a white chip, flattening a glass bar). That was tried once and reverted on request. The light design's shapes, layout and active states stay; only their colours adapt.

11

The shell

Header, sidebar, drawer, bottom nav and footer: the frame every page shares.

Do the shell before any page. Once it is dark, every page looks half done in a predictable way, and you can do pages in any order.

  1. Inventory: list the colour lines in layouts/header, layouts/sidebar/*, layouts/footer-stripe, layouts/main-layout, MarketplacePageShell, MobileBottomNav.
  2. Read Figma: header bar (surface with a hairline bottom border), nav links (inactive white 56%, active white), sidebar (section titles white, rows white 50%, active row #2f2f2f).
  3. Map to roles: header and sidebar backgrounds to --color-bg-surface, dividers to --color-border-subtle, labels to text roles.
  4. Add the few dark overrides: white active link, white section titles, 50% rows, white active tab in the bottom nav.
  5. Swap the logo (module 8).
  6. Fix the page background: the legacy global CSS painted body white, which showed as a white band under short pages. One rule in tokens.scss: :root[data-theme='dark'] body { background-color: var(--color-bg-page); }.
Mixed state is normal

After the shell, the dark header and sidebar wrap light page content, and some white text sits on still white cards. That is expected while the toggle is hidden. Each page phase removes it.

12

Pages, one at a time

A repeatable recipe, shown on the home page and My Domains.

12.1 The recipe for any page

  1. List the page's composites and count their colour lines.
  2. Open the dark Figma frame for the page and its sections. Note backgrounds, borders and text opacities.
  3. Migrate each composite to roles with the rulebook (module 7).
  4. Add the dark overrides the page needs (module 10), colours only.
  5. Compile, screenshot in dark and light (module 13), compare with Figma.
  6. Log the phase.

12.2 Worked example: the home listings panel

In dark, everything from the category tabs to the table sits in one surface panel, and the listing rows are black inside it. In light there is no panel. Two pieces:

/* MarketplacePageShell.module.scss: the wrapper becomes a panel in dark only */
.listingsSlot {
  display: flex; flex-direction: column; gap: var(--space-6);
  @include dark {
    padding: 14px;
    background: var(--color-bg-surface);
    border: 1px solid var(--color-border-subtle);
    border-radius: 4px;
  }
}

/* ListingRow.module.scss: white rows in light, black rows in dark */
.row {
  background: var(--color-bg-surface);
  border: 1px solid var(--color-border-subtle);
  border-radius: 3px;
  @include dark { background: var(--color-bg-page); }
}
Why not just use --color-bg-page for rows?

In light, --color-bg-page is #f9f9f9, so white rows would turn gray. The rows need "surface in light, page in dark", and that combination is exactly what a dark override is for.

12.3 Worked example: gradients from the design

The promoted domains panel in Figma is darker than its cards and fades to black at the edges. A pseudo element with three gradients does it without touching the markup:

.section {
  @include dark {
    background-color: rgba(255, 255, 255, 0.05);
    &::after {
      content: '';
      position: absolute; inset: 0; z-index: 1; pointer-events: none;
      background:
        linear-gradient(to right, #000 0, #000 24px, rgba(0, 0, 0, 0) 118px),
        linear-gradient(to left,  #000 0, #000 24px, rgba(0, 0, 0, 0) 118px),
        linear-gradient(to top,   #000 0, rgba(0, 0, 0, 0) 33px);
    }
  }
}

pointer-events: none keeps the cards underneath clickable; the heading gets position: relative; z-index: 2 in dark so it stays above the fade, like in Figma.

12.4 Reuse patterns across pages

My Domains used the same pattern as home: a dark panel around tabs, filters and table, black rows and grid cards, surface right rail panels. The right rail panels share one primitive (InfoListCard), so a single dark rule there fixed all three. Always look for the shared piece before editing three files.

Checking your work

Fast checks you can run after every change, without breaking anything.

13.1 Static checks

npx tsc --noEmit -p .                      # types
npx eslint src/path/to/changed/files       # lint, look for new warnings only
git diff | grep "^+" | grep -c "!important" # must be 0 (project rule)

13.2 Compile a stylesheet on its own

Sass can compile a module directly, which catches syntax errors and shows you the final dark selectors, in about a second:

node -e "
const sass = require('sass')
const css = sass.compile('src/design-system/layouts/header/Header.module.scss', {
  silenceDeprecations: ['import'],
  importers: [{ findFileUrl: u => u.startsWith('@newstyles/')
    ? new URL('file:///' + process.cwd().replace(/\\\\/g, '/') + '/src/design-system/styles/' + u.slice(11)) : null }]
}).css
console.log(css.match(/[^}]*data-theme[^{]*\{[^}]*\}/g))"

13.3 Screenshots in dark, from the command line

A plain headless screenshot cannot set localStorage first. Chrome's DevTools protocol can: open the site, set theme, reload, capture. The script used during the build (shot.js) does exactly that against the dev server you are running:

node shot.js http://localhost:3002/ home-dark.png dark 1440 1300
node shot.js http://localhost:3002/ home-light.png light 1440 1300

Always take both. The light screenshot is your regression check: it should look the same as before the phase.

Never build while the dev server runs

next build writes into the same .next folder that npm run dev uses. Running it during development broke the dev server once (every page returned 500 with "Cannot find module ./chunks/vendor-chunks/next.js") until it was restarted with a fresh .next. Verify through the running dev server; build only in CI or with the dev server stopped.

13.4 Pages behind a login

Headless screenshots have no session, so My Domains and the watchlist need a human check. Give the person a short list of exactly what to look at, in both themes.

14

Working like a team

How to do a long, risky change without breaking production or losing track.

  • Plan first, code later. The plan (darkmodeplan.html) was written and revised before any code: phases, Figma map, questions for the designer.
  • Phases that are each safe to merge. 0 design alignment, 1 tokens, 2 switch and toggle, 3 primitives, 4 dark values and shell, 5 to 11 one page area each, 12 final QA and enabling the toggle. Because of the flag, every phase can merge without users seeing it.
  • Own branch. dark-mode, cut from marketplace-v2, so feature PRs stay clean.
  • A progress log. darkmodeprogress.html: what each phase changed, files, decisions with reasons, what was verified and what was not. Update it at the end of every phase.
  • Decisions are written down with their reason. "Sidebar uses the single surface (Figma shows black): one surface for every panel." Future you will forget why.
  • Commit when the owner says so. Phases can be built and checked but held back; that is fine, the log records the state.
  • Splitting work across people (or helpers). The primitives were migrated in four parallel groups. It only worked because everyone followed one written rulebook and reported every change in the same table format, so one person could review the whole diff.
15

Mistakes and lessons

Real mistakes from this build. Each one is cheap to avoid once you know it.

What happenedLesson
A production build ran while the dev server was up; every page returned 500.Never build into the dev server's .next. Check through the running server.
The category tabs were restyled to Figma's dark design (white chip, flat bar).Dark mode changes colours, not designs. Ask before changing anything else.
An interrupted command had already applied two of its edits (an ellipsis and a duplicate CSS rule).After any interruption, check git diff before continuing. Partial edits are easy to miss.
A helper screenshot page compiled CSS from fragments and a missing } swallowed rules, so the toggle looked broken.When a test looks wrong, first suspect the test. Verify the real compiled CSS.
Find and replace on Windows files missed lines because of \r\n line endings.Match with \r?\n, or use an editor, and confirm with git diff that every intended line changed.
A dark override silently disabled a hover state.Specificity: repeat states inside the dark block (module 10).
The brand blue was unreadable as text in dark.Run contrast numbers for every coloured text role, not just a visual check.

The rules to add to CLAUDE.md at the end
  • New colours use a role token, never a raw hex or palette token, unless they are brand fills, shadows or decorative gradients.
  • Single colour icons use currentColor; SVG files only for multicolour art.
  • Theme specific images swap with CSS on data-theme, never in JavaScript.
  • Every new component is checked in both themes before review.

Glossary

Token
A named design value, here a CSS custom property like --color-text-primary.
Palette token
Names what a colour is (--color-blue-primary). Same in both themes.
Role token
Names what a colour does (--color-bg-surface). Redefined in dark.
Surface
The background of a card, row, panel or input.
Near shade
A colour barely different from a role's value, mapped to the role.
Flash
The wrong theme showing for a moment before JavaScript fixes it.
Hydration
React attaching to server rendered HTML; the first client render must match the server.
currentColor
A CSS keyword meaning "this element's text colour"; lets icons follow the theme.
Mask
Using an image as a stencil so a background colour shows through its shape.
Specificity
The weight of a selector that decides which rule wins.
Contrast ratio
Readability measure between two colours; 4.5 for text, 3 for icons.
Feature flag
An environment switch that hides unfinished work from users.
Shell
The parts every page shares: header, sidebar, drawer, bottom nav, footer.
