The hero banner and the promoted domains marquee

A component that's smaller than it looks because the design did the hard work in an image file, next to a component that's bigger than it looks because it runs a real CSS animation loop.

1MarketplaceHero: know when NOT to build something

The hero looks like it should be the most complex component on the page — an abstract network illustration with five floating category chips (Collectibles, Credit, Real Estate, Equity, Commodity) scattered across it. It's actually one of the smallest files in the whole codebase:

MarketplaceHero/MarketplaceHero.tsx
export const MarketplaceHero = () => {
  return (
    <div className={styles.hero}>
      <div className={styles.badge}>
        <img src="/assets/img/hero/logo-white-text.svg" alt="Endless Domains" className={styles.logo} />
      </div>
    </div>
  )
}

That's the whole component: a container div with a background image, and one badge with the logo on top. No chip elements, no positioning math, no data array of five category labels.

A wrong assumption caught before it became wasted work

Earlier in this project, a HeroCategoryChip type was defined in the types file, assuming the five floating chips would be separate positioned React elements that needed real data and layout code. Pulling the actual design data for this node via Figma's get_design_context tool (not just eyeballing the screenshot) showed the truth: the network illustration and all five chips are baked into a single exported background image, hero-network-bg.png. There was never anything to position. The HeroCategoryChip type still exists in the types file, unused, as a record of that dead end.

The lesson generalizes past this one component: before writing layout code for something that looks like a set of separately positioned pieces, check whether the design tool's structured data agrees that they're separate elements at all. A screenshot alone can't tell you that a flat image and five real DOM elements would render identically.

The one real responsive decision it makes

MarketplaceHero.module.scss
.hero {
  aspect-ratio: 835 / 172; // design-specific: Figma-exact hero proportions
  background-image: url('/assets/img/hero/hero-network-bg.png');
  background-size: cover;

  @include mobile {
    aspect-ratio: 355 / 105; // mobile crop is a different image proportion, not a scaled-down desktop one
  }
}

aspect-ratio reserves the right amount of vertical space for the image before it's even loaded (so nothing jumps as the page paints), and background-size: cover lets one image file serve both ratios by cropping rather than stretching. This one line was also a bug fix: it used to read 4/3 at mobile, a guess that made the hero far taller and squatter than the real mobile mockup (Figma node 20:1191) called for.

2PromotedDomainsSection: a real CSS-only marquee

This is the row of domain cards that auto-scrolls sideways forever. It's a genuinely common UI pattern — and one that's very easy to get almost right and subtly wrong (visible jump at the loop point, unreadable while it's moving, or impossible to stop for anyone who needs it stopped). Walking through it slowly is worth it because the same three techniques reappear anywhere you need an infinite scroller.

Trick 1: duplicate the content, animate exactly half its width

PromotedDomainsSection.tsx
<div className={styles.track} style={trackStyle}>
  {[0, 1].map((pass) => (
    <div className={styles.pass} key={pass} aria-hidden={pass === 1}>
      {mockPromotedListings.map((listing) => (
        <PromotedDomainCard key={`${listing.id}-${pass}`} listing={listing} />
      ))}
    </div>
  ))}
</div>
PromotedDomainsSection.module.scss
.track {
  display: flex;
  width: max-content; // two passes side by side, never wraps
  animation: promoted-marquee var(--loop-seconds, 28s) linear infinite;
}

@keyframes promoted-marquee {
  from { transform: translateX(0); }
  to   { transform: translateX(-50%); }
}

The list of cards is rendered twice, back to back, inside one flex row wide enough to hold both copies. The animation slides that row left by exactly half its own width. Because the second half is an exact copy of the first, the instant the animation finishes, what's on screen is pixel-identical to what was on screen at frame zero — so the animation can jump straight back to translateX(0) and repeat, and nobody watching can tell the loop restarted. This is the whole trick behind every seamless CSS marquee: duplicate, then translate by exactly one copy's width.

The second pass is marked aria-hidden="true", since it's a visual duplicate with no new information — a screen reader should only ever announce the promoted domains list once.

Trick 2: pace the loop by content, not by a magic duration

PromotedDomainsSection.tsx
const SECONDS_PER_CARD = 3.5

const trackStyle = {
  '--loop-seconds': `${mockPromotedListings.length * SECONDS_PER_CARD}s`,
} as React.CSSProperties

A fixed animation-duration: 28s would look fine with today's 8 mock cards and wrong the day someone adds a 9th — either too fast (each card barely gets a moment on screen) or, worse, still 28 seconds for more content, which just changes the effective speed as a side effect of an unrelated data change. Computing the duration from list.length * secondsPerCard keeps the apparent speed constant no matter how many cards there are, and it's passed into CSS through an inline style object, landing as a CSS custom property (--loop-seconds) that the @keyframes rule reads back with var(--loop-seconds, 28s). 28s there is only a fallback for the rare case the variable is missing entirely.

A number isn't a time

The inline style deliberately writes `${...}s`, not the bare number. animation-duration is a CSS <time> value and requires a unit — a custom property holding a bare number like 28 is not a valid time, so var(--loop-seconds) would fail to parse and CSS quietly falls back to the property's initial value, which for duration is 0s. The visible symptom is the whole row just sitting still with no console error at all, because this fails silently as invalid CSS rather than as a JavaScript exception. If you ever build something like this and the animation refuses to move, check that a unit made it into the string.

Trick 3: pause on hover, and give reduced-motion users a real fallback

PromotedDomainsSection.module.scss
.track {
  .marquee:hover &,
  .marquee:focus-within & {
    animation-play-state: paused;
  }

  @media (prefers-reduced-motion: reduce) {
    animation: none;
  }
}

.marquee {
  @media (prefers-reduced-motion: reduce) {
    overflow-x: auto; // becomes a plain manually-scrollable row
  }
}

.pass {
  @media (prefers-reduced-motion: reduce) {
    &:last-child { display: none; } // don't scroll past a duplicated set of cards
  }
}

animation-play-state: paused freezes the animation exactly where it is (not a snap back to the start) the instant a pointer hovers the row or keyboard focus lands inside it — without this, an infinitely sliding row of clickable buttons would be nearly impossible to actually click, the target keeps moving out from under the cursor. :focus-within matters as much as :hover here: a keyboard user tabbing into a card's buy button needs the row to stop too, not just a mouse user hovering it.

prefers-reduced-motion is an operating-system-level accessibility setting some users turn on because motion causes them real discomfort (vestibular disorders, migraines). The media query above turns the animation off entirely and switches the row back to an ordinary manually-scrollable flex row — and since there's no more animation to loop seamlessly, the second, duplicate pass is hidden too, so a reduced-motion visitor scrolling the row by hand doesn't run into the same 8 cards twice.

The scroll fade and the design's own decorative asset

PromotedDomainsSection.module.scss
.marquee {
  overflow: hidden;
  mask-image: linear-gradient(90deg, transparent, black 24px, black calc(100% - 24px), transparent);
}

mask-image is CSS's way of making parts of an element transparent using a gradient as the transparency map, rather than its actual color. Here it fades the row's own left and right edges to nothing over 24px, which signals "there's more content past this edge" without needing a separate overlay element. It's paired with a -webkit- prefixed duplicate for Safari, which still requires the vendor-prefixed property for this feature.

The glow bar along the section's top edge (promoted-glow.png) is a real exported asset from the Figma file, not a CSS gradient approximation — confirmed the same way the hero's chips were: by reading get_design_context's output rather than guessing from the screenshot which pieces were images versus which were CSS.

3PromotedDomainCard: composing primitives you already know

Once you've read phase 02, this card has almost nothing new in it — it's a demonstration of composing primitives rather than introducing one. ExtensionBadge, ChainBadge, and TrendIndicator are all badge-family primitives with the variant-prop pattern from phase 02; the buy-now button reuses PrimaryButton's stylesheet directly rather than wrapping it in a new component, since nothing about it differs from the primitive except size.

PromotedDomainCard.tsx
<button type="button" className={`${primaryBtnStyles.button} ${primaryBtnStyles.sm} ${styles.buyNow}`}>
  {/* PrimaryButton's ::before fill layer sits above unwrapped text — span required */}
  <span>buy now</span>
</button>

That inline comment is worth pausing on — it's a direct callback to phase 02's ::before fill-layer explanation for the chamfered button shape. The layer sits above the button's own content in stacking order, so any text placed as a bare, unwrapped child of the button would render underneath it and disappear. Wrapping the label in its own <span> gives it a real stacking context that the fill layer's z-index doesn't reach into. This is exactly the kind of thing that looks like an unnecessary extra element until you delete it and the button text vanishes.

This button is real-looking, not real-acting

The comment directly above it says so: {/* Static mock data — this button is visually real but not wired to BuyNowModal or any wallet call */}. It's a deliberate, labeled gap — phase 10 covers exactly what wiring this up for real involves.

The one piece of local state on this card, favorited, is a small preview of a pattern phase 06 covers in depth for the listings table: useState(!!listing.isFavorited) seeds initial state from the mock data (so a listing marked favorited in the data starts already favorited on screen) but afterwards the click handler owns it entirely — toggling this card's heart icon never writes back to mockPromotedListings itself.

4What to remember from this phase

  • Before writing layout code for something that looks like several positioned pieces, check the design tool's structured data (not just the screenshot) for whether they're actually separate elements or one baked-in image.
  • A seamless CSS marquee is: duplicate the content once, animate a translate of exactly negative one copy's width, loop.
  • Pace a loop's duration from the data driving it (item count) instead of a fixed number, so the apparent speed doesn't silently change when the data does.
  • A CSS custom property holding a duration needs its unit baked into the string — a bare number is an invalid time value and fails silently to the property's zero default.
  • Pause continuous motion on both :hover and :focus-within, and turn it off entirely under prefers-reduced-motion: reduce — this isn't optional polish, it's an accessibility requirement some visitors depend on.
