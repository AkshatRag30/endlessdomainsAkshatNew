Existing "My Domains" API & data analysis

Five separate hooks currently power one page, three of them fired straight out of the deepest component in the tree rather than the page:

HookFileCalled fromResponse shape
useGetDomainSummaryByUserQuerydomainListing.tspageDomainSummaryResponse{ data, paginationInfo, totalDomains, totalListed, totalUnlisted }
useLazyGetRefreshDomainListQuerydomain.tspage (Refresh button)refetch trigger only
useGetDomainExpiryDateQuerydomain.tsDomainItem, polled every 60s{ data: { domainName, expiry_date }[] }, joined client‑side by domainName
useGetDomainTldListQuerydomain.tsDomainsList templatestring[] of TLDs for the filter panel
useSetDomainAppraiselMutation / useSetCancelDomainListingMutationdomain.ts / domainListing.tsDomainItemaction mutations, not read data

confirmed gap  the inner domain object inside DomainSummaryResponse is loosely typed any everywhere it's passed around, and today's API only knows Listed/Unlisted — nothing about estimated value, view/save counts, or the five‑way status split (For sale / Not listed / Sold / Expiring soon / Expired) this design calls for. All of that is new surface, not a rename job.

List, delist, promote, and appraise are full client‑side blockchain transactions inside DomainItem: reading the connected wallet's network, mapping the domain's provider to an expected chain ID and marketplace contract address + ABI, prompting a network switch, then calling the contract directly with ethers. None of this changes for the redesign — only where it's triggered from does.

formatMyDomain.ts holds the USD/renewal formatters and the trend/status label maps MyDomainRow and MyDomainCard both need — written once, since a row and a card rendering the exact same fields drifting out of sync would be a worse outcome than a small shared file.

Why one InfoListCard, not three bespoke panels: Needs Attention, Getting The Most Views, and Quick Actions are visually identical containers — a title, a divided list of rows, each row an icon avatar + a two‑line label block + trailing content. Only the trailing content and the row data differ (a "Review" link, a view/save count pair, or a static description). One component with a row‑renderer prop covers all three, mirroring how the marketplace redesign's ListingRow was split into reusable cell pieces.

Reuse found while building, beyond what section 02 anticipated: MyDomainsCategoryTabs needed zero new styling — it's a data adapter over the marketplace redesign's existing ListingCategoryTabs, not a new component. ListingsHeading ("Live Listings" + a count) is reused verbatim, since this design's table heading turned out to say the exact same thing.

12

Risks and open items

  • The design's sidebar is the marketplace redesign's sidebar reused wholesale, not the old ProfileSidebar — open question whether "My Domains" moves out of /profile/* into the same shell/route family as the marketplace page. Needs a decision at Phase 04, not an assumption.
  • The table's Action column reads "Edit Price," with no DeList or Promote button visible per row, unlike the current page's actual behavior. Whether these moved to a secondary menu, got cut, or "Edit Price" is meant to cover reprice only is unconfirmed.
  • "Transfer" in Quick Actions has no existing mutation, modal, or API hook anywhere in the codebase — a genuinely new feature, not a reskin, and out of scope for this plan's phases unless explicitly added.
  • The Figma file's own placeholder numbers are mutually inconsistent (24 vs a 45 sum vs 14,208 vs 80) — none of them should be treated as real reference values, only the labels and layout.
  • Self‑correction, not a new risk: the first pass guessed a 5‑color left‑edge mapping and Price/EST. value both showing ETH+USD, before the card/list reference (node 375:51246) existed. Both were wrong and are now fixed — a reminder that anything not yet confirmed by an actual Figma pull in this doc is a guess, flagged or not.
  • The on‑chain delist/list logic in DomainItem is tightly coupled to per‑chain env‑keyed contract/ABI maps; moving or splitting this component needs care to avoid duplicating that logic.
  • DomainResponse is declared twice elsewhere in the codebase with different shapes (Domain.ts vs DomainList.ts) — same landmine flagged in the marketplace plan, still unresolved.
  • The real API applies its own listed/unlisted filtering server‑side, and the old page re‑filters again client‑side on top of that — worth resolving which layer owns filtering (now across five statuses, not two) before useMyDomains is wired to the real query.
