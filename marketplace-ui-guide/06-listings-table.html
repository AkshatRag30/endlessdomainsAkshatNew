Phase 06 · Sections

The listings table, and the mobile layout that took three tries

This phase spends more time on failed attempts than successful code, on purpose. The table you can scroll on a phone today is the third architecture tried for it, and the two that got abandoned teach the mechanism better than a clean success story would.

1The pieces above the table itself

ListingCategoryTabs and ListingFilterBar sit above LiveListingsTable and both lean on components you already know from earlier phases — tabs are a row of buttons with an active-state border radius fixed to match Figma exactly (a literal, Figma-measured 3.9px, not a token, since no existing radius token matched it), and the filter bar is a row of FilterDropdowns, the exact outside-click-to-close primitive from phase 02.

useListingFilters: state and filtering logic kept out of the component

hooks/marketplace/useListingFilters.ts
export function useListingFilters() {
  const [filters, setFilters] = useState<ListingFilters>(DEFAULT_LISTING_FILTERS)
  const debouncedSearch = useDebounces(filters.search)

  const setFilter = <K extends keyof ListingFilters>(key: K, value: ListingFilters[K]) => {
    setFilters((prev) => ({ ...prev, [key]: value }))
  }

  return { filters, debouncedSearch, setFilter }
}

This is a small but worth-noticing separation: the page component doesn't hold six separate useState calls for search/extension/price/length/chain/listed. It holds one hook call. Anything about how filter state is stored or debounced can change inside this one file without touching the component that uses it — the component only ever sees { filters, debouncedSearch, setFilter }.

Reusing the project's existing debounce, not writing a new one

The comment in the real file is blunt about why: "matches src/utils/useDebounce.ts's existing 300ms default rather than introducing a second debounce implementation (this repo already has three)." When you're adding a new feature to an existing codebase, grep for whether the thing you're about to write already exists somewhere else first — a fourth debounce implementation would work fine in isolation and still make the codebase harder to reason about.

filterListings: honest about what it doesn't do yet

hooks/marketplace/useListingFilters.ts
export function filterListings(listings: MarketplaceListing[], search: string, filters: ListingFilters) {
  const term = search.trim().toLowerCase()

  return listings.filter((listing) => {
    if (term && !listing.domainName.toLowerCase().includes(term)) return false
    if (filters.extension !== 'any' && listing.extension !== filters.extension) return false
    if (filters.chain !== 'any' && listing.chain.id !== CHAIN_VALUE_TO_ID[filters.chain]) return false
    return true
  })
}

Search and chain filters actually run against real fields on MarketplaceListing. Price, length, and listed-date don't — there's no matching field on the type yet. The function still accepts those filter values as parameters (so the dropdowns for them are fully functional UI, nothing is disabled), it just never checks them. That's a deliberate, visible gap rather than a silent lie: it would have been easy to fake a length filter against domainName.length and have it look like it worked while actually filtering on the wrong thing. Leaving it unimplemented and saying so in the comment is more honest than a filter that quietly does the wrong computation.

2ListingRow: one row, split into three exports

The desktop table is a single grid row: Domain Name, Price, Appraised Value, Chain, Action, five columns, one component. The mobile table needed the Domain Name cell to live in a completely different place in the DOM from the other four cells (more on why in a moment) — so ListingRow.tsx exports three things instead of one:

ListingRow.tsx
export const ListingDomainCell = ({ listing }) => ( // just the Domain Name cell
  <div className={styles.cell}>...</div>
)

export const ListingRestCells = ({ listing, favorited, onToggleFavorite }) => ( // Price/Appraised/Chain/Action
  <>...</>
)

export const ListingRow = ({ listing, favorited, onToggleFavorite }) => ( // desktop: both, together
  <div className={styles.row}>
    <ListingDomainCell listing={listing} />
    <ListingRestCells listing={listing} favorited={favorited} onToggleFavorite={onToggleFavorite} />
  </div>
)

Desktop uses the combined ListingRow. Mobile uses ListingDomainCell and ListingRestCells separately, rendering each into a different parent. Nothing about a single cell's own markup or styling had to change to support this — only where it gets mounted.

3Three architectures for the mobile table, in the order they were actually tried

The requirement was simple to state: on a phone, the table is wider than the screen, so it needs to scroll sideways — but the Domain Name column should stay visible the whole time, so you always know which row you're looking at while the rest of the data slides underneath it. Three real approaches were built, in this order.

Attempt 1: one scrolling grid with position: sticky on the Domain column

The obvious-sounding first approach: keep the desktop's single 5-column grid, wrap the whole row in a horizontally scrolling container, and make the Domain Name cell position: sticky; left: 0 so it stays pinned to the left edge while the rest of the row scrolls underneath it.

Why this was abandoned

A sticky element doesn't just stay in place, it stays on top — it occupies a real band of screen width for as long as it's stuck, and everything else in the scrolling row still has to pass underneath that band to reach the far edge. In practice that meant the Action column's Buy Now button and heart icon, way over on the right of the row, could only ever be scrolled behind the sticky Domain column, never past it and back into clear space on the other side — there is no "other side" once you're pinned to the left edge of the same scrolling viewport. No amount of extra scroll range fixes this, because the problem isn't how far you can scroll, it's that the sticky column and the content trying to reach past it are fighting over the same physical space the whole time.

This was tried first specifically because it reuses the existing single-grid row with the smallest amount of new code — worth knowing sticky's real failure mode before reaching for it on a similar problem in the future, rather than rediscovering it the hard way.

Attempt 2: extend the scroll range so the overlap clears

The next idea kept the sticky column but tried to compensate: add extra right-side padding and a wider min-width to the scrolling row, so there'd be enough empty scroll distance past the Action column for it to eventually clear the sticky column's overlay band entirely.

Why this was also rejected

This one actually got built and then explicitly reverted. It technically could work, but only by making the row artificially wider than its real content — scrolling "through" empty padding space just to get Buy Now out from behind the pinned column. That's a real UX cost (you have to scroll further than the actual data requires, and there's a stretch of blank space at the end) for a problem that's really about the sticky column overlapping content, not about there being too little scroll distance. This is the point where a step back to "is sticky even the right primitive here" happens, instead of continuing to patch around its failure mode.

A quieter option was floated here too: drop the Action column from the scrollable area on mobile entirely, so Buy Now/favorite simply aren't reachable by horizontal scroll at all. It was tried, worked exactly as described, and still didn't feel right once it was visible on a real device — a listings row you can't act on from the scrolled view is a real functional loss, not just a visual compromise.

Attempt 3 (final): two independent panes instead of one scrolling column

The idea that actually solved it: stop trying to make one scrolling area behave like it has a frozen column, and build two separate flex children side by side instead — a narrow pane that never scrolls, holding only Domain Name cells, and a second pane next to it that scrolls independently and holds everything else. There's no overlap because there's no shared coordinate space to overlap in — the fixed pane and the scrolling pane are just two ordinary siblings in a flex row.

LiveListingsTable.tsx
<div className={styles.mobileSplit}>
  <div className={styles.domainPane}>
    <div className={styles.domainPaneHeader}>Domain Name</div>
    {visible.map((listing) => <ListingDomainCell key={listing.id} listing={listing} />)}
  </div>

  <div className={styles.scrollPane}>
    <div className={styles.scrollPaneInner}>
      <div className={styles.restHeader}>Price / Appraised / Chain / Action</div>
      {visible.map((listing) => <ListingRestCells key={listing.id} listing={listing} ... />)}
    </div>
  </div>
</div>
LiveListingsTable.module.scss
.domainPane {
  flex-shrink: 0;
  width: 172px;
}

.scrollPane {
  flex: 1;
  min-width: 0; // lets the pane shrink below its content's natural width — see the gotcha below
  overflow-x: auto;
}

.scrollPaneInner {
  min-width: 581px; // $rest-width: Figma-exact width of Price+Appraised+Chain+Action
}

.domainPane is a fixed 172px and never scrolls — it's simply not wide enough to need to, since it holds nothing but domain names. .scrollPane is the flexible sibling that fills whatever width is left and scrolls its own contents (.scrollPaneInner, held to its real Figma-measured minimum width) independently. Scrolling one has zero effect on the other, because they don't share a scroll container at all.

min-width: 0, the one-line fix flexbox almost always needs

A flex item's default minimum width is its own content's natural width, not zero — so without min-width: 0 on .scrollPane, the flex item would refuse to shrink smaller than .scrollPaneInner's full 581px content, which defeats the entire point of giving it overflow-x: auto in a narrower space. This single-line fix comes up constantly any time a flex or grid child needs to scroll or truncate its own oversized content — it's worth remembering as a reflex, not re-discovering each time a flex child refuses to shrink.

Why two independently rendered structures, not one that reflows

Notice that LiveListingsTable.tsx renders both .scrollWrap (the desktop single grid) and .mobileSplit (the two-pane version) unconditionally, same as every other responsive component in this codebase — CSS shows exactly one via display: none at the matching breakpoint. This is why favoritedIds got explicitly lifted up to LiveListingsTable instead of staying as local state inside ListingRow: mobile renders a listing's favorite button somewhere entirely different in the tree from where desktop renders the same listing's favorite button, so if each kept its own local useState, toggling favorite on mobile would have zero effect on what desktop's copy of that same row shows, and vice versa. One Set<string> of favorited ids, owned by the table and passed down as props to whichever layout is currently visible, is what keeps them in agreement regardless of which one CSS is showing right now.

4Keeping two independently-laid-out panes in row alignment

Once domain names and their row's data live in genuinely separate DOM trees, a new problem appears that a single grid never had: nothing guarantees the two panes' rows are the same height, so a taller row on one side visually drifts out of alignment with its own data on the other side as you scroll down the list.

LiveListingsTable.module.scss
// Fixed (not min-) heights, shared by both panes' header and every row —
// a guessed min-height on the header pair didn't match the desktop
// .header span's inherited line-height, and any per-pane difference, even
// a couple of px, compounds down the list as every row after it inherits
// the offset.
$table-header-height: 32px;
$table-row-height: 56px;

.domainPaneHeader { height: $table-header-height; }
.domainPaneRow     { height: $table-row-height; }
.restHeader        { height: $table-header-height; }
.restRow           { height: $table-row-height; }
min-height is a suggestion, height is a guarantee

min-height only sets a floor — if either pane's content (say, a row whose price text wraps, or whose badge is taller than expected) needs more room than the floor, that row simply grows past it, and now the two panes' Nth rows are different heights again with no error, no warning, just a slow visual drift that gets worse the further down the list you scroll. Using an explicit height instead, shared by both panes through the same SCSS variable, removes the possibility entirely — every row in both panes is exactly the same height no matter what, because nothing is allowed to grow past it. (Content that doesn't fit gets centered and clipped rather than reflowing, which is an acceptable tradeoff for table cells holding short, predictable values like these.)

5Inside the Domain Name cell: two nested scroll problems, one real fix

A long domain name (the demo data includes one specifically for testing: thisisanextremelylongdomainnamefortestingpurposes.io) doesn't fit in a 172px pane. The requirement was specific: the long name should scroll horizontally inside its own cell, while the extension badge next to it (.io) stays fixed in place on the right, never scrolling out of view.

ListingRow.tsx
<div className={styles.domain}>
  <span className={styles.domainNameScroll}>
    <span className={styles.domainName}>{listing.domainName}</span>
  </span>
  <ExtensionBadge extension={listing.extension} />
</div>

Three nested layers, each with one job: .domain is the flex row holding the scrollable name and the fixed badge side by side. .domainNameScroll is the scroll viewport — it has a real, constrained width and overflow-x: auto. .domainName is the content inside it, which at mobile width is told to stop truncating and instead grow to its real full-text width, becoming wider than its own viewport and therefore scrollable.

ListingRow.module.scss
.domainNameScroll {
  @include mobile {
    display: block;
    flex: 1;
    overflow-x: auto;
    -webkit-overflow-scrolling: touch;
    touch-action: pan-x;
    scrollbar-width: none;
  }
}

.domainName {
  overflow: hidden; text-overflow: ellipsis; white-space: nowrap; // desktop: truncates

  @include mobile {
    width: max-content; // mobile: grows past its own box instead
    overflow: visible;
    text-overflow: clip;
  }
}

The first version of this fix added touch-action and -webkit-overflow-scrolling: touch and looked correct in the code — it compiled, the rule was there — and still didn't actually scroll on a real device. Two more rounds of guessing (different touch properties, explicit display: block) didn't fix it either. The real cause turned out to live one level up, outside this file entirely.

The actual root cause: a sibling's align-items, not a missing touch property

.cell, the ancestor one level above .domain, sets align-items: flex-start. Flex items with align-items: flex-start size themselves to their own content along the cross axis by default, rather than stretching to fill their container. Since .domain never got an explicit width of its own, it was sizing itself to whatever content it held — which meant it simply grew to fit the entire long domain name, and its flex sibling .domainNameScroll (given flex: 1) had no actual constrained space to be squeezed into, so there was nothing for it to overflow against. No real width constraint means no real overflow, means overflow-x: auto has nothing to do, means no scrollbar, no scroll gesture, no matter how many touch-specific properties get added.

The one-line fix was .domain { @include mobile { width: 100%; } } — forcing .domain itself to actually fill its parent's width, which finally gives .domainNameScroll's flex: 1 a real, smaller-than-content space to be constrained into. Once that width is real, everything downstream (the overflow, the touch scrolling, the badge staying put) started working with no other changes.

This was confirmed with actual before/after screenshots taken through a headless browser, not just re-reading the CSS and reasoning about it — after two guess-based attempts had already failed silently (no compile error, no visible breakage in a static screenshot, just "doesn't scroll" only discoverable by actually trying to drag it), verifying against a real rendered page was what found the sibling's align-items as the actual cause instead of a fourth guess.

The general lesson

When a CSS fix "should" work by every reading of the rule you changed, and it still doesn't behave correctly, the bug is very often one level up the tree — in a container property (align-items, min-width, overflow) that's silently constraining or unconstraining the element you're actually trying to fix, rather than in the rule you keep re-editing.

6ListingsHeading: a component that was planned for and never built

Above the search/filter row, every breakpoint of the reference design shows a small heading: "Live Listings" next to a live count of how many domains are showing. For a while, this codebase's implementation simply didn't have it — not a bug exactly, more a step that got skipped. The evidence it was always meant to exist was sitting in the data file the whole time:

data/marketplace/domains.ts
export const MOCK_LISTINGS_TOTAL = mockListings.length // 28, matches "28 domains" in the reference design

That export existed, with a comment explaining exactly what it was for, and nothing in the entire app ever imported it. That's a useful thing to be able to notice while reading a codebase: an exported constant with a comment referencing a specific piece of UI ("matches X in the reference design") that no component actually uses is a strong signal that a piece of the design was planned for but the component that was supposed to read it never got built. The fix was small — a new, single-purpose component:

ListingsHeading/ListingsHeading.tsx
export interface ListingsHeadingProps {
  count: number
}

export const ListingsHeading = ({ count }: ListingsHeadingProps) => (
  <div className={styles.row}>
    <span className={styles.title}>Live Listings</span>
    <span className={styles.count}>{count} domains</span>
  </div>
)

Two small decisions here are worth pulling out, because they're the kind of small decisions that come up in every component you'll ever add to an existing app. First: where does this new piece live in the file tree? It's not part of ListingFilterBar even though it sits directly above that component's own search row in the final layout, because it isn't really about filtering — it's its own small fact about the page (how many listings exist right now), so it gets its own folder, listings/ListingsHeading/, following the exact one-component-one-job convention every other composite in this codebase follows. Second: where does the count number actually come from? Not the unused MOCK_LISTINGS_TOTAL constant — that number never changes no matter what you search or filter for, which would make the heading quietly wrong the moment a filter actually narrows the list. Instead it's wired to filtered.length, the same already-filtered array the table itself renders:

pages/design-preview/marketplace.tsx
const filtered = filterListings(mockListings, debouncedSearch, filters)

<ListingCategoryTabs ... />
<ListingsHeading count={filtered.length} />
<ListingFilterBar ... />
<LiveListingsTable listings={filtered} pageSize={14} />

ListingsHeading, LiveListingsTable, and the filtered count all read from the exact same filtered array computed once at the top of the page — so the heading's number and the table's actual contents can never disagree with each other, and it happens to equal the unused MOCK_LISTINGS_TOTAL constant's value only when no filter is narrowing the results, which is a consequence of reading real data rather than something that had to be kept in sync by hand.

7What to remember from this phase

  • position: sticky occupies real screen space for as long as it's stuck — anything that needs to scroll past it has to pass behind it first, which fails badly for interactive content (buttons) at the far end of a scrolling row.
  • When a sticky/pinned element and the content trying to scroll past it are fundamentally fighting over the same space, the fix is usually architectural (two independent panes) rather than a CSS tweak (more padding, more scroll range).
  • Split a "reused everywhere" row component into named sub-pieces (ListingDomainCell / ListingRestCells) when different layouts need to mount the same cells in different places in the tree.
  • State that two independently-rendered layouts both need to agree on (favorited, selected, etc.) has to be lifted to their common parent — local state inside a component that gets mounted twice in two different places will desync.
  • Use explicit, shared height values (not min-height) to keep two separately-laid-out structures' rows aligned — a floor doesn't stop drift, a fixed value does.
  • min-width: 0 is the single most common missing line when a flex or grid child refuses to shrink or scroll below its content's natural size.
  • When a CSS rule looks correct and still doesn't behave right, check the parent's align-items/min-width/overflow before adding more properties to the rule you're already looking at — and verify against a real rendered page once guessing twice hasn't worked.
  • An exported constant with a comment pointing at a specific piece of UI that nothing actually imports is a signal that a planned piece of the design never got wired up — worth noticing while reading a codebase, not just while writing one.
  • Derive a displayed count from the same data the rest of the UI is already rendering (filtered.length), not from a separate constant — two numbers computed from the same source can never quietly disagree.
