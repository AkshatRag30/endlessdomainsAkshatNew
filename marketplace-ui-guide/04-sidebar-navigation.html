Phase 04 · Structure

Sidebar, mobile drawer, and bottom nav

Three different navigation surfaces — a persistent desktop sidebar, a rich off-canvas mobile drawer, and a fixed mobile tab bar — and why they're three separate components instead of one component reflowing.

1Desktop sidebar: avoiding a false-active bug

MarketplaceSidebar renders two SidebarSections (Browse, Your Account), each a list of SidebarNavItems. The interesting part isn't the rendering, it's how "is this link currently active" gets decided.

SidebarSection.tsx
const { pathname } = useRouter()
return (
  ...
  {section.items.map((item) => (
    <SidebarNavItem key={item.id} item={item}
      active={!item.isPlaceholder && pathname === item.href} />
  ))}
)
The bug this line avoids

Most sidebar items don't have a real page to link to yet, so they all point at the same placeholder href, /. A naive active={pathname === item.href} check would compare every item's href against the current path — and since several share the exact same placeholder href, several would light up as "active" simultaneously the moment you're on the homepage. The fix is the !item.isPlaceholder && guard: an item can only ever be marked active if it has a real, unique destination. This is why the mock navigation data (phase 08) carries an explicit isPlaceholder flag on every item — it's not decorative, it's what this check depends on.

2Two components for one visual slot: render both, let CSS decide

The mobile drawer's content, once you open it, doesn't look like a smaller version of the desktop sidebar — it's a genuinely different layout with a search field, a Navigation section that mirrors the header's own links, and a highlighted Explore row that the desktop sidebar doesn't have at all. Rather than one component branching internally on screen size, this project builds it as two separate components, both always rendered, with CSS showing exactly one at a time.

MarketplaceSidebar.module.scss
.sidebar {
  // the desktop sidebar's own styles, unconditional
  @include tablet-down { display: none; }
}
MobileDrawerMenu.module.scss
.drawer {
  display: none;
  @include tablet-down { display: flex; flex-direction: column; }
}

Both get passed into the same sidebar slot on MarketplacePageShell as siblings:

pages/design-preview/marketplace.tsx
sidebar={
  <>
    <MarketplaceSidebar />
    <MobileDrawerMenu onClose={() => setMenuOpen(false)} />
  </>
}
Why not one component with an if/else on screen width

Checking window.innerWidth in JavaScript and branching what to render requires a useEffect, only knows the true width after the component has already mounted once (causing a visible flash on first paint), and re-renders on every resize event. A pure CSS media query has none of those costs — the browser decides which block is visible before anything paints, and resizing the window just repaints, no JavaScript involved. This exact "render both, CSS decides" shape reappears in phase 07 for an even more dramatic case — two completely different chart layouts for the same data.

Reusing the header's own navigation data

The drawer's Navigation section isn't a second copy of the header's Marketplace/Portfolio/Sell/Resources links — it imports the exact same data and the exact same active-check the header uses:

MobileDrawerMenu.tsx
import { HEADER_NAV_ITEMS } from '@/design-system/layouts/header/menuItems'

{HEADER_NAV_ITEMS.map((item) => {
  const isActive = pathname === item.href && item.label === 'Marketplace'
  return <Link href={item.href} className={isActive ? styles.navLinkActive : ''}>{item.label}</Link>
})}

If a new nav item is ever added to the real header, the drawer picks it up automatically — there is no second list to remember to update.

A decoration that follows selection, not stuck to one item

The Explore row in the drawer has a distinctive highlighted background and a decorative flourish graphic. An earlier version of this component hardcoded that decoration onto Explore specifically. When the drawer later needed a "which item did you just tap" indicator for design review, the fix wasn't to add a second, different highlight — it was to realize the Explore decoration was already exactly that indicator, just wired to the wrong thing.

MobileDrawerMenu.tsx
{browseSection.items.map((item) => {
  const isSelected = previewMode && previewSelectedBrowseId === item.id
  return (
    <Link key={item.id} className={`${styles.browseRow} ${isSelected ? styles.browseRowSelected : ''}`}>
      ...
      {isSelected && <...decorative flourish images...>}
    </Link>
  )
})}

Every row in the Browse list, including Explore, is now rendered from the exact same map over the exact same array — whichever one's id matches the currently-selected id gets the highlight and flourish, and it starts on Explore only because that's the initial state value, not because Explore is special-cased in the markup anymore.

3previewMode: a temporary, clearly-scoped escape hatch

Every link in this preview page would, in a real logged-out session, either navigate away from the page entirely or redirect to a login screen for anything behind auth — both of which make it impossible to actually look at the design you're reviewing. The fix is a prop, explicitly documented as temporary:

MobileDrawerMenu.tsx
// TEMPORARY, preview-only — nav links mark themselves selected instead of
// navigating. Only ever passed from the preview page. Remove once real
// destinations exist.
previewMode?: boolean

<Link href={item.href}
  onClick={previewMode ? (e) => { e.preventDefault(); setPreviewSelectedId(item.id) } : onClose}
>

e.preventDefault() stops the browser's default behavior for a link click (actually navigating), and the click instead just updates local state that drives which row looks "active." Every component across this whole page that got this treatment — Header, MarketplaceSidebar, MobileDrawerMenu — takes the same optional, default-off prop, for the same reason section 3 of phase 03 explained: a shared component gets new behavior through a prop that defaults to not changing anything for callers that don't pass it.

4The bottom nav: a genuinely new component, and why it was removed then rebuilt

MobileBottomNav is a fixed tab bar pinned to the bottom of the viewport — a real addition to the design, not a responsive reflow of anything that exists on desktop. It teaches a small but important lesson about fixed-position UI and page layout.

MobileBottomNav.module.scss
.nav {
  @include mobile {
    display: flex;
    position: fixed;
    left: 0; right: 0; bottom: 0;
    padding: var(--space-3) var(--space-3) calc(var(--space-3) + env(safe-area-inset-bottom, 0px));
  }
}
Fixed elements don't reserve their own space

position: fixed takes an element completely out of the page's normal document flow — the rest of the page has no idea it's there and will happily render content underneath it. The fix lives one file away, on the page shell itself:

MarketplacePageShell.module.scss
.shell {
  @include mobile { padding-bottom: 76px; } // clears the fixed nav's own height
}

76px of bottom padding on the page's own outer wrapper leaves exactly enough empty space at the end of the page for the fixed bar to sit over without covering real content. Any time you add a position: fixed element pinned to an edge of the screen, this is the matching move: pad the scrollable content by that element's own size, on the same edge.

env(safe-area-inset-bottom, 0px) in the padding above is worth knowing too — it's a CSS environment variable that iPhones with a home-indicator bar (no physical home button) expose automatically, so the nav's padding grows slightly on those devices to clear the indicator, and is simply 0px (the fallback) everywhere else.

5SidebarPromoCard: a real design shape from raw CSS, and hiding on a real condition

The "What Is Your Name Worth?" card's notched blue background is built the same way as phase 02's buttons — clip-path: polygon(...) — just with different corner coordinates and a gradient fill instead of a flat color, matched to a decorative CSS glow behind it using layered box-shadow-like radial gradients.

How clip-path: polygon() actually draws that shape, point by point

clip-path doesn't change an element's size or background — it takes an element that's already a normal rectangle and hides everything outside a shape you describe, as if you cut the rectangle out with scissors along a line you drew. polygon(...) is one way to describe that line: a list of x y coordinate pairs, each one a point, connected in order, one straight edge at a time, until the last point connects back to the first to close the shape.

SidebarPromoCard.module.scss
$notch: polygon(
  20px 0,                    // 1. top edge, 20px in from the left
  calc(100% - 20px) 0,      // 2. top edge, 20px in from the right
  100% 20px,                  // 3. right edge, 20px down — these two points cut the top-right corner
  100% calc(100% - 21px),      // 4. right edge, 21px up from the bottom
  calc(100% - 21px) 100%,      // 5. bottom edge, 21px in from the right — cuts the bottom-right corner
  0 100%,                    // 6. straight to the real bottom-left corner — no cut here
  0 21px                     // 7. left edge, 21px up from the bottom — back toward point 1
);

Each coordinate is measured from the shape's own top-left corner: the first number is how far across (x), the second is how far down (y) — so 0 0 would be the exact top-left corner, and 100% 100% the exact bottom-right one. Walk the seven points above in order and you're tracing the card's outline clockwise: start a little in from the top-left corner, run right along the top, cut diagonally down-and-right to skip the top-right corner entirely, run down the right edge, cut diagonally again to skip the bottom-right corner, then — this is the one corner that's different — go straight to the actual bottom-left corner (point 6, 0 100%) instead of cutting it, then straight back up to where the pattern started.

Why one corner needed a fix: two points make a cut, one point makes a real corner

The shape originally chamfered all four corners — the bottom-left one was cut using the same two-point technique as the other three, a point on the bottom edge (21px 100%) followed by a point on the left edge (0 calc(100% - 21px)), with a diagonal line connecting them exactly like the top-right and bottom-right cuts. Cutting a corner is always two points that each sit a little short of the real corner, one on each of the two edges that meet there — remove those two points and put a single point at the real corner coordinates instead (0 100%, the literal bottom-left of the box), and that corner stops being cut and becomes a sharp, real 90° vertex, while the other three corners keep their chamfer untouched since their own point pairs weren't touched at all.

This is really the entire trick behind every chamfered shape in this codebase — phase 02's button corners, this card's notch — a small, fixed number of pixels shaved off however many corners the design calls for, described as pairs of points instead of a single sharp one. Wanting a specific corner to stay sharp is just wanting fewer pairs: collapse that corner's two points back into the one real coordinate it was always approximating.

Its "connect wallet" button is real, and real means it has to respect real auth state, not just the visual review mode above:

SidebarPromoCard.tsx
const { authenticated } = useAuth()
if (authenticated) return null
Why hide the whole card, not just the button

The header's own connect-wallet button already hides itself once a user is signed in, showing a profile menu instead. This card's CTA is the exact same action pointed at the exact same destination — leaving the card visible with nothing useful for it to do would be a dead end for a signed-in visitor. Reusing the same useAuth() hook the header already relies on, rather than inventing a second way to check auth state, is what keeps this consistent if the real auth logic ever changes.

6What to remember from this phase

  • Guard "is this active" checks against placeholder/shared data, not just a raw equality check, or several items can light up at once.
  • When a mobile layout is genuinely different, not just resized, build it as a separate component and let CSS choose between the two, rather than branching one component on window width.
  • A decoration meant to indicate "selected" should be driven by the same state/id comparison for every item, not hardcoded onto whichever item happened to be selected in the reference design.
  • A position: fixed element needs the rest of the page padded to match its size on the edge it's pinned to, or it covers real content.
  • In a clip-path: polygon() shape, a chamfered corner is always two points, one just short of the real corner on each edge that meets there — collapse them into the single real coordinate to make that specific corner sharp again, without touching any other corner's own points.
  • Hide UI based on the real condition it depends on (auth state), separately from any temporary review-only behavior layered on top of it.
