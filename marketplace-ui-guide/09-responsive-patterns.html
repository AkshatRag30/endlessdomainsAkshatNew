Phase 09 · Systems

The responsive system, seen all at once

Every earlier phase used pieces of this system without stopping to look at the whole thing. This phase is the recap — the breakpoint scale, the one recurring layout pattern that shows up in six different components, and a catalog of the real bugs that came from getting it wrong, gathered in one place instead of scattered across six files.

1The four-tier breakpoint scale

MixinRangeUsed for
small-mobile≤ 499pxRare — a handful of extra-narrow-phone adjustments
mobile≤ 767pxPhone-width layout switches (drawer nav, split-pane table, bottom nav)
tablet768px–1024pxThe iPad-Pro-portrait band specifically — the expanded Market Activity chart, sidebar rail row layout
tablet-down≤ 1024px"Anything narrower than desktop" — mobile drawer, hidden desktop sidebar, MarketActivityPanel's expanded layout
desktop≥ 1025pxImplicit default — most component base styles, no media query needed

Two mixins are worth calling out because they're easy to reach for interchangeably and mean different things: tablet alone is a narrow band (768–1024px only), while tablet-down is everything at or below that band's top edge, phone widths included. Anywhere a mobile layout and a tablet layout happen to share the same treatment (the drawer menu, the hidden desktop sidebar), the code reaches for tablet-down once instead of duplicating the same rule under both mobile and tablet. Anywhere tablet needs something phones specifically shouldn't get (the expanded chart layout, before the later mockup made it apply at mobile too), it's tablet alone.

The 992–1024px dead zone

Phase 01 covered this in passing; it belongs here too, because it's the canonical example of what happens when a breakpoint scale has a gap. $breakpoint-tablet used to be 992px while $breakpoint-desktop was 1025px — leaving 992–1024px covered by neither tablet-down nor desktop. A real iPad Pro (834px portrait, 1024px landscape) landed exactly in that gap and silently got the unmodified desktop layout, no error, just the wrong design. The fix was making $breakpoint-tablet and $breakpoint-desktop equal (1025px), so every pixel width is covered by exactly one of the two mixins with nothing left in between. Any time you introduce a new breakpoint variable, check that its range is contiguous with its neighbors — a gap doesn't throw an error, it just quietly falls through to whatever rule happens to apply by default.

2The one pattern that appears six times: render both, let CSS decide

By now you've seen this shape enough times to recognize it as one idea wearing different clothes. Every time a section of the UI looks genuinely different between breakpoints (not just resized, but different elements entirely), the solution in this codebase is the same: render every version unconditionally, and let a CSS media query show exactly one.

WhereVersion AVersion B

Why this pattern won over a JavaScript width check, every single time

A useEffect that reads window.innerWidth only knows the real width after the component has already mounted once — so the very first paint either guesses wrong or renders nothing until that effect runs, which is a visible flash or a layout jump depending on which way the guess is wrong. It also means every resize event re-triggers a React re-render just to flip a boolean. A CSS media query has neither cost: the browser resolves which rule applies before anything paints, and resizing the browser window is purely the browser's own paint pipeline, no JavaScript involved, no flash, no re-render. The one price paid for this is that both versions exist in the DOM at once — acceptable for the small, mostly-static components on this page; worth reconsidering only if a hidden variant were doing something expensive (a live data subscription, a heavy chart library) that shouldn't run at all while invisible.

The one time this pattern actually broke: cascade order

Phase 07's .cardsOnly/.expanded bug is the pattern's one real failure mode: when the "show" and "hide" rules have equal CSS specificity, whichever is declared later in the file wins, regardless of which one looks like it should be conditional. The fix isn't specific to that component — any time you add a new toggle rule to a stylesheet that already has an unconditional rule for the same class, declare the toggle after it, or reach for a higher-specificity/more explicit selector so source order can't decide the outcome by accident.

3previewMode: one prop pattern, four components, a hard scope boundary

Phase 04 introduced this in the sidebar; it's worth seeing as a system rather than a one-off. Header, MarketplaceSidebar/SidebarSection/SidebarNavItem, and MobileDrawerMenu all take the same optional prop, default undefined/falsy, that changes exactly one thing: a link click calls e.preventDefault() and updates local "selected" state instead of actually navigating.

Why this is safe to leave in a shared component instead of a real risk

Three things keep this from leaking into the real app. First, it's opt-in with a falsy default — every caller that doesn't explicitly pass previewMode gets completely unmodified, real-navigation behavior, which is every page except this one preview page. Second, only pages/design-preview/marketplace.tsx — an unlinked route nothing else routes to — actually passes it. Third, every place it's added carries a comment marking it temporary and explaining what it's standing in for, so it reads as a deliberate, findable exception rather than something that could be mistaken for permanent behavior later. This is the general shape worth remembering: a temporary behavior change to a shared component should be an explicit, defaulted-off prop with a comment explaining why, not a global flag, an environment check, or a silent behavior change with no trace of why it's there.

4Touch and scroll: the gotchas that only show up on a real device

Three separate scroll-related bugs across phases 06 and 07 share a common thread: none of them were visible in a static screenshot or caught by a type checker, and two of the three survived a first "fix" that looked correct in the source code.

SymptomReal causeWhere

The practical takeaway isn't a specific property to memorize, it's a debugging order of operations: if a scroll/overflow rule looks right in the CSS and still doesn't behave right in the browser, check the element's own real, computed width/height before adding more scroll-specific properties to it. overflow-x: auto and touch-action: pan-x can't do anything for an element that never actually became narrower than its content in the first place — and no amount of touch-specific CSS fixes a width problem.

5What to remember from this phase

  • Keep a breakpoint scale contiguous — verify each mixin's range starts exactly where the previous one ends, or a width in the gap silently gets the wrong layout with no error.
  • "Render both, CSS decides" beats a JavaScript width check for anything structural — no first-paint flash, no resize-triggered re-render — but a toggle pair added to an existing stylesheet needs to be declared after any unconditional rule for the same class, or cascade order picks the wrong winner.
  • A temporary behavior change to a shared component should be an explicit, default-off prop with a comment, scoped to exactly the one place that opts in — not a global flag or a silent special case.
  • When a scroll or overflow rule looks correct and still doesn't work, check the element's actual computed width/height in the browser before adding more properties to the rule.
