How the Profile page gets its data

A friendly, step by step walk through the mock data, the services, the api folder, the hooks, and how they all link up to the components on /profile. No prior knowledge of the code needed. Every example is copied from the real files on the profile-settings branch.

Why any of this exists

The Figma design for the Profile page shows a lot of information: a username, a bio, active sessions, five notification switches, display preferences, account stats, and more. When the page was built, the backend only had endpoints for a small part of that: reading the profile, saving the name, email, phone and Telegram, changing the password and resending the verification email.

So there were two choices. We could wait for the backend, or build the whole page now with pretend data (called mock data) and plug in the real data later. You chose the second, with one important condition: the pretend data must be easy to remove and replace.

Everything in this guide is the answer to that condition. The idea is simple: the screens never know whether the data is real or pretend. They ask for data through one door, and behind that door a single settings file decides where the data really comes from.

The big picture

Think of the page like a restaurant.

Component (the customer)The thing you see on screen: a card, a switch, a form. It just wants food (data) and doesn't care how it's cooked.
Hook (the waiter)Takes the order from the component, brings back the food, and says "still cooking" (loading) or "sorry, we're out" (error).
Service contract (the menu)A fixed list of what you can order for each area, like "get notification settings" or "change password".
Mock and API (two kitchens)The mock kitchen cooks with pretend ingredients. The API kitchen uses the real backend. Both cook exactly the dishes on the menu.
config.ts (the manager)Decides, for each area, which kitchen cooks. Changing one word moves an area from the pretend kitchen to the real one.
Types (the recipe card)Describes exactly what each dish looks like, so both kitchens serve the same plate.

Here is the same thing as layers, top to bottom. Data requests go down, data comes back up.

Componentscomposites/profile/…
Cards, forms and tab panels. They call hooks and draw what they get back.
↓ call a hook, like useNotificationSettings()
Hookssrc/hooks/profile/
Handle loading, errors, caching and saving. They only talk to profileServices.
↓ call profileServices.notifications.get()
Service registrysrc/services/profile/index.ts
Looks at config.ts and hands over either the mock or the api version of each area.
↓ one or the other, per area
Mockservices/profile/mock/
Pretend data from the Figma frames, a short fake delay, saved in the browser.
APIservices/profile/api/
Calls the real backend through the existing RTK Query endpoints, then reshapes the answer.

The one sentence to rememberComponents → hooks → profileServices → mock or api, chosen per area in config.ts.

The steps below follow the order they were built in, from the bottom of the diagram up to the screen.

1Decide what the data looks like (types)

Before writing any data, I wrote down the shape the page needs, by reading the Figma frames field by field. This is the "recipe card". It lives in src/types/profile-settings/index.ts.

src/types/profile-settings/index.ts

export interface NotificationSettings {
  watchedDomainSold: boolean
  watchlistPriceDrop: boolean
  listingSold: boolean
  expiringSoon: boolean
  productNews: boolean
  channels: { email: boolean; telegram: boolean }
}

// The eight areas of the page
export type ProfileArea = 'details' | 'summary' | 'security' | 'sessions'
  | 'wallets' | 'notifications' | 'preferences' | 'account'

Why start here? Because both kitchens (mock and api) must serve exactly this shape. The backend might send something different (for example one phone string like "+911111111111"), but the page always gets the tidy version ({ countryCode: 'IN', number: '1111111111' }). The api folder does that tidying in step 4.

Small detailThe folder is called profile-settings and not profile because a file src/types/Profile.ts already exists, and Windows treats profile and Profile as the same name.

2Write the contract for each area (the menu)

Next, for each area, I listed what the page can ask for. This is an interface in src/services/profile/types.ts. It doesn't contain any data or logic. It's only a promise: "whoever cooks for this area will provide these functions".

src/services/profile/types.ts

export interface NotificationsService {
  get(): Promise<NotificationSettings>
  update(patch: Partial<NotificationSettings>): Promise<NotificationSettings>
}

export interface WalletsService {
  list(): Promise<ConnectedWallet[]>
  disconnect(walletId: string): Promise<void>
  setPrimary(walletId: string): Promise<void>
  getSettings(): Promise<WalletSettings>
  updateSettings(patch: Partial<WalletSettings>): Promise<WalletSettings>
}

// All eight together
export interface ProfileServices {
  details: ProfileDetailsService
  summary: AccountSummaryService
  security: SecurityService
  sessions: SessionsService
  wallets: WalletsService
  notifications: NotificationsService
  preferences: PreferencesService
  account: AccountService
}

Three things to notice:

  • Every function returns a Promise, even in the mock. Real network calls take time, so the pretend version behaves the same way. That means nothing has to change when we switch to real data.
  • Partial<…> means "some of these fields". So update({ productNews: false }) changes only that one switch.
  • The same file defines ProfileServiceError, the one error type both kitchens throw. Because every error looks the same, every card can show errors the same way.
export class ProfileServiceError extends Error {
  constructor(message: string, public readonly status?: number) {
    super(message)
    this.name = 'ProfileServiceError'
  }
}

3Build the mock data (the pretend kitchen)

The mock folder has three files, each with one job.

3a. fixtures.ts: the pretend values

I copied the sample values shown in the Figma frames (John Doe, johndoe, Bangalore, 28 domains, and so on) and typed them with the step 1 types. If I made a typo in a field name, TypeScript would complain straight away.

3b. runtime.ts: make it feel like a real server

A pretend kitchen that answers instantly would hide bugs, because a real server takes time and remembers what you saved. So this file adds two behaviours:

  • A fake delay of 300ms, so loading skeletons actually appear and get tested.
  • Memory across reloads, using the browser's localStorage under keys like mock:profile:notifications. If you turn a switch off and reload, it stays off, just like it would with a real server.

src/services/profile/mock/runtime.ts

const MOCK_DELAY_MS = 300

// Wait 300ms, then give back the value (like a network round trip)
export const mockDelay = <T>(value: T, ms = MOCK_DELAY_MS): Promise<T> =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms))

// Read saved pretend data, or fall back to the fixture
export function readMock<T>(area: string, fallback: T): T {
  try {
    const raw = localStorage.getItem(`mock:profile:${area}`)
    return raw ? { ...fallback, ...JSON.parse(raw) } : fallback
  } catch {
    return fallback   // storage blocked (private mode): just use the fixture
  }
}

// Save pretend data so it survives a reload
export function writeMock<T>(area: string, value: T): T { … }

TipTo reset all the pretend data, open the browser DevTools → Application → Local Storage, and delete the keys that start with mock:profile:.

3c. mock/index.ts: the pretend kitchen itself

This file follows the contract from step 2 for all eight areas, using the fixtures and the runtime helpers. Because it's typed as ProfileServices, TypeScript refuses to compile if any function on the menu is missing.

src/services/profile/mock/index.ts

export const mockServices: ProfileServices = {
  notifications: {
    get: () => mockDelay(readMock('notifications', mockNotificationSettings)),
    update: (patch) =>
      mockDelay(writeMock('notifications', {
        ...readMock('notifications', mockNotificationSettings),
        ...patch,                       // only the changed switches
      })),
  },

  wallets: {
    disconnect: async (walletId) => {
      const wallets = readMockList('wallets', mockWallets)
      // Behaves like a real server rule: you can't remove your last wallet
      if (wallets.length <= 1) throw new ProfileServiceError('You need at least one connected wallet.', 400)
      writeMock('wallets', wallets.filter((w) => w.id !== walletId))
      return mockDelay(undefined)
    },
    …
  },
  …
}

I also made the mock act like the real backend in a few places, so the error states could be tried without a backend:

  • Typing wrong-password as the current password gives "Your current password is incorrect."
  • Changing the email turns isEmailVerified off, because a new address needs verifying again.
  • Deleting the account only works if you type the right username.
  • You can't disconnect the last wallet.

4Build the real API side (the real kitchen)

The api folder follows the same contract, but gets its data from the real backend. It doesn't call the server in a new way: it reuses the RTK Query endpoints the app already has in src/core/redux/userProfile.ts. I only added two small endpoints there that were missing: resendVerificationEmail and changePassword.

4a. Calling the existing RTK Query endpoints from outside React

RTK Query endpoints are usually used inside components as hooks. The service layer isn't a component, so it dispatches the endpoint on the app's store directly. It still goes through the same cache as the rest of the app.

src/services/profile/api/index.ts

async function fetchProfile(forceRefetch = false) {
  const request = store.dispatch(
    ProfileApi.endpoints.getUserProfile.initiate(undefined, { forceRefetch })
  )
  try {
    const response = await request.unwrap()   // wait for the answer
    return response.result                      // the backend User object
  } catch (error) {
    throw toServiceError(error, 'Could not load your profile.')
  } finally {
    request.unsubscribe()                       // tidy up
  }
}

4b. Reshaping backend data: mapUser.ts

The backend's User doesn't look like our page's types. For example, it stores the phone as one string and has no username yet. mapUser.ts converts it into the step 1 shape. Fields the backend doesn't have yet come back empty.

src/services/profile/api/mapUser.ts

export function mapUserToDetails(user: User): ProfileDetails {
  return {
    fullName: user.name ?? '',
    username: '',                       // backend doesn't have it yet
    email: user.email,
    isEmailVerified: user.isEmailVerified,
    // "+911111111111"  →  { countryCode: 'IN', number: '1111111111' }
    phone: user.phoneNumber ? parsePhoneString(user.phoneNumber, COUNTRIES, DEFAULT_COUNTRY_CODE) : null,
    telegram: user.telegram ?? '',
    bio: '', location: '', website: '', avatarUrl: null,
  }
}

4c. Friendly errors: toServiceError

The server sometimes answers with technical words like "Unauthorized". This function turns them into sentences a person understands, wrapped in the same ProfileServiceError the mock uses.

Server saysPerson sees
401 UnauthorizedYour session has expired. Sign in again to continue.
500 and aboveThe server didn't respond. Please try again in a moment.
No connection (FETCH_ERROR)You seem to be offline. Check your connection and try again.
401 on change passwordYour current password is incorrect.

4d. Only the areas that really exist

The api folder only implements the three areas the backend can support today. Where an endpoint is missing, it says so honestly instead of pretending.

export const apiServices = {
  details,     // GET profile, save name/email/phone/telegram, resend verification
  security,    // sign in methods from GET, change password
  wallets,     // list from GET; disconnect etc. say "not available yet"
} satisfies Partial<ProfileServices>

5The switch and the front door

5a. config.ts: one line per area

This is the only file you edit to move an area from pretend to real data.

src/services/profile/config.ts

export const PROFILE_SOURCES: ProfileSourceConfig = {
  details: 'mock',        // waits for backend item 1 (username, bio, …)
  summary: 'mock',        // item 2
  security: 'mock',       // item 3
  sessions: 'mock',       // item 4
  wallets: 'mock',        // item 5
  notifications: 'mock',  // item 6
  preferences: 'mock',    // item 7
  account: 'mock',        // item 8
}

Built in safetyThe type ProfileSourceConfig only allows 'api' for areas that api/index.ts actually implements. If you write notifications: 'api' today, the editor shows a red error, because there's no real notifications code yet. You can't accidentally point the page at something that doesn't exist.

How that trick works, in plain words: keyof typeof apiServices means "the names of the areas in the api folder" (details, security, wallets). The config type says "an area may be 'api' only if its name is in that list".

type ApiReady = keyof typeof apiServices            // 'details' | 'security' | 'wallets'
export type ProfileSource<A extends ProfileArea> =
  'mock' | (A extends ApiReady ? 'api' : never)     // 'api' only when ready

5b. services/profile/index.ts: the front door

This file reads the config and builds one object, profileServices, picking the mock or api version of each area. This is the only thing the rest of the app imports.

src/services/profile/index.ts

function pick<A extends ProfileArea>(area: A): ProfileServices[A] {
  if (PROFILE_SOURCES[area] === 'api') return apiServices[area]
  return mockServices[area]
}

export const profileServices: ProfileServices = {
  details: pick('details'),
  summary: pick('summary'),
  …
  account: pick('account'),
}

// True while an area is still pretend; shows the "Sample data" chip
export const isMockArea = (area: ProfileArea) => PROFILE_SOURCES[area] === 'mock'

6The hooks (the waiters)

Components could call profileServices directly, but then every component would have to handle loading, errors, saving and caching itself. Hooks do that once, for everyone.

6a. useProfileResource: the shared loader

One general hook that knows how to load anything. You give it a name (the cache key) and a function that loads the data. It gives back everything a screen needs.

src/hooks/profile/useProfileResource.ts

const resource = useProfileResource('notifications', () => profileServices.notifications.get())

resource.data       // the settings, or undefined while loading
resource.isLoading  // true the first time → show a skeleton
resource.isError    // true if it failed → show an error banner
resource.error      // the friendly message
resource.reload()   // the Retry button calls this
resource.replace(x) // put new data in after a save

Two extra things happen inside it:

  • A cache. Loaded data is kept in memory under its key. When you switch from Notifications to Security and back, the data is shown immediately instead of loading again.
  • Listeners. If two parts of the page use the same key, they stay in sync. Example: the Wallets tab badge (the "3" on the tab) and the wallet list both use 'wallets'. Disconnect a wallet and the badge updates to 2 by itself.

Next to it, useProfileAction wraps a save so the screen knows when it's busy (to show "Saving…" or disable a button).

const { run: save, isSaving } = useProfileAction(async (patch) => { … })

6b. One hook per area: hooks/profile/index.ts

Each area gets a small, easy to read hook built from the two pieces above. Components use these, never the services.

src/hooks/profile/index.ts

export function useNotificationSettings() {
  // 1. load the data
  const resource = useProfileResource('notifications', () => profileServices.notifications.get())

  // 2. a way to save changes
  const { run: update, isSaving } = useProfileAction(async (patch) => {
    const next = await profileServices.notifications.update(patch)
    resource.replace(next)          // keep the cache up to date
    return next
  })

  // 3. hand it all to the component, plus "is this pretend?"
  return { ...resource, update, isSaving, isSample: isMockArea('notifications') }
}

The full list: useProfileDetails, useResendVerification, useAccountSummary, useSignInMethods, useChangePassword, useActiveSessions, useConnectedWallets, useWalletSettings, useNotificationSettings, useProfilePreferences, useYourData, useWalletCount.

6c. useProfileDraft: the Profile form's edits

The Profile form is special: you type in several fields, then press Save. This hook keeps a draft (your unsaved copy) next to the saved version from useProfileDetails.

  • It compares draft and saved to know if anything changed (isDirty), which enables the Save button and powers the "Discard unsaved changes?" prompt.
  • It checks each field with the rules in src/helpers/profileValidation.ts, showing errors when you leave a field or press Save.
  • On Save it sends only the changed fields through useProfileDetails().save, so through the same service layer as everything else.

7The components (the customers)

Each tab has a "panel" component that uses the hooks and decides what to draw. Here's the Notifications tab, simplified. It shows the three states every card has: loading, error, and ready.

composites/profile/notifications/NotificationsTabPanel/NotificationsTabPanel.tsx

const notifications = useNotificationSettings()
const [local, setLocal] = useState(notifications.data)

// When the switch is flipped: show it now, save, undo if saving fails
const handleToggle = async (key, value) => {
  const previous = local
  setLocal({ ...local, [key]: value })          // 1. update the screen at once
  try {
    await notifications.update({ [key]: value }) // 2. save
  } catch (error) {
    setLocal(previous)                           // 3. failed? put it back
    ToastMessage(TOAST_TYPE.ERROR, "Couldn't save that alert", error.message)
  }
}

if (notifications.isLoading) return <SettingsCardSkeleton rows={4} />
if (notifications.isError)   return <NoticeBanner … action={<Retry onClick={notifications.reload} />} />
return <NotificationSwitches settings={local} onToggle={handleToggle} isSample={notifications.isSample} />

Notice that this component has no idea whether the data is pretend or real. It never imports anything from mock/ or api/. That's the whole point.

The small visual pieces (NotificationSwitches, SettingsRow, Switch) don't load data at all. They just receive values and callbacks as props. Only the panels talk to hooks.

A full journey: flipping one switch

Let's follow what happens when you turn off "Product news" on the Notifications tab, with notifications on 'mock'.

  1. You open /profile?tab=notifications. The page renders NotificationsTabPanel.
  2. The panel calls useNotificationSettings().
  3. That hook calls useProfileResource('notifications', …). Nothing is in the cache yet, so isLoading is true and you see a skeleton.
  4. The loader calls profileServices.notifications.get().
  5. The registry built profileServices.notifications from config.ts, which says 'mock', so this is mockServices.notifications.get().
  6. The mock reads localStorage (or the fixture), waits 300ms, and gives back the settings.
  7. The hook stores them in the cache, isLoading becomes false, and the five switches appear.
  8. You flip Product news. The panel shows it off straight away (optimistic) and calls notifications.update({ productNews: false }).
  9. That goes down the same path to mockServices.notifications.update, which saves to localStorage and returns the new settings after 300ms.
  10. The hook calls resource.replace(next), so the cache and anything listening to 'notifications' now hold the new value.
  11. If step 9 had failed, the panel would put the switch back and show an error toast.

With real dataOnce the backend ships notifications and someone writes the api version, step 5 picks the api version instead, and steps 6 and 9 talk to the server. Every other step stays exactly the same.

The safety rule that keeps mock data contained

If a component imported the pretend data directly, deleting mock/ later would break it. To stop that from ever happening, I added a rule to eslint.config.mjs: importing anything from services/profile/mock outside src/services/profile is a lint error.

// eslint.config.mjs
"no-restricted-imports": ["error", {
  patterns: [{
    group: ["@/services/profile/mock", "**/services/profile/mock", …],
    message: "Read profile data through the hooks in src/hooks/profile, not the mock implementations.",
  }],
}]

So the only file that knows the mock exists is services/profile/index.ts.

Recipes

Recipe A: the backend shipped notifications. How do I switch to real data?

  1. Add the endpoints to RTK Query in src/core/redux/ (and the URL to src/constants/Api.ts), the same way the rest of the app does.
  2. In services/profile/api/index.ts, write a notifications object with get and update that call those endpoints. If the backend's shape is different, add a small mapper like mapUser.ts.
  3. Add notifications to the apiServices list at the bottom of that file.
  4. In config.ts, change notifications: 'mock' to notifications: 'api'. (Before step 3, this line would show a red error.)
  5. Done. The "Sample data" chip disappears from that card by itself. No hook or component changes.

Recipe B: the areas that already have real code

Details, security and wallets already have api code. Switching them is just step 4 above. They stay on mock for now only because the backend is missing some of their fields (username, bio, sessions, disconnect Google, and so on); switching early would show those parts empty.

Recipe C: every area is real. How do I delete the mock data?

  1. Make sure every line in config.ts says 'api'.
  2. Delete the folder src/services/profile/mock/.
  3. In services/profile/index.ts, remove the mockServices import and the mock branch in pick.
  4. Run the type check. It points at anything left over (for example the "Sample data" chip prop, which can then go too).

Recipe D: I want to see the error states while on mock

  • Change password: type wrong-password as the current password.
  • Wallets: disconnect wallets until only one is left, then try again.
  • Delete account: type a username that doesn't match.
  • A loading error for a whole card: temporarily set details, security or wallets to 'api' while not logged in with a real account. Remember to set it back.

Why this design, and what it costs

What we gain

  • The whole page could be built and tested before the backend was ready.
  • Moving an area to real data is a one line change, and the type system stops mistakes.
  • Removing the pretend data later is deleting one folder.
  • Loading, errors and saving behave the same way on every card, because they're written once in the hooks.
  • The page always gets tidy data, whatever shape the backend sends.

What it costs

  • src/services/ is a new top level folder, and this pattern is only used by the Profile page so far. Other pages call RTK Query hooks directly.
  • There are more files than calling RTK Query from components would need.
  • If you prefer, it could live under src/core/ next to the redux code instead. The design would be the same, only the location would change.

FAQ

Does this replace RTK Query?

No. The api folder calls the existing RTK Query endpoints and shares their cache. It just adds reshaping and friendly errors on top.

Will real users ever see John Doe?

Only on cards whose area is still on mock, and those cards show a "Sample data" chip. When an area is switched to api, its pretend data is no longer used anywhere.

Why does the mock wait 300ms?

So the loading skeletons appear and get tested. Without a delay, bugs in loading states would stay hidden until the real backend arrived.

Where is the theme (light/dark) saved?

Not in this layer. The theme lives on the device through src/context/ThemeContext.tsx, the same as the header toggle. Saving it to the account waits for the backend.

Why are some hooks shared between tabs?

Because some data belongs to one area but shows in several places. Telegram is part of profile details, so the Notifications tab uses useProfileDetails to show and disconnect it. Thanks to the cache, both tabs always agree.
