Phase 03 · Structure

The header and the page shell

Two files decide where everything else in this guide gets to live: Header (the top bar, shared by the whole site) and MarketplacePageShell (the three-column grid that's this page's private skeleton).

1The page file itself: assembly, not building

Start at the top: pages/design-preview/marketplace.tsx. It's short because its only job is arranging composites, not implementing any of them.

pages/design-preview/marketplace.tsxshape, trimmed
export default function MarketplacePreview() {
  const [menuOpen, setMenuOpen] = useState(false)
  const { filters, debouncedSearch, setFilter } = useListingFilters()
  const filtered = filterListings(mockListings, debouncedSearch, filters)

  return (
    <div>
      <Header onMenuClick={() => setMenuOpen(p => !p)} menuOpen={menuOpen} />
      <LiveActivityTicker />
      <MarketplacePageShell
        sidebar={<><MarketplaceSidebar /><MobileDrawerMenu onClose={...} /></>}
        hero={<MarketplaceHero />}
        sidebarOpen={menuOpen}
        onCloseSidebar={() => setMenuOpen(false)}
        rightRail={<...><LiveActivityPanel /><MarketActivityPanel /></...>}
      >
        <...><PromotedDomainsSection /><ListingCategoryTabs /><LiveListingsTable listings={filtered} /></...>
      </MarketplacePageShell>
      <MobileBottomNav />
    </div>
  )
}

Everything this file does: own two pieces of state (whether the mobile menu is open, and the active search/filter values), fetch/filter the mock listings, and pass all of that down as props. No layout math happens here — that's MarketplacePageShell's job, next.

2MarketplacePageShell: a CSS Grid with named areas

The desktop layout is sidebar, main content, and a right rail, side by side. Rather than three separate flex containers with manually matched widths, it's one CSS Grid with named template areas — the cleanest way to describe "these regions exist, here's roughly how they're arranged" without hand-computing pixel math.

MarketplacePageShell.module.scss
.grid {
  display: grid;
  grid-template-columns: 240px 1fr 320px;
  grid-template-areas:
    "sidebar hero rail"
    "sidebar main rail";
  gap: var(--space-6);
}
.sidebar { grid-area: sidebar; }
.hero    { grid-area: hero; }
.main    { grid-area: main; }
.rightRail { grid-area: rail; }

Read the grid-template-areas block literally as a picture of the layout: two rows, three columns. The word rail appears in both rows at the same column position — CSS Grid automatically merges that into one cell spanning both rows, which is why the right rail visually runs the full height beside both the hero and the main content below it, without any explicit "span 2 rows" instruction anywhere.

Then any element given grid-area: hero (via a class like .hero above) is placed into whichever named area matches, regardless of where it sits in the actual HTML/JSX source order. That decoupling — DOM order doesn't have to match visual order — is exactly what makes the mobile rewrite below possible with one extra media query instead of restructuring any component.

The same grid, one property changed, becomes the mobile layout

MarketplacePageShell.module.scss
@include tablet-down {
  grid-template-columns: 1fr;
  grid-template-areas:
    "hero"
    "rail"
    "main";
}

Below 1025px, the sidebar column drops out of the layout entirely (it becomes an off-canvas drawer instead — phase 04) and the remaining three areas collapse to one column, stacked hero, then rail, then main. Notice the order changed too: on desktop the rail sits beside hero+main, but on mobile it's deliberately placed between them — Live Activity and Market Activity move up to sit right under the hero instead of trailing at the very bottom, matching what the real Figma mobile mockup showed. Nothing about Header, MarketplaceHero, or any rail component had to know this reorder was happening — it's purely a property of where the grid places each named area at each breakpoint.

3The header: one component, used by the whole site

src/design-system/layouts/header/index.tsx is not marketplace-specific — every page in the real app renders it. That matters for how new behavior gets added to it.

Header/index.tsx
type HeaderProps = {
  hidden?: boolean
  // Opt-in only — omitted by every page except the marketplace preview,
  // so no other page's header changes.
  onMenuClick?: () => void
  menuOpen?: boolean
}
Why the hamburger button is an optional prop, not just always-on

Header is used across the real site, most of which has no off-canvas drawer to open. Making onMenuClick optional and only rendering the hamburger chip when it's actually passed means every other page's header renders exactly as it did before this feature existed — the marketplace preview page is the only caller that passes it. This "opt-in prop" shape reappears constantly in this project any time a shared component needs new behavior that only one caller wants.

Header/index.tsx
{onMenuClick && (
  <button className={styles.menuToggle} onClick={onMenuClick} aria-expanded={menuOpen}>
    <span className={styles.menuToggleBar} />
  </button>
)}

The chip's chamfered shape uses the exact same clip-path technique from phase 02, just applied to a small square button instead of a pill. Its three horizontal bars (the hamburger icon itself) are drawn with pure CSS — no image — three <span>-like bars positioned with ::before/::after, the same technique used again for the drawer's close ("X") button in phase 04.

4The mobile drawer: fixed position, animated with a transform

The sidebar's off-canvas behavior below 1025px lives entirely in CSS, driven by one boolean class:

MarketplacePageShell.module.scss
.sidebar {
  @include tablet-down {
    position: fixed;
    top: 59px;               // matches the header's own height, so the drawer opens below it, not over it
    left: 0; bottom: 0;
    width: 280px;
    transform: translateX(-100%);  // off-screen to the left by default
    transition: transform 0.2s ease;
  }
}
.sidebarOpen {
  @include tablet-down { transform: translateX(0); }
}

translateX(-100%) shifts the whole drawer left by exactly its own width, which is what makes it invisible off-screen without needing display: none (which couldn't be transitioned). When the sidebarOpen class is added, transform changes to translateX(0), and because transition: transform 0.2s ease is already declared on the base rule, the browser animates smoothly between the two positions instead of snapping.

The React side is almost nothing — MarketplacePageShell doesn't own this state itself, it's a fully controlled component for this:

MarketplacePageShell.tsx
export const MarketplacePageShell = ({ sidebar, hero, rightRail, children, sidebarOpen, onCloseSidebar }: Props) => {
  const sidebarClass = [styles.sidebar, sidebarOpen ? styles.sidebarOpen : ''].filter(Boolean).join(' ')
  return (
    <div className={styles.shell}>
      <div className={styles.grid}>
        <aside className={sidebarClass}>{sidebar}</aside>
        <div className={styles.hero}>{hero}</div>
        <aside className={styles.rightRail}>{rightRail}</aside>
        <main className={styles.main}>{children}</main>
      </div>
      {sidebarOpen && <div className={styles.scrim} onClick={onCloseSidebar} />}
    </div>
  )
}
Controlled vs. self-owned state

Earlier in this project, the shell owned sidebarOpen itself with its own useState, and rendered its own toggle button floating above the grid. That button needed to move inside the header bar to match the real design (this phase, section 3) — but the header is a sibling of the shell in the page tree, not a child, so it has no way to reach into the shell's internal state. The state had to move up to the one component that's an ancestor of both: the page itself. This is the standard React answer whenever two separate components need to agree on one piece of state — lift it to their nearest common parent, and pass it down to both as props.

The scrim is the semi-transparent dark overlay behind the open drawer — it only renders when the drawer is open, and clicking it calls the same onCloseSidebar the close button uses, giving you "tap anywhere outside to dismiss" for free from one onClick.

5What to remember from this phase

  • CSS Grid named areas decouple visual order from DOM order — reordering a responsive layout is often just rewriting grid-template-areas, no JSX changes.
  • A shared component (Header) gets new behavior through optional props that default to off, so every other caller is provably unaffected.
  • An off-canvas drawer is position: fixed + translateX(-100%) + a transition, toggled by adding one class.
  • When two sibling components need to share state, lift that state to their nearest common parent and pass it down as props to both.
