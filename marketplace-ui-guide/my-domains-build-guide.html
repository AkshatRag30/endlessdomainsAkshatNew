01

How it's structured

Five layers, each only knowing about the one below it. This is the same shape the marketplace redesign already established — My Domains reuses most of layers 1 and 2 outright instead of rebuilding them.

layer stacktop to bottom
1. Page           pages/design-preview/account/my-domains.tsx
                    owns state: which status tab, which filters, grid or list

2. Shell (shared)  MarketplacePageShell + MarketplaceSidebar + Header
                    pure layout — sidebar / main / right rail grid, no data of its own

3. Composites     MyDomainsHeroBanner, PortfolioStatsRow, MyDomainsCategoryTabs,
                    MyDomainsFilterBar, MyDomainsTable, MyDomainRow, MyDomainCard,
                    NeedsAttentionPanel, MostViewedPanel, QuickActionsPanel
                    each one domain-shaped — knows what a "domain" or a "quick action" is

4. Primitives     StatCard, InfoListCard, ViewToggle, DomainAvatar
                    + reused: Badge, ExtensionBadge, ChainBadge, TrendIndicator,
                    SearchInput, FilterDropdown, PrimaryButton, SecondaryButton
                    generic — no idea what a "domain" is, just take props and render

5. Data           src/types/my-domains/*, src/data/my-domains/*,
                    src/hooks/my-domains/useMyDomainsFilters.ts
                    typed shapes + static fixtures, no API calls yet

The rule that keeps this from turning into spaghetti: a layer only ever imports from the layer below it. The page imports composites and the shell; composites import primitives and data; primitives import nothing domain-specific at all. Break that rule once (say, a primitive importing a composite) and the whole point of having layers — being able to change one without reading the others — is gone.

The swap boundary

Every composite receives data as typed props or reads it from a hook — never an API hook directly. That's what makes "swap the mock data for a real endpoint" a one-file change instead of a rewrite.

src/hooks/my-domains/useMyDomains.tstoday → later, not yet built
// today — every composite already calls something shaped like this
export function useMyDomains(params: MyDomainsQueryParams) {
  return mockMyDomainsSummary
}

// later — same export shape, nothing above this line changes
export function useMyDomains(params: MyDomainsQueryParams) {
  const { data } = useGetDomainSummaryByUserQuery(params)
  const { data: expiry } = useGetDomainExpiryDateQuery(undefined, { pollingInterval: 60_000 })
  return useMemo(() => toMyDomainsSummary(data, expiry), [data, expiry])
}

Nobody above this hook — not MyDomainsTable, not the page — needs to change when the right side of that function changes. That's the entire point of the layering: the pain of a real API integration gets contained to one small file instead of spreading through every component that touches domain data.

02

Building it by hand, without AI

The mechanics that actually mattered, in the order you'd hit them. None of this is specific to AI-assisted work — it's just the discipline that kept this build from accumulating a pile of small visual bugs.

Pull real measurements before you build, not after. The first pass at the category tabs, the trend arrows, and the hero background were all built from a screenshot or a reasonable guess. All three turned out wrong once the real Figma node was actually pulled — not "close but needs polish" wrong, structurally wrong (reusing the wrong component entirely, a mirrored asset that was never actually mirrored, a CSS mixin silently deleting the background it sat under). A screenshot tells you what it looks like; it doesn't tell you the exact colors, the exact spacing, or whether two elements are actually the same component reused. Get the real numbers first.
Reuse before you build. MyDomainsCategoryTabs at one point was a thin wrapper around the marketplace page's own tab component, because they looked similar enough at a glance. They weren't the same design at all. The fix wasn't "build a new component," it was "notice the existing one doesn't fit and build the right one instead of forcing the wrong one to work." Before writing a new component, check whether one already exists that fits — but be honest when it doesn't, instead of bending it until it half-fits.
Override a shared component's size safely. Reusing SecondaryButton or FilterDropdown in a new context sometimes means they're the wrong size for where you're putting them (they were built for a different, wider row elsewhere in the app). You can't just add a class and hope it wins — two CSS Modules files both defining a plain class selector have equal specificity, and which one "wins" depends on module load order, which isn't something to rely on. The safe pattern: wrap the shared component in your own element, then target the plain HTML tag it renders (button, img) from inside your wrapper class. A tag selector inside a class selector always beats a bare class selector, regardless of load order, with no !important needed.
patternspecificity-safe override
// the shared component always renders a plain <button>
<span className={styles.bulkListWrap}>
  <SecondaryButton transparent>Bulk List</SecondaryButton>
</span>

/* targets the tag, not a class — wins regardless of CSS module order */
.bulkListWrap button {
  width: 126px;
  height: 48px;
}
Keep the "reserved space" trick in mind for state changes. Adding a border to only the active state of a list item shifts that item's size by the border width unless the inactive state reserves the same space with a transparent border. Same idea any time a property only applies conditionally — give the base state a neutral value for that property instead of omitting it, so toggling the state doesn't move anything else on the page.
Sticky sidebars are two CSS declarations, not a scroll listener. "Left and right columns stay in place while the middle scrolls" sounds like it needs JavaScript. It doesn't: position: sticky; top: 0; on the column, plus align-items: start on the parent grid (without that, grid items stretch to fill the row and have nowhere to "stick" from). The browser handles the rest, including the exact behavior of "scrolls normally until its content runs out, then holds in place."
Know when to stop guessing at a shape. A small decorative connector between the sidebar label and its count pill went through three different attempts (two disconnected lines, a filled shape that read as a plain rectangle, a stroked outline) before it got dropped entirely rather than attempting a fourth guess. Recognizing "I'm pattern-matching on a shape I don't have exact data for" and stopping is itself a useful skill — a missing decoration is a smaller problem than three wrong ones in a row.

Page gutter fix

2 files

The header and page shell were both using --container-padding-x (80px), a token copied byte-for-byte from the main marketing site's own tokens file and left untouched there deliberately, for future syncs. That token is sized for a spacious marketing page, not a dashboard. Rather than edit a token meant to stay in sync with an external source, both files got their own literal 32px gutter instead — confirmed against the real Figma frame's own near-zero side margins, much closer than 80px.

Phase 10

Hero background bug

real bug4 assets

Raised as feedback: white hero text was invisible. Root cause was a genuine CSS bug, not a missing decoration — a stripe-bg mixin included after the gradient in the same rule set background-image directly, which silently overwrote the gradient entirely (it's a longhand the shorthand above it also sets, and the later declaration wins). Fixed by moving the real noise texture onto a separate ::before pseudo-element blended on top with mix-blend-mode: plus-lighter, matching how the export actually layers it, and added the five faint decorative accents pulled as real assets, positioned as percentages of the banner's own box rather than the export's fixed pixel frame.

Real API integration

Same swap-boundary pattern as section 01: nothing above useMyDomains needs to change. What varies is whether the backend already has the endpoint.

DataBackend todayWhat's neededEffort
Listings table
MyDomainListing[]		 Real endpoint exists, already used by the old page (useGetDomainSummaryByUserQuery) Map the response's loosely-typed inner object to MyDomainListing; join in expiry from the separate poll instead of doing it per-card Easy
Renewal countdown Real endpoint exists (useGetDomainExpiryDateQuery), polled every 60s Merge into the same mapper above instead of a second per-card query Easy
List / Edit Price / Bulk List / Appraise actions Real, working mutations already exist in src/component/domain-self-item — on-chain delist, appraisal API call, listing modal Wire the existing logic to the new UI's buttons once Edit Price/DeList/Promote semantics are confirmed against the design (see open questions) Medium
Estimated value, views, saved count No backend precedent at all — new fields this design introduced Confirm with backend whether these exist or need building; no frontend blocker once a shape is confirmed Hard, backend-blocked
Needs Attention / Getting The Most Views Not a separate endpoint — these are just filtered/sorted views over the same domain list No new backend work; derive both from the same mapped list once views/estimated value exist Medium
Transfer action No mutation, modal, or hook exists anywhere in the codebase Genuinely new feature — needs its own backend endpoint and its own modal, not a reskin of anything that exists Hard, backend-blocked

Net read: the listings table itself is close, the real endpoints already exist and are already used by the old page. The genuinely new surface, estimated value, view/save counts, and Transfer, is blocked on backend work, not frontend effort.

06

Becoming a real page in the sidebar

Closer than it looks. The sidebar already has an entry for this page — it was never built to match, that's the actual remaining gap.

src/data/marketplace/navigation.tsalready there, unedited
{ id: 'my-domains', label: 'My domains', href: '/profile/domains' }

This page currently lives at the temporary preview route, and the sidebar item above points at the real page's real URL. Three concrete steps close that gap:

  • Swap what pages/profile/domains/index.tsx renders. The old page uses Layout + the old ProfileSidebar; the new one needs Header + MarketplacePageShell + MarketplaceSidebar instead, the exact tree already proven out at the preview route. The page's server-side auth redirect stays untouched either way.
  • Confirm the active-state match. Since the real route is /profile/domains (not the preview route), MarketplaceSidebar's existing pathname-based active check will just work without the initialSelectedId workaround the preview route currently needs.
  • Wire useMyDomains to the real query (see the API table above) before or alongside the route swap, so the newly-real page isn't showing mock data at its real URL.

The open question this doesn't answer on its own: whether "My Domains" should keep living under /profile/* at all, or move to sit alongside the marketplace page under a shared route family, given it now shares that page's exact shell. That's a routing/navigation decision, not a technical blocker either way.

07

Open questions, said plainly

  • The table's Action column reads "Edit Price," with no DeList or Promote button visible per row anywhere in the design, even though both are real, working features on the old page today. Whether they moved behind a menu not visible in the static export, or are out of scope for this page, is unconfirmed.
  • "Transfer" in Quick Actions has no existing mutation, modal, or hook anywhere in the codebase — new scope, not a reskin.
  • The Figma file's own placeholder numbers (Domains card, category tab counts, sidebar badge) don't agree with each other — none should be treated as real reference values, only the labels and layout.
  • Mobile currently uses a simplified stacked layout for the listings table rather than the marketplace table's full fixed-pane-plus-scroll-pane split; real device-width verification hasn't happened, since this environment has no browser automation tool installed.
  • The left-sidebar decorative connector between a nav label and its count pill (Phase 12) is unresolved — dropped after three wrong attempts rather than guessed a fourth time.
