Phase 01 · Foundations

Design tokens & global styles

Before any component, three small files: tokens.scss, _mixins.scss, fonts.scss. Every color, size, and breakpoint used anywhere in this guide traces back to one of these.

1Why tokens instead of raw values

Open any component's stylesheet in this project and you'll almost never see a bare hex color or a bare pixel value for spacing. Instead you'll see things like var(--color-blue-primary) or var(--space-4). These are CSS custom properties — plain CSS, no build step needed — declared once on :root in src/design-system/styles/tokens.scss and then referenced everywhere else.

Why this matters

If the brand blue ever changes, it changes in one line, not in forty files. If you're reading a component's CSS and see var(--color-black-alpha-55), you immediately know it's a semi-transparent black used elsewhere too, not a one-off value someone typed by hand — the variable name is the documentation.

2Reading tokens.scss

The file is one giant :root { ... } block, organized into labeled sections with comment dividers. Here's the shape, trimmed to the parts you'll see referenced constantly in later phases:

src/design-system/styles/tokens.scssexcerpt
// ── Blue ──────────────────────────────────────────────────────────────────
--color-blue-primary: #2639ED;
--color-blue-light: #e9ebfd;
--color-blue-dark: #1d2bb2;

// ── Font families ─────────────────────────────────────────────────────────
--font-satoshi: 'Satoshi', sans-serif;
--font-space-grotesk: 'Space Grotesk', sans-serif;

// ── Font sizes ────────────────────────────────────────────────────────────
--text-h1: 65px;
--text-body: 22px;
--text-small-13: 13px;
--text-small-12: 12px;

// ── Font weights ──────────────────────────────────────────────────────────
--font-weight-regular: 400;
--font-weight-medium: 500;
--font-weight-semibold: 600;
--font-weight-bold: 700;

// ── Base Spacing Scale ────────────────────────────────────────────────────
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-6: 24px;

Notice the naming pattern: --text-small-13 literally means "a small text size, 13px" — the number in the name is the pixel value, so you never have to jump back to this file to know what a size token means when you see it used. The spacing scale (--space-1 through --space-15) is a fixed ladder of values, not arbitrary numbers, so any two components that both use --space-4 automatically line up.

Colors that don't fit the palette

You'll also spot literal hex values inside component stylesheets throughout this project, always with a comment like // design-specific: Figma-exact, no token match. That's intentional, not an oversight: when a design calls for a one-off color that doesn't belong in the shared palette, the convention here is to write the literal value with a comment explaining it's deliberate, rather than inventing a new token that would only ever be used once.

3Breakpoints live in _mixins.scss, not in every file

Every responsive rule in this whole codebase — every single @media query — goes through one of a handful of named mixins defined once in src/design-system/styles/_mixins.scss. Nobody writes a raw @media (max-width: 767px) by hand.

src/design-system/styles/_mixins.scssexcerpt
$breakpoint-mobile: 768px;
$breakpoint-tablet: 1025px;   // widened from 992px — see phase 09
$breakpoint-desktop: 1025px;

@mixin mobile {
  @media (max-width: #{$breakpoint-mobile - 1px}) { @content; }
}

@mixin tablet-down {
  @media (max-width: #{$breakpoint-tablet - 1px}) { @content; }
}

@mixin tablet {
  @media (min-width: $breakpoint-mobile) and (max-width: #{$breakpoint-tablet - 1px}) { @content; }
}

Every component you'll see in later phases writes responsive CSS like this:

a typical mobile override, this pattern repeats hundreds of times
.someClass {
  // desktop styles here, unconditional

  @include mobile {
    // only applies below 768px
  }
}

Three named ranges matter for this page: mobile (below 768px), tablet (768–1024px), and everything at 1025px and above is treated as desktop by simply not being wrapped in a mobile/tablet-down mixin — the base, unconditional rule in every stylesheet is the desktop styling. tablet-down means "mobile and tablet combined," used constantly because this page's off-canvas drawer behavior applies to both.

A real bug this caused

Until this project's breakpoints were widened, $breakpoint-tablet was 992px while $breakpoint-desktop was 1025px — a 33px gap that belonged to neither range. A real iPad Pro landscape width (1024px) fell straight into that gap and silently got the full desktop layout, sidebar column and all, breaking the mobile-style listings table. Phase 09 covers the fix and how the gap was found.

Other mixins you'll see constantly

MixinWhat it's for
@include focus-ringOne consistent keyboard-focus outline style, used on every interactive element
@include stripe-bgA subtle diagonal hairline texture used as a background on several panels — see phase 07

4Fonts: a real bug worth knowing about

Two font families are used throughout — Satoshi (most text) and Space Grotesk (numbers, prices, anything monospace-flavored in the original design). They're declared as tokens in tokens.scss exactly like colors:

src/design-system/styles/tokens.scss
--font-satoshi: 'Satoshi', sans-serif;
--font-space-grotesk: 'Space Grotesk', sans-serif;
The bug: declaring a font is not the same as loading it

For a long stretch of this project, every component correctly wrote font-family: var(--font-satoshi), but the actual font file was never loaded anywhere — no <link> tag, no @font-face, no next/font. The browser silently fell back to its default system sans-serif for every single piece of text on the page. Nothing errored, nothing looked broken exactly, it just looked thinner and slightly wrong everywhere at once, which made it hard to spot until someone compared it side-by-side against the real Figma file.

The fix lives in pages/_document.tsx, the one file in a Next.js app that wraps every page and is the right place for document-level <link> tags:

pages/_document.tsx
<Head>
  <link rel="stylesheet"
    href="https://api.fontshare.com/v2/css?f[]=satoshi@variable&display=swap" />
  <link rel="stylesheet"
    href="https://fonts.googleapis.com/css2?family=Space+Grotesk:wght@400;500;600;700&display=swap" />
</Head>

Two details worth noticing. First, Satoshi is requested as @variable rather than fixed weights — the font-hosting service Fontshare doesn't ship a static "semibold" (600) file for this typeface, only 400/500/700/900, so a fixed-weight request would have silently substituted the nearest weight it had. A variable font file covers the entire 300–900 range continuously, so every weight this project's CSS asks for actually renders as that real weight. Second, both are <link> tags in the document head, not a CSS @import — a @import in a stylesheet is render-blocking in a way a discovered-during-HTML-parsing <link> isn't, so this loads in parallel with everything else instead of one more thing in a blocking chain.
