The building blocks, explained from zero

Every later phase assumes you already know what a React hook is, what a flex container does, and why a media query is wrapped in a Sass mixin. This phase is where all of that gets explained in plain language, with small throwaway examples, before you meet any of it for real. If you already know React and CSS well, skim the headings and jump to whatever's unfamiliar — otherwise, read it straight through once. Nothing here is specific to this project; it's the vocabulary the rest of the guide is written in.

1What a React component actually is

Strip away everything else, and a React component is just a JavaScript function that returns a description of some markup. The description isn't real HTML yet — it's a JavaScript object tree that React later turns into real DOM elements in the browser. You write that description using JSX, which looks like HTML mixed directly into JavaScript:

a component, from scratch
function Greeting(props) {
  return <p>Hello, {props.name}</p>
}

// used elsewhere as:
<Greeting name="Akshat" />

props is just the function's argument — whatever attributes you write on the JSX tag (name="Akshat") arrive as an object ({ name: "Akshat" }) that the function reads. Every component this project defines works exactly like this: a function, an optional props object in, some JSX out. When you see export interface FooProps { ... } above a component in this codebase, that's TypeScript describing the shape of that props object so your editor can catch a typo (a missing prop, a wrong type) before the code ever runs.

The curly braces { } inside JSX are how you drop back into plain JavaScript in the middle of markup — {props.name} above, {listing.domainName} everywhere in this codebase, {items.map(...)} to turn an array into a list of elements. Anywhere you see curly braces inside a tag in this guide's code samples, that's a JavaScript expression being evaluated and dropped into the markup at that spot.

2State: a component's own memory

A plain JavaScript variable inside a function forgets its value the moment the function returns — and a component function re-runs every time it re-renders. useState is React's way of giving a component a piece of memory that survives across those re-runs, and — critically — changing it is what triggers React to re-run the component and update the screen in the first place.

state, from scratch
function Counter() {
  const [count, setCount] = useState(0) // 0 is the starting value

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  )
}

useState(0) returns a pair: the current value (count) and a function to change it (setCount) — always destructured with array syntax like this, always in that order. Calling setCount(count + 1) does two things: it updates the value React remembers for next time, and it schedules the component to re-render, so the new count actually shows up on screen. This is the mechanism behind every interactive thing in this codebase — a dropdown's open/closed flag, which tab is active, which listing is favorited, all of it is a useState call somewhere, and every one of them follows this exact shape.

A pattern you'll see constantly: functional updates

Instead of setCount(count + 1), this codebase very often writes setCount((prev) => prev + 1) — passing a function instead of a value. That form receives React's own most up-to-date version of the state as prev, rather than trusting whatever count happened to be when the surrounding code last ran. It matters most when a state update depends on the previous value and might fire more than once before a re-render catches up — setFavoritedIds((prev) => { const next = new Set(prev); ...; return next }) in LiveListingsTable is a real example from phase 06.

3Effects: doing something when the component appears (or changes)

useState handles values the component renders. useEffect handles everything else a component might need to do that isn't rendering — subscribing to an event, starting a timer, fetching data, or (the example this codebase uses constantly) listening for a click anywhere on the page.

an effect, from scratch
useEffect(() => {
  // this runs after the component first renders
  const handleClick = () => console.log('clicked somewhere')
  document.addEventListener('click', handleClick)

  return () => {
    // this runs right before the component disappears (or before the effect re-runs)
    document.removeEventListener('click', handleClick)
  }
}, []) // the dependency array — empty means "run once, on mount"

Three parts to notice. The function you pass in runs after render, not during — so it's safe to touch things outside React (the real DOM, the network, timers) without interfering with what's being drawn on screen. The function you return from inside it is the cleanup — React calls it automatically when the component is about to be removed from the page, and this matters enormously: forgetting to remove an event listener you added means it keeps firing forever, even after the component that added it is long gone, silently leaking. And the array at the end ([] here) controls when the effect re-runs at all — empty means only once, ever; list a variable in it ([open], say) and the effect re-runs any time that specific value changes.

This exact shape — listen on mount, remove on unmount — is precisely how every dropdown and menu in this codebase closes itself when you click outside it. You'll meet the real version of it in phase 02 (FilterDropdown) and see it reused twice more, verbatim in shape, in phase 07.

4Refs: a box that doesn't trigger a re-render

useRef looks similar to useState — it also gives a component a value that survives across re-renders — but changing a ref's value does not cause the component to re-render. Its most common job in this codebase is holding a direct handle to a real DOM element, so plain JavaScript can be run against it (checking "did this click land inside this element or outside it").

a ref, from scratch
const boxRef = useRef<HTMLDivElement>(null)

<div ref={boxRef}>...</div>

// later, inside an effect or event handler:
if (boxRef.current && !boxRef.current.contains(event.target)) {
  // the click landed outside this div
}

boxRef.current starts as null and React fills it in with the real DOM node the moment that element mounts — from then on, boxRef.current is that actual <div> in the browser, with every real DOM method (.contains(), .focus(), .scrollTo()) available on it. Put together with the useEffect pattern above, this is the entire outside-click-to-close mechanism this project reuses everywhere: a ref on the menu's root element, a document-wide click listener in an effect, and a check of whether the click target is inside or outside that ref.

5CSS Modules: why a class name isn't just a string

Every component in this codebase imports its stylesheet like this: import styles from './Thing.module.scss', then writes className={styles.card} instead of className="card". This isn't decoration — .module.scss is a special file extension the build tool (webpack, underneath Next.js) recognizes, and it does something to every class name written inside a file with that extension: it rewrites each one into a longer, unique string, and hands you back a JavaScript object mapping your original names to the rewritten ones.

Why bother — what problem this solves

Plain CSS class names are global — a .card rule in one file can accidentally override a .card rule from a completely unrelated file, purely because they happen to share a name, with no error or warning. As a project grows past a handful of components, avoiding name collisions by convention (increasingly long, hand-negotiated class names) gets unsustainable fast. CSS Modules solve it structurally: styles.card in SidebarPromoCard.module.scss might compile to something like SidebarPromoCard_card__a1b2c, and styles.card in a totally different file compiles to a different unique string — so two components can both use the friendly name .card in their own source and never once collide in the actual browser. This is also exactly why you'll never see a plain string literal as a className anywhere in this codebase's components (outside of combining several styles.x values together) — className="card" would refer to a real, global class that doesn't exist and would style nothing.

6The box model: what padding, border, and margin actually are

Every element on a page is a rectangle made of four nested layers, from the inside out: content (the text or child elements), padding (empty space inside the element's own background/border), border (a visible or invisible edge), and margin (empty space outside the element, pushing neighboring elements away). Padding and border are "inside" the element in the sense that they're part of what gets a background color; margin is always transparent and never gets one.

One global setting changes how an element's declared width is measured against these layers, and it matters enough to call out here because it's set once, globally, and then quietly assumed everywhere: box-sizing: border-box. Without it, width: 200px; padding: 20px renders as 240px wide overall (the padding adds on top of the 200px). With it — which is what this project's global reset applies to every element — that same rule renders as exactly 200px wide overall, with the padding eating into the content area instead of adding to the total. Every width/padding number quoted anywhere in this guide assumes border-box is in effect, because it always is.

7Display: block, inline, and the two layout modes that matter here

display is the single most consequential CSS property an element has — it decides the entire layout algorithm used for that element and its children. The two values that matter for basically everything in this codebase are flex and grid; the two you need to recognize as their opposite are block (default for things like <div> and <p> — stacks top to bottom, each element as wide as its parent) and inline (default for things like <span> — flows left to right like text, can't take a width or height). display: none is the fourth value you'll see constantly — it removes the element from the page's layout entirely, as if it weren't in the markup at all (not just invisible — it takes up zero space), which is the exact mechanism behind every "render both, CSS decides" pattern in this guide.

8Flexbox: arranging things in a single row or column

display: flex turns an element into a flex container, and every direct child becomes a flex item, laid out along one line (row by default, or column) rather than each stacking on its own line the way block elements do.

flexbox, from scratch
.row {
  display: flex;
  flex-direction: row;      // or column — which way items line up
  align-items: center;      // position along the CROSS axis (perpendicular to direction)
  justify-content: space-between; // position along the MAIN axis (the direction itself)
  gap: 12px;              // space between items, no manual margins needed
}

The two axes are the whole trick to remembering which property does what: in a row, the main axis runs left to right (so justify-content controls horizontal spacing — space-between pushes the first and last items to the edges and spreads the rest evenly, center bunches them in the middle), and the cross axis runs top to bottom (so align-items controls vertical alignment — center vertically centers every item, flex-start aligns them all to the top). Switch to flex-direction: column and the two axes swap roles entirely: now justify-content controls vertical spacing and align-items controls horizontal.

Growing and shrinking: flex-grow, flex-shrink, flex-basis

Every flex item has three more properties, almost always set together through the flex shorthand. flex: 1 — the single most common value in this codebase — means flex-grow: 1; flex-shrink: 1; flex-basis: 0%: this item should start from zero and grow to fill whatever space is left over, sharing it proportionally with any other sibling that also has flex: 1. flex-shrink: 0 alone (seen constantly on icons and badges in this codebase) means the opposite: never let this item shrink below its natural size, no matter how tight the container gets — everything else should shrink first.

The single most common flexbox surprise: min-width

A flex item's default minimum width isn't zero — it's the natural width of its own content. That means a flex item with flex: 1 and a long line of text or a wide child can refuse to shrink smaller than that content, even though you gave it flex: 1 specifically hoping it would compress. The fix is one line: min-width: 0 (or, on a column, min-height: 0), which explicitly removes that content-based floor. You'll meet this exact bug, and this exact one-line fix, as a real production issue in phase 06's listings table.

Two more properties round this out. gap puts even spacing between items without needing a margin on every child (and without the classic "last item has an extra margin I need to remove" problem). flex-wrap: wrap lets items that don't fit on one line drop to a second line instead of overflowing or squeezing forever — off by default, so a flex row will otherwise cram everything onto one line no matter how narrow the container gets.

9Grid: arranging things in rows AND columns at once

Flexbox is fundamentally one-dimensional — a single row or a single column. display: grid is for when you need both at once — real rows and real columns, with items placed into specific cells.

grid, from scratch
.layout {
  display: grid;
  grid-template-columns: 2.4fr 1fr 1.4fr; // three columns, proportional widths
  grid-template-areas:
    "sidebar header header"
    "sidebar main    rail";
}

.sidebar { grid-area: sidebar; } // placed by name, not by row/column numbers

fr is grid's own unit, short for "fraction" — 2.4fr 1fr 1.4fr splits the available width into 4.8 total shares and gives the first column 2.4 of them, proportional sizing without ever computing a percentage by hand. grid-template-areas is the feature this codebase leans on hardest: you draw the layout as a little ASCII map of named regions (each string is one row, each word one column's occupant), and any child can be dropped into one of those named regions with a single grid-area: name — including spanning multiple rows or columns automatically, just by repeating its name in more than one cell of the map. The payoff, covered in depth in phase 03, is that a completely different map for mobile (different row/column shape, different reading order) can reuse the exact same child elements with zero changes to the actual markup — only the CSS map changes.

10The cascade and specificity: how CSS decides between two conflicting rules

Two rules can both apply to the same element and disagree about a property. CSS has to pick one, and it does so with a fixed set of tie-breakers, checked in order: first, whichever rule is more specific wins (an id selector beats a class selector, which beats a plain element selector like div); second, if two rules are exactly tied in specificity, whichever one is written later in the stylesheet wins — full stop, regardless of which one "sounds" more like it should apply.

In practice, nearly everything in this codebase is styled with single classes (.card, .title) — which are all equally specific — so the second rule, source order, ends up mattering constantly. This isn't an obscure edge case: phase 07 walks through a real bug in this exact codebase where two same-specificity rules disagreed about whether an element should be visible, and the one declared earlier in the file silently lost, every time, at every screen width, because CSS always resolves same-specificity ties by position in the file rather than by which rule looks more like the "special case."

11Positioning: the five values of `position`, in one line each

ValueWhat it does
staticThe default — normal document flow, top/left/etc. have no effect.
relativeStill takes up its normal space in the flow, but top/left/etc. can nudge it visually, and it becomes the anchor for any absolute children.
absoluteRemoved from normal flow entirely; positioned relative to its nearest relative (or absolute/fixed) ancestor instead of the page.
fixedRemoved from flow; positioned relative to the browser viewport itself, stays put even as the page scrolls.
stickyNormal flow until the page scrolls past a threshold, then behaves like fixed within its own parent's bounds.

The pairing that shows up constantly in this codebase is position: relative on a parent plus position: absolute on a child — a decorative glow behind a card, a badge pinned to a corner, a fill layer sitting on top of a button's own background. The parent doesn't need any other property changed to become that anchor; just declaring position: relative on it (even with no top/left values at all) is what makes it the reference point for any absolutely-positioned child, instead of the child measuring itself against the whole page.

Why sticky isn't a free "stay in place" — and takes up real space while it's stuck

It's tempting to read position: sticky as "this element floats above everything, out of the way." It doesn't — while it's in its stuck state, it still occupies a real band of screen space, on top of whatever's near it, and anything that needs to move past that band in the same scroll container has to pass behind it first. Phase 06 covers a real case where this made an entire button permanently unreachable, and walks through why the fix wasn't a CSS tweak but a different structural approach entirely.

One more idea worth having before phase 04: stacking context and z-index. When two positioned elements overlap, z-index (a plain number) decides which one draws on top — higher numbers win, and elements with no explicit z-index stack in the order they appear in the markup. This is exactly how a button's own colored fill layer can be drawn as a separate ::before element sitting visually on top of the button's flat background but still underneath its own text (covered for real in phase 02).

12Media queries, and why this project never writes one directly

A media query is a CSS rule that only applies when some condition about the viewport is true — most commonly a minimum or maximum width:

a media query, from scratch
.card {
  padding: 24px; // applies always
}

@media (max-width: 767px) {
  .card {
    padding: 12px; // only applies when the viewport is 767px wide or narrower
  }
}

You will never see a raw @media (max-width: ...) written directly in this codebase's own component stylesheets — instead, every one of them writes @include mobile { ... }, or @include tablet-down { ... }, and so on. These are Sass mixins — reusable blocks of CSS (here, specifically, reusable media-query wrappers) defined once, centrally, in _mixins.scss, and reused everywhere with @include. The entire benefit is that the actual pixel breakpoint (767px, or wherever "mobile" ends) lives in exactly one place — change it once in the mixin's own definition, and every component that ever wrote @include mobile picks up the new value automatically, instead of someone needing to find and edit forty separate @media (max-width: 767px) blocks scattered across forty files. Phase 01 covers the real mixin file and its actual breakpoint values in detail.

13Two different kinds of "variable": $sass-variables vs. var(--css-custom-properties)

This codebase uses both kinds constantly, and they look similar but behave completely differently — worth being sure of the difference before phase 01 leans on it.

$sass-variablevar(--css-custom-property)
ExistsOnly while Sass compiles your .scss into plain CSS — gone by the time the browser sees anything.For real, in the browser, as an actual CSS feature the browser understands natively.
Can change at runtime?No — once compiled, it's just whatever raw value got substituted in.Yes — JavaScript can set one per-element via an inline style, and it can be overridden differently under a media query.
Typical use hereA breakpoint number, a polygon shape reused a few times in one file ($clip, $notch).A design token meant to be shared across the whole app (var(--space-4), var(--color-blue-primary)).

The fact that var(--x) is a real, live browser feature — not just a compile-time text substitution — is exactly what makes one of this project's more clever tricks possible: PromotedDomainsSection computes an animation's duration in JavaScript (based on how many cards there are) and hands it to CSS through an inline style={{ '--loop-seconds': '28s' }}, which the stylesheet then reads back with animation-duration: var(--loop-seconds, 28s). A $sass-variable could never do this — it has no way to receive a value computed at the moment the page actually runs, only values known when the stylesheet was written. Phase 05 covers this trick in full.
