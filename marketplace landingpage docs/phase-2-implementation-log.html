Before any edit in this phase, all three target files were read again in full and compared line by line against that document's own description, since code moves and the plan itself says not to trust it blindly.

Confirmed as written, line for line

All three files matched the plan's description exactly, down to the same line numbers, in BuyNowModal.tsx, DomainListingModal.tsx, and domain-self-item/index.tsx. Nothing had drifted since the plan was written, so it was safe to proceed straight into step 1 without correcting anything in the plan itself.

Nuance worth stating plainly

BuyNowModal.tsx already had a way to switch networks, just not an automatic one

The plan's wording, "wrong network just bails, no switch attempted at all," is accurate about what happens inside domainBuyHandler itself, but read on its own it could sound like there was no way to switch networks anywhere in this file. There was: the Buy button already swapped to a "Switch Network" label and called a separate handleSwitchNetwork function when isWrongNetwork was true, it just took two clicks, one to switch and a second one to actually buy. This is also the exact mechanism behind an earlier question in this project, why "Switch Network" wasn't appearing on one branch during manual testing, the two click path was there the whole time, just easy to miss without reading the button's own logic.

1

Rewrite BuyNowModal.tsx

domainBuyHandler rewritten end to end to the corrected order: guard against a second submission, switch networks inline and continue automatically, check the balance against the exact amount actually sent with gas included, send the transaction, confirm the receipt before telling anyone it worked, then and only then tell the backend and show success.

Decision

The Buy button now always calls the same function

Making the network switch genuinely automatic meant more than rewriting the function's insides, the button itself used to call one of two different functions depending on isWrongNetwork. It now always calls domainBuyHandler, which handles switching and buying in the same click. The old separate handleSwitchNetwork function was deleted once nothing referenced it anymore, confirmed by the linter finding zero remaining usages.

Checked before building

Searched the codebase for an existing block explorer link helper and any existing gas estimation call before writing either, found neither. Both are genuinely new code in this file, not patterns borrowed from elsewhere in this app, which is exactly why they're the two pieces of this rewrite worth the closest look during actual testing, see the note at the end of the testing section below.

Also checked how the shared ToastMessage component renders its message prop, in src/component/toast-message/info-primary.tsx and its siblings. It renders as plain text inside a paragraph tag, no HTML or link support. The block explorer link the plan asked for is shown as plain, copyable text rather than a real hyperlink, changing that would mean editing a component shared across the whole app, out of scope for this file.

Decision

Errors no longer close the modal automatically

The original code called handleClose() in its one catch block for every failure, including a cancelled wallet prompt. That meant the popup vanished the instant anything went wrong, taking the error message's context with it. The rewrite only closes the modal on a genuine success, every failure path now leaves it open so the message is actually visible and the user can retry without reopening it.

Deliberately left open

The 2% buffer question from the original review

Whether the 2% native token buffer added on top of the required amount is refunded on chain if unused, or simply kept, was flagged as an open question in the original review. The calculation itself was left exactly as it was, with a comment marking it unresolved, rather than guessing at an answer that would change how much a buyer actually pays.

✓ Typecheck clean across the whole project, zero new lint errors, only pre-existing "any" style warnings already present before this change.
2

Rewrite DomainListingModal.tsx

Three fixes in one file: approval() now throws instead of swallowing a cancelled prompt, a successful network switch now continues straight into the submission instead of stopping, and the create listing block now checks the receipt, reads the listing id from the transaction's own event log, and checks the backend save for every listing.

Decision, beyond the literal wording

approval()'s own toast messages were removed, not just its return value

The plan asked for the cancelled prompt to throw instead of returning false, so the caller's already correct, already distinct messages become reachable. Making that change on its own would have caused two stacked toasts for the same event, since approval() was also independently showing its own message before throwing. The internal toasts inside approval()'s catch block were removed so the caller's existing messages, which already say the right thing for a cancelled prompt versus a genuine failure, are the only thing the user actually sees.

Checked before trusting it

Confirmed the ListingAdded event exists, with a listingId field, on every network's ABI

Reading the listing id from the transaction receipt's own event log instead of a second contract call meant first confirming that event actually exists and is shaped the way it needed to be. Checked directly inside BnbAbi.json, EthSepoliaAbi.json, and PolyAbi.json, the three ABI files this file's envConfig actually loads, all three define a ListingAdded event with a listingId field as its first indexed argument. Confirmed before writing the decoder, not assumed.

Decision

A missing listing id, and a failed backend save, are queued locally instead of lost

Both cases mean the chain has already confirmed the listing but the app can't yet, or didn't, get it saved. Rather than close the modal as if nothing happened, either case now writes the listing's data plus its transaction hash to a small local queue and shows an honest "still syncing" message. Being upfront about the limit here: this only builds the side that captures the data so it isn't silently lost, nothing today reads that queue back and retries it automatically. Building that consumer, or a "pending listings" screen, is a real product decision, not something to invent by guessing, and is left explicitly open the same way the 2% buffer question was in step 1.

Gap fixed beyond the literal prompt

isSubmitting could get stuck true forever, or never get set at all

Two separate problems surfaced while touching this code, both sitting squarely inside the plan's own "disabled for the whole duration of a submission" goal. First, isSubmitting was only ever set to true inside approval(), which is skipped entirely when the NFT is already approved, so a re-listing would never have actually disabled the button. Second, neither of this function's two outer catch blocks ever reset isSubmitting back to false, so a real failure would leave the button permanently stuck disabled. Both fixed: submitting state is now set before the create listing step regardless of whether approval ran, and both catches reset it. SubmitButton.tsx gained a new isSubmitting prop to actually make use of this.

✓ Typecheck clean across the whole project, zero new lint errors, in either this file or SubmitButton.tsx.
3

Fix the delist file's ordering, not its correctness check

domain-self-item/index.tsx's delistHandler already checked receipt.status === 1 correctly, it was the reference pattern the other two files copied from in steps 1 and 2. The only bug here was that the backend was told before the chain had confirmed anything. That receipt check was left completely untouched, only the ordering moved.

Decision, made necessary by the reorder itself

The backend failure message could no longer honestly say "Transaction failed"

Once the backend call moved to after chain confirmation, its own failure message needed to change too, the on-chain transaction had already succeeded by that point, only the backend record failed to update. Leaving the old wording in place would have made the message actively misleading, a regression introduced purely by moving the code rather than a pre-existing issue. It now reads "Delisted on chain, but failed to update our records" for that specific case.

Deliberately not built

No retry queue was added here the way one was for a failed listing save in step 2. Step 3's own prompt scoped this file to the ordering fix only, and its own title says as much, "fix the ordering, not the correctness check." Adding a retry mechanism here would have gone beyond what was actually asked.

✓ Typecheck clean across the whole project, zero new lint errors.

Testing this phase

Everything above is static verification: the type checker confirming the code's shapes are consistent, the linter confirming nothing is obviously dangling. Neither one proves a real wallet, a real network switch, or a real transaction actually behaves the way this rewrite intends. As of this document, that live testing has not yet been run in this session, this section lays out exactly what to run and, for the part that can't be run yet, exactly why not, rather than leaving that unclear.

Can be tested right now, no valid on chain listing required

Every one of these fails, or should fail, before a transaction is ever sent, which is exactly why none of them depend on a real listing existing on chain. Each line below is what the actual rewritten code should now do, not the plan's abstract description of it.

  • Reject the wallet prompt on Buy. Should show "You cancelled the transaction." and leave the modal open, not the old flat "Something went wrong." expects: err.code === 4001 branch in BuyNowModal.tsx's catch
  • Reject the wallet prompt during listing approval. Should show "NFT approval rejected by user." and not proceed into creating the listing. expects: approval() now throws on 4001, caught at the call site around line 583
  • Start a Buy while on the wrong network. Should prompt a network switch and, once approved in the wallet, continue straight into the purchase in the same click. expects: no second click, no separate "Switch Network" action needed
  • Submit a listing while on the wrong network. Same expectation, a successful switch should fall through into approval and listing creation, not stop and require clicking Submit a second time.
  • Double click Buy Domain. The second click should do nothing, the button should read "Processing..." and be genuinely disabled, not just visually covered by the loader.
  • Double click Publish Listing. Same expectation, including for a re-listing where the NFT is already approved, the button should still disable immediately, this was the specific gap fixed in step 2.
  • Force insufficient funds in the connected wallet before buying. Should be caught by the balance check before anything is sent, and the amount it checks against should now match safeEthAmount plus estimated gas, not the old unrelated priceInWei figure.

Needs a domain genuinely listed on the connected chain right now, blocked

These four all depend on a transaction actually being accepted by the contract before succeeding or failing further downstream, which means they can't be exercised at all without a listing that's real on both sides, in the backend's database and on the actual deployed contract for that chain.

Exact reason this is blocked in this environment

Phase 1's own testing already hit this, documented in the Phase 1 Paper Trail: clicking Buy on a real domain card threw call revert exception ... method="getRequiredNativeAmount(uint256)", a genuine on chain revert, not a frontend bug. The most likely cause identified at the time was that this domain's listing exists in the backend's database but not, or not correctly, on the actual smart contract for the connected chain, a data mismatch common on staging environments where backend and on chain state get seeded separately. That condition was never confirmed fixed. Every one of the four checks below needs a transaction to actually be accepted by the contract before it can even begin, so all four are blocked by this exact same unresolved condition, not by anything new in phase 2's own code.

One concrete difference worth expecting once this is resolved: if the same underlying revert happens again, step 1's error classification means it would now show "The transaction reverted on chain..." instead of the old flat "Something went wrong.", a clearer message, not a working purchase. The rewrite makes the failure honest, it doesn't make a listing that doesn't really exist on chain purchasable.

  • A full successful purchase. Would confirm the success message only appears after receipt.status === 1, and that the backend is only told once that check passes.
  • Forcing a backend save failure right after a successful purchase (for example, by disconnecting briefly right after the transaction confirms). Would confirm the failure no longer gets caught and silently ignored.
  • A full successful listing. Would confirm the receipt check, and confirm the listing id actually gets read correctly from the ListingAdded event log rather than falling back to the second contract call.
  • Delisting an existing listing. Would confirm the backend is now told only after the chain confirms the cancellation, not before.

What to look at hardest, once testing is possible

Least proven pieces of this rewrite

Two specific additions in step 1 have no prior working example anywhere else in this codebase to have leaned on while writing them, confirmed by search before building either. The gas estimate added to the balance check, using contract.estimateGas.buy(...) and provider.getGasPrice(), and the block explorer link built from a small chain id lookup table. Both typecheck cleanly and follow standard ethers v5 usage, but neither has been exercised against a real wallet and a real network yet, and they're the two pieces of this phase worth the closest attention the first time a real transaction actually runs.
